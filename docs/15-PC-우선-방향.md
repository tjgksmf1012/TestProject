# 15. 방향 전환 — PC 우선, 브라우저 통화, GitHub 최우선

> 이 문서가 `docs/14`(모바일)보다 **뒤에 옵니다.** 14를 지우지 않는 이유는
> 거기 적힌 판단(왜 하이브리드였는지, iOS 비용, 폰 UI 규칙)이 여전히
> 맞고, 나중에 다시 쓸 것이기 때문입니다. 다만 **순서가 바뀌었습니다.**

## 1. 무엇이 바뀌는가

이 시스템의 실제 모습이 이렇게 정리됐습니다.

```
    회의를 여는 곳(웹)
      └─ 디스코드처럼 여럿이 브라우저에서 통화
          └─ 각자의 목소리를 각자 브라우저가 녹음
              └─ 누가 무엇을 말했나 · 누구 아이디어인가
                  └─ 승인 → 칸반
                      └─ GitHub 활동  ←★ 가장 중요
                          └─ 기여도
```

바뀐 것은 **회의를 어디서 하느냐**입니다.

| | 이전 (docs/04 모드 A) | 지금 |
|---|---|---|
| 사람들 | **같은 회의실**에 모여 있다 | **각자 자기 PC** 앞에 있다 |
| 목소리 전달 | 공기 (직접 들림) | **WebRTC 통화** |
| 녹음 | 각자 폰 | 각자 브라우저 |
| 트랙 | 사람당 하나 | 사람당 하나 (**같음**) |

**트랙 모델은 그대로입니다.** 사람당 트랙 하나를 각자 기기가 녹음해 올리는
구조가 바뀌지 않았습니다 — 그래서 `src/lib/recording/`(160개 테스트),
청크 업로드, 재개, 커버리지·공백 계산이 **전부 그대로 쓰입니다.**

## 2. ⚠️ 통화로 바뀌면서 뒤집히는 것

여기가 이 문서에서 가장 중요한 부분입니다. **지금 코드의 핵심 전제 하나가
반대가 됩니다.**

### 2.1 GCC-PHAT 정렬은 원격에서 쓸 수 없다

`capture.ts` 는 브라우저 오디오 처리를 **전부 끄라고** 합니다. 이유가
문서에 이렇게 적혀 있습니다.

> GCC-PHAT 시간 정렬 — 트랙 간 정렬은 *새어 들어온 옆사람 목소리*로
> 맞춘다. 잡음 억제가 그 누출을 지워버리면 정렬할 근거 자체가 사라진다.

**같은 방에 있을 때만 성립하는 이야기입니다.** 각자 자기 집에 있으면
옆사람 목소리가 마이크에 안 들어옵니다. 상관시킬 공통 신호가 **아예
없습니다.**

즉 원격 통화에서는:

| 기능 | 같은 방 (모드 A) | 원격 통화 (새 모드) |
|---|---|---|
| GCC-PHAT 정렬 | 필요하고 가능 | **불가능**. 근거 신호가 없다 |
| 시계 동기화 (`/api/time`) | 보조 | **유일한 정렬 수단** |
| 누출 제거(`suppress_crosstalk`) | 필수 | **불필요**. 누출이 없다 |
| 주화자 판정 | 어렵다 (에너지 비교) | **확정**. 트랙 = 사람 |

마지막 줄이 좋은 소식입니다. 같은 방에서 가장 어려웠던 "이 프레임에서
누가 말했나" 가 원격에서는 **질문 자체가 없어집니다.** 내 마이크에 들어온
건 나뿐입니다.

### 2.2 그래서 오디오 설정이 **반대**가 된다

| 설정 | 같은 방 | 원격 통화 | 왜 |
|---|---|---|---|
| `echoCancellation` | **끈다** | **켠다** | 스피커로 들으면 남의 목소리가 내 트랙에 들어간다 |
| `noiseSuppression` | **끈다** | 켠다 | 정렬 근거가 필요 없어졌다 |
| `autoGainControl` | **끈다** | **끈다** | 조용한 사람의 트랙이 증폭되면 발언량이 부풀려진다 (docs/05 §5) |

`autoGainControl` 만 그대로 꺼 둡니다. **AGC 는 기여도를 왜곡합니다** —
듣고만 있던 사람의 트랙이 자동으로 증폭되면 그 사람이 말한 것으로 잡힙니다.
그건 원격이든 대면이든 같습니다.

### 2.3 ⚠️ 헤드폰이 **필수 요건**이 된다

스피커로 통화를 들으면 이런 일이 벌어집니다.

```
    B 가 말한다 → 네트워크 → A 의 스피커 → A 의 마이크 → A 의 트랙
                                              ↑
                             네트워크 지연만큼 늦게 들어간다
```

A 의 트랙에 B 의 목소리가 **수백 ms 늦게** 섞입니다. 그러면
"A 가 말했다" 로 잡히고, **B 의 아이디어가 A 의 기여로 기록됩니다.**
에코 제거가 대부분 걸러 주지만 완벽하지 않습니다.

이 시스템은 그 결과를 성적에 쓸 수 있는 값으로 내놓습니다. 그러니
헤드폰은 권장이 아니라 **로비에서 확인하고 안 쓰면 경고해야 하는 조건**
입니다.

## 3. 통화를 어떻게 만드는가

### 3.1 WebRTC 메시(mesh)

```
        A ────── B
        │  ╲  ╱  │
        │   ╳    │        3명: 연결 3개
        │  ╱  ╲  │        4명: 연결 6개
        C ────── D        5명: 연결 10개
```

각자가 나머지 전원과 직접 연결합니다. 서버는 **연결을 주선만** 하고
목소리는 지나가지 않습니다.

- **장점** — 서버 대역폭 0. 비용 0원 제약에 맞는다
- **한계** — 인원이 늘면 각자의 업로드가 (n−1)배. **5명까지가 현실적**

팀 프로젝트는 보통 3~4명이므로 메시로 충분합니다. 그 한계를 문서에
적어 두고, 넘으면 SFU(미디어 서버)를 검토합니다 — 그건 자체 호스팅이라
여전히 전기요금이지만 CPU 를 씁니다.

### 3.2 필요한 것과 비용

| 것 | 무엇 | 비용 |
|---|---|---|
| 시그널링 | SDP·ICE 를 주고받는 통로. 기존 FastAPI 에 **WebSocket** 하나 | 0원 |
| STUN | 내 공인 주소를 알아내는 서버. 공개 STUN 사용 | 0원 |
| TURN | P2P 가 막힐 때 중계. 자체 호스팅(coturn) | 전기요금 |

TURN 은 대칭형 NAT 뒤에서만 필요하고(대략 10~20%), 자체 호스팅이면
추가 비용이 없습니다. **다만 이 개발 환경에서는 실행해 볼 수 없습니다** —
네트워크가 없습니다.

### 3.3 녹음과의 관계

**통화와 녹음은 서로 다른 스트림입니다.**

```
    내 마이크 ─┬─→ WebRTC (남에게 들려주는 용도, 압축·에코제거)
               └─→ MediaRecorder (내 트랙, 서버에 올림)
```

`getUserMedia` 로 얻은 트랙 하나를 둘 다에 씁니다. 이미 있는
`RecordingClient` 가 두 번째 갈래를 그대로 담당합니다 — **녹음 쪽 코드는
고칠 게 거의 없습니다.**

### 4.3 §5 의 1번을 하면서 나온 것

#### 34. 저장소 표기의 대소문자가 다르면 배달이 전부 버려진다

웹훅 본문의 `repository.full_name` 은 GitHub 의 **정식 표기**로 옵니다
(`tjgksmf1012/TestProject`). 사람은 설정 화면에 소문자로 적습니다
(`tjgksmf1012/testproject`). PostgreSQL 의 `=` 도 SQLite 의 기본 대조도
대소문자를 구분하므로 **둘은 다른 문자열**입니다.

```
    사람이 적은 것   tjgksmf1012/testproject
    GitHub 이 보낸 것 tjgksmf1012/TestProject
                          ↓
              "연결되지 않은 저장소" → 202 → 버림
```

PR 을 백 번 병합해도 기여도가 0 이고, **아무 곳에도 오류가 남지 않습니다.**

→ 대조용 표기(`github_repo_key`, 소문자)를 따로 두고 그걸로 찾습니다.
화면에 보여줄 표기는 사람이 적은 그대로 두되, 배달이 오면 GitHub 의
정식 표기로 맞춰 줍니다.

#### 35. 대소문자를 달리 적으면 두 프로젝트가 같은 저장소를 가진다

34를 고치는 순간 이게 **더 나빠집니다** — 대조가 대소문자를 무시하게
되면서, `team/x` 와 `team/X` 로 나뉘어 있던 두 프로젝트가 같은 저장소를
가리키게 되고 배달이 **어느 쪽에 붙을지 정해지지 않습니다.**
그래서 둘은 같이 고쳐야 합니다.

→ `github_repo_key` 에 DB 유니크 인덱스. 응용 코드의 검사만으로는
동시에 들어온 두 요청을 막을 수 없습니다.

#### 36. 구성원이 설치 id 에 아무 숫자나 써 넣을 수 있다

`PATCH /api/projects/{id}` 가 `github_installation_id` 를 그대로 받았습니다.
워커는 그 값으로 `build_client()` 를 불러 **그 설치의 액세스 토큰을
발급**합니다. 즉 이 팀과 아무 상관 없는 설치의 권한으로 GitHub API 를
부르게 만들 수 있었습니다. 요청 본문의 id 를 권한에 그대로 쓰던
`member_ids` 결함과 같은 부류입니다.

→ 필드를 스키마에서 **없앴습니다**(보내면 422). 서명이 검증된 웹훅
본문의 `installation.id` 로만 채웁니다.

⚠️ 그 자리에 있던 테스트가 이 결함을 **고정하고 있었습니다.** 예전
테스트는 `{"github_installation_id": 12345}` 를 보내고 응답에 그 숫자가
안 나오는지만 봤습니다 — 나가는 길은 막혀 있었지만 들어오는 길이 열려
있었고, 테스트는 그걸 정상으로 못 박았습니다.

#### 37. 이름을 적기만 하면 신뢰도가 오른다

신뢰도의 `github_coverage` 를 `github_connected_at` — **저장소 이름을
적어 넣은 시각** — 으로 계산하고 있었습니다. 그래서 오타를 적었든 App 을
설치하지 않았든:

```
    실제 도착한 GitHub 이벤트: 0건
    github_coverage:          1.0
    전체 신뢰도:               0.8 "보통"
```

신뢰도는 "얼마나 많은 근거로 계산했는가" 입니다. 근거가 없는데 높게
나오면 그건 신뢰도가 아니라 거짓말이고, 이 시스템에서는 **성적에 쓰일 수
있는 값을 뒷받침하는 숫자**입니다.

→ `github_verified_at`(서명된 배달이 **처음 도착한** 시각) 기준으로
바꿨습니다. 같은 상황에서 `github_coverage: 0.0`, 전체 0.4 "낮음" 이 되고
사유에 "GitHub 연결 이전 기간의 활동이 누락되었습니다" 가 붙습니다.

#### 연결 진단 화면

`GET /api/projects/{id}/github` 가 상태·근거·**지금 할 일**을 같이
돌려줍니다. 상태만 보여주면 사람은 못 고칩니다.

| 상태 | 언제 | 누가 고치나 |
|---|---|---|
| `no_repo` | 저장소를 안 적음 | 팀 |
| `server_missing_webhook_secret` | 배달이 전부 401 | **관리자** |
| `repo_name_mismatch` | 웹훅은 오는데 이름이 다름 | 팀 |
| `waiting_for_delivery` | 아직 배달이 없음 | 팀 (App 설치) |
| `server_missing_app_credentials` | 배달은 오는데 API 를 못 부름 | **관리자** |
| `no_member_logins` | 활동을 사람과 못 이음 → **전원 0** | 팀 |
| `actors_do_not_match` | 활동 계정이 팀원과 안 겹침 | 팀 |
| `connected` | 정상 | — |

`repo_name_mismatch` 가 이 중 가장 값어치 있습니다. 서명은 맞는데 어느
프로젝트에도 안 붙은 배달을 저장소 이름과 횟수만 기록해 두고, 적어 둔
이름의 오타로 볼 만하면 **"`tjgksmf1012/testproject` 로 고치세요"** 라고
말합니다. 그 기록이 없으면 오타는 증거를 남기지 않고, 화면은 "아직
아무것도 안 왔습니다" 밖에 말할 수 없어 사람은 App 설치를 의심하며
엉뚱한 곳을 고칩니다.

⚠️ **캐내기를 막는 선** — 안 붙은 배달을 전부 보여주면 진단 화면이
"App 이 설치된 저장소 목록" 을 알아내는 도구가 됩니다. 그래서 **소유자
또는 저장소 이름 중 한쪽이 정확히 맞을 때만** 보여줍니다. 이미 알고 있는
이름의 나머지 반쪽만 알려 주는 셈이라 흔한 오타는 다 잡으면서 캐내기에는
쓸모가 없습니다.

#### 소유권 검증 — 어디까지 됐고 무엇이 남았나

**된 것.** 저장소를 적는 것은 *주장*이고 서명된 배달이 오는 것이
*증거*입니다. 배달은 App 이 그 저장소에 설치돼 있다는 뜻이고, 설치는
저장소 관리 권한이 있어야 할 수 있습니다. 확인 전에는 `github_connected`
가 거짓이고 신뢰도도 오르지 않습니다.

**남은 것.** 웹훅 시크릿은 App 마다 하나라, 서명이 맞다는 것은 "우리 App 이
설치된 **어떤** 저장소" 를 뜻할 뿐 그 저장소가 이 팀 것이라는 증명은
아닙니다. 남의 저장소 이름을 먼저 적어 둔 사람이 그 저장소의 배달을
받는 경우가 남습니다. 진단의 `actors_do_not_match` 가 이걸 **보이게는**
하지만 막지는 못합니다. 완전한 증명은 설치 토큰으로
`GET /installation/repositories` 를 불러 확인해야 하고, **이 환경에서는
네트워크가 없어 실행해 볼 수 없습니다.** 지어내지 않고 여기 적어 둡니다.

#### 덤 — 낡은 번들을 잡는 그물

이 작업 중에 화면을 고치고 `npm run build:demo` 를 잊었습니다. 테스트
510개가 전부 통과했고, 타입 검사도 통과했고, **브라우저는 고치기 전
코드를 받고 있었습니다.** 테스트는 `src/` 를 읽고 브라우저는 `public/*.js`
를 받기 때문입니다.

→ `frontend/build.mts` 로 빌드를 옮기고, 진입점을 손으로 적는 대신 **화면
HTML 이 실제로 불러오는 스크립트**를 세게 했습니다. 그리고 `guards.test.ts`
가 지금 소스로 빌드한 것과 `public` 에 놓인 것을 비교합니다.

### 4.4 §5 의 2번 — 업무 ↔ PR 잇기

대표 주장의 마지막 끊긴 곳이었습니다.

```
회의 → 자막 → 업무 후보 → 승인 → 칸반 → ✂ → 기여도
                                        ↑
                            "이 업무가 이 PR 로 끝났다" 를
                            보여줄 방법이 없었다
```

`task_github_links` 표는 처음부터 있었고 `extract_task_refs` 도 있었는데
**둘을 잇는 코드가 0곳**이라 그 표에 행이 한 번도 쓰인 적이 없습니다.

#### 38·39. 그런데 `extract_task_refs` 자체가 틀려 있었다

호출자가 0곳이었고 **테스트도 0개**였습니다. 그래서 아무도 몰랐습니다.

```python
extract_task_refs("2026-08-07 회의 정리")  → {2026}   # 날짜
extract_task_refs("1000-line refactor")   → {1000}   # 줄 수
extract_task_refs("Closes #12")           → {12}     # GitHub 이슈 번호
extract_task_refs("TASK-12")              → {12}     # 우리 업무 번호
```

**38** — 브랜치용 패턴(`숫자-`)을 자유 텍스트에도 적용해서 날짜와 줄 수가
업무 번호가 됩니다. 이 상태로 배선했으면 회의록 PR 하나가 2026번 업무에
붙었을 겁니다.

**39** — GitHub 이슈 번호와 우리 업무 번호가 **같은 집합에** 섞입니다.
GitHub 은 `#12` 를 그 저장소의 이슈 링크로 렌더링하므로, 그렇게 쓴 사람은
대개 이슈를 가리킨 것입니다. `Closes #12` 가 우리 12번 업무에 붙습니다.

→ `github/linking.py` 로 다시 만들고 33개 테스트를 붙였습니다.
`webhook.extract_task_refs` 는 **지웠습니다** — 남겨 두면 다음 사람이
그걸 부릅니다.

#### 무엇을 참조로 보는가

| 쓴 것 | 뜻 | 처리 |
|---|---|---|
| `TASK-12` `TF-12` | 우리 업무 12번 | ✅ **확정** (relevance 1.0) |
| 브랜치 `feat/12-login` | 아마 업무 12번 | 🟡 추정 (0.6) |
| `#12` | GitHub 이슈 12번 | 🟠 추정 (0.3) |

브랜치 패턴은 **브랜치 이름에만** 적용합니다. 확정과 추정을 화면이 색으로
나누고 근거를 한 줄로 답니다 — "PR 에 TASK 번호가 적혀 있습니다" 와
"PR 의 #번호로 추정했습니다 (GitHub 이슈 번호일 수 있습니다)" 는 다릅니다.

#### ⚠️ 프로젝트 범위를 반드시 건다

`tasks.id` 는 **전역 시퀀스**입니다. 프로젝트마다 1번부터 시작하지 않습니다.
그래서 `TASK-12` 의 12번은 다른 팀의 업무일 수 있고, 범위를 안 걸면
**남의 업무 카드에 우리 PR 이 붙습니다.**

#### 왜 워커가 아니라 웹훅에서 하는가

`ingest_github_event_task` 는 GitHub App 자격 증명이 없으면
`not_configured` 로 통째로 빠져나갑니다. 거기 두면 자격 증명을 갖추기
전까지 업무 카드에 PR 이 영영 안 붙습니다.

그런데 **연결에는 API 도 자격 증명도 필요 없습니다.** 웹훅 본문에 제목·
본문·브랜치가 이미 다 들어 있고, 필요한 것은 select 하나와 insert 몇
개뿐입니다. 그래서 웹훅에서 바로 합니다.

#### 표식을 화면이 알려준다

자동 연결은 사람이 `TASK-12` 를 적어야 성립합니다. **무엇을 적어야
하는지 알려주는 곳이 없으면 이 기능 전체가 죽은 코드가 됩니다.** 그래서
칸반 카드마다 그 업무의 표식을 띄우고, 아직 안 붙은 카드는
"PR 제목이나 본문에 `TASK-12` 를 적으면 붙습니다" 라고 말합니다.

시연 데이터(`seed_demo.py`)도 병합된 PR 을 하나 만들어 붙입니다.
⚠️ 손으로 링크를 넣지 않고 **운영 코드와 같은 함수**를 부릅니다 — 손으로
넣으면 시연은 되는데 실제 웹훅에서는 안 되는 상태를 못 알아챕니다.

### 4.5 §5 의 3번 — 회의 발화 → 기여 이벤트

기여도 세 다리 중 **마지막**이었습니다.

    칸반 업무 완료 → 기여 이벤트   ✅
    GitHub 활동   → 기여 이벤트   ✅
    회의 발화     → 기여 이벤트   ← 여기. **운영 코드에 0곳**

`scoring.py` 는 `UTT_DECISION`(5.0) 같은 가중치를 정확히 알고 있는데 그
이벤트를 만드는 코드가 없었습니다. 즉 **운영에서 회의 기여도는 언제나
0**이었고, 시연 화면의 숫자는 손으로 넣은 것이었습니다. 하필 회의 분석
시스템에서 회의 쪽 다리입니다.

#### 분류기 — 왜 규칙 기반 기준선인가

계획(docs/08 §9주차)은 KLUE-RoBERTa 파인튜닝이고 GPU 가 필요합니다.
그런데 **분류기가 없는 것과 배선이 없는 것은 다른 문제**입니다 — 분류기가
생겨도 배선이 없으면 여전히 0입니다.

그래서 8라벨(docs/10 Q9)과 인터페이스를 확정하고 규칙 기반 기준선을
뒀습니다. 이건 임시방편이 아니라 **9주차 실험의 비교 기준선**이기도
합니다. "우리 모델이 규칙 대비 Macro F1 을 얼마나 올렸는가" 를 말하려면
어차피 필요합니다.

한국어는 어순이 아니라 **문말 어미**가 화행을 표시합니다.

    ~할까요? ~어때요?        제안
    ~하겠습니다 ~할게요       업무 약속
    그럼 ~로 하죠 ~로 갑시다   결정
    네 맞아요 그러네요        맞장구

⚠️ **규칙은 틀립니다.** 그래서 셋으로 막습니다.

1. **확신이 낮으면 `other`(0점)로 떨어뜨립니다.** 애매한 것을 `decision`
   으로 찍으면 근거 없는 5점이 생깁니다.
2. **애매하면 싼 라벨로.** 의견(1.0)을 제안(2.0~5.0)으로 잘못 보면 점수가
   부풀고, 반대는 조금 모자랍니다. 성적에 쓰일 값이므로 부풀리는 쪽이 더
   나쁩니다. 실제로 처음 규칙이 `"~하면 좋을 것 같아요"` 를 제안으로
   잡았고, 테스트가 그걸 잡았습니다.
3. **무엇이 매겼는지 기록합니다.** 신뢰도에 새 신호
   (`utterance_classification`)를 넣어, 규칙으로 매긴 회의는 학습 모델로
   매긴 회의보다 낮게 나옵니다.

#### ⚠️ 조심한 것

**화자가 없으면 아무에게도 주지 않습니다.** 모드 B 의 `SPEAKER_XX` 는
사람이 이름을 매기기 전까지 주인이 없습니다. 아무에게나 붙이면 측정이
아니라 오답입니다. 그 발언은 사라지지 않고 **주인 미상 상태로 회의록에
남습니다.**

**맞장구는 0점이지만 반드시 기록합니다.** 안 기록하면
`mostly_social_utterances` 탐지의 분모가 사라져서 **"네" 만 백 번 한
사람이 오히려 탐지를 피해 갑니다.**

**재처리하면 점수가 두 배가 됩니다.** `persist_results_task` 는 발화를
지우고 새로 만드는데, 옛 발화에 딸린 기여 이벤트를 **발화를 지우기 전에**
같이 지워야 합니다. 지운 뒤에는 어떤 이벤트가 이 회의 것이었는지 알
방법이 없습니다.

#### 40. 회의 참석자가 셋이면 한 명만 기록된다

`MEETING_ATTENDED`(3.0점)도 배선이 0곳이었는데, 배선하려고 보니 스키마가
막고 있었습니다. `contribution_events` 의 유니크 제약이 이랬습니다.

    (source_kind, source_id, event_type)

`user_id` 가 없습니다. 웹훅 중복 방어에는 맞지만 **하나의 근거에서 여러
사람의 이벤트가 나오는 경우를 막습니다.**

```
    user 1: 기록됨
    user 2: 실패 — UNIQUE constraint failed
    user 3: 실패 — UNIQUE constraint failed
```

참석자 3명 중 1명만 잡히고 나머지 둘은 **참석했는데 참석 기록이 없고**,
그건 "참석 안 함"(0점)으로 읽힙니다.

→ 제약에 `user_id` 를 넣었습니다. 중복 방어는 그대로입니다 — GitHub
이벤트는 행위자가 하나라 같은 행으로 막힙니다. 되돌려 보니 회의 다리
테스트 **18개가 전부** 깨졌습니다. 이 제약이 다리 전체를 막고 있었습니다.

⚠️ 함께 고친 것: `github_ingest_service.persist_events` 의 중복 검사도
`user_id` 를 봐야 합니다. 안 그러면 **다른 사람의 같은 유형 이벤트를 보고
건너뜁니다.**

#### 남은 것

- **분류기 상향** — KLUE-RoBERTa. GPU 필요
- **`fulfilled` 판정** — 약속(1.5)이 실제 완료된 업무로 이어지면 6.0 이
  되어야 하는데, 지금은 항상 1.5 입니다. 약속 발화 ↔ 업무 후보 ↔ 완료를
  잇는 계산이 필요하고 이건 산정 시점에 해야 합니다(메타데이터에 얼려
  두면 나중에 완료된 업무가 반영되지 않습니다)

### 4.6 §5 의 4번 — 시그널링 (서버 쪽만)

목소리는 **여기를 지나가지 않습니다.** SDP·ICE 만 오가고 그 다음부터
사람들끼리 직접 연결합니다.

    A ──(offer)──→ 서버 ──(offer)──→ B
    A ←─(answer)── 서버 ←─(answer)── B
    그 다음부터 목소리는 A ↔ B 직접

#### ⚠️ 시그널링은 조용한 권한 통로다

이 채널은 세 가지를 새게 할 수 있습니다.

1. **명단** — 누가 회의에 있는지. 팀 밖 사람이 붙으면 그것만으로 샙니다
2. **주입** — 남의 이름으로 offer 를 보내 연결을 가로챌 수 있습니다
3. **기록 없는 통로** — 아무 JSON 이나 중계하면 팀원끼리 흔적 없는
   메신저가 됩니다. 이 시스템은 회의 내용을 기록해 기여도로 쓰는데,
   **기록되지 않는 옆길이 생기면 그 주장이 무너집니다**

그래서 `call/signaling.py` 는 **막는 규칙이 본체**입니다. 중계 자체는
몇 줄입니다.

| 막는 것 | 왜 |
|---|---|
| 인증·구성원 확인을 `accept()` **앞에서** | 받아 놓고 끊으면 그 사이에 명단이 샌다 |
| `from` 을 본문에서 안 읽음 | 남의 이름으로 연결을 가로챈다 (`member_ids` 와 같은 부류) |
| 종류 **허용 목록** (`offer`/`answer`/`ice`) | 거부 목록은 새 종류마다 뚫린다 |
| 본문 16,000자 상한 | 없으면 이 통로로 파일을 보낸다 |
| 방 밖 대상은 조용히 거절 | "있다/없다" 를 달리 답하면 명단을 캐낼 수 있다 |
| `connection_id` 를 화면에 안 보냄 | 알면 특정 소켓을 겨냥할 수 있다 |
| 나갈 때 **연결 id 로** 뺌 | user_id 로 빼면 새로고침한 자기 자신을 쫓아낸다 |
| 한 사람당 연결 하나 | 탭 둘이면 같은 목소리가 두 트랙에 → 발언량 두 배 |
| 메시 5명 상한 | docs/15 §3.1 |

#### 헤드폰 — 막지 않고 보이게

브라우저는 헤드폰 여부를 **확인할 방법이 없습니다.** 그래서 자기
신고를 받고, 헤드폰이 없다고 회의에서 빼지는 않습니다 — 그게 더
나쁩니다. 대신 **방에 있는 전원이 지금 봅니다.**

> 헤드폰을 쓰지 않는 사람이 있습니다: 팀원2.
> 스피커로 들으면 남의 목소리가 그 사람 트랙에 섞이고, 그러면
> **다른 사람의 발언이 그 사람의 기여로 기록될 수 있습니다.**

기여도 화면에서 처음 보면 늦습니다. 통화 중에 말해야 고칠 수 있습니다.

#### ⚠️ 방은 프로세스 메모리에 있다

워커를 늘리면 **같은 회의의 두 사람이 서로를 못 봅니다.** 각자 다른
워커에 붙어 서로 다른 방에 들어가고, offer 를 보내도 조용히 버려집니다.
**오류가 안 납니다.**

지금은 워커가 하나라 문제가 없고(`docker/Dockerfile.api`), 성능 때문에
`--workers` 를 붙이는 것은 자연스러운 변경이라 **그물을 쳤습니다** —
`test_packaging.py::test_the_api_runs_as_a_single_worker`. 늘리려면 방을
Redis pub/sub 으로 옮겨야 합니다.

### 4.7 §5 의 5·6·7번 — 통화 화면과 PC 레이아웃

판단은 `frontend/src/lib/call/mesh.ts` (24개 테스트) 에 있고
`src/demo/call.ts` 가 `RTCPeerConnection` 에 배선합니다.

#### glare — 둘 다 걸면 멈춘다

```ts
export function shouldInitiate(me: number, other: number): boolean {
  return me < other;
}
```

메시에서는 모든 쌍이 서로를 봅니다. 양쪽이 동시에 offer 를 걸면
`setLocalDescription` 과 `setRemoteDescription` 이 엇갈려 협상이
끝나지 않습니다. **낮은 id 쪽만** 겁니다. 규칙이 무엇이든 상관없고
**양쪽이 같은 규칙을 쓰는 것**만 중요합니다.

#### 캡처 설정이 같은 방 녹음과 반대다

| | 같은 방 (모드 A) | 원격 통화 |
|---|---|---|
| `echoCancellation` | **끈다** | **켠다** |
| `noiseSuppression` | **끈다** | **켠다** |
| `autoGainControl` | **끈다** | **끈다** |

같은 방에서는 옆 사람 목소리가 내 마이크에 들어오는 것이 정렬의
단서라 아무것도 지우면 안 됐습니다. 원격은 그 누출이 아예 없는
대신 **내 스피커 소리가 내 마이크로 되돌아옵니다** — 그걸 안 지우면
남의 발언이 내 트랙에 실립니다.

`autoGainControl` 만 **양쪽 다 끕니다.** 조용한 사람의 트랙이
증폭되면 발언량이 부풀려지고, 그건 기여도를 직접 틀리게 합니다.

#### PC 레이아웃 (7번)

48rem 이상에서 바뀌는 것:

| | 폰 | PC |
|---|---|---|
| 탭바 | 아래 고정 | 위로 |
| 본문 | 화면 폭 | 72rem 가운데 |
| 칸반 | 열 셋 세로 | **가로** |
| 기여도·참가자 | 세로 목록 | 격자 |

#### 확인한 것과 확인 못 한 것

⚠️ **여기를 정확히 적습니다.** 이전 판에는 "실제로 통화해 본 적이
없습니다 — 이 환경에는 네트워크가 없어 WebRTC 연결이 성립하지
않습니다" 라고 적혀 있었는데, **그건 틀렸습니다.**

같은 기기 안의 두 브라우저 컨텍스트는 host 후보로 직접 붙습니다.
STUN 도 인터넷도 필요 없습니다. 실제로 3인 통화를 띄워 확인했습니다:

```
[김민수] 요약: 2명과 통화 중입니다.
  · 이하늘 — 연결됨    · 박지원 — 연결됨
  ⚠ 헤드폰을 쓰지 않는 사람이 있습니다: 박지원…
```

세 화면 모두 나머지 둘을 연결됨으로 봤고 헤드폰 경고가 셋 다
떴습니다. 즉 **주선·협상·미디어 트랙·화면 표시까지** 확인됐습니다.

확인 못 한 것은 **실제 네트워크**입니다 — 서로 다른 NAT 뒤,
TURN 이 필요한 대칭 NAT, 가정용 업로드 대역폭에서 5명. 그건
그대로 `docs/09` 실험 6 입니다.

### 4.8 §4.2 의 3번 — 백필

**웹훅은 연결한 순간부터 옵니다.** 팀은 대개 몇 주 코드를 짜다가 이
시스템을 붙입니다.

    3월~4월  PR 40개 병합   ← 기여도에 **없음**
    5월 1일  연결
    5월~     PR 5개 병합    ← 기여도에 있음

진단 화면은 "연결됨" 이라고 말하고 기여도 화면은 5건을 보여 줍니다.
**어디에도 오류가 없습니다.** 3월에 제일 많이 일한 사람이 제일 적게
일한 것으로 보이고, 본인도 이유를 알 방법이 없습니다.

#### 절반은 "가져오기", 나머지 절반은 "안 가져왔다고 말하기"

둘 중 **뒤쪽이 더 중요합니다.** 백필을 안 돌린 팀이 훨씬 많을 것이고,
그 팀들에게 지금 화면은 거짓을 말하고 있습니다.

그래서 칸을 하나 더 뒀습니다.

    projects.github_backfilled_to   이 시각 이후는 GitHub 에 물어봤다

이벤트만 봐서는 이걸 알 수 없습니다. `min(occurred_at)` 은 "우리가 가진
가장 오래된 활동" 이지 "그 전에 활동이 없었다" 가 아닙니다. 둘을 가르는
것이 이 한 칸입니다.

| 상태 | 화면이 하는 말 |
|---|---|
| 배달 0건 | 이 저장소에서 받은 활동이 아직 없습니다 |
| 배달 있음 · 백필 안 함 | **연결한 날 이후만** 반영돼 있습니다 — 그 전은 아직 |
| 백필 함 | **2026-03-02 이후**의 활동이 반영돼 있습니다 |

#### 웹훅 경로를 그대로 다시 걷는다

백필용 저장 경로를 따로 만들면 **웹훅에서 고친 것이 백필에서는 안
고쳐집니다.** 이 저장소는 이미 그 부류로 여러 번 당했습니다.

    목록 조회 → 웹훅 모양 payload → GithubEvent 저장
              → link_pull_request        (업무 카드에 붙는다)
              → ingest_merged_pull_request  (기여 이벤트)

바뀐 것은 배달 id 가 `backfill:` 로 시작한다는 것 하나뿐입니다.

#### 겹쳐도 한 번만 — 세 겹

    1. 이미 있는 PR 번호를 건너뛴다      ← 여기서 대부분 걸린다
    2. uq_github_delivery (배달 id)      ← 백필 재실행
    3. contribution_events 유니크 제약   ← 마지막 방어선

1번이 중요합니다. 2번만 있으면 웹훅으로 이미 들어온 PR 을 백필이
**다른 배달 id 로** 또 넣고, 업무 카드에 같은 PR 이 두 번 붙습니다.

3번은 1·2번이 다 뚫려도 **점수만은** 안 틀리게 합니다. 카드에 두 번
보이는 것은 보기 싫은 것이고, 점수가 두 배가 되는 것은 오답입니다.

#### ⚠️ 잘리면 반드시 말한다

저장소가 크면 다 못 가져옵니다(기본 상한 200건 — PR 하나에 API 를 네 번
부르므로 800 요청). 그때 조용히 자르면 사람은 "백필했으니 이제 완전하다"
고 믿습니다 — **백필을 안 한 것보다 나쁩니다.** 안 한 줄 알면 최소한
의심은 하니까요.

그리고 **잘린 지점을 `github_backfilled_to` 에 적지 않습니다.** 적으면
다음 실행이 그 앞을 안 보게 되고, 못 가져온 구간이 영구히 빈 채로
굳습니다.

#### 확인한 것과 확인 못 한 것

판단(`github/backfill.py`)과 배선(`services/github_backfill_service.py`)은
`FakeGitHubClient` 로 전 구간을 돌려 확인했습니다 — 겹침·잘림·실패·
커버리지 기록까지.

⚠️ **`list_closed_pull_requests` 의 실제 HTTP 호출은 이 환경에서 실행된
적이 없습니다.** `HttpGitHubClient` 전체가 그렇습니다(§4.1). 요청 형태는
문서 기준으로 작성했고 실제 머신에서 확인해야 합니다.

## 6. 모바일은 어떻게 되나

**지웁니다가 아니라 미룹니다.**

- 화면은 여전히 폰에서 열립니다. `app.css` 는 폰 기준이지만 넓은 화면
  에서도 깨지지 않습니다 (`max-width` 로 가운데 정렬)
- PWA(`manifest`·`sw.js`)는 그대로 둡니다. 있어도 PC 에 해가 없고,
  빼면 다시 넣을 때 같은 일을 두 번 합니다
- 안드로이드 셸(`android/`)은 별도 디렉터리라 PC 작업이 건드릴 일이
  없습니다. 빌드도 별개입니다

폰 기준 폭(34rem)이 PC 에서 너무 좁던 것은 §4.7 에서 고쳤습니다 —
48rem 이상에서 72rem 으로 벌어지고 칸반 열 셋이 가로로 눕습니다.
**폰 폭은 그대로 둡니다.** 넓은 화면 규칙을 미디어 쿼리 안에만
넣었으므로 좁은 화면은 예전 그대로입니다.

셸까지 만들어 해결하려던 문제가 **PC 에서는 대체로 없습니다.**

바꿔 말하면 **PC 우선이 기술적으로도 더 안전한 선택**입니다.
