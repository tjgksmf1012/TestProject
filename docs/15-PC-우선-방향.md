# 15. 방향 전환 — PC 우선, 브라우저 통화, GitHub 최우선

> 이 문서가 `docs/14`(모바일)보다 **뒤에 옵니다.** 14를 지우지 않는 이유는
> 거기 적힌 판단(왜 하이브리드였는지, iOS 비용, 폰 UI 규칙)이 여전히
> 맞고, 나중에 다시 쓸 것이기 때문입니다. 다만 **순서가 바뀌었습니다.**

---

## 1. 무엇이 바뀌는가

이 시스템의 실제 모습이 이렇게 정리됐습니다.

```
    회의를 여는 곳(웹)
      └─ 디스코드처럼 여럿이 브라우저에서 통화
          └─ 각자의 목소리를 각자 브라우저가 녹음
              └─ 누가 무엇을 말했나 · 누구 아이디어인가
                  └─ 승인 → 칸반
                      └─ GitHub 활동  ←★ 가장 중요
                          └─ 기여도
```

바뀐 것은 **회의를 어디서 하느냐**입니다.

| | 이전 (docs/04 모드 A) | 지금 |
|---|---|---|
| 사람들 | **같은 회의실**에 모여 있다 | **각자 자기 PC** 앞에 있다 |
| 목소리 전달 | 공기 (직접 들림) | **WebRTC 통화** |
| 녹음 | 각자 폰 | 각자 브라우저 |
| 트랙 | 사람당 하나 | 사람당 하나 (**같음**) |

**트랙 모델은 그대로입니다.** 사람당 트랙 하나를 각자 기기가 녹음해 올리는
구조가 바뀌지 않았습니다 — 그래서 `src/lib/recording/`(160개 테스트),
청크 업로드, 재개, 커버리지·공백 계산이 **전부 그대로 쓰입니다.**

## 2. ⚠️ 통화로 바뀌면서 뒤집히는 것

여기가 이 문서에서 가장 중요한 부분입니다. **지금 코드의 핵심 전제 하나가
반대가 됩니다.**

### 2.1 GCC-PHAT 정렬은 원격에서 쓸 수 없다

`capture.ts` 는 브라우저 오디오 처리를 **전부 끄라고** 합니다. 이유가
문서에 이렇게 적혀 있습니다.

> GCC-PHAT 시간 정렬 — 트랙 간 정렬은 *새어 들어온 옆사람 목소리*로
> 맞춘다. 잡음 억제가 그 누출을 지워버리면 정렬할 근거 자체가 사라진다.

**같은 방에 있을 때만 성립하는 이야기입니다.** 각자 자기 집에 있으면
옆사람 목소리가 마이크에 안 들어옵니다. 상관시킬 공통 신호가 **아예
없습니다.**

즉 원격 통화에서는:

| 기능 | 같은 방 (모드 A) | 원격 통화 (새 모드) |
|---|---|---|
| GCC-PHAT 정렬 | 필요하고 가능 | **불가능**. 근거 신호가 없다 |
| 시계 동기화 (`/api/time`) | 보조 | **유일한 정렬 수단** |
| 누출 제거(`suppress_crosstalk`) | 필수 | **불필요**. 누출이 없다 |
| 주화자 판정 | 어렵다 (에너지 비교) | **확정**. 트랙 = 사람 |

마지막 줄이 좋은 소식입니다. 같은 방에서 가장 어려웠던 "이 프레임에서
누가 말했나" 가 원격에서는 **질문 자체가 없어집니다.** 내 마이크에 들어온
건 나뿐입니다.

### 2.2 그래서 오디오 설정이 **반대**가 된다

| 설정 | 같은 방 | 원격 통화 | 왜 |
|---|---|---|---|
| `echoCancellation` | **끈다** | **켠다** | 스피커로 들으면 남의 목소리가 내 트랙에 들어간다 |
| `noiseSuppression` | **끈다** | 켠다 | 정렬 근거가 필요 없어졌다 |
| `autoGainControl` | **끈다** | **끈다** | 조용한 사람의 트랙이 증폭되면 발언량이 부풀려진다 (docs/05 §5) |

`autoGainControl` 만 그대로 꺼 둡니다. **AGC 는 기여도를 왜곡합니다** —
듣고만 있던 사람의 트랙이 자동으로 증폭되면 그 사람이 말한 것으로 잡힙니다.
그건 원격이든 대면이든 같습니다.

### 2.3 ⚠️ 헤드폰이 **필수 요건**이 된다

스피커로 통화를 들으면 이런 일이 벌어집니다.

```
    B 가 말한다 → 네트워크 → A 의 스피커 → A 의 마이크 → A 의 트랙
                                              ↑
                             네트워크 지연만큼 늦게 들어간다
```

A 의 트랙에 B 의 목소리가 **수백 ms 늦게** 섞입니다. 그러면
"A 가 말했다" 로 잡히고, **B 의 아이디어가 A 의 기여로 기록됩니다.**
에코 제거가 대부분 걸러 주지만 완벽하지 않습니다.

이 시스템은 그 결과를 성적에 쓸 수 있는 값으로 내놓습니다. 그러니
헤드폰은 권장이 아니라 **로비에서 확인하고 안 쓰면 경고해야 하는 조건**
입니다.

## 3. 통화를 어떻게 만드는가

### 3.1 WebRTC 메시(mesh)

```
        A ────── B
        │  ╲  ╱  │
        │   ╳    │        3명: 연결 3개
        │  ╱  ╲  │        4명: 연결 6개
        C ────── D        5명: 연결 10개
```

각자가 나머지 전원과 직접 연결합니다. 서버는 **연결을 주선만** 하고
목소리는 지나가지 않습니다.

- **장점** — 서버 대역폭 0. 비용 0원 제약에 맞는다
- **한계** — 인원이 늘면 각자의 업로드가 (n−1)배. **5명까지가 현실적**

팀 프로젝트는 보통 3~4명이므로 메시로 충분합니다. 그 한계를 문서에
적어 두고, 넘으면 SFU(미디어 서버)를 검토합니다 — 그건 자체 호스팅이라
여전히 전기요금이지만 CPU 를 씁니다.

### 3.2 필요한 것과 비용

| 것 | 무엇 | 비용 |
|---|---|---|
| 시그널링 | SDP·ICE 를 주고받는 통로. 기존 FastAPI 에 **WebSocket** 하나 | 0원 |
| STUN | 내 공인 주소를 알아내는 서버. 공개 STUN 사용 | 0원 |
| TURN | P2P 가 막힐 때 중계. 자체 호스팅(coturn) | 전기요금 |

TURN 은 대칭형 NAT 뒤에서만 필요하고(대략 10~20%), 자체 호스팅이면
추가 비용이 없습니다. **다만 이 개발 환경에서는 실행해 볼 수 없습니다** —
네트워크가 없습니다.

### 3.3 녹음과의 관계

**통화와 녹음은 서로 다른 스트림입니다.**

```
    내 마이크 ─┬─→ WebRTC (남에게 들려주는 용도, 압축·에코제거)
               └─→ MediaRecorder (내 트랙, 서버에 올림)
```

`getUserMedia` 로 얻은 트랙 하나를 둘 다에 씁니다. 이미 있는
`RecordingClient` 가 두 번째 갈래를 그대로 담당합니다 — **녹음 쪽 코드는
고칠 게 거의 없습니다.**

## 4. GitHub 연동 — 1순위

사용자가 **가장 중요하다**고 한 부분이고, 실제로 지금 가장 약합니다.

### 4.1 지금 있는 것

| 것 | 상태 |
|---|---|
| 이벤트 정규화·diff 필터·조작 저항성 | ✅ 테스트로 고정 |
| `mapping.py`(순수 판단) | ✅ 31개 테스트 |
| 웹훅 수신 + 서명 검증 | ✅ |
| PR → 기여 이벤트 배선 | ✅ (이 PR 에서 이었음) |
| `HttpGitHubClient` | 🟡 **한 번도 실행된 적 없음** — 자격 증명·네트워크 없음 |

### 4.2 지금 비어 있는 것

1. **연결이 됐는지 사람이 알 방법이 없다**
   저장소를 적어 넣어도 웹훅이 오는지, 서명이 맞는지, 설치 id 가 유효한지
   화면에 아무것도 안 나옵니다. 틀리면 **오류 없이 기여도만 빕니다.**

2. **저장소 소유권 검증이 없다** (전면 감사 확인)
   `github_repo` 는 그냥 문자열이고 유니크 제약도 없습니다. 남의 저장소
   이름을 적으면 **그 저장소의 웹훅을 가로챌 수 있습니다.**

3. **백필이 없다**
   프로젝트를 중간에 연결하면 그 전의 PR·커밋이 통째로 빠집니다.

4. **`extract_task_refs` 호출자 0곳**
   `Fixes #12` 같은 참조로 PR 과 칸반 업무를 잇는 코드가 있는데 아무도
   부르지 않습니다 → `task_github_links` 에 행이 한 번도 안 쓰입니다.
   **"이 업무가 이 PR 로 끝났다" 를 보여줄 수 없습니다.**

4번이 특히 중요합니다. 이 프로젝트의 대표 주장이
**회의 → 업무 → GitHub → 기여도** 인데, 업무와 GitHub 사이가 아직
끊겨 있습니다.

## 5. 순서

| 순 | 무엇 | 왜 이 순서인가 |
|---|---|---|
| 1 | **GitHub 연결 상태를 보이게** + 소유권 검증 | 가장 중요하다고 한 것. 지금은 틀려도 조용하다 |
| 2 | **업무 ↔ PR 잇기** (`extract_task_refs` 배선) | 대표 주장의 마지막 끊긴 곳 |
| 3 | **회의 발화 → 기여 이벤트** 배선 | 기여도 세 다리 중 남은 하나 (docs/08 §0) |
| 4 | 시그널링 WebSocket + 통화 로비 | 통화의 뼈대 |
| 5 | WebRTC 메시 + 헤드폰 확인 | 통화 본체 |
| 6 | 통화 모드용 캡처 설정 (AEC 켬, AGC 끔) | §2.2 |
| 7 | PC 화면 정리 (넓은 화면 활용) | 지금은 폰 기준으로 좁게 잡혀 있다 |
| — | PWA·안드로이드 셸 | **보류.** 지운 게 아니라 순서를 뒤로 |

1~3은 하드웨어 없이 **지금 만들고 테스트할 수 있습니다.**
4~6은 만들 수는 있지만 **이 환경에서 실제로 통화해 볼 수 없습니다**
(네트워크 없음). 그건 정직하게 적고 넘어갑니다.

## 6. 모바일은 어떻게 되나

**지웁니다가 아니라 미룹니다.**

- 화면은 여전히 폰에서 열립니다. `app.css` 는 폰 기준이지만 넓은 화면
  에서도 깨지지 않습니다 (`max-width` 로 가운데 정렬)
- PWA(`manifest`·`sw.js`)는 그대로 둡니다. 있어도 PC 에 해가 없고,
  빼면 다시 넣을 때 같은 일을 두 번 합니다
- 안드로이드 셸(`android/`)은 별도 디렉터리라 PC 작업이 건드릴 일이
  없습니다. 빌드도 별개입니다

다만 **PC 화면은 폰 기준 폭(34rem)이 너무 좁습니다.** 칸반은 열 셋을
가로로 놓을 공간이 있고, 회의 중에는 참가자 목록과 발화가 같이 보여야
합니다. 그건 §5 의 7번입니다.

## 7. 이 전환으로 **줄어드는 위험**

`docs/09` 실험 5는 이렇게 시작합니다.

> 팀원 폰이 한 시간짜리 회의를 끝까지 녹음하는가?
> **이 실험이 실패하면 모드 A 자체를 재검토해야 한다.**

PC 브라우저에서는 이 위험이 크게 줄어듭니다. 화면 보호기가 켜져도 탭이
죽지 않고, 배터리 세이버가 마이크를 끄지 않습니다. `docs/14` 가 안드로이드
셸까지 만들어 해결하려던 문제가 **PC 에서는 대체로 없습니다.**

바꿔 말하면 **PC 우선이 기술적으로도 더 안전한 선택**입니다.
