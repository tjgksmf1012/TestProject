# 06. 데이터 모델

제안서 10장 스키마를 기반으로, 세 가지를 추가합니다.

1. **기여도 재계산 구조** (`contribution_events`, `score_runs`) — 점수를 저장하지 않고 재계산
2. **법적 요구사항 반영** (`consents`, `audio_assets`) — 녹음 동의 + 생체정보 분리 보관
3. **멀티트랙 지원** (`meeting_tracks`)

---

## 1. 제안서 스키마 유지 (그대로 좋음)

```sql
users                 (id, name, email, role)
projects              (id, title, deadline, status)
members               (project_id, user_id, project_role, skills)
tasks                 (title, assignee, deadline, status, priority)
task_dependencies     (predecessor_id, successor_id)
github_events         (repo, actor, type, ref, occurred_at)
task_github_links     (task_id, github_event_id, relevance)
meetings              (project_id, started_at, duration, status)
utterances            (speaker_id, start_ms, end_ms, text, type)
meeting_events        (type, severity, evidence, time_range)
decisions             (meeting_id, content, status, source)
meeting_task_candidates (action, assignee, deadline, confidence)
reports               (project_id, type, content, generated_at)
```

특히 좋은 설계:
- `meeting_task_candidates` 와 `tasks` 분리 → **AI 출력은 후보, 사람 승인 후 확정**
- `decisions.status` + `source` → 결정 번복 추적 가능
- `task_github_links.relevance` → 자동 연결의 확신도를 수치로 보관

## 2. 추가 ①: 기여도 재계산 구조

제안서의 `analytics(scope, metric, value, period)`를 **대체**합니다.

### 2.1 불변 이벤트 로그

```sql
CREATE TABLE contribution_events (
    id              BIGSERIAL PRIMARY KEY,
    project_id      BIGINT NOT NULL REFERENCES projects(id),
    user_id         BIGINT NOT NULL REFERENCES users(id),
    occurred_at     TIMESTAMPTZ NOT NULL,      -- 실제 발생 시각 (수집 시각 아님)
    recorded_at     TIMESTAMPTZ NOT NULL DEFAULT now(),

    category        TEXT NOT NULL,   -- task | code | meeting | document | schedule | peer
    event_type      TEXT NOT NULL,   -- pr_merged | review_given | task_completed | utterance_decision ...

    -- 원본 근거 (정확히 하나만 채움)
    source_kind     TEXT NOT NULL,   -- github_event | task | utterance | document | peer_review
    source_id       BIGINT NOT NULL,

    -- 산식 입력값
    magnitude       NUMERIC,         -- 유의미 diff 라인 수, 발화 길이 등
    metadata        JSONB NOT NULL DEFAULT '{}',

    CONSTRAINT uq_source UNIQUE (source_kind, source_id, event_type)
);

CREATE INDEX ON contribution_events (project_id, user_id, occurred_at);
```

**규칙**
- `INSERT` 만. `UPDATE` / `DELETE` 없음. (정정이 필요하면 상쇄 이벤트를 추가)
- `UNIQUE (source_kind, source_id, event_type)` → 웹훅 **중복 수신 방어**.
  GitHub 웹훅은 재전송될 수 있고, 백필과 웹훅이 겹칠 수 있습니다. 이 제약이 없으면 점수가 부풀려집니다.
- `occurred_at` 과 `recorded_at` 을 분리 — 백필한 과거 이벤트를 올바른 기간에 귀속시키기 위해.

### 2.2 가중치 버전

```sql
CREATE TABLE scoring_profiles (
    id           BIGSERIAL PRIMARY KEY,
    project_id   BIGINT REFERENCES projects(id),   -- NULL이면 시스템 기본값
    project_role TEXT NOT NULL,                    -- developer | planner | designer
    weights      JSONB NOT NULL,                   -- {"task":0.30,"code":0.35,...}
    created_by   BIGINT REFERENCES users(id),
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    note         TEXT                              -- 왜 조정했는지
);
```

가중치를 바꿔도 **덮어쓰지 않고 새 행을 만듭니다.** 조정 이력이 그대로 남습니다.
([`05-기여도-산정-설계.md`](05-기여도-산정-설계.md) §3 — 가중치를 팀이 합의해서 정한다는 설계와 맞물림)

### 2.3 계산 실행 기록

```sql
CREATE TABLE score_runs (
    id           BIGSERIAL PRIMARY KEY,
    project_id   BIGINT NOT NULL REFERENCES projects(id),
    profile_id   BIGINT NOT NULL REFERENCES scoring_profiles(id),
    algo_version TEXT NOT NULL,                    -- 산식 코드 버전
    period_start TIMESTAMPTZ,
    period_end   TIMESTAMPTZ,
    computed_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE score_results (
    run_id        BIGINT NOT NULL REFERENCES score_runs(id) ON DELETE CASCADE,
    user_id       BIGINT NOT NULL REFERENCES users(id),
    category      TEXT NOT NULL,
    raw_value     NUMERIC NOT NULL,
    weighted      NUMERIC NOT NULL,
    confidence    NUMERIC NOT NULL,     -- 0~1, 데이터 커버리지 기반
    range_low     NUMERIC,              -- 조정 가능 범위 하한
    range_high    NUMERIC,
    evidence_ids  BIGINT[] NOT NULL,    -- contribution_events.id 배열
    PRIMARY KEY (run_id, user_id, category)
);
```

**`evidence_ids` 가 핵심입니다.** 화면의 모든 숫자가 원본 이벤트로 역추적됩니다.
제안서 7장의 `"교수자와 팀원이 원본 활동까지 확인 가능"` 이 스키마 수준에서 보장됩니다.

### 2.4 최종 확정값

```sql
CREATE TABLE final_contributions (
    project_id   BIGINT NOT NULL REFERENCES projects(id),
    user_id      BIGINT NOT NULL REFERENCES users(id),
    run_id       BIGINT NOT NULL REFERENCES score_runs(id),  -- 어떤 계산을 기준으로 했나
    system_value NUMERIC NOT NULL,     -- 시스템 제안값
    final_value  NUMERIC NOT NULL,     -- 사람이 확정한 값
    adjusted_by  BIGINT REFERENCES users(id),
    reason       TEXT,                 -- 범위를 벗어나면 필수
    confirmed_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (project_id, user_id)
);
```

**시스템 값과 최종 값을 분리**합니다. "AI가 점수를 정하지 않는다"는 원칙이 데이터로 표현됩니다.

## 3. 추가 ②: 법적 요구사항

→ 근거: [`07-법적-윤리-요구사항.md`](07-법적-윤리-요구사항.md)

### 3.1 녹음 동의

```sql
CREATE TABLE recording_consents (
    id            BIGSERIAL PRIMARY KEY,
    meeting_id    BIGINT NOT NULL REFERENCES meetings(id),
    user_id       BIGINT NOT NULL REFERENCES users(id),
    consented     BOOLEAN NOT NULL,
    consent_type  TEXT NOT NULL,     -- recording | voiceprint_storage | raw_audio_retention
    consented_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    ip_address    INET,
    UNIQUE (meeting_id, user_id, consent_type)
);
```

**`consent_type`을 나눈 이유**: 개인정보보호법상 **생체인식정보 원본 보관**은 별도 동의 사안입니다.
"회의를 녹음해도 되는가"와 "당신의 성문을 저장해도 되는가"는 다른 질문입니다.

**애플리케이션 제약**: `recording` 동의가 없는 참석자가 있으면 녹음 시작을 막습니다.

### 3.2 오디오 자산 분리 보관

```sql
CREATE TABLE audio_assets (
    id             BIGSERIAL PRIMARY KEY,
    meeting_id     BIGINT NOT NULL REFERENCES meetings(id),
    track_id       BIGINT REFERENCES meeting_tracks(id),
    storage_key    TEXT NOT NULL,        -- 파일 경로 (별도 디렉터리/볼륨)
    encryption_key_id TEXT NOT NULL,     -- 다른 개인정보와 다른 키
    kind           TEXT NOT NULL,        -- raw | segment | voiceprint_sample
    bytes          BIGINT,
    retention_until TIMESTAMPTZ NOT NULL, -- 보존기간 만료 시각
    deleted_at     TIMESTAMPTZ
);
```

- **별도 디렉터리(볼륨) + 별도 암호화 키.** 개인정보보호법의 "생체인식정보는 다른 개인정보와 분리 보관" 요구 반영.
  (제안서 9장은 MinIO를 썼으나 2026-04 아카이브됨 → [`11-비용-제로-구성.md`](11-비용-제로-구성.md) §2.
  스키마는 그대로 두고 `storage_key` 해석만 "객체 키 → 파일 경로"로 바꾸면 나중에 오브젝트 스토리지로 이전 가능)
- `retention_until` — 만료된 원본을 지우는 배치 잡을 둡니다. **전사 텍스트는 남기고 원본 오디오만 삭제**하는 게 기본 정책입니다.
- `deleted_at` — 삭제 요청 이력이 남아야 합니다.

### 3.3 성문 등록 (모드 B용)

```sql
CREATE TABLE voiceprints (
    id           BIGSERIAL PRIMARY KEY,
    user_id      BIGINT NOT NULL REFERENCES users(id),
    project_id   BIGINT REFERENCES projects(id),  -- 프로젝트 범위로 한정
    embedding    vector(192),                      -- ECAPA-TDNN 차원
    sample_asset_id BIGINT REFERENCES audio_assets(id),
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    revoked_at   TIMESTAMPTZ
);
```

⚠️ 성문은 **가장 민감한 데이터**입니다.
- `consent_type='voiceprint_storage'` 동의 없이는 생성 금지.
- **프로젝트 범위로 한정** — 프로젝트가 끝나면 폐기.
- 멀티트랙(모드 A)을 쓰면 **이 테이블 자체가 불필요**합니다.
  → 법적 리스크를 줄이는 또 하나의 이유입니다. ([`04-회의-처리-파이프라인.md`](04-회의-처리-파이프라인.md))

## 4. 추가 ③: 멀티트랙

```sql
CREATE TABLE meeting_tracks (
    id             BIGSERIAL PRIMARY KEY,
    meeting_id     BIGINT NOT NULL REFERENCES meetings(id),
    user_id        BIGINT NOT NULL REFERENCES users(id),   -- 트랙 = 사람
    device_label   TEXT,
    started_at     TIMESTAMPTZ NOT NULL,     -- 서버 기준
    offset_ms      INTEGER NOT NULL DEFAULT 0,  -- 정렬 보정값
    sample_rate    INTEGER,
    UNIQUE (meeting_id, user_id)
);
```

`utterances` 에 트랙 정보를 연결합니다:

```sql
ALTER TABLE utterances
  ADD COLUMN track_id       BIGINT REFERENCES meeting_tracks(id),
  ADD COLUMN speaker_source TEXT NOT NULL DEFAULT 'diarization',
      -- 'track'        : 멀티트랙 → 화자 확정 (신뢰도 1.0)
      -- 'voiceprint'   : 임베딩 매칭 → 신뢰도 있음
      -- 'manual'       : 사람이 지정
      -- 'diarization'  : SPEAKER_XX 미매핑
  ADD COLUMN speaker_confidence NUMERIC,
  ADD COLUMN is_overlap    BOOLEAN NOT NULL DEFAULT false;
```

**`speaker_source` 가 중요합니다.** 기여도 계산에서 신뢰도를 반영하려면 화자 라벨이
어떻게 정해졌는지 알아야 합니다. 멀티트랙(`track`)이면 신뢰도 1.0,
`diarization`이면 그 회의의 기여도 신뢰도를 낮춥니다.
([`05-기여도-산정-설계.md`](05-기여도-산정-설계.md) §4.1)

## 5. 반복 논의 탐지용 임베딩

제안서가 pgvector를 넣은 건 좋은 판단입니다. 구체화하면:

```sql
ALTER TABLE utterances ADD COLUMN embedding vector(768);
CREATE INDEX ON utterances USING hnsw (embedding vector_cosine_ops);
```

- 같은 회의 내 유사 발화 클러스터 → 반복 논의 구간
- **이전 회의**의 결정 임베딩과 대조 → 결정 번복 후보 (제안서 5장 ✅)
- 커밋 diff 임베딩 ↔ 업무 설명 임베딩 → 자동 연결 후보
  ([`03-시스템-아키텍처.md`](03-시스템-아키텍처.md) §4.3)

## 6. 감사 로그

기여도를 다루는 서비스에는 필수입니다.

```sql
CREATE TABLE audit_logs (
    id         BIGSERIAL PRIMARY KEY,
    actor_id   BIGINT REFERENCES users(id),
    action     TEXT NOT NULL,       -- score_adjusted | consent_revoked | audio_deleted | weights_changed
    target     TEXT NOT NULL,
    before     JSONB,
    after      JSONB,
    at         TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

"팀장이 내 점수를 몰래 내렸다"는 분쟁이 실제로 생길 수 있습니다.
`final_contributions.adjusted_by` + `audit_logs` 로 추적 가능해야 합니다.

## 7. 요약: 제안서 대비 변경점

| | 제안서 | 이 문서 |
|---|---|---|
| 기여도 저장 | `analytics(metric, value)` | `contribution_events`(불변) + `score_runs`/`score_results`(재계산) |
| 가중치 | 없음 | `scoring_profiles` (버전 관리, 역할별) |
| 최종 확정 | 없음 | `final_contributions` (시스템값 ≠ 최종값) |
| 녹음 동의 | 없음 | `recording_consents` (동의 유형 분리) |
| 오디오 | `파일 저장: MinIO` | `audio_assets` (별도 키·버킷·보존기간) |
| 성문 | 없음 | `voiceprints` (프로젝트 범위, 폐기 가능) |
| 멀티트랙 | 없음 | `meeting_tracks` + `utterances.speaker_source` |
| 감사 | 없음 | `audit_logs` |
