# 요구사항 정의서 ↔ 저장소 대조

받은 「AI 기반 팀 프로젝트 협업 플랫폼 요구사항 정의서」의 요구 ID 를 지금
코드와 하나씩 대조한 것입니다.

## ⚠️ 이 문서를 만든 이유

**"얼마나 만들어졌나" 에 아무도 답할 수 없었습니다.** README 의 현황표는
저장소가 스스로 정한 항목으로 되어 있고, `docs/08` 로드맵은 요구사항
정의서보다 먼저 쓰였습니다. 요구 ID 로 물으면 코드를 다 읽어야 답이 나왔고,
그래서 **주석이 선언한 것을 구현으로 착각하는 일**이 실제로 있었습니다
(아래 §4 결함 122).

## ⚠️ 숫자를 손으로 적지 않았습니다

이 저장소는 문서가 사실과 다른 곳을 열세 군데 발견한 적이 있습니다. 그래서
**개수와 "있음" 주장은 테스트가 다시 셉니다** — `backend/tests/test_requirements_map.py`.
아래 표의 `근거` 칸에 적힌 경로가 없어지면 테스트가 터집니다.

## 2. 다르게 만든 것 — 그리고 그 이유

요구사항 정의서와 저장소가 다른 곳입니다. **되돌리기 전에 이유를 보십시오.**
전부 근거가 문서에 남아 있고, 모르고 "고치면" 되살아나는 문제들이 있습니다.

### ⛔ 일부러 범위에서 뺀 것 — §11 음성·억양 분석

`AI-VOICE-001~006`(말하기 속도·음량·음높이·억양·말버릇)은 `docs/08` §2 에서
**범위 제거**로 결정했습니다. 이유 둘:

1. **평가할 방법이 없습니다.** 정답 데이터가 없어 "맞았는지" 를 잴 수 없습니다
2. **감정 해석 위험.** 정의서 §11 머리말도 "감정이나 성격을 단정하는 용도로
   사용하지 않는다" 고 못 박고, NFR-005 도 같은 말을 합니다. 그런데 억양
   변화를 사람 옆에 적어 두면 **읽는 사람이 알아서 해석합니다** — 도구가
   금지해도 표는 이미 그 자리에 있습니다

되살리려면 평가셋부터 만들어야 합니다. 지금 켜면 근거 없는 숫자가 사람 옆에
붙습니다.

## 3. ⚠️ 정의서 안에서 서로 어긋나는 곳 — 발언 비중

`AI-AUDIO-005` 의 예시는 이렇게 생겼습니다.

```
윤식 32%
민수 27%
지연 25%
철수 16%
```

**내림차순으로 늘어놓은 이 모양이 곧 리더보드입니다.** 그런데 같은 문서가
두 곳에서 반대로 말합니다.

* `AI-REVIEW-007` — "발언 비중은 사용자의 프로젝트 기여도를 판단하는 기준으로
  직접 사용하지 않는다"
* `NFR-005` — 단정적 평가를 금지하며 **올바른 예**로 "이번 회의에서 철수의
  발언 비중은 전체 발언의 8%였다" 를 듭니다

읽으면 뜻은 분명합니다. 요구는 **값을 만들라**는 것이지 **줄을 세우라**는
것이 아닙니다. 예시의 생김새만 리더보드였습니다.

그래서 이렇게 정했습니다 (`backend/teamflow/audio/multitrack.py::speaking_ratios`):

* 값은 **트랙 순서 그대로** 돌려줍니다. 정렬하지 않습니다 — 정렬해서 주면
  부르는 쪽은 그게 뜻있는 순서라고 믿습니다
* 화면에 그릴 때는 **이름 순 · 값은 글자로**. 같은 축 위에 폭이나 위치로
  그리면 그 순간 순위표입니다 (이 저장소가 두 번 낸 결함)
* **기여도 점수에 넣지 않습니다.** `docs/05` §5 가 "총 발언 시간 = 점수 아님
  (참고 표시만)" 으로 이미 정해 뒀습니다

## 4. 이번 대조에서 나온 결함

### ⭐ 결함 121 — `speaking_ratio` 가 언제나 `0.0`

`TrackStats.speaking_ratio` 가 `return 0.0` 으로 박혀 있었고 부르는 곳은
0곳이었습니다.

**구조적으로 계산이 불가능한 자리였습니다** — 비중에는 분모(팀 전체 발언
시간)가 필요한데 그 dataclass 는 자기 트랙만 압니다. 스텁을 넣어 둔 것으로
보이는데, **`0.0` 은 "안 쟀다" 가 아니라 "한마디도 안 했다" 로 읽힙니다.**
이 저장소가 제일 하면 안 된다고 정한 것(측정 불가 ≠ 0점)을 정면으로
어기는 값입니다.

목록 전체를 받는 `speaking_ratios()` 로 옮겼습니다. **아무도 말하지 않은
회의는 `None`** 입니다 — 분모가 0이면 비중이라는 것이 존재하지 않고, 그때
0.0 을 돌려주면 "다들 0% 말했다" 는 **잰 값**처럼 보입니다.

### ⭐ 결함 122 — 주석이 탐지기 다섯을 선언하는데 **넷은 코드가 0곳**

`meeting_events.event_type` 의 주석이 이랬습니다.

```
# repeated_discussion | unanswered_question | incomplete_task |
# topic_drift | decision_conflict
```

CHECK 제약은 없었고, **실제로 만들어지는 것은 `unanswered_question` 하나**
뿐이었습니다. 나머지 넷이 정의서의 `AI-REVIEW-001`(반복 논의)·`003`(주제
이탈)·`004`(미완성 업무)·`006`(결정 번복)이라, 이 주석이 **요구가 이미
구현된 것처럼** 보이게 만들고 있었습니다.

**같은 결함의 세 번째 사례입니다.** `speaker_source` 는 값이 다섯 곳에서
갈라져 있었고(결함 118), `report_type` 은 주석 한 줄이 전부였으며(결함 119),
이 열은 **둘 다**였습니다.

`db/vocab.py` 로 옮기고 `EVENT_PRODUCED` / `EVENT_NOT_PRODUCED_YET` 으로
갈랐습니다. ⭐ 그리고 테스트가 **"만들어진다고 적은 값에 진짜 코드가 있는지"**
를 소스에서 다시 셉니다 — 반대 방향(만든다고 적었는데 없음)이 바로 이
저장소의 대표 실패 ① 이고, 오래 안 들킨 이유는 **아무도 대조해 보지 않아서**
였습니다.

#### CHAT-008 을 왜 이름으로 만들었는가

정의서는 "이모지 반응" 이라고 적었지만 저장하는 값은 `ok`·`agree`·
`question`·`thanks` 라는 **이름**이고, 그림은 화면이 SVG 로 그립니다
(`lib/nav/icons.ts`). 두 가지 이유이고 둘 다 이 저장소가 이미 겪은 것입니다.

1. **색 이모지는 화면에 못 나갑니다.** `guards.test.ts` 가 막습니다 — 기기
   마다 다른 그림이 나오고, 색이 박혀 있어 어두운 모드를 안 따라가고,
   베이스라인이 서체에 딸려 있어 세로 정렬이 틀어집니다. 칸반 카드의 `🗣`
   를 SVG 로 바꾼 것이 그 규칙이 생긴 자리입니다
2. **자유 입력이면 조롱 통로가 됩니다.** 반응은 **남이 쓴 글 위에** 붙고,
   이 제품은 성적에 쓰일 수 있는 기여도를 다룹니다(`docs/07`). 지금 이
   저장소에는 신고도 차단도 없습니다 — 없는 것을 전제로 통로부터 열지
   않습니다. 넷 다 중립이거나 긍정이고, **부정 반응은 일부러 없습니다**

#### CHAT-006·007 을 왜 미뤘는가

파일 업로드는 "저장 통로" 하나가 아니라 **저장 자리 + 인증이 붙은
내려받기 + MIME 판별 + 크기 상한 + 보존 기간**이 한 벌로 필요합니다.
이 중 하나라도 빠지면 남의 팀 파일이 주소만 알면 열리는 통로가 됩니다.
`audio/chunk_store.py` 가 이미 비슷한 문제를 풀고 있으므로 그것을 넓히는
쪽이 맞고, 그건 이 작업과 별개 크기입니다. **반쯤 만들어 두지 않습니다.**

⚠️ 왼쪽 열의 "회의 채널" 은 여전히 **회의 목록**입니다
(`lib/nav/channels.ts`) — 텍스트 채널은 `chat.html` 에 있습니다. 둘이 같은
말로 불리므로 여기 적어 둡니다.

#### ⚠️ 마감 알림을 **행으로 쌓지 않습니다**

`due_soon`·`overdue` 는 지금 상태에서 나옵니다. 저장하면 마감일을 미뤘을 때
"곧 마감" 이 남고, 업무를 끝냈을 때 "지연" 이 남습니다 — 알림이 사실이
아니라 **베낀 순간의 사실**을 가리키게 됩니다. CHECK 제약이 그 둘을
아예 거절하고(`test_notifications.py` 가 DB 가 막는 것까지 잽니다),
`test_moving_the_deadline_moves_the_notice` 가 "옮기면 따라오는가" 를
직접 잽니다.

문장도 저장하지 않습니다 — 가리키는 번호만 두고 읽을 때 만듭니다. 업무
이름을 고치면 알림 문장도 따라옵니다.
| SEARCH-001 채팅 검색 | ✅ | `GET /api/projects/{id}/messages/search` |
| SEARCH-002 업무 검색 | ✅ | 이름·담당자·상태·우선순위. 넷을 겹칠 수 있습니다 |
| SEARCH-003 회의 검색 | ✅ | 이름·날짜. **예정된 회의도** 나옵니다 — 이름으로 찾는 사람은 그것이 열렸는지 모릅니다 |
| SEARCH-004 회의 내용 검색 | ✅ | `utterances`. ⚠️ **동의의 산물**이라 지우면 검색에서도 사라집니다 (베껴 둔 색인이 없습니다) |
| SEARCH-005 GitHub 검색 | 🟡 | 저장소·이벤트 종류·참조까지. ⚠️ **원문(`payload`)은 안 훑습니다** — 저장소 설정과 이메일이 검색으로 새어 나갑니다 |

#### ⚠️ `calendar_events` 표를 **안 만들었습니다**

요구하는 다섯 중 넷은 이미 있는 행에서 나옵니다 — 업무 마감일·프로젝트
마감일·회의. 그걸 따로 베껴 담으면 **칸반에서 마감일을 고쳤을 때 달력만
옛 날짜를 말합니다.** 이 저장소가 반복해서 당한 실패 ② 입니다. 달력은
그때그때 읽어서 만들고, `test_calendar_api.py` 가 "마감일을 옮기면 달력이
따라오는가" 를 직접 잽니다 — 베낀 자료를 보고 있으면 그 검사가 터집니다.

예정된 회의도 **`meetings` 행**입니다. `scheduled_at` 이 있고
`started_at` 이 비어 있으면 아직 안 연 회의입니다. 예정을 별도 표에 두면
"그 예정이 이 회의가 됐다" 를 잇는 칸이 또 필요하고, 안 이어진 것들이
쌓입니다.
