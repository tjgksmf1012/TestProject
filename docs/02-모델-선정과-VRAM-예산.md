# 02. 모델 선정과 VRAM 예산

대상 하드웨어: **RTX 5080 16GB (Blackwell, sm_120)**

이 문서의 결론을 한 줄로: **16GB에는 ASR + 화자분리 + LLM을 동시에 올릴 수 없습니다.
이건 튜닝으로 해결되는 문제가 아니라 아키텍처로 해결해야 하는 제약입니다.**

원본 ChatGPT 대화는 "2B급이나 양자화된 7~8B급부터 시작"이라고만 했는데,
진짜 문제는 모델 하나의 크기가 아니라 **파이프라인 전체의 동시 상주 여부**입니다.

---

## 1. 환경 구축 (여기서 며칠 날리기 쉽습니다)

RTX 5080은 compute capability **sm_120**입니다.

```bash
# 반드시 cu128 인덱스 명시. 기본 인덱스로 깔면 sm_120 미지원 에러.
pip install torch torchaudio --index-url https://download.pytorch.org/whl/cu128
```

- **PyTorch 2.7.0이 sm_120을 stable에서 지원한 최초 버전**입니다. 그 이전 버전은 전부 안 됩니다.
- `-cuda12.8-` 태그가 붙은 PyTorch 2.7.0+ 이미지면 RTX 50 시리즈에서 동작합니다.
- 검증: `python -c "import torch; print(torch.cuda.get_device_capability())"` → `(12, 0)` 이어야 합니다.

⚠️ **알려진 함정**: CUDA 12.8/12.9 설치본에서 `libnvptxcompiler.so`가 빠져 PTX JIT이 깨지는
사례가 보고돼 있습니다. vLLM이나 FlashAttention처럼 JIT 컴파일에 의존하는 도구에서 터집니다.
→ vLLM은 사전빌드 휠 사용, 소스 빌드는 피하세요.

> 🔧 **첫 주 과제**: 빈 프로젝트에서 `torch` + `vLLM` + `transformers(≥5.13)` + `pyannote.audio 4.x`가
> 한 가상환경에 공존하는지부터 확인하세요. 이게 되면 절반은 끝난 겁니다.
> 안 되면 각 컴포넌트를 별도 컨테이너로 분리하는 게 정답입니다.

## 2. 컴포넌트별 VRAM 추정

⚠️ **아래 숫자는 추정치입니다.** 파라미터 수 × 정밀도로 계산한 값이며, 실제로는 활성화 메모리,
단편화, 프레임워크 오버헤드로 20~40% 더 듭니다. **직접 측정해서 이 표를 갱신하세요.**
(측정 방법: [`09-리스크와-검증-실험.md`](09-리스크와-검증-실험.md) 실험 0)

| 컴포넌트 | 모델 | 정밀도 | 가중치 추정 | 실사용 추정 |
|---|---|---|---|---|
| ASR | `Qwen3-ASR-1.7B` | FP16 | ~3.4 GB | **5~6 GB** |
| ASR (경량) | `Qwen3-ASR-0.6B` | FP16 | ~1.2 GB | **2~3 GB** |
| 화자 분리 | pyannote `community-1` | FP32 | 작음 | **1~2 GB** |
| 화자 임베딩 | ECAPA-TDNN | FP32 | ~80 MB | **< 1 GB** |
| LLM | `EXAONE-4.0-1.2B` | FP16 | ~2.4 GB | **3~4 GB** |
| LLM | `EXAONE-4.0-1.2B` | 4bit | ~0.9 GB | **1.5~2 GB** |
| LLM | `Qwen3-8B` 급 | 4bit(AWQ) | ~5 GB | **6~7 GB + KV** |
| LLM | `Qwen3-14B` 급 | 4bit | ~8.5 GB | **9~10 GB + KV** |
| LLM | `EXAONE-4.0-32B` | Q4_K_M | ~19 GB | ❌ **안 들어감** |
| LLM | `EXAONE-4.0-32B` | Q3_K_M | ~15.5 GB | ⚠️ **KV 캐시 자리 없음** |
| LLM | `K-EXAONE-2.0-750B` | — | — | ❌ **논외** |

### 2.1 진짜 병목: KV 캐시 (원본 대화가 놓친 부분)

**회의록은 깁니다.** 1시간 회의 = 한국어 기준 대략 9,000~15,000 토큰입니다.
프롬프트 + 전사 + 출력을 합치면 **32K 컨텍스트**를 잡아야 안전합니다.

KV 캐시는 컨텍스트 길이에 **선형 비례**합니다. 대략:

```
KV 캐시 = layers × 2(K,V) × kv_heads × head_dim × 2바이트 × seq_len
```

8B급 모델(36층, GQA 8 kv-heads, head_dim 128) 기준 대략 **토큰당 ~144KB**
→ 32K 컨텍스트에서 **약 4.7GB**. 가중치(4bit 5GB)와 합치면 **10GB 내외**.

**즉 8B 4bit + 32K 컨텍스트만으로 16GB의 3분의 2가 사라집니다.**
여기에 ASR 6GB를 더할 자리는 없습니다.

**완화 수단**
- KV 캐시 양자화 (FP8/INT8) → 절반 절감. vLLM 지원.
- 회의를 **청크로 쪼개서** 처리 (10분 단위 → 계층적 요약). 컨텍스트 요구가 줄어듭니다.
- `--max-model-len`을 실제 필요한 값으로 **낮게** 잡기. 기본값은 대부분 과합니다.

## 3. 세 가지 배치 전략

### 전략 A. 순차 적재 (권장 — MVP 기본값)

```
[잡 시작]
  → GPU 락 획득
  → 화자분리 모델 로드 → 실행 → 언로드
  → ASR 모델 로드 → 실행 → 언로드
  → LLM 로드 → 실행 → 언로드
  → GPU 락 해제
[잡 완료]
```

- ✅ 16GB에 확실히 들어감. 각 단계가 GPU를 독점.
- ✅ 각 단계에서 가장 좋은 모델을 쓸 수 있음 (크기 제약 완화).
- ❌ 모델 로딩 시간이 매 잡마다 발생 (10~60초씩).
- ❌ 동시에 잡 1개만 처리 가능.

**이 프로젝트에는 이게 맞습니다.** 이유: 회의 분석은 **비실시간 배치 작업**입니다.
사용자는 회의 끝나고 녹음 올린 뒤 "분석 중입니다" 화면을 보면 됩니다.
1시간 회의를 10분 걸려 처리해도 아무도 불만이 없습니다.
원본 대화도 "1차 버전은 녹음 후 일괄 분석"이라고 정확히 짚었습니다.

> 구현 주의: PyTorch에서 모델 언로드는 `del model` 만으로 부족합니다.
> `gc.collect()` + `torch.cuda.empty_cache()` 를 같이 호출해야 실제로 반환됩니다.
> vLLM은 프로세스 자체를 내리는 게 확실합니다 → **단계별 서브프로세스** 권장.

### 전략 B. 상시 상주 (소형 조합)

```
Qwen3-ASR-0.6B (2.5GB) + pyannote (1.5GB) + EXAONE-4.0-1.2B 4bit (2GB) ≈ 6GB
→ 나머지 10GB를 KV 캐시와 동시 처리에 사용
```

- ✅ 로딩 오버헤드 없음, 응답 빠름, 동시 잡 처리 가능.
- ❌ 모든 컴포넌트가 최소 크기 → **품질 저하.** 특히 1.2B LLM의 구조 추출 능력이 관건.
- 실시간/스트리밍으로 확장할 때 필요해집니다.

### 전략 C. 하이브리드 (실전 추천)

```
GPU 상주: ASR + 화자분리 (합계 ~8GB)
GPU 임시: LLM 단계에서만 로드 (~7GB)
```

또는 더 과감하게: **LLM 단계를 CPU로 내리기.**
`EXAONE-4.0-1.2B` 정도는 llama.cpp Q4로 CPU에서 초당 수십 토큰 나옵니다.
배치 처리라면 충분합니다. → **GPU는 음성 처리에만, CPU는 텍스트 처리에.**
이러면 16GB 제약이 갑자기 여유로워집니다.

## 4. 모델 선정 결정

### 4.1 ASR: `Qwen3-ASR-1.7B` (1순위)

| 근거 | 내용 |
|---|---|
| 성능 | 오픈소스 SOTA, Whisper-large-v3 상회, 상용 API와 경쟁 |
| 라이선스 | **Apache 2.0** — 상업화 걸림돌 없음 |
| 기능 | 타임스탬프 예측 내장, 긴 오디오, 52개 언어 자동 식별 |
| 서빙 | 공식 툴킷이 vLLM 배치/비동기/스트리밍 지원 |
| 통합 | Transformers v5.13.0+ 네이티브 |
| 확장 | `Qwen3-ForcedAligner-0.6B`로 단어 단위 정렬 보강 가능 |

**폴백**: VRAM이 빠듯하면 `Qwen3-ASR-0.6B`. 동시성 128에서 2000배 처리량이라
서비스 확장 시에도 선택지가 됩니다.

**비교군**: `whisper-large-v3` (한국어 CER 11.13% @ KsponSpeech Eval-Other).
"우리가 왜 Qwen3-ASR을 골랐는가"를 숫자로 보여주려면 **둘 다 돌려서 CER 비교**하세요.
발표 슬라이드 한 장이 나옵니다.

> ⚠️ 한국어는 **CER**로 평가합니다. WER 아닙니다. 교착어라 어절 단위 오류율이 과장됩니다.

### 4.2 화자 분리: pyannote.audio 4.0 + `community-1`

- 현존 최고 오픈소스. 3.1 대비 화자 수 추정·할당 개선.
- **라이선스 CC-BY-4.0** → 서비스 크레딧에 pyannote 귀속 표시 **필수**.
- HuggingFace gated → 사용 동의 + 토큰 필요. **배포 파이프라인에 토큰 주입 경로를 미리 만드세요.**

**대안**: NVIDIA NeMo `Sortformer`. 스트리밍 버전(`diar_streaming_sortformer_4spk-v2`)도 있으나
**4인 화자 모델**이라 5인 팀에는 확인이 필요합니다.

**절대 하지 말 것**: pyannoteAI **Precision-2**는 community-1보다 28% 정확하고 화자 식별·성문·
신뢰도를 지원하는 유일한 모델이지만 **상용 API**입니다. "외부 API 미사용"이라는 이 프로젝트의
핵심 포지셔닝과 정면충돌합니다. 쓰면 프로젝트의 존재 이유가 사라집니다.

### 4.3 화자 임베딩(식별): ECAPA-TDNN

- SpeechBrain `spkrec-ecapa-voxceleb` 또는 WeSpeaker `ecapa-tdnn512-LM`.
- 아시아권 화자 데이터를 원하면 `3D-Speaker`의 CN-Celeb 레시피 참고.
- 한국어 전용 공개 모델은 못 찾았습니다. 화자 임베딩은 언어보다 음향 특성 의존이므로
  VoxCeleb 기반이어도 대체로 동작하나, **이건 검증 대상**입니다.

### 4.4 LLM: 목적이 두 개로 갈립니다

| 목적 | 추천 | 라이선스 |
|---|---|---|
| **졸업작품 / 연구 / 교육** | `EXAONE-4.0-32B` 또는 `4.5-33B` (한국어 최강) | NC — 교육 목적 **명시 허용** |
| **상업화 가능성을 남기려면** | `Qwen3` 계열 | **Apache 2.0** |
| **16GB 로컬 실험** | `EXAONE-4.0-1.2B` / `Qwen3` 소형 4bit | 각각 위와 동일 |

⚠️ **EXAONE 4.0 = `EXAONE AI Model License Agreement 1.2 - NC`.**
연구·교육은 허용, **상업 이용은 별도 계약 필요**. 창업이나 유료화를 조금이라도 고려한다면
Qwen3를 기본으로 잡고 EXAONE은 비교군으로만 쓰세요.

**태스크 특성 고려**: 이 프로젝트의 LLM 작업은 "한국어 회의록 → 구조화된 JSON"입니다.
창의적 글쓰기가 아니라 **지시 따르기 + 스키마 준수 + 정보 추출**입니다.
한국어 뉘앙스 능력보다 **구조 출력 안정성**이 더 중요하고, 이건 Qwen3가 강한 영역입니다.

### 4.5 출력 형식은 프롬프트가 아니라 **디코딩으로 강제**

원본 대화의 "JSON 형식으로 출력하도록 한다"를 실제로 안전하게 만드는 방법:

```python
from pydantic import BaseModel
from typing import List

class Task(BaseModel):
    assignee: str
    title: str
    deadline: str | None
    confidence: float

class MeetingAnalysis(BaseModel):
    summary: str
    decisions: List[str]
    tasks: List[Task]
    unresolved_issues: List[str]

# vLLM guided decoding — 스키마를 벗어나는 토큰은 생성 자체가 불가능
schema = MeetingAnalysis.model_json_schema()
# vLLM: guided_json=schema, guided_decoding_backend="xgrammar"
```

- vLLM은 `outlines` / `lm-format-enforcer` / **`xgrammar`** 를 백엔드로 지원.
- **2026년 권장 기본값은 xgrammar** — JIT 컴파일 문법, 대부분의 스키마에서 최속.
  **문법이 재사용될 때 캐싱 효과가 큰데, 이 프로젝트는 항상 같은 스키마를 씁니다.** 최적 조건입니다.
- 효과: JSON 파싱 실패가 **원리적으로 발생하지 않습니다.** 소형 모델을 쓸수록 이득이 큽니다.

이 한 가지 결정으로 "1.2B 모델도 쓸 만한가?"의 답이 바뀝니다.
구조가 강제되면 소형 모델의 약점(형식 붕괴)이 사라지고, 남는 건 **내용 정확도**뿐입니다.

## 5. LoRA 파인튜닝 가능성

**하드웨어는 문제가 아닙니다.**

- QLoRA는 7B에 최소 8GB, **16GB면 여유** 있음.
- **Unsloth**: 표준 QLoRA 대비 2배 빠르고 VRAM 70% 절감. Qwen3 30B-A3B QLoRA가 17.5GB에서 동작.
- Unsloth dynamic 4-bit는 8-bit 대비 perplexity 차이 0.02 — 사실상 무손실.
- 지원: Llama 3.x, **Qwen 2.5/3**, Mistral, Gemma 2, DeepSeek, Phi-3/4 등.

**문제는 데이터입니다.** 회의 녹취 + 정답 라벨(요약/결정사항/담당자/업무/마감일)을
수백 건 만들려면 회의 수백 회분의 수작업 라벨링이 필요합니다. 졸업작품 기간에 불가능합니다.

→ **재정의**: 20~30건에 정답 라벨을 붙여 **평가 데이터셋**으로 쓰세요.
학습이 아니라 **모델·프롬프트 비교 측정용**입니다.
이것만으로도 "정량 평가를 수행했다"는 방어 가능한 주장이 되고,
LoRA는 "데이터가 모이면 이렇게 확장한다"는 **설계 확장점**으로 문서에 남깁니다.
