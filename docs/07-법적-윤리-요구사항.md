# 07. 법적·윤리 요구사항

> ⚠️ **법률 자문이 아닙니다.** 공개 자료 조사 결과이며, 실제 서비스 출시 전에는 전문가 검토가 필요합니다.
> 다만 졸업작품·공모전 관점에서는 **"우리는 이 요구사항을 설계에 반영했다"**고 말할 수 있는 것 자체가
> 강력한 차별점입니다. 대부분의 학부 프로젝트는 이 항목을 다루지 않습니다.

제안서 17장은 이 주제를 한 줄로 처리했습니다:
> `개인정보·녹음 동의 → 사전 동의, 접근 제어, 보존 기간과 삭제 기능`

방향은 맞지만 근거가 없습니다. **두 개의 다른 법**이 각각 다른 요구를 합니다.

---

## 1. 통신비밀보호법 — "녹음해도 되는가"

### 1.1 확인된 사실

| 상황 | 적법성 |
|---|---|
| **대화 당사자**가 녹음 | ✅ **합법.** 본인이 대화에 참여했다면 몰래 녹음해도 위법하지 않음 |
| **제3자**가 녹음 | ❌ **형사처벌.** 대화자 중 1명의 동의를 얻었더라도 상대방 동의가 없으면 위법한 감청 |

2022년 8월, 당사자 녹음도 상대 동의 없이는 금지하는 개정안이 발의됐으나 **철회**되었습니다.
현행법은 여전히 **"당사자 참여 여부"가 적법성 판단의 핵심**입니다.

출처: [법무법인 법승](https://www.lawwin.co.kr/incheon/knowledgedetail?index=7039),
[뉴로이어 법률사무소](https://www.newlawyer.co.kr/41/241),
[나무위키 - 비동의 녹취 불법화 논란](https://namu.wiki/w/비동의%20녹취%20불법화%20논란)

### 1.2 설계 요구사항

| # | 요구사항 | 이유 |
|---|---|---|
| L1 | **녹음 시작은 회의 참석자 본인만 가능** | 비참석자가 시작하면 제3자 녹음 = 형사처벌 |
| L2 | 참석하지 않은 팀장/교수의 **원격 녹음 시작 기능 금지** | 위 |
| L3 | 회의 참석자 명단을 녹음 시작 시점에 기록 | 나중에 "누가 당사자였나"를 증명 |
| L4 | 외부 파일 업로드 시 **"본인이 참여한 회의입니까?" 확인** | 제3자 녹음 파일 업로드 차단 |

⚠️ **L2가 제안서와 충돌할 수 있습니다.** 제안서 3장의 사용자 표에서 팀장의 목적이
"업무 배분, 일정·병목 관리, 회의 진행 개선"이고, 11장 화면에 "회의 업로드·실시간 회의"가 있습니다.
**팀장이 원격으로 녹음을 시작하는 UI를 만들면 안 됩니다.**

## 2. 개인정보보호법 — "저장하고 처리해도 되는가"

### 2.1 확인된 사실

- 개인정보보호위원회는 **회의 석상에서 녹음된 목소리도 개인정보**라고 판단했습니다.
  음성이 개인을 구별할 수 있는 고유 정보라는 이유입니다.
- 녹음된 음성은 **생체인식정보**로 간주될 수 있으며, 이 경우:
  - **원본정보를 보관하려면** 이용자 동의 또는 법령 근거가 필요합니다.
  - **다른 개인정보와 분리해 보관**하도록 설계·제조해야 합니다.
  - 위·변조된 생체인식정보를 이용한 공격에 대한 보안대책이 필요합니다.

출처: [보안뉴스 - 생체정보 가이드라인](http://www.boannews.com/media/view.asp?idx=102064),
[개인정보보호위원회](https://www.privacy.go.kr/)

> 참고: 전문가들 사이에 "이름이나 개인식별 정보가 없는 단순 녹취록 목소리를 개인정보로 보는 건
> 과하다"는 반론이 있습니다. ([공공투데이](https://www.publictoday.co.kr/news/articleView.html?idxno=65708))
> 즉 이 영역은 **아직 확정적이지 않습니다.** 보수적으로 설계하는 게 안전합니다.

### 2.2 설계 요구사항

| # | 요구사항 | 스키마 반영 |
|---|---|---|
| P1 | **녹음 동의**를 참석자 전원에게 받고 기록 | `recording_consents(consent_type='recording')` |
| P2 | **원본 오디오 보관 동의를 별도로** 받음 | `consent_type='raw_audio_retention'` |
| P3 | **성문(voiceprint) 저장 동의를 또 별도로** 받음 | `consent_type='voiceprint_storage'` |
| P4 | 오디오 원본을 **별도 스토리지 + 별도 암호화 키**로 분리 보관 | `audio_assets.encryption_key_id`, 별도 버킷. ⚠️ **절반만 됨** — 볼륨은 분리(`audio_storage_root`, docker 볼륨 `audio`)했지만 **암호화는 안 돼 있습니다. 오디오는 평문입니다.** `audio_encryption_key_id` 는 "어느 키로 썼는가" 를 적어 두는 자리일 뿐 암·복호 코드가 없습니다 |
| P5 | **보존기간 설정 + 자동 삭제** | `audio_assets.retention_until` + 배치 잡. **`beat` 서비스가 매일 04:00 에 돌립니다** — 이게 안 떠 있으면 잡이 정의만 돼 있고 하나도 실행되지 않습니다 |
| P6 | 개인별 **삭제 요청** 처리 | `audio_assets.deleted_at`, `voiceprints.revoked_at` |
| P7 | 접근 제어 — 같은 프로젝트 구성원만 열람 | 애플리케이션 권한 |
| P8 | 처리 이력 감사 로그 | `audit_logs` |

→ 스키마 상세: [`06-데이터-모델.md`](06-데이터-모델.md) §3

### 2.3 동의를 세 단계로 나누는 이유

```
① recording            "이 회의를 녹음합니다"
② raw_audio_retention  "원본 음성 파일을 N일간 보관합니다"     ← 거부해도 서비스 이용 가능
③ voiceprint_storage   "화자 식별을 위해 목소리 특징을 저장합니다"  ← 거부해도 서비스 이용 가능
```

②③을 거부해도 서비스가 동작해야 합니다:
- ② 거부 → 전사 완료 후 원본 즉시 삭제. 텍스트만 남김.
- ③ 거부 → 화자 자동 식별 없이 수동 매핑. **멀티트랙 모드면 애초에 불필요.**

**필요 최소 수집 원칙**을 지키는 설계이고, 발표에서 설명하기 좋습니다.

### 2.4 기본 보존 정책 (제안)

| 데이터 | 기본 보존기간 | 근거 |
|---|---|---|
| 원본 오디오 | **30일** | 전사 검증 기간 후 불필요 |
| 구간 오디오 (재생용) | 프로젝트 종료 + 30일 | 제안서 6.1 "자막 클릭 시 음성 재생" 기능 |
| 성문 임베딩 | **프로젝트 종료 시 폐기** | 프로젝트 범위 한정 |
| 전사 텍스트 | 프로젝트 종료 + 1년 | 보고서 근거 |
| 기여도 이벤트 | 프로젝트 종료 + 1년 | 분쟁 대응 |

**"자막 클릭 시 해당 음성 재생"(제안서 6.1)과 오디오 삭제가 충돌합니다.**
해결: 전체 원본은 30일 후 삭제하되, **발화 단위 짧은 구간만** 별도 보관.
용량도 줄고 프라이버시 노출도 줄어듭니다.

## 3. 윤리 요구사항

법이 요구하지 않아도 **제품이 살아남기 위해** 필요한 것들입니다.

### 3.1 제안서에서 이미 잘한 것

- 7장: `"성격·성실성을 AI가 단정하지 않음"` ✅
- 6.4: `"화남"이 아닌 "음성 변화 가능 구간"으로 표현` ✅ (표현은 신중함)
- 8장: `"LLM이 기여도나 위험도를 임의로 결정하지 않는다"` ✅
- 17장: `"기여도 오해 → 항목별 근거 공개"` ✅

### 3.2 추가 제약

| # | 제약 | 이유 |
|---|---|---|
| E1 | **무임승차자 판정 기능 금지** | 대학 팀플은 인간관계가 걸린 환경. AI 낙인은 회복 불가 |
| E2 | **팀원 간 순위·리더보드 표시 금지** | 같은 데이터라도 순위로 보이면 서비스 성격이 바뀜 |
| E3 | **갈등 책임 판정 기능 금지** | 원본 대화·제안서 모두 동의 |
| E4 | **음성 변화 분석 제외 권장** | 평가 불가 + 감정 해석 위험 → [`00`](00-제안서-TeamFlowAI-검토.md) §4 |
| E5 | 모든 점수에 **근거 이벤트 링크 필수** | 근거 없는 숫자를 띄우지 않음 |
| E6 | 본인의 기여도 데이터에 대한 **이의 제기 경로** 제공 | 분쟁 완화 |
| E7 | 교수자 화면에서도 **개별 발언 원문 열람은 제한적으로** | 감시 도구가 되면 학생이 회의에서 말을 안 함 |

**E7이 특히 중요합니다.** 이 서비스의 존재가 회의 자체를 왜곡할 수 있습니다.
"교수님이 내 발언을 다 본다"고 인식되면 학생들은 솔직하게 논의하지 않습니다.
그러면 수집되는 데이터의 질이 떨어지고, 서비스의 가치도 함께 무너집니다.

→ **교수자에게는 집계 지표와 요약만.** 개별 발화 원문은 팀 내부에만.

### 3.3 데이터 주체 권리

- 본인 데이터 열람 / 정정 요청 / 삭제 요청 경로
- 팀 탈퇴 시 데이터 처리 방침 명시
- 동의 철회 시 이후 녹음 제외 (이미 수집된 것은 보존기간까지)

## 4. 체크리스트

발표·제출 전 확인용.

**법적**
- [ ] 녹음 시작 버튼이 회의 참석자에게만 노출되는가
- [ ] 비참석자의 원격 녹음 시작 경로가 없는가
- [ ] 외부 파일 업로드 시 당사자 확인 절차가 있는가
- [ ] 참석자 전원의 녹음 동의 없이 녹음이 시작되지 않는가
- [ ] 동의가 3단계(녹음 / 원본보관 / 성문저장)로 분리되어 있는가
- [x] 원본 오디오가 별도 버킷에 저장되는가 — 볼륨 분리는 됨
- [ ] **원본 오디오가 별도 키로 암호화되는가 — 안 됨. 평문입니다** (하다 만 암호화는 안 한 것보다 나쁩니다: 없는 보호를 믿게 만듭니다)
- [ ] 보존기간 만료 자동 삭제 잡이 동작하는가
- [ ] 개인 삭제 요청 기능이 있는가
- [ ] 접근 제어가 프로젝트 구성원으로 한정되는가

**윤리**
- [ ] 무임승차 판정 문구가 UI 어디에도 없는가
- [ ] 팀원 간 순위 표시가 없는가
- [ ] 모든 점수에 근거 링크가 붙는가
- [ ] 시스템 값과 최종 확정값이 분리되어 있는가
- [ ] 교수자 화면에서 개별 발언 원문 노출이 제한되는가
- [ ] 이의 제기 경로가 있는가

**라이선스 고지**
- [ ] pyannote (CC-BY-4.0) **귀속 표시** — 필수
- [ ] 사용 LLM 라이선스 명시 (EXAONE=NC / Qwen3=Apache 2.0)
- [ ] Qwen3-ASR (Apache 2.0) 고지
- [ ] 상업화 계획이 있다면 NC 모델을 쓰지 않았는지 확인
