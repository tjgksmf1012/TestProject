대상 문서: `AI 기반 팀 프로젝트 협업 및 회의 리뷰 통합 플랫폼` 제안서 (19장 구성, 다른 팀원 작성)
검토 기준: [`01-사실검증-2026-08.md`](01-사실검증-2026-08.md) 의 2026년 8월 기준 검증 결과

## 총평

**완성도가 높습니다.** 학부 졸업작품 제안서로서 상위권입니다. 특히 세 가지가 좋습니다.

1. **문제 정의가 ChatGPT 대화보다 낫습니다.**
   원본 대화의 목표는 "기여도 측정"이었습니다. 제안서는 이걸
   **"회의 결정 → 칸반 업무 → GitHub 활동"의 연결**로 재정의했습니다.
   이게 훨씬 강한 포지셔닝입니다. 기여도는 그 연결의 **부산물**이 되고,
   "AI가 사람을 평가한다"는 정치적 부담이 자동으로 줄어듭니다.
   → 5장의 6개 매핑 표(`"로그인 API는 민수가 금요일까지"` → 업무 후보 생성)가 이 제안서의 핵심입니다.

2. **8장의 설계 원칙이 정확합니다.**
   > "LLM이 기여도나 위험도를 임의로 결정하지 않는다. DB에서 조회한 지표를 일반 알고리즘과
   > 예측 모델이 계산하고, LLM은 그 결과를 요약하고 개선 방안을 설명한다."

   ChatGPT 대화의 "정량 계산=프로그램 / 의미 분석=AI / 최종 확정=사람" 3분할과 일치하며,
   표현은 제안서 쪽이 더 명확합니다. **이 문장을 프로젝트 헌법으로 삼으세요.**

3. **13장 성능 평가 계획이 진짜입니다.**
   CER/WER, DER, Macro F1 + Confusion Matrix, **IoU**, Entity F1 / Relation F1, ROC-AUC.
   학부 프로젝트에서 IoU와 Relation F1까지 잡는 경우는 드뭅니다. 그대로 유지하세요.

4. **18장 시연 시나리오의 "의도적으로 포함할 장면"** — 매우 영리합니다.
   같은 안건 두 번 논의 / 미응답 질문 / 담당자 없는 업무 / 결정 번복을 **미리 심어둔 회의**로
   시연하면 기능이 확실히 보입니다. 그리고 이건 12장의 "합성 시나리오 회의"와 연결되어
   **평가용 정답 데이터를 만드는 방법**이기도 합니다. 이 두 장을 연결해서 생각하세요.

## 반드시 고쳐야 할 것

### ❌ 1. 범위 과다 — 이 제안서의 최대 위험

12장은 이렇게 씁니다:
> "졸업작품의 직접 연구 범위는 발언 유형 분류, 비효율 구간 탐지, 코드 활동 분류 중 **1~2개에 집중**한다."

**옳은 판단입니다. 그런데 나머지 장이 이 판단을 지키지 않습니다.**

- 12장 실험 표: **5개** 실험 (발언 유형 / 반복 논의 / 코드 작업 유형 / 프로젝트 지연 / 업무 추출)
- 13장 평가 표: **8개** 평가 대상
- 14장 MVP "반드시 구현": `STT · 화자 · 발언 유형 · 반복 · 미결정 · 업무 추출` = **AI 기능 6개**
- 15장 일정: 이 6개를 **7~10주 (4주)** 안에

4주에 AI 기능 6개는 불가능합니다. 게다가 15장 일정에는 **환경 구축 기간이 0주**입니다.
RTX 5080은 Blackwell(sm_120)이라 PyTorch 2.7+ cu128 전용 셋업이 필요하고,
여기서 며칠~일주일 날리는 게 흔합니다. ([`02-모델-선정과-VRAM-예산.md`](02-모델-선정과-VRAM-예산.md) §1)

**권고**: 12장의 자기 규칙을 나머지 장에 강제 적용하세요.
직접 학습은 **발언 유형 분류 1개**로 줄이고, 나머지는 사전학습 모델 + 규칙으로 처리합니다.
조정안: [`08-MVP-로드맵.md`](08-MVP-로드맵.md)

→ **직접 학습 1개를 고른다면 이것입니다.**

### ❌ 3. LLM 라이선스가 프로젝트 성격을 결정합니다 (제안서에 없음)

8장은 LLM을 "구조화 JSON 출력, RAG 또는 조회 기반 프롬프트"라고만 하고
**어떤 모델인지 명시하지 않습니다.** 여기에 함정이 있습니다.

```
EXAONE 4.0 / 4.5  →  EXAONE AI Model License 1.2 - NC (비상업)
                     연구·교육 목적 명시 허용 / 상업 이용은 별도 계약
Qwen3             →  Apache 2.0 (제한 없음)
K-EXAONE 2.0      →  Apache 2.0 이지만 750B MoE — 로컬 실행 불가
```

| 이 프로젝트의 목적 | 권장 |
|---|---|
| 졸업작품으로 끝 | EXAONE 사용 가능 (교육 목적 허용) |
| 공모전 출품 → 수상 후 사업화 가능성 | **Qwen3 (Apache 2.0)** |
| 창업·유료화 | **Qwen3 필수** |

19장 "최종 제안 제목"과 전반적 톤을 보면 **실제 서비스를 지향**하는 것으로 읽힙니다.
그렇다면 **Qwen3를 기본으로, EXAONE은 한국어 성능 비교군으로만** 쓰세요.
어차피 두 모델 비교는 13장 평가 계획에 넣을 좋은 실험입니다.

### ❌ 4. 6.4 「음성 변화 분석」은 MVP는 물론 최종본에서도 빼는 걸 권합니다

제안서는 매우 신중하게 처리했습니다 — `"화남"이 아닌 "음성 변화 가능 구간"`,
`개인 기준 대비 변화만 표시`, `감정 단정 없음`. 표현은 나무랄 데 없습니다.

그런데 두 가지 문제가 남습니다.

1. **평가 불가능합니다.** 13장 평가 표에 이 기능이 **없습니다.** 정답 라벨을 만들 수 없기 때문입니다.
   "이 구간은 진짜로 음성이 유의미하게 변한 구간이다"를 누가 판정합니까?
   평가할 수 없는 기능은 졸업작품에서 **점수를 못 받습니다.**
2. **사회적 위험이 남습니다.** 아무리 "감정 단정 없음"이라 써놔도, 화면에 팀원 이름 옆에
   "음성 변화 구간 3회"가 뜨면 학생들은 그걸 감정으로 읽습니다.
   대학 팀플은 **인간관계가 걸린 환경**입니다.

14장이 이미 후순위로 뒀습니다. 한 발 더 나가서 **범위에서 제거**하고,
확보한 시간을 6.5(비효율 구간 탐지)에 투자하세요. 6.5는 평가 가능하고 독창적입니다.

### ⚠️ 5. 화자 식별 방법이 명시되지 않았습니다 — 그리고 생각보다 어렵습니다

6.2는 `SPEAKER_00을 등록된 팀원 이름과 연결`이라고만 씁니다. **어떻게** 연결하는지가 없습니다.

### ⚠️ 7. 법적 요구사항이 한 줄뿐입니다

17장: `개인정보·녹음 동의 → 사전 동의, 접근 제어, 보존 기간과 삭제 기능`

방향은 맞지만 **너무 얕습니다.** 실제 요구사항은 두 개의 다른 법에서 나옵니다.

- **통신비밀보호법**: 대화 **당사자**의 녹음은 합법. **제3자 녹음은 형사처벌.**
  → 회의에 참석하지 않은 팀장이 원격으로 녹음 시작하는 기능은 **만들면 안 됩니다.**
- **개인정보보호법**: 개인정보보호위원회는 **회의 녹음된 목소리도 개인정보**로 판단.
  **생체인식정보**로 간주될 수 있어, **원본 보관 시 별도 동의 + 다른 개인정보와 분리 보관** 필요.
  → 10장 DB 설계에 반영이 필요합니다. 지금 스키마에는 동의 테이블도, 오디오 분리 보관도 없습니다.

이건 나중에 붙이는 기능이 아니라 **스키마 설계 사항**입니다.
자세한 내용: [`07-법적-윤리-요구사항.md`](07-법적-윤리-요구사항.md)

## 추가 제안 — 제안서에 없는 아이디어

### 💡 A. 멀티트랙 녹음: 가장 어려운 AI 문제를 엔지니어링으로 치환

제안서 6.2와 17장은 화자 오류를 "사용자 화자 수정 UI"로 대응합니다. 타당한 완화책입니다.
하지만 **애초에 오류가 안 생기게 할 수 있습니다.**

```
[기존 설계]  하나의 마이크 → 혼합 오디오 → 화자 분리 AI → SPEAKER_00 → 사람이 이름 매핑
             DER 17~20%, 동시 발언 구간에서 급격히 악화

[제안]       팀원 각자 자기 휴대폰으로 회의방 접속 → 각자 트랙 개별 녹음
             → 트랙 = 사람. 화자 라벨 정확도 100%.
```

- 오프라인 회의에서도 됩니다. 각자 폰을 테이블에 놓고 브라우저에서 참여하면 됩니다.
- 화자 분리 AI가 **불필요해지는 게 아니라**, 역할이 바뀝니다:
  각 트랙에서 **본인 발화 구간만 남기고 옆사람 목소리 누출을 제거**하는 용도로 씁니다.
  (에너지 기반 + 트랙 간 상호상관으로 처리 가능. AI 없이도 상당 부분 됩니다.)
- **동시 발언 문제가 자동으로 해결됩니다.** 트랙이 분리돼 있으니 겹쳐 말해도 각자 잡힙니다.
  6.5의 "동시 발언·겹침 구간" 분석이 **오히려 더 정확해집니다.**

**제안서 관점에서의 이득**:
- 17장 위험 "소음·동시 발언 → STT·화자 오류"가 상당 부분 소거됩니다.
- 6.2의 "팀원별 발언 시간·횟수·평균 길이"가 **정확한 수치**가 됩니다.
  지금 설계로는 DER 20%가 그대로 기여도 지표 오차로 들어갑니다.
- 시연에서 실패할 확률이 크게 낮아집니다. (18장 시연 시나리오는 **실패하면 안 되는 자리**입니다)

**비용**: 프런트엔드에 다중 클라이언트 녹음 + 시간 동기화 구현이 필요합니다.
동기화는 서버 타임스탬프 + 시작 시 동기화 신호(비프음)로 처리합니다.

**권고**: 멀티트랙을 **1순위 경로**로, 단일 마이크 + 화자분리를 **폴백**으로 두세요.
둘 다 지원하면 "우리는 두 모드를 비교 평가했다"는 실험이 하나 더 나옵니다. (DER 비교)

### 💡 B. 기여도 점수는 저장하지 말고 **재계산**하세요

10장 스키마의 `analytics(scope, metric, value, period)`는 **계산 결과만** 저장합니다.
문제: 나중에 "왜 이 점수인가"를 물었을 때 **재현할 수 없습니다.**
가중치가 바뀌면 과거 점수와 현재 점수가 뒤섞이고, 7장의 "산출 근거 공개" 약속을 지킬 수 없습니다.

```
점수 = f(불변 이벤트 로그, 가중치 버전, 역할)
```
로 만드세요. 이벤트는 append-only, 점수는 **순수 함수의 출력**.
그러면 가중치를 바꿔도 과거를 통째로 재계산할 수 있고, 모든 점수에 근거 이벤트 ID가 붙습니다.
자세한 스키마: [`06-데이터-모델.md`](06-데이터-모델.md)

### 💡 C. 업무 추출은 recall을 우선하세요

13장은 업무 추출을 `Entity F1, Relation F1`로 평가합니다. 맞습니다.
다만 **F1이 아니라 recall에 가중치를 두세요.**

이유: 업무 하나를 놓치면 그 담당자의 기여도가 통째로 누락됩니다.
반대로 잘못 뽑힌 업무는 승인 화면에서 사람이 지우면 끝입니다.
**과다 추출 후 사람이 지우는 게, 과소 추출 후 사람이 찾아 넣는 것보다 낫습니다.**

2026년 기준 회의록 요약 평가에서도 "action item **completeness**가 결정적 차원"으로 봅니다.
제안서 5장의 승인 워크플로("팀장이 검토 → 승인된 업무가 칸반에 생성")가
이미 이 전략과 맞물려 있습니다. 평가 지표만 정렬시키면 됩니다.

### 💡 D. JSON 출력은 프롬프트가 아니라 **디코딩으로 강제**

8장 `구조화 JSON 출력`을 실제로 안전하게 만드는 방법:
**vLLM + xgrammar guided decoding.** JSON Schema에서 문법을 만들어 매 토큰마다 마스크를 씌우므로
스키마를 벗어나는 출력이 **원리적으로 불가능**합니다. 파싱 실패율 0%.

2026년 권장 백엔드는 xgrammar이고, **같은 스키마를 반복 사용할 때 캐싱 이득이 큽니다.**
이 프로젝트는 항상 같은 스키마를 씁니다 — 최적 조건입니다.

이 결정 하나로 "소형 LLM을 써도 되는가?"의 답이 바뀝니다.
형식 붕괴가 사라지면 소형 모델의 남은 약점은 **내용 정확도뿐**입니다.

### 💡 E. 동료평가는 CATME 구조를 차용하세요

제안서 7장 기여도 요소에 **동료평가가 없습니다.** (ChatGPT 대화에는 15% 비중으로 있었습니다)

의도적 배제라면 합리적입니다 — 동료평가는 감정적으로 작성되기 쉽고, 갈등 유발 요소입니다.
하지만 넣는다면 **아무 근거 없이 자체 설계하지 말고 CATME의 5개 카테고리를 참조하세요.**

> 💰 단, **CATME 서비스 자체는 고등교육 기관에 유료**입니다. 가입하지 말고
> 논문에 공개된 프레임워크만 참조하세요. → [`11-비용-제로-구성.md`](11-비용-제로-구성.md) §1

**CATME**(Comprehensive Assessment of Team Member Effectiveness)는 공학교육에서 가장 널리 쓰이는
팀 동료평가 도구로, 29개 유형의 기여 행동에 대한 87개 항목 루브릭으로 5개 카테고리를 산출합니다:
팀 업무 기여 / 팀원과의 상호작용 / 팀 궤도 유지 / 품질 기대 / 관련 지식·기술·역량.

구조화된 심리측정 도구를 쓰면 동료평가의 **공정성·정확도·평가자 간 신뢰도가 개선된다**는
연구 결과가 있습니다. 교수·심사자에게 "검증된 도구 기반"이라고 설명할 수 있는 것도 이점입니다.

### 💡 F. 아키텍처 결정: Spring Boot를 넣을 것인가

- **ChatGPT 대화**: Spring Boot(메인) + FastAPI(AI) + React + PostgreSQL — 사용자가 Spring 학습 중이라서
- **제안서 9장**: Next.js + **FastAPI 단일 백엔드** + Celery + PostgreSQL/pgvector + MinIO

**제 권고는 제안서 쪽(FastAPI 단일)입니다.** 근거:
- 16주에 4인(혹은 그 이하) 팀입니다. 백엔드를 2개 언어로 나누면 **경계 API·직렬화·배포·디버깅이 전부 2배**가 됩니다.
- 이 프로젝트의 무게중심은 전부 Python입니다 (STT, 화자, 임베딩, LLM, 예측 모델).
  Spring은 CRUD만 담당하게 되는데, 그 CRUD를 FastAPI로 못 할 이유가 없습니다.
- pgvector, Celery, PyTorch가 한 프로세스 경계 안에 있으면 개발 속도가 확연히 빠릅니다.

**단, Spring 학습 자체가 목적이라면** 이야기가 다릅니다. 그건 기술적 판단이 아니라
개인 커리어 판단이므로 팀에서 결정할 문제입니다.
→ [`10-열린-질문.md`](10-열린-질문.md) Q1
