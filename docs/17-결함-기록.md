# 17. 결함 기록 — 무엇이 조용히 틀려 있었나

PR #3 을 여는 동안 찾은 결함 여든하나의 전체 기록입니다. (번호가 붙은 항목 **82건** · 34~116번 · 54번은 비어 있습니다 — 중간에 취소한 번호입니다. 75번은 틀린 값을 낸 결함이 아니라 **가드**라서 결함 수 여든하나에는 안 넣었습니다.)

**왜 PR 본문이 아니라 여기 있는가.** 이 글은 6만 자가 넘어 GitHub 의 PR 본문
한도(65,536자)에 거의 닿았습니다. 결함이 하나 늘 때마다 본문 전체를 다시
올려야 했고, 그 비용 때문에 **본문이 코드보다 뒤처지는 일**이 실제로 생겼습니다.
기록은 저장소 안에서 커밋과 함께 자라는 것이 맞습니다 — PR 본문에는 요약과
이 문서로 가는 링크만 둡니다.

각 결함의 **전체 근거는 커밋 메시지**에 있습니다. 이 문서는 그것을 주제별로
묶어 읽을 수 있게 한 것입니다.

**62 — 작성자를 못 붙였다고 남의 리뷰까지 버리지 않는다.** `to_pull_request` 가 작성자를 팀원에게 못 붙이면 `None` 을 돌려주는 것 자체는 맞습니다 — 아무에게나 붙이면 그게 곧 잘못된 기여도니까요. 문제는 **거기서 끝낸다**는 것이었습니다.

```
dependabot 의 PR              ← 작성자를 못 붙임
  └ 이하늘의 리뷰 "이 버전 올리면 로그인 화면이 깨집니다"  ← 같이 사라짐
```

봇 PR, 외부 기여자 PR, 그리고 **팀원이 GitHub 로그인을 아직 등록 안 한 동안** 전부 같은 일이 벌어집니다. 오류는 어디에도 안 납니다. **리뷰는 작성자가 누구든 리뷰어 자신의 기여**이므로 이유를 둘로 갈랐습니다 — 병합 안 됨은 `skipped(not_merged)`(이벤트가 없는 게 맞다), 작성자 못 붙임은 `reviews_only`(리뷰는 살린다). ⚠️ `source_id` 식(`pr_id * 100_000 + reviewer_id`)을 **두 경로에서 같게** 뒀습니다 — 나중에 그 사람이 로그인을 등록해 PR 이 다시 처리돼도 `persist_events` 가 중복을 막습니다.

⚠️ **고치려던 흔적이 있었는데 그게 안 되는 방법이었습니다.** `kanban.html` 에 `.origin .ico, .origin svg { --ico: 14px; … }` 라고 적혀 있어 챙긴 것처럼 보이지만, `--ico` 를 **읽는** 규칙은 `.ico svg` 하나뿐이고 그 선택자는 여기 안 걸립니다. **값을 정해 놓고 아무도 안 읽는** 상태 — 이 저장소의 대표 실패 방식이 CSS 변수로 나타난 것입니다.

⭐ **이 결함은 옆 문단을 거짓말로 만들었습니다.** 칸반 아래에 "**말풍선 표시가 붙은 업무는** 회의에서 나온 결정이 사람의 승인을 거쳐 여기까지 온 것입니다" 라고 적혀 있습니다. 이 제품의 대표 주장을 화면에서 가리키는 문장인데, 가리킬 말풍선이 없고 검은 덩어리만 있었습니다.

감싸는 것을 잊지 말라고 적어 두는 대신 **안 감싸도 되게** 했습니다 — `iconSvg()` 가 `width`·`height`·`fill="none"`·`stroke="currentColor"` 를 스스로 붙입니다. CSS 는 여전히 이기므로(선언 > 표현 속성) `--ico` 로 크기를 바꾸는 길은 그대로입니다.

### 확정 화면에 &#34;김민수 은(는)&#34; 이라고 적혀 있었다 (결함 76)

감사 #13 검증 스크립트를 다시 돌려 보다가 나왔습니다.

> 2026. 8. 8. 오후 1:03:30 **에** 확정했습니다 — 김민수 **은(는)** 시스템 값과 다르게 정했습니다.

**`은(는)` 은 사람이 읽는 글자가 아닙니다.** 미완성 소프트웨어로 읽히고, 이 화면은 **성적에 쓰일 수 있는 숫자**를 보여주는 곳이라 그 인상이 숫자에까지 옮겨 갑니다. 이 저장소가 초대 코드에서 `0/O`·`1/I/L` 을 뺀 것도, 별표째 나온 마크다운(결함 44)을 고친 것도 같은 이유였습니다. 같은 줄에 문제가 하나 더 있습니다 — **조사는 앞말에 붙여 씁니다.** 띄우면 조사가 다음 낱말처럼 보입니다.

**눈으로 고르지 않고 계산합니다.** `lib/text/josa.ts` 를 뒀습니다.

```
한글   (코드 − 0xAC00) % 28 ≠ 0 이면 받침이 있다      ← 정확한 규칙
숫자   읽는 소리로 (3=삼 받침 있음, 4=사 없음)        ← 정확한 규칙
기호   판단 못 함 → null                             ← 모르면 모른다고
```

⚠️ **로마자로 끝나는 값은 관례입니다.** `PR` 은 &#34;피알&#34;(ㄹ), `API` 는 &#34;에이피아이&#34;(없음)처럼 **읽는 소리**를 따라야 하는데 글자만 봐서는 정해지지 않습니다. 흔한 읽기표를 쓰되 그게 관례라고 파일에 적어 뒀고, 화면 문구는 되도록 로마자 뒤에 조사를 두지 않는 쪽으로 씁니다.

⚠️ **짝 표기를 절대 돌려주지 않습니다.** 판단 못 하면 받침 없는 쪽을 씁니다 — `은(는)` 이 화면에 나오는 것이 이 함수를 만든 이유입니다.

고친 자리는 여섯(변수+조사)과 여덟(글자 그대로 띄어 쓴 것)입니다. 뒤의 여덟은 조사 선택은 원래 맞았고 **띄어쓰기만** 틀렸습니다.

⚠️ **개발자용 오류 메시지는 그대로 뒀습니다** — `timesliceMs 는 양수여야 합니다` 처럼 **코드 이름 뒤**에 오는 것은 띄우는 것이 이 저장소의 문서 관례이고 화면에 안 나옵니다. 그래서 가드도 `${…}` **보간만** 봅니다. 글자 그대로 적힌 것까지 잡으면 그 메시지들을 **틀린 신고**로 올립니다 — 눈으로 보고 고쳤고, 안 고친 이유를 여기 적어 둡니다.

### 폰에서 라벨이 **겹쳤습니다** — 그리고 도구는 0px 이라고 답했습니다 (결함 77)

승인 화면(`review.html`)을 360px 로 다시 찍어 보다가 나왔습니다. &#34;마감일&#34; 칸이 옆의 &#34;담당자&#34; 글자 **위로 올라타** 있었습니다.

```
담당자 [ 김민수  ▾ ]마감일[ 2026-08-15 ]      ← 360px. 글자가 겹친다
```

원인은 두 규칙이 **서로 반대 방향으로** 잡아당긴 것입니다.

```
app.css      .row > *  { min-width: 0 }        ← 결함 53 때 넣음. 0 까지 줄어들어라
review.html  select    { min-width: 8rem }     ← iOS 확대 방지. 8rem 밑으로는 못 줄어든다
```

라벨 상자는 0 까지 줄어들 수 있다고 선언됐지만 그 **안**의 `select` 는 못 줄어듭니다. 그래서 내용이 상자 밖으로 넘치고, flex 는 넘친 부분을 옆 항목 자리에 그대로 그립니다.

⚠️ **`audit360.mjs` 는 이걸 못 잡습니다.** 그 도구는 `scrollWidth − clientWidth` 로 가로 넘침을 재는데, `body { overflow-x: hidden }` 이라 넘친 부분이 **잘려서** 0px 로 나옵니다. 잘린 것은 가로 스크롤보다 나쁩니다 — 밀어서 볼 수조차 없습니다. 이 세션에서 측정 방법이 틀려 결함이 안 보이거나 없는 결함이 보인 것이 **열 번째**입니다(아래 §C 에 열둘을 모아 뒀습니다).

고침은 `.row { flex-wrap: wrap }` + `.row > label { min-width: max-content }` 입니다. 숫자를 손으로 고르지 않은 이유: 라벨 글자 폭은 글꼴·번역·글자 크기 설정에 따라 달라지는데 `max-content` 는 그때그때 실제 폭을 씁니다.

가드(`guards.test.ts`)는 **관계**를 봅니다 — `.row` 안에 하드 `min-width` 를 가진 컨트롤이 있으면 그 화면의 `.row` 에 `flex-wrap: wrap` 과 `min-width: max-content` 가 함께 있어야 합니다. ⚠️ **너무 넓지 않은지 확인했습니다**: `.row` 를 쓰지만 안에 바닥 없는 화면 넷은 그대로 통과합니다. 되돌려 보니 두 규칙 각각에서 깨졌습니다.

### 오류 문구가 **내부 상태 이름**을 흘렸습니다 (결함 78)

이미 끝난 회의에 다시 들어가 보다가 나왔습니다.

> 트랙에 참가하지 못했습니다: 트랙 상태가 `completed` 여서 녹음을 받을 수 없습니다

`completed` 는 DB 컬럼 값입니다. 이 화면을 보는 사람은 학생이고, 알아야 할 것은 **&#34;내가 지금 무엇을 하면 되는가&#34;** 인데 저 문구는 그걸 안 알려 줍니다. 게다가 `completed` 는 &#34;완료&#34; 로 읽혀 **좋은 소식처럼** 보입니다 — 실제로는 &#34;더 이상 녹음할 수 없다&#34; 는 뜻입니다.

`describe_track_state()` 를 두고 상태마다 사람 문장을 붙였습니다.

```
completed  이 회의의 녹음은 이미 끝났습니다
unusable   이 트랙은 녹음이 너무 많이 끊겨 쓸 수 없습니다
aborted    이 트랙은 강제 종료됐습니다
```

⚠️ **모르는 상태가 오면 감추지 않고 그대로 붙입니다** — `이 트랙은 지금 녹음을 받을 수 없습니다 (상태: xyz)`. 상태가 새로 생겼는데 문구를 안 붙였을 때 &#34;알 수 없는 오류&#34; 로 뭉개면 고칠 실마리가 사라집니다. 사람에게는 할 일을 주고, 개발자에게는 괄호 안에 값을 남깁니다.

부르는 자리마다 **다음 행동**을 덧붙였습니다 — 참가 실패는 `— 로비에서 회의 상태를 확인하세요`, 조각 업로드 실패는 `— 더 이상 녹음을 보낼 수 없습니다`.

가드(`test_repo_integrity.py`)는 `raise ConsentError/TrackError/ValueError` 안에 `status={…}`·`state={…}` 같은 보간이 들어가는 것을 막습니다. ⚠️ **로그는 일부러 통과시킵니다** — `logger.warning("... status=%s", ...)` 는 개발자가 읽는 곳이고 거기서는 상태 이름이 **있어야** 합니다. 되돌려 보니 잡혔고, 로그 줄은 그대로 통과했습니다.

이 고침 때문에 기존 테스트 하나(`test_chunks_are_refused_after_completion`)가 옛 문구 &#34;녹음이 끝난&#34; 을 고정하고 있어 깨졌습니다. 새 문구로 갱신하면서 **`status=` 와 `completed` 가 응답에 없다는 것까지** 단언하게 했습니다 — 문구가 바뀌어도 &#34;내부 이름이 새 나가지 않는다&#34; 는 조건은 남습니다.

### 칸반 카드가 &#34;PR 에 TASK 번호가&#34; 라고 말했습니다 (결함 79)

결함 76 절 마지막에 &#34;백엔드 가드는 `${…}` **보간만** 본다&#34; 고 적었습니다. 그 범위가 **좁았습니다.**

```
"PR 에 TASK 번호를 적어야 연결됩니다"        ← 보간이 없다. 글자 그대로 틀렸다
"GitHub 이 401 로 응답했습니다"              ← 〃
```

보간만 보는 검사는 이런 리터럴을 통과시킵니다. `github/connection.py`·`linking.py`·`api/main.py` 에서 **화면에 나가는 문구 열넷**이 조사를 띄어 쓰고 있었습니다(`PR 은`·`401 로`·`GitHub 이`·`App 이`·`GitHub Apps 에서`·`API 를`·`PR 의`·`PR 에`).

⚠️ **grep 한 번으로 &#34;없다&#34; 고 단정한 것이 이 세션 네 번째입니다.** 결함 76 을 고칠 때 저는 보간 패턴만 훑고 &#34;백엔드는 깨끗하다&#34; 고 적었습니다. 커밋 메시지에도 그렇게 남겨 뒀습니다 — 다음에 같은 실수를 하면 이 줄이 먼저 보이도록.

가드는 `connection.py`·`linking.py` **두 파일만** 대상으로 하고 docstring·`logger.*`·주석은 제외합니다. ⚠️ **너무 넓지 않은지 확인했습니다**: `PR 이 3 개` 같은 **수 세는 말**(`3 개`·`3 중`)과 로그·주석의 `PR 이` 는 그대로 통과합니다. 조사와 의존명사는 띄어쓰기 규칙이 정반대라 한 패턴으로 묶으면 맞는 글을 틀렸다고 신고합니다.

### 화면 HTML 에 박힌 글자에 조사가 띄어져 있었다 (결함 80)

기여도 화면에 이렇게 적혀 있었습니다.

> 측정하지 못한 영역은 **0 이** 아닙니다

이 프로젝트의 **핵심 불변식**(측정 불가 ≠ 0점, `docs/05` §5)을 사람에게 말하는 문장입니다. 그 문장의 조사가 떨어져 나가 &#34;0&#34; 과 &#34;이&#34; 가 다른 낱말처럼 보였습니다.

**같은 부류를 세 번째 잡습니다 — 층이 하나씩 더 있었습니다.**

```
결함 76   `.ts` 의 `${값} 조사`         → 고침 + 가드
결함 79   백엔드의 글자 그대로          → 고침 + 가드
결함 80   **화면 HTML 에 박힌 글자**    ← 어느 가드도 안 보던 곳
```

고친 자리는 열넷입니다 — `Wake Lock 을`·`iOS 는`·`설치형 PWA 는`·`모드 A 를`·`30% 를`(녹음 화면), `scrypt 로`(로그인), `?meeting=1 만`·`?me=1 로`(로비), `repository.full_name 으로`(프로젝트), `0·O·1·I·L 은`(초대 코드 오류), `&#34;홈 화면에 추가&#34; 를`(iOS 설치 안내), `0 이`·`&#34;…있는가&#34; 를`(기여도). `18.4+ 부터` 는 붙이는 대신 `18.4 이상에서` 로 고쳐 썼습니다 — 기호 뒤에 조사를 붙이면 읽기 어렵고, 애초에 그 자리에 안 두는 것이 낫습니다.

⚠️ **기존 백엔드 가드가 자기 파일 안에서 놓치고 있었습니다.** 앞말을 `[A-Za-z0-9)]` 로만 봐서 **닫는 따옴표 뒤**를 못 잡았고, 그래서 `connection.py` 안의 `‘지난 활동 가져오기’ 를` 가 **가드가 걸린 파일에서** 통과했습니다. 앞말 문자 집합을 넓히고, 대상에 `api/main.py`(`HTTPException` 의 `detail` 은 그대로 화면에 뜹니다)와 `recording_service.py` 를 더했습니다.

**브라우저가 보는 대로 재야 합니다.** ⚠️ 처음 쓴 검사가 **멀쩡한 네 자리를 결함으로 신고**했습니다 — `<strong>이유</strong>를` 는 붙어 있는데, 태그를 공백으로 바꿔 읽으면 `이유 를` 로 보입니다. 그래서 인라인 태그는 **폭 0** 으로 지우고 줄바꿈을 만드는 태그만 줄바꿈으로 바꿉니다. ⚠️ 그리고 **소스의 줄바꿈은 브라우저가 공백으로 만듭니다** — 처음에는 줄바꿈으로 남겨 둬서 줄 끝에 걸린 `0 이⏎아닙니다` 를 놓쳤습니다. 되돌림 검사에서 이것만 안 깨져서 알았습니다.

⚠️ **줄 단위로 보면 안 됩니다.** 백엔드 가드는 `"logger." in line` 으로 로그를 걸렀는데, **인자가 다음 줄에 있는** 로그 호출이 그물을 빠져나가 멀쩡한 로그 두 줄을 결함으로 신고했습니다. 파이썬 코드는 파이썬에게 물어봅니다 — `ast` 로 문자열이 **어디에 쓰이는지**(로그 인자인가 · docstring 인가)를 봅니다.

면제한 것 넷(`seq 는`·`timesliceMs 는`·`BrowserMediaAdapter 는`·`toServerTime 을`)에는 **근거를 적게** 했고, 목록이 낡으면(파일이 없거나 근거가 비면) 따로 실패합니다.

### 복사가 안 돼도 화면이 아무 말도 안 했다 (결함 81)

초대 코드 복사 버튼은 팀원을 프로젝트에 들이는 **유일한 통로**입니다. 두 화면 모두 이렇게 쓰고 있었습니다.

```js
void navigator.clipboard.writeText(text).then(() => {
  $('copy').textContent = '복사됨';
});
```

`navigator.clipboard` 는 **보안 컨텍스트에서만 있습니다.** 폰에서 `http://192.168.0.5:8000` 으로 열면 `undefined` 이고, 위 줄은 클릭 핸들러 안에서 `TypeError` 로 죽습니다. `.catch` 도 없어서 권한 거절·포커스 없음도 같은 결과입니다 — **화면은 아무 말도 안 합니다.**

```
버튼을 누른다 → 아무 변화가 없다 → 한 번 더 누른다 → 그래도 없다
→ 카톡에 붙여 넣는다 → 아까 복사해 둔 **다른 글**이 나간다
```

결함 71 이 &#34;성공했다고 말하면서 틀린 것을 준다&#34; 였다면 이건 **아무 말도 안 하면서 틀린 것을 남겨 두는** 쪽입니다. 팀원이 받는 결과는 같습니다.

⚠️ **이 저장소는 이미 보안 컨텍스트를 압니다** — 녹음 클라이언트는 `isSecureContext()` 를 보고 왜 녹음을 못 하는지 화면에 말합니다. 복사 쪽만 그 판단이 없었습니다.

`lib/ui/copy.ts` 의 `copyText()` 는 **절대 던지지 않고** 무슨 일이 있었는지(`copied`·`unavailable`·`refused`) 돌려줍니다 — 던지면 부르는 쪽이 `try` 를 잊는 순간 다시 조용해집니다. 실패하면 **왜 안 됐는지와 대신 할 일**을 말합니다.

> 이 주소에서는 브라우저가 복사를 막습니다 — 코드를 길게 눌러 직접 복사하세요

⚠️ 안내는 **버튼 글자가 아니라 아래 줄**에 적습니다. 버튼에 넣으면 360px 에서 옆의 &#34;코드 새로 만들기&#34; 와 겹칩니다(결함 77 과 같은 자리). ⚠️ 조사는 `withJosa` 가 고릅니다 — `코드` 는 `를`, `한 줄` 은 `을` 입니다.

**녹음 화면은 화면 글자를 복사하고 있었습니다.** `main.ts` 가 `$('row').textContent` 를 읽어 클립보드에 넣었습니다 — 결함 71 을 고칠 때 `setup.ts` 만 보고 이 자리를 놓쳤습니다. 결함 73 과 같은 &#34;한 곳만 고쳤다&#34; 입니다.

⚠️ **PR 본문의 주장 하나를 정정합니다.** C 절에 &#34;겹치는 지역 선택자 열둘이 **전부** 뜻이 다르다&#34; 고 적었는데 틀렸습니다. 세어 보니 열하나가 다르고 `.status` 하나는 **글자까지 같았습니다.** 그 하나만 `app.css` 로 올리고 지역 규칙 둘을 지웠습니다. 나머지 열하나는 그대로 둡니다 — `#result` 는 칸반에서 목록이고 승인 화면에서 제출 결과입니다.

⚠️ 그리고 그 주석을 쓰면서 **또 단정했습니다.** &#34;홈은 `.status` 규칙이 없다&#34; 고 적었는데 홈에는 `.meeting .status` 라는 후손 선택자가 있습니다. `class="status"` 를 쓰는 자리만 찾고 후손 선택자를 안 봤습니다 — grep 한 번으로 &#34;없다&#34; 를 단정한 것이 이 세션 **다섯 번째**입니다. 브라우저로 재서 잡았습니다.

### 로그아웃이 실패해도 로그아웃한 것처럼 굴었다 (결함 82)

서버의 `logout` 은 자기 docstring 에 이렇게 적어 두고 있습니다.

> 쿠키만 지우면 토큰은 살아 있습니다. 그 토큰이 어딘가에 복사돼 있으면 **로그아웃한 줄 알고 있는 동안 남이 그 계정으로 들어옵니다.**

서버는 그래서 `revoke()` 로 제대로 끊습니다. 그런데 **화면이 그게 성공했는지를 안 봤습니다.** `fetch` 는 500 이든 502 든 정상적으로 resolve 하고, `.catch` 도 없었습니다. 홈과 로비가 이 코드를 **글자까지 똑같이** 한 벌씩 가지고 있었습니다.

**옛 코드로 되돌려 실제로 무슨 일이 벌어지는지 재현했습니다.**

```
이동 경로     : /home.html → /login.html → /home.html
/api/auth/me : 200   ← 세션이 살아 있다
화면의 설명   : (없음)
```

⚠️ **제 예상이 틀렸습니다.** 저는 &#34;로그인 화면에 남는다&#34; 고 봤는데, `login.html` 이 살아 있는 세션을 보고 홈으로 되돌려 보냅니다. 실제 증상은 **화면이 한 번 깜빡이고 제자리로 돌아오는 것**입니다 — 폰에서는 그 깜빡임을 놓치기 쉽고, 봤다면 오히려 &#34;로그아웃됐구나&#34; 로 읽습니다. 예상보다 **더 조용한** 결함이었습니다.

이제 상태를 보고 나서 옮깁니다. ⭐ **401 은 성공으로 봅니다** — 서버가 이 세션을 모른다는 뜻이라 그 토큰으로는 아무도 못 들어옵니다. 실패로 처리하면 이미 만료된 사람이 로그아웃 버튼에 갇힙니다. 못 끊었으면 **옮기지 않고** 지금 상태와 할 일을 말합니다.

> 로그아웃하지 못했습니다 — 서버가 처리하지 못했습니다 (HTTP 500). 이 기기에 로그인 상태가 그대로 남아 있으니 다시 눌러 주세요.

`demo/logout.ts` 하나를 두 화면이 같이 씁니다. **두 벌이 있으면 한쪽만 고쳐집니다** — 결함 73·81 이 그랬습니다.

### 로비가 회의 중에 죽은 폰을 &#34;녹음 중&#34; 이라고 불렀다 (결함 83)

로비의 존재 이유는 **회의 도중에** 누구 폰이 망가지고 있는지 알려 주는 것입니다. 그걸 못 하고 있었습니다.

```ts
if (track.status === 'recording') {
  if (coverage !== null && coverage < MIN_USABLE_COVERAGE) return 'broken';
  if ((track.total_gap_ms ?? 0) >= WARN_GAP_MS) return 'at_risk';
  return 'healthy';
}
```

`coverage` 와 `total_gap_ms` 는 **`complete_track` 에서만** 채워집니다. 녹음 중에는 둘 다 NULL 입니다. 그래서 위 두 가지는 **회의가 끝나기 전에는 한 번도 못 탑니다.** 모든 녹음 트랙이 언제나 `healthy` — &#34;녹음 중&#34; 입니다.

결함 63(`DEADLINE_CHANGED` 를 세는 코드는 있는데 만드는 곳이 0곳)과 같은 모양인데, 여기서는 **소비자는 있고 생산자가 그 시점에 안 도는** 쪽입니다.

**브라우저로 재현했습니다.** 박지원의 트랙을 진짜 녹음 중인 모습으로 두고 로비를 열었습니다.

```
김민수   녹음 종료 (커버리지 100%)
이하늘   녹음 종료 (커버리지 98%)
박지원   녹음 중            ← 조각이 **한 개도** 안 왔는데
```

회의가 끝나고 나서야 &#34;커버리지 42% — 이 사람의 발언량은 측정할 수 없습니다&#34; 가 뜹니다. 그때는 그 회의를 못 살립니다.

**이미 저장돼 있는 것으로 지금 판단합니다.** `track_chunks` 는 조각마다 `received_at` 을 남기고 있었습니다. `track_health()` 에 읽기 전용 값 둘(`chunk_count`·`silent_ms`)을 더했습니다 — 새 스키마도 새 저장도 없습니다.

⚠️ **시간은 서버가 잽니다.** 조각의 시각은 녹음하는 폰의 동기화된 시계 기준이라, 로비를 보는 사람의 브라우저에서 빼면 시계가 어긋난 만큼 전부 죽은 것으로 보이거나 전부 멀쩡한 것으로 보입니다 — 운행도표의 축 문제와 같습니다. ⚠️ **문턱은 새로 만들지 않았습니다** — `WARN_GAP_MS`(30초)를 그대로 씁니다. ⚠️ **끝난 트랙에는 안 줍니다** — 뜻이 없는 값은 언젠가 누가 씁니다. ⚠️ **모르면 경고하지 않습니다** — 없는 근거로 &#34;폰을 확인하세요&#34; 를 띄우면 다음부터 아무도 안 믿습니다.

**할 일이 다르면 다르게 말합니다.**

```
조각이 하나도 안 옴  →  "6분째 녹음이 한 조각도 안 왔습니다 —
                         그 폰에서 녹음을 시작했는지 확인해 주세요"
오다가 끊김          →  "4분째 녹음이 안 올라옵니다 — 폰 화면을 켜 주세요"
```

앞은 녹음을 아예 시작 안 했을 수 있고, 뒤는 화면이 꺼졌을 가능성이 큽니다.

⚠️ 시드의 회의 날짜(2026-09-01)가 **오늘보다 미래**라 처음에는 재현이 안 됐습니다. `max(0, …)` 이 음수를 0 으로 잘라 &#34;방금 소식이 왔다&#34; 가 된 것입니다. 그 자체는 맞는 처리입니다 — 시계가 이상할 때 조용한 쪽으로 가는 것이 안전합니다.

### 후보를 다 검토해도 &#34;회의에서 업무가 나오지 않았습니다&#34; (결함 84·85)

홈 화면이 회의를 이렇게 설명하고 있었습니다.

> 1주차 정기회의 — **검토 필요**
> 검토할 업무 후보가 없습니다 — **회의에서 업무가 나오지 않았습니다**

**업무는 세 건 나왔고, 사람이 방금 셋 다 검토한 참이었습니다.** 한 줄에 거짓이 둘입니다.

**아무도 `confirmed` 를 넣지 않았습니다.** 화면에는 세 자리에 그 상태가 준비돼 있었습니다 — `MEETING_STATUS_LABEL.confirmed`(&#34;검토 완료&#34;) · `nextStepFor` 의 `case 'confirmed'` · 승인 화면의 빈 상태 문구. 그런데 `meeting.status` 에 값을 넣는 코드는 넷뿐입니다(`queued`·`processing`·`failed`·`needs_review`). **셋 다 한 번도 못 타는 죽은 가지**였습니다 — 결함 83 과 같은 부류입니다.

그래서 &#34;남은 후보 0건&#34; 이라는 **하나의 값이 두 상황**을 떠맡았습니다: `AI 가 뽑을 게 없었다` 와 `사람이 다 검토했다`. 화면은 앞쪽 문장을 고르고 있었고, 실제로 흔한 것은 뒤쪽입니다.

⚠️ **후보가 처음부터 0건이면 안 옮깁니다** — 그 회의는 볼 것이 없었던 것이지 검토를 마친 것이 아니고, 그때는 원래 문장이 맞는 말입니다. ⚠️ **`failed` 는 안 덮습니다** — &#34;트랙을 확인하세요&#34; 안내가 사라집니다. ⚠️ **되돌아갈 수 있습니다** — 다시 처리하면 `needs_review` 로 돌아갑니다.

**덤 — 제출 결과에 빈 꼬리표 (결함 85).** 셋 다 거절하고 제출하면 `0건이 칸반에 등록됐습니다 (task )` 였습니다. 괄호만 남고 안이 빈 것은 결함 58(빈 `.note` 가 가로줄만 남김)과 같은 부류이고, &#34;0건이 등록됐습니다&#34; 는 그 사람이 한 일을 안 말합니다. 이제 `검토를 반영했습니다 — 칸반에 등록된 업무는 없습니다` 라고 합니다. ⚠️ 거절을 &#34;실패&#34; 라고 하지 않습니다.

**브라우저로 재현하고, 고친 뒤 다시 확인했습니다.**

```
고치기 전  제출: "0건이 칸반에 등록됐습니다 (task )"
           홈:   "검토 필요 — …회의에서 업무가 나오지 않았습니다"
고친 뒤    제출: "검토를 반영했습니다 — 칸반에 등록된 업무는 없습니다"
           홈:   "검토 완료 — 검토를 마쳤습니다 · 칸반 보기"
           승인: "이 회의의 후보는 모두 검토를 마쳤습니다 · 칸반 보기"
```

⚠️ **처음 쓴 테스트가 아무것도 안 보고 통과했습니다.** &#34;후보 0건인 회의는 안 옮긴다&#34; 를 `items: []` 로 확인했는데, 엔드포인트가 `min_length=1` 이라 **422 로 막혀 그 코드에 닿지도 않았습니다.** 되돌려도 안 깨져서 알았습니다 — 이 세션에서 &#34;내 검사가 다른 이유로 통과 중&#34; 을 겪은 **일곱 번째**입니다. 실제로 닿는 길(이미 사라진 후보 번호를 보내는 것)로 고치니 되돌림이 잡혔습니다.

### 두 언어에 걸친 어휘를 표 하나로 (`72232ba`)

같은 결함을 두 번 당하고 두 번 손으로 테스트를 썼습니다 — 기여 카테고리(화면에 영어 식별자가 찍힘)와 회의 상태(결함 84). **세 번째부터는 표로 둡니다.**

```
기여 카테고리  Category               ↔ CATEGORY_LABEL
회의 상태      MeetingStatus          ↔ MEETING_STATUS_LABEL
업무 상태      task_service.STATUSES  ↔ STATUS_LABEL
역할          Role                   ↔ ROLE_NAMES
공백 이유      GapReason              ↔ REASON_TEXT
승인이 막힌 이유 ApprovalError         ↔ BLOCKER_TEXT   ← 결함 86 에서 추가
```

⚠️ **뒤의 셋은 지금 맞습니다.** 확인하고 없다고 적습니다 — 문제는 맞게 유지해 주는 것이 아무것도 없었다는 것입니다. 이 저장소는 &#34;같은 것이 두 벌 있으면 한쪽만 고쳐진다&#34; 를 결함 73·81·82 에서 이미 세 번 겪었습니다.

그리고 `Gap.reason` 의 `#: recorder_stalled | chunk_lost` 라는 **주석**을 `GapReason` StrEnum 으로 바꿨습니다. 주석은 아무도 안 읽고 아무것도 못 막습니다 — 값을 적어 놓고 읽는 곳이 없는 것은 결함 74(`--ico`)·84(`confirmed`)와 같은 모양입니다.

### 승인 실패 화면이 내부 이름을 그대로 보여줬다 (결함 86)

목록이 서버보다 낡은 채로 승인을 누르면 화면에 이렇게 떴습니다.

> 0건 승인, 1건 실패: **#999 unknown_candidate**

한글 화면에 영어 내부 이름입니다. 결함 78 과 같은 부류인데, 이번에는 글자를 지어낸 것이 아니라 **옮길 말이 아예 없어서** 코드가 새어 나왔습니다.

서버 `ApprovalError` 는 값이 아홉인데 화면 `BLOCKER_TEXT` 에는 일곱만 있었습니다. 빠진 둘은 **화면이 스스로 만들지 않는** 것들입니다 — `unknown_candidate`(목록에 없는 후보 번호)와 `no_reviewer`(세션에 검토자가 없음). 화면은 승인 가능 여부를 서버와 같은 규칙으로 미리 계산하므로(`approvalBlockers`) &#34;화면이 만드는 코드 = 서버가 내는 코드&#34; 처럼 보였고, 일곱을 다 적고 나면 다 적은 것처럼 보였습니다. **`tsc` 도 못 잡습니다** — `Record<BlockerCode, string>` 은 `BlockerCode` 에 적힌 것만 강제하고, 그 타입 자체가 둘 모자란 것은 모릅니다.

⭐ **이것이 `72232ba` 의 표를 만든 이유를 그대로 증명합니다.** 어휘를 다섯만 넣고 여섯째를 안 넣었더니 바로 여기서 났습니다. 표에 여섯째 줄(`ApprovalError` ↔ `BLOCKER_TEXT`)을 넣었고, 표를 찾는 정규식이 `Record<string, string>` 만 보고 있어서 키 타입이 좁은 표를 못 찾던 것도 같이 넓혔습니다.

```
고치기 전  #999 unknown_candidate
고친 뒤    #999 이 회의에 없는 후보입니다 — 목록이 오래됐습니다. 새로 고쳐 주세요
```

서버 문구는 &#34;이 회의에 없는 후보입니다&#34; 뿐입니다. 그것만 읽으면 사람은 무엇을 해야 할지 모릅니다 — 이 코드가 나오는 경우는 하나(화면이 든 목록이 낡음)뿐이므로 할 일을 같이 적었습니다.

### 연결이 끊기면 화면이 아무 말도 안 했다 (결함 87·88)

폰을 들고 지하철에 들어간 순간을 브라우저에서 재현했습니다.

```
새 프로젝트 만들기   아무 일도 안 일어남 · 오류 칸은 빈 채
칸반 카드 옮기기     아무 일도 안 일어남 · 카드는 제자리
승인 제출            아무 일도 안 일어남
기여도 확정          화면에 **"확정했습니다."** 가 그대로 남음
```

마지막 것이 이 시스템의 **유일한 사람 개입 지점**입니다(`docs/05` §5). 확정이 안 됐는데 됐다고 읽히면 팀은 합의한 값이 저장된 줄 알고 화면을 닫습니다. 콘솔에는 `Failed to fetch` 가 있었지만 **화면에는 없었습니다.**

`fetch` 는 서버가 500 을 줘도 **성공**으로 끝나고(`ok === false`), 서버에 닿지 못하면 **거부**합니다. 화면은 전부 `!response.ok` 만 봤습니다 — 받아 오는 길(GET)은 `failureHtml` 로 이유와 다시 시도 버튼까지 갖췄는데, **누르면 바뀌는 길**은 응답이 없는 경우를 통째로 안 봤습니다. 그 뒤가 `void …` 나 `async` 클릭 처리기라 거부가 아무 데도 안 걸립니다.

예외를 잡던 세 곳은 `` `전송 실패: ${String(err)}` `` 였습니다 — 화면에 `전송 실패: TypeError: Failed to fetch` 가 나옵니다. 잡는 곳마다 문구를 새로 쓰니 이렇게 갈라졌습니다.

`lib/http/send.ts` 한 벌로 모았습니다 — `trySend(() => fetch(…))` 는 **던지지 않고 `null`**, `unreachableText(what)` 가 문구, `describeUnexpected()` 가 영어 예외 대신입니다. 바꾸는 요청 **열둘**을 전부 이 길로 보내고 여덟 화면을 끊긴 채로 눌러 확인했습니다.

⚠️ **`unreachableText` 는 &#34;아무것도 바뀌지 않았습니다&#34; 라고 쓰지 않습니다.** 요청이 나가기 전에 끊겼는지, 서버까지 갔는데 답이 못 왔는지 브라우저는 구분해 주지 않습니다. 모르는 것을 안다고 쓰면 그게 더 나쁩니다.

덤으로 **초대 코드 새로 만들기**는 `if (r.ok)` 하나뿐이라 서버 오류에도 조용했습니다. 그대로 두면 사람은 코드가 바뀐 줄 알고 **옛 코드를 다시 나눠 줍니다.**

**덤 — "진행 중로" (결함 88).** 칸반 카드 버튼을 눈으로 보다 찾았습니다. `` `${describeStatus(s)}로` `` 라 `진행 중` 뒤에 `로` 가 붙었는데, 받침이 있으니 **`진행 중으로`** 입니다. `할 일로`·`완료로` 는 맞아서 세 버튼 중 **하나만** 틀린 채였습니다. 조사 가드 셋은 `${값} 조사` 처럼 **띄운** 것만 봤고, 이건 **붙여 놓은** 것이라 셋 다 통과시켰습니다 — **네 번째 층**을 붙였습니다.

### 두 번 눌러 프로젝트가 셋 생겼다 (결함 89)

결함 87 이 **연결이 끊긴 경우**였다면, 이건 **끊기지 않고 늦은 경우**입니다. 훨씬 흔합니다.

느린 망을 흉내 내고(응답만 2초 늦춤 — 요청은 서버까지 실제로 갑니다) 홈에서 &#34;만들기&#34; 를 세 번 눌렀습니다.

```
보낸 요청 3  ·  서버가 받은 POST 3  ·  생긴 프로젝트 3
화면은 그중 하나로 들어감 → /project.html?project=3
```

**같은 이름의 프로젝트 둘이 목록에 남고, 셋은 각자 다른 초대 코드를 가집니다.** 이 제품에서 특히 나쁜 이유: 초대 코드는 팀원이 들어오는 유일한 통로입니다. 사람이 A 의 코드를 나눠 주고 나중에 목록에서 B 를 열면 **팀이 갈라지고 기여도도 갈라집니다** — 이 PR 이 계속 고쳐 온 &#34;오류 없이 기여도만 빈다&#34; 그대로입니다.

⚠️ **처음 잰 값이 틀렸습니다.** Playwright 의 `route` 에서 `continue()` 앞에 2초를 넣었더니 요청이 **브라우저를 떠나기 전에** 화면 전환으로 취소돼 서버에는 하나만 닿았습니다 — &#34;괜찮구나&#34; 로 읽힐 뻔했습니다. `route.fetch()` 로 **먼저 보내고 응답을 늦추자** 셋 다 서버에 닿았습니다. 이 세션에서 측정 방법이 틀려 결함이 가려진 **열세 번째**이고, 처음으로 **없는 결함이 아니라 있는 결함을 지운** 쪽이었습니다.

**잠그는 곳과 안 잠그는 곳이 섞여 있었습니다.** 로그인·`del-run`·`gh-backfill` 셋은 이미 `button.disabled = true` 를 하고 있었고 나머지 열둘은 안 했습니다 — 결함 73·81·82·87 과 같은 &#34;두 벌&#34; 입니다. `lib/ui/pending.ts` 에 `whilePressed(button, run)` 을 두고 전부 그 길로 보냈습니다.

⚠️ **원래 상태로 되돌립니다.** `disabled = false` 로 풀면, 원래 잠겨 있어야 할 버튼(승인 화면의 제출은 결정한 항목이 없으면 잠깁니다)이 요청 한 번 뒤에 열립니다.

⚠️ **이건 서버 쪽 멱등성이 아닙니다.** 탭 두 개에서 각각 누르거나 이미 나간 요청이 재전송되는 것은 못 막습니다. 진짜 해법은 요청에 키를 붙여 서버가 같은 것을 두 번 만들지 않는 것인데, 그건 API 를 바꾸는 일이라 이 범위에서 **안 했고 그렇게 적어 둡니다**(§C 의 남은 한계). 여기서 없앤 것은 **실제로 관찰된 실패** 하나 — 사람이 같은 버튼을 두 번 누르는 것입니다.

```
고치기 전  세 번 누름 → 서버 POST 3 → 프로젝트 3개
고친 뒤    세 번 누름 → 두 번은 막힘 → 서버 POST 1 → 프로젝트 1개
```

⚠️ 가드가 **또 자기 정의 파일**(`demo/logout.ts`)과 **상관없는 파일**(`demo/call.ts` 의 WebSocket `send()`)을 신고했습니다. 81·82·87 에 이어 **네 번째**입니다. 규칙을 `trySend(` 로 좁히고, 로그아웃 버튼도 같은 모양으로 잠갔습니다.

### 실패 문구를 3초 뒤에 폴링이 지웠다 (결함 90)

결함 87 에서 로비의 실패 문구를 채워 넣었습니다. **그 문구가 화면에 안 남았습니다.**

로비는 3초마다 `render()` 를 돌려 방 상태를 다시 그립니다. 실패 문구를 그 자리(`#room-message`·`#consent-message`)에 썼더니 다음 폴링이 덮었습니다. 브라우저에서 재 봤습니다.

```
 400ms  "동의를 제출하지 못했습니다 — 서버에 닿지 못했습니다…"
1500ms  "동의를 제출하지 못했습니다 — 서버에 닿지 못했습니다…"
3500ms  "전원 동의했습니다. 녹음을 시작할 수 있습니다"   ← 지워졌다
```

빈칸이 되는 것보다 나쁩니다. **누르기 전과 똑같은 화면**이 돌아오고, 폰을 주머니에 넣었다 꺼낸 사람은 아무 일도 없었던 화면을 봅니다.

**같은 자리에 두 번째 문제가 있었습니다.** `forceFinish` 는 `response.ok` 를 아예 안 보고 `body.message ?? ''` 만 읽었습니다. 서버가 500 을 주면 `message` 가 없어 빈 문자열이 들어가고, 곧바로 폴링이 원래 문장을 되돌려 놓습니다 — **처음부터 끝까지 화면이 그대로**입니다. 사람은 강제 종료가 된 줄 압니다. 그 버튼은 &#34;그 사람의 발언은 기록되지 않습니다&#34; 라고 확인까지 받는 버튼입니다.

고침은 결함 81·82 가 이미 쓰던 방법입니다 — **아무도 안 덮는 자리**에 씁니다.

```
#room-note      강제 종료의 결과 (성공·실패 모두)
#consent-note   동의 제출의 실패
#room-message   `render()` 만 쓴다 — 방 상태
```

⚠️ **성공 문구도 옮겼습니다.** `2개 트랙을 강제 종료했습니다` 라는 건수가 바로 뒤의 `refresh()` 에 덮여 사라지고 있었습니다.

⚠️ **첫 측정이 또 틀렸습니다.** 동의 실패를 재려고 `**/api/meetings/1/consent` 를 통째로 막았더니 **폴링의 GET 까지** 죽어 `render()` 가 안 돌았고, 문구가 5초 뒤에도 남아 있어 &#34;여긴 괜찮구나&#34; 로 읽힐 뻔했습니다. `POST` 만 막으니 3.5초에 지워지는 것이 보였습니다 — 새 검사 도구를 쓸 때마다 그 도구부터 틀린다는 것이 **열네 번째**입니다.

```
고치기 전  3.5초 뒤 실패 문구가 사라지고 원래 문장이 돌아옴 · 500 은 처음부터 침묵
고친 뒤    5초 뒤에도 그대로 · 500 은 "녹음 파일을 저장소에 등록하지 못했습니다"
```

### 시연 프로젝트에 초대 코드가 없었다 (결함 91)

폰 캡처를 찍으려고 프로젝트 화면을 열었더니 **복사 버튼이 잠겨** 있었습니다. 코드 자리에는 `(없음)`.

```
API 가 만드는 프로젝트   invite_code = _fresh_invite_code(session)
시드가 만드는 프로젝트   invite_code = (없음)
```

화면은 정직하게 굴었습니다 — `(없음)` 을 코드 조판으로 그리지 않고, 버튼을 잠그고, 이유를 `title` 로 말합니다(결함 71). **그런데 그 결과가 &#34;시연에서 팀원을 초대할 방법이 없다&#34; 입니다.** 첫 화면이 &#34;시작하는 두 가지 방법&#34;(만들기·참가)인데 시연 데이터에서는 그중 하나가 막힌 채였고, 저는 **그 상태로 화면을 재고 캡처해 왔습니다.**

⚠️ **제품이 만들 수 없는 상태를 시드가 만들고 있었습니다.** 이 저장소에는 이미 같은 부류의 가드가 있습니다 — 시드가 `start_ms`(스네이크)로 구멍을 써서 화면이 `startMs` 를 못 읽던 것. 이번에는 칸 이름을 손으로 적지 않고 **두 파일에서 `Project(...)` 의 키워드를 읽어 비교**합니다. 나중에 칸이 하나 늘면 시드도 같이 걸립니다.

### 같은 실패가 화면마다 다른 색이었다 (결함 92)

로비 캡처를 **눈으로** 보다가, 실패 문구가 바로 위의 평범한 상태 줄과 똑같이 생긴 것이 눈에 걸렸습니다. 아홉 자리에서 재 봤습니다.

```
빨강 rgb(163,32,32)   홈 만들기 · 칸반 옮기기 · 승인 제출 · 프로젝트 이름
회색 rgb(94,114,115)  **기여도 확정** · 로비 동의 · 복사
```

사람은 화면 몇 개만 봐도 &#34;빨간 줄 = 뭔가 잘못됐다&#34; 를 배웁니다. 그 다음부터 **회색 실패는 평범한 상태 줄로 읽힙니다.** 하필 회색인 곳 하나가 **기여도 확정** — 이 시스템에서 사람이 개입하는 유일한 지점이고, 결함 87 에서 &#34;확정했습니다&#34; 가 남는 것을 고친 바로 그 자리입니다. **고쳐 놓은 문구가 안 보이면 고친 것이 아닙니다.**

`lib/ui/failure.ts` 의 `showNote(자리, 글자, 색)` 하나가 글자와 색을 **같이** 정합니다. ⚠️ 성공 문구(`2개 트랙을 강제 종료했습니다`)는 같은 자리를 쓰되 `plain` 입니다 — 같은 자리라도 뜻이 다릅니다. ⚠️ 지울 때 클래스도 같이 지웁니다 — 안 그러면 다음 안내가 엉뚱한 색으로 뜹니다.

⚠️ **여기서도 도구가 먼저 틀렸습니다.** 첫 측정에서 복사·내 녹음 지우기가 회색·본문색으로 나왔는데, 그 둘은 **안내가 안 뜬 빈 요소**를 잰 것이었습니다. 클립보드를 지우고 실제로 눌러 다시 재니 복사도 원래 회색이 맞았고(고쳤습니다), 내 녹음 지우기는 **원래 `.bad` 를 붙이고 있었습니다** — 없는 결함을 하나 만들 뻔했습니다.

### 서버가 보내는 경고를 아무 화면도 안 읽었다 (결함 93)

시드와 제품이 같은 모양을 만드는지 훑다가(결함 91 의 렌즈) `MeetingTrack.capture_warnings` 가 걸렸습니다. 따라가 보니 시드가 아니라 **화면**이 문제였습니다.

```
녹음 클라이언트가 경고를 잡는다        capture.ts
  → /complete 로 올린다                complete.ts
  → 서버가 저장한다                     recording_service.py:532
  → 트랙 상태에 실어 보낸다             recording_service.py:704  "warnings": t.capture_warnings
  → 화면 타입에 칸이 있다               room.ts   warnings: unknown[]
  → **읽는 곳이 0곳**
```

녹음 화면은 자기가 방금 잡은 경고를 보여줍니다 — 그런데 그건 **그 폰에서 그 순간에만** 보입니다. 업로드돼 저장된 뒤로는 아무 화면도 이 값을 안 봤습니다. 로비가 &#34;누구 폰이 잘못됐나&#34; 를 보는 곳인데도요.

이 저장소의 대표 실패 방식(47·63·75·83·84)이 **타입 한 줄**로 나타난 경우라, 죽은 export 가드에도 안 걸렸습니다.

⚠️ **언제 채워지는지 확인했습니다**(결함 83 의 교훈). `capture_warnings` 는 참가할 때 `[]` 로 만들어지고 `complete_track` 에서만 채워집니다 — 녹음 중에는 언제나 비어 있습니다. 그래서 이 값은 &#34;회의 중 경보&#34; 가 아니라 **&#34;끝난 뒤 이 사람 녹음을 얼마나 믿을지&#34;** 입니다. 그렇게 적어 뒀습니다.

`captureAlerts()` 는 `critical` 만 올리고(경고를 다 쏟으면 진짜 문제가 묻힙니다), **문구를 다시 만들지 않고** 기기가 남긴 말을 그대로 씁니다. 모양이 이상하면 버립니다 — `[object Object]` 를 띄우는 것보다 안 띄우는 게 낫습니다.

⚠️ **수치는 통과하고 그림이 잡았습니다.** 처음 넣었을 때 넘침은 0px 이었는데, 캡처를 보니 경고가 이름 칸(6rem)에 떨어져 **한 줄에 한두 낱말**씩 쪼개져 있었습니다.

```
녹음 중에
마이크가
바뀌었습니다
— 앞뒤
```

`li .warn { grid-column: 1 / -1 }` 로 줄 전체를 쓰게 했습니다(96px → 284px). 상태 칸만 써도 180px 이라 여전히 좁았습니다.

⚠️ **가드가 다른 이유로 통과했습니다.** 처음에는 `src/` 전체에서 `.warnings` 를 찾았는데, 승인 화면의 `candidate.warnings`·진단의 `health.warnings`·녹음 화면의 `client.warnings` 가 **다른 객체인데도** 걸려 되돌려도 안 깨졌습니다 — &#34;내 검사가 다른 이유로 통과 중&#34; 을 **여덟 번째**로 겪었습니다. `TrackHealth` 를 아는 파일만 보게 좁히니 잡혔습니다.

| `capture_confidence` | `coverage` 가 이미 &#34;얼마나 담겼나&#34; 를 말합니다. 비슷한 숫자를 둘 띄우면 사람이 어느 쪽을 믿을지 모릅니다 |
| `track_id` | 로비는 트랙을 **사람으로** 찾습니다(`user_id`). 트랙 하나만 여는 화면이 없어 번호를 쓸 데가 없습니다 |

가드는 이 표를 **코드 안에** 들고 있고, 이미 읽기 시작한 칸이 표에 남아 있으면 그것도 실패합니다 — 면제 목록이 낡는 것을 막습니다.

### 저장된 거부가 화면에서 동의로 되돌아왔다 (결함 94)

결함 93 의 가드를 만들고 나서, 같은 렌즈를 **서버 payload 타입 전부**에 돌렸습니다. 로스터에서 걸렸습니다.

```
서버가 사람마다 보내는 값   raw_audio_retention · voiceprint_storage
화면 타입에 있는 칸          RosterEntry 에 둘 다 있음
읽는 곳                      **0곳**
lobby.html                   <input type="checkbox" checked>  ← 박아 둔 기본값
```

화면은 이 체크박스를 **제출할 때만 읽었습니다.** 브라우저에서 재현했습니다.

```
둘 다 끄고 제출 → 서버에 false 로 저장됨 (확인함)
새로고침        → **둘 다 다시 켜져 있음**
```

화면이 기록과 어긋나는 것만도 문제지만, 더 나쁜 것은 그 상태에서 사람이 &#34;동의합니다&#34; 를 한 번 더 누르면 화면이 `true` 를 보내 **거부가 조용히 뒤집힌다**는 것입니다. 그러면 `retention.purge_unconsented_audio()` 가 그 사람의 원본을 더 이상 지우지 않습니다 — **결함 67 이 고친 바로 그 구멍이 반대 방향으로 다시 뚫립니다.** `docs/07` §2.3 이 요구하는 &#34;② 거부 → 전사 완료 후 원본 즉시 삭제&#34; 가 무력해집니다.

⚠️ **`null` 은 거부가 아닙니다.** 아직 답을 안 한 사람은 화면의 기본값을 그대로 둡니다 — 이 저장소가 로스터에서 줄곧 지켜 온 구분(`recording: null` vs `false`)입니다.

⚠️ **폴링이 사람의 손을 덮지 않게 했습니다.** 3초마다 도는 `render()` 에서 매번 서버 값을 쓰면, **사람이 방금 끈 체크가 3초 뒤에 다시 켜집니다** — 결함 90 과 같은 부류입니다. 그래서 첫 로드에 **한 번만** 되돌립니다. 브라우저에서 확인했습니다: 제출하지 않고 하나를 끈 뒤 7초를 기다려도 꺼진 채로 있었습니다.

```
고치기 전  새로고침하면 거부가 동의로 보임
고친 뒤    거부가 그대로 · 제출 전 편집도 폴링이 안 덮음 (1·4·7초 확인)
```

가드는 이제 **표**로 payload 타입을 들고 있습니다(`TrackHealth`·`RosterEntry`) — 늘면 한 줄만 더합니다.

### ⭐ 확정 문장이 **엉뚱한 사람을 지목**하고 있었습니다 (결함 95·96)

기여도 확정 화면은 이렇게 말했습니다.

```
… 확정했습니다 — 이하늘은 시스템 값과 다르게 정했습니다.
```

브라우저로 재현해 보니 **이하늘은 값이 깎인 사람**이고, 깎은 사람은 김민수였습니다. 빠진 정보가 아니라 **잘못된 귀속**입니다 — 읽는 사람은 이하늘이 제 점수를 스스로 올렸다고 읽습니다.

서버는 이미 `adjusted_by` 에 누른 사람을 남기고 있었고, 그 자리를 둔 이유도 `api/main.py` 에 직접 적혀 있었습니다 — &#34;조정은 판단이고, 판단에는 주체가 있어야 이의를 제기할 상대가 생깁니다&#34;. **화면이 그 칸을 안 읽었습니다.**

같은 함수에서 `reason` 도 안 읽고 있었습니다(결함 96). 화면과 서버가 둘 다 &#34;시스템 값과 다르게 확정하려면 이유를 적어야 합니다&#34; 로 막아 놓고, 그렇게 받아 낸 이유를 아무 데도 안 보여줬습니다. **근거를 강제로 받아 놓고 감춰 두면 받은 뜻이 없습니다.**

```
2026. 8. 9. 오전 7:56:56에 김민수님이 확정했습니다
  — 이하늘님 30.0%(시스템 33.6%, 이유: 문서 작업이 많았습니다)
```

시스템 값 그대로 확정한 경우에도 이제 주어를 답니다. 주어가 없으면 시스템이 정한 것처럼 읽히고, 그게 `docs/05` §5 가 금지한 그림입니다. `adjusted_by` 가 비어 있으면 **지어내지 않고** 모른다고 적습니다.

⚠️ **테스트는 뜻이 맞았고, 자료가 그 뜻을 못 재고 있었습니다.**

```
it('조정한 사람 이름을 말한다 — 조정에는 주체가 있어야 한다', …)
  strictEqual(text.includes('김민수'), true);
```

`row()` 의 `user_id` 가 1(김민수)이고 `adjusted_by` 는 9 였습니다. 화면이 조정**당한** 사람을 대고 있었는데 그게 우연히 김민수라서 통과했습니다.

⚠️ **`reason` 은 가드가 신고하지 않았습니다.** 같은 파일의 `Draft.reason` 이 자리를 메웠고, 확정 표를 그리는 CSS 선택자 `'.reason'` 도 메웠습니다. 결함 93 에서 겪은 &#34;같은 이름의 다른 칸&#34; 이 **한 파일 안에서** 다시 난 것입니다 — 문자열 안은 읽기로 안 세고, 이름이 겹치는 칸은 인정할 조각(`f.reason`)을 적게 했습니다.

### ⭐ 남의 조정이 **말없이 지워지고** 있었습니다 (결함 97)

위 둘을 브라우저로 확인하다, 한 화면에서 두 값이 서로 다른 말을 하는 것을 봤습니다. 문장은 &#34;이하늘님 30.0%&#34; 인데 바로 아래 확정 칸은 `33.5` 였습니다. 재현해 보니 훨씬 나쁜 것이 있었습니다.

```
① 김민수가 이하늘의 값을 33.6 → 30 으로 조정하고 이유를 적는다
② 나중에 같은 화면을 열면 이하늘 칸은 **비어 있다** (안내도 없다)
③ 김민수가 **자기 값만** 고치고 확정을 누른다
④ 이하늘의 30 과 이유가 **말없이 33.6 으로 되돌아간다**
```

실제 브라우저 기록입니다.

```
① 저장된 확정   : 2:30/문서 작업이 많았습니다
③ 다시 확정한 뒤 : 2:33.552/-          ← 사람의 판단이 사라짐
```

빈 칸은 &#34;안 건드림&#34; 이고 서버는 안 건드린 칸에 시스템 값을 씁니다. 규칙 자체는 맞습니다 — **저장된 조정을 화면에 되돌려 놓지 않은 것**이 틀렸습니다. 아무도 지우겠다고 하지 않았고, 지웠다는 말도 안 했습니다. 기여도는 성적에 쓰일 수 있는 숫자입니다.

이제 `adjustmentsToRestore` 가 저장된 확정 중 **사람이 조정한 것만** 돌려주고 화면이 입력칸에 되돌려 놓습니다. 안 건드린 칸은 **비워 둡니다** — 시스템 값 41.713 을 `41.7` 로 적어 놓으면 반올림이 새 조정으로 읽혀서 다음 확정 때 &#34;이유를 적으라&#34; 고 막힙니다.

확정 조회가 실패하면 확정을 **막습니다**. 그 상태의 빈 칸은 &#34;시스템 값 그대로&#34; 인지 &#34;못 불러온 것&#34; 인지 화면도 구분 못 합니다. 모르면 멈춥니다. 브라우저로 확인했습니다 — GET 만 503 으로 막으면 POST 는 0건이고 이하늘의 30 은 그대로였습니다.

⚠️ **가드 두 겹이 되돌림에서 통과했습니다.**

| 가드 | 왜 통과했나 | 고친 것 |
|---|---|---|
| 결함 75 &#34;화면이 안 부르는 export&#34; | `import` 줄만 보고 &#34;쓰고 있다&#34; 로 셈 | `import` 줄을 걷어내고 셈 |
| 그래도 안 걸린 `adjustmentsToRestore` | 아무도 안 부르는 `restoreAdjustments` 가 부름 | 화면 파일 안의 안 불리는 함수를 보는 가드를 새로 넣음 |

**죽은 것이 죽은 것을 부르면 둘 다 살아 보입니다.**

`tsc --noEmit` 은 셋 다 TS6133 으로 잡습니다. `pretest` 로 붙여 봤지만 그러면 `npm test` 가 `npm install` 을 요구하게 됩니다 — **&#34;설치 없이 도는 테스트&#34; 라는 이 저장소의 약속**을 깨서 되돌리고, 같은 것을 의존성 없이 보는 가드를 대신 넣었습니다.

### ⭐ 실패 문구가 성공과 **같은 색**으로 나오는 자리 다섯 (결함 98)

결함 92 가 안내 자리(`…-note`)의 색을 `showNote` 한 곳으로 모았습니다. 그런데 그 가드는 **이름이 `-note` 인 자리만** 봅니다. 다른 이름을 쓰는 자리들이 그대로 남아 있었습니다.

프로젝트 화면의 `#role-message` 를 브라우저로 쟀습니다.

```
지금 개발 100%                  rgb(94,114,115)
합이 1 이어야 합니다 (지금 5)    rgb(94,114,115)
역할을 저장하지 못했습니다        rgb(94,114,115)   ← 실패
저장했습니다 — 개발 100%         rgb(94,114,115)
```

네 가지 뜻이 **전부 같은 회색**입니다. 사람은 화면 몇 개만 봐도 &#34;빨간 줄 = 뭔가 잘못됐다&#34; 를 배우고, 그 다음부터 회색 실패는 평범한 상태 줄로 읽습니다.

가드를 새로 넣었더니 네 자리가 더 걸렸습니다. **전부 진짜였습니다.**

| 자리 | 무엇이 섞였나 |
|---|---|
| `#role-message` (프로젝트) | 상태·입력 문제·저장 실패·저장 성공 넷이 한 회색 |
| `#sub` (로비) | &#34;회의 1 · 팀원 3명&#34; 과 &#34;불러오지 못했습니다&#34; 가 한 회색 |
| `#who` (녹음) | 실패가 **내 이름을 덮어씀** — 부제색으로 |
| `#mic` (통화) | &#34;마이크가 켜졌습니다&#34; 와 &#34;열지 못했습니다&#34; 가 한 회색 |
| `#finish-state` (녹음) | 종료 알림의 진행·실패·성공이 한 본문색 |

⭐ **`#finish-state` 가 제일 나쁩니다.** 청크가 다 안 올라간 상태인데 회색으로 &#34;…못했습니다&#34; 라고 하면 사람은 잘 끝난 줄 알고 나갑니다. 회의 녹음이 통째로 없어질 수 있는 자리입니다.

⚠️ **`.bad` 를 붙이는 것만으로는 안 됐습니다.** `.rolestatus` 와 `app.css` 의 `.bad` 는 특이도가 같은데, 화면별 `<style>` 이 **뒤에** 오므로 `.rolestatus` 가 이깁니다 — 결함 61 과 같은 부류입니다. `.rolesum.bad` 와 `#del-result.bad` 는 이미 그렇게 적혀 있었고 이 자리만 빠져 있었습니다.

`#who` 는 색만 바꾸지 않고 **자리를 나눴습니다**(`#join-note`). 거기는 내가 누구인지를 말하는 자리라, 실패로 덮으면 이름을 잃습니다. 로비의 `#sub` 은 반대로 색만 바꿨습니다 — 그 숫자는 지금 못 믿을 값이라 지우는 쪽이 맞습니다.

⚠️ **가드가 부분 되돌림을 못 잡았습니다.** 처음 규칙은 &#34;이 자리에 `showNote` 가 한 번이라도 있으면 통과&#34; 였습니다. 그랬더니 다섯 줄 중 **두 줄만** 옛 모양으로 되돌려도 조용했습니다 — 남은 `showNote` 세 줄이 자리를 메워 줬기 때문입니다. **한 줄만 새어 나가는 것이 실제로 더 흔한 회귀입니다.** 그래서 **그 줄**을 보도록 고쳤습니다. 실패를 직접 쓰는 줄은 자기 바로 옆에서 색을 정해야 합니다 — `review.ts` 가 `className` 을 윗줄에서 정하는 모양은 통과하고, 칸반 `#result`(CSS 가 항상 빨강, 실패만 씀)도 대상이 아닙니다.

⚠️ **재는 동안 두 번 틀렸습니다.** `#role-sum` 은 합계가 이미 1로 돌아온 뒤에 재서 &#34;빨갛지 않다&#34; 로 읽을 뻔했고(실제로는 잘못된 순간에 빨갛습니다 — **없는 결함을 만들 뻔한 두 번째**), `#mic` 은 **이미 `.bad` 가 붙은 상태**에서 재서 &#34;색이 안 갈라진다&#34; 가 나왔습니다. 둘 다 재는 시점·상태를 고쳐서 다시 쟀습니다.

### ⭐ 시연 트랙의 커버리지·총 공백·구멍 목록이 **서로 안 맞았다** (결함 99)

로비 캡처를 **눈으로** 보다가 잡았습니다. 이하늘은 커버리지 98% 인데 운행도표가 100% 인 김민수와 **똑같이 꽉 찬 막대**였습니다. 2% 가 어디서 비었는지 그림이 말하지 못합니다.

DB 를 열어 보니 시드가 셋을 각각 손으로 적고 있었습니다.

| 사람 | 적힌 커버리지 | 적힌 총 공백 | 구멍 목록 합 | 공식이 요구하는 값 |
|---|---|---|---|---|
| 김민수 | 100% | 0 | 0 | 맞음 |
| **이하늘** | **98%** | **0** | **0개** | 48,000ms |
| **박지원** | **42%** | 1,392,000 | **900,000** | 1,392,000 |

운영은 셋을 **하나의 원천**에서 뽑습니다 — `audio/assembly.py` 가 `coverage = 1 - total_gap_ms / duration` 이고 `total_gap_ms` 는 구멍의 합입니다. 그래서 이 상태는 **API 가 만들 수 없습니다.** 결함 91 과 같은 부류입니다.

박지원은 빗금이 화면 폭의 37.5% 인데 &#34;42% 커버리지&#34;(= 58% 빔)라고 말했습니다. **20% 가 그림에서 사라졌습니다.** 이 저장소의 시그니처가 &#34;구멍이 **언제** 생겼는지&#34; 인데, 시연 자료가 바로 그 질문에 답하지 못하고 있었습니다.

⚠️ **이 자리에는 이미 가드가 있었습니다** (결함 57). 그런데 그 가드는 **키 이름**(`startMs` 스네이크/카멜)만 봤습니다. 시드 주석도 &#34;운영 코드와 같은 키를 씁니다&#34; 라고 자랑하고 있었습니다 — **키는 맞췄고 값의 일관성은 안 맞췄습니다.** 같은 부류의 다음 층입니다.

고친 뒤 실측입니다.

```
김민수 100%  구멍 0개
이하늘  98%  22~23분에 18px(=2%) 빗금 하나
박지원  42%  364px + 164px = 528/910 = 58% 빔
```

⚠️ **재는 동안 두 번 틀렸습니다.** 막대의 세로 눈금 다섯 개를 **구멍으로** 읽고 &#34;100% 인데 조각났다&#34; 로 신고할 뻔했고(눈금은 `.tl` 의 `repeating-linear-gradient` 입니다 — **없는 결함을 만들 뻔한 세 번째**), 되돌림을 grep 으로 재다가 **테스트 소스 줄**을 실패 메시지로 착각했습니다. pass/fail 수로 다시 쟀습니다.

### ⭐ 서버와 화면에 **같은 숫자가 두 벌**인데 아무것도 안 지키고 있었다 (결함 100)

결함 99 를 파다가, 커버리지와 구멍 목록이 갈라지는 **운영 경로**가 따로 있다는 것을 알았습니다.

| 뜻 | 서버 | 화면 | 값 |
|---|---|---|---|
| 이보다 짧은 공백은 보고하지 않는다 | `assembly.MIN_REPORTED_GAP_MS` | `timeline.MIN_REPORTED_GAP_MS` | 100 |
| 이만큼까지는 정상 지터 | `assembly.STALL_TOLERANCE_MS` | `DEFAULT_STALL_TOLERANCE_MS` | 300 |
| 이 아래면 트랙을 안 쓴다 | `recording_service.MIN_USABLE_COVERAGE` | `timeline.MIN_USABLE_COVERAGE` | 0.8 |

주석이 스스로 그렇다고 말합니다.

```python
# (프런트 timeline.ts 의 stallToleranceMs 와 같은 값)
STALL_TOLERANCE_MS = 300
```

**그런데 아무것도 그것을 지키지 않았습니다.** 주석은 아무도 안 읽고 아무것도 못 막습니다 — 이 저장소가 `GapReason` 에서 이미 배운 것인데, **바로 옆 파일**에서 같은 일이 남아 있었습니다.

갈라지면 조용히 어긋납니다. `STALL_TOLERANCE_MS` 가 갈라지면 화면은 공백으로 세고 서버는 안 세어, **커버리지는 낮은데 구멍은 하나도 안 그려집니다** — 결함 99 에서 시연 자료로 본 그 그림이 이번엔 운영에서 납니다. `MIN_USABLE_COVERAGE` 가 갈라지면 녹음 화면은 &#34;쓸 만합니다&#34; 라고 하고 서버는 `unusable` 로 저장합니다.

가드는 둘입니다 — 값이 같은지 보는 것, 그리고 **표가 낡지 않았는지** 보는 것(주석이 &#34;같은 값&#34; 이라고 말하는 상수가 표에 없으면 신고). 되돌림 넷이 잡히고, **양쪽을 같이** 바꾸거나 서버만 쓰는 새 상수를 만들면 통과합니다.

### ⭐ 개인 삭제 요청이 **모든 프로젝트**의 녹음을 지우고 있었다 (결함 101)

`revoke_user_data` 는 `project_id` 를 인자로 **받아 놓고 오디오 조회에는 안 쓰고** 있었습니다.

```python
track_ids = session.scalars(
    select(m.MeetingTrack.id).where(m.MeetingTrack.user_id == user_id)
).all()          # ← project_id 가 어디에도 없다
```

바로 아래 성문은 `revoke_project_voiceprints_for_user(…, project_id)` 로 좁힙니다 — **한쪽만 좁혔습니다.**

라우트는 `/api/projects/{project_id}/…` 이고 `_require_project_member` 로 그 프로젝트 구성원인지까지 확인합니다. 화면은 사람에게 이렇게 약속합니다.

```
내 녹음 원본과 성문을 지웁니다.
되돌릴 수 없습니다. 회의록의 발화 텍스트는 남습니다.
```

그 약속은 **이 프로젝트 안에서** 한 것입니다. 그런데 A 프로젝트 설정에서 그 버튼을 누르면 **B 팀·C 팀의 내 녹음 원본까지** 지워졌습니다. 되돌릴 수 없고, 그 팀들은 통보를 못 받고, 감사 로그는 A 에만 남고, 아직 전사 전인 회의였다면 그 팀의 **회의록 자체가 안 만들어집니다.** 동의한 범위를 넘는 삭제입니다.

⚠️ **테스트 셋이 전부 통과하고 있었습니다.** 셋 다 **프로젝트를 하나만** 만들고 불렀습니다.

```python
# 다른 사람 트랙은 건드리지 않는다
assert (storage / "others.opus").exists()
```

&#34;다른 **사람**의 트랙&#34; 은 쟀는데 &#34;다른 **프로젝트**의 내 트랙&#34; 은 아무도 안 쟀습니다. 뜻은 맞고 자료가 그 뜻을 못 재는 테스트입니다 — 결함 95 와 같은 모양입니다.

### ⭐ 읽는 요청이 끊기면 세 화면이 **텅 빈 채**로 남았다 (결함 102·103)

결함 87 은 **바꾸는 요청**만 `trySend` 로 보냈습니다. 가드 이름부터 &#34;누르면 **바뀌는** 요청은 전부 `trySend` 를 거친다&#34; 였고, 코드에도 `if (!/\bmethod:/.test(args)) continue; // GET 은 받아 오기 길이다` 라고 적혀 있었습니다.

그런데 받아 오기도 서버에 닿지 못하면 **던집니다.** GET 만 끊고 네 화면을 열어 봤습니다.

```
기여도  #members 가 **빈 문자열** · pageerror: Failed to fetch
홈      #projects 가 **빈 문자열**
칸반    #board 가 **빈 문자열**
승인    말은 했는데 화면에 **`Failed to fetch`**
```

앞의 셋은 아무 말도 안 하고 텅 빈 채로 남습니다. 사람은 그걸 &#34;아직 아무도 아무것도 안 했구나&#34; 로 읽습니다 — 대표 실패 방식 그대로이고, 기여도 화면에서는 **오답**입니다.

넷째(결함 103)는 한글 화면에 영어 브라우저 예외를 붙였습니다. 결함 87 이 금지한 그것인데, 그 가드는 `${String(err)}` 만 봐서 **변수에 담아 쓰는 모양**을 놓쳤습니다.

⚠️ **네 화면이 각자 `const get = … fetch(…)` 를 들고 있었습니다.** 본문까지 거의 같은 네 벌이라 한 곳만 고치면 셋이 남습니다 — `lib/http/send.ts` 의 `tryGet` 한 벌로 합쳤습니다. 반환이 `Response | null` 이 되면서 **tsc 가 호출부를 전부 짚어 줬습니다.**

⚠️ **`null` 을 로그인 만료로 읽지 않습니다.** 그렇게 하면 지하철에서 화면을 연 사람이 이유도 모른 채 로그아웃당합니다.

로비와 로그인은 **이미 맞게 처리하고 있어** 근거와 함께 면제 표에 넣었습니다 — 로비는 `getJson` 이 던지고 호출부가 `catch` 로 `#sub` 에 빨갛게 쓰고(결함 98 에서 실측), 로그인의 `void fetch(…/me)` 는 이미 로그인돼 있으면 넘겨 주려는 곁길이라 닿지 못하면 로그인 폼이 그대로인 것이 맞습니다.

⚠️ **타입만 바꾸고 본문은 그대로였던 순간이 있었습니다.** `Promise<Response | null>` 로 선언만 하고 본문은 맨 `fetch` 인 채로 tsc 가 **통과했습니다** — `Response` 는 `Response | null` 에 할당 가능하기 때문입니다. **타입이 통과했다는 것이 동작이 바뀌었다는 뜻은 아닙니다.**

### 백필 상태가 한 회색이었고, 확정이 HTML 500 에 침묵했다 (결함 104)

여섯 렌즈로 저장소를 동시에 훑는 워크플로를 돌려 후보 15개를 받고, 반증을 거쳐 살아남은 것 중 둘을 고쳤습니다.

**① 백필 상태가 진행·실패·성공 한 회색** — 결함 98 의 **여섯 번째 자리**입니다.

```js
const status = $('gh-backfill-status');
status.textContent = unreachableText('가져오지 못했습니다');
```

결함 98 의 가드는 `$('id').textContent =` 만 봅니다. 여기는 요소를 **지역 변수에 담아** 써서 못 봤습니다 — **가드도 자기가 보는 모양만 봅니다.**

**② 확정이 HTML 500 을 받으면 &#34;확정했습니다.&#34; 가 그대로 남는다** — 서버가 500 을 줄 때 본문이 JSON 이라는 보장이 없습니다. 프록시가 HTML 오류 페이지를 돌려주면 `.json()` 이 던지고, 그 자리가 `whilePressed(…, confirm)` 안이라 거부가 아무 데도 안 걸립니다. **결함 87 이 고친 자리가 다른 길로 다시 열려 있었습니다.**

⚠️ **②에는 가드를 못 만들었습니다.** &#34;실패 응답의 `.json()` 에 `.catch` 가 있는가&#34; 가드를 넣어 봤더니 **여덟 화면을 전부 신고**했습니다. 정적으로 실패 분기를 가릴 정확도가 안 나옵니다. 억지 예외 목록을 만드느니 가드를 빼고 여기 적어 둡니다 — 다음에 같은 부류를 만나면 `.json()` 전체에 `.catch` 를 요구하는 쪽으로 한 번에 가는 것이 낫습니다.

### ⭐ 제출할 화면이 없는 동료평가를 **미제출로 세고** 있었다 (결함 105)

`compute_confidence` 의 docstring 이 스스로 이렇게 약속합니다.

```
데이터가 아예 없는 신호(분모 0)는 계산에서 제외한다. 예를 들어
동료평가 모듈을 안 쓰는 팀은 그 항목 때문에 신뢰도가 깎이지 않는다.
```

그런데 기대치를 이렇게 세우고 있었습니다.

```python
peer_expected = member_count * max(0, member_count - 1)
```

팀원이 둘만 넘으면 0 이 아닙니다. 그리고 `PeerReview` 를 만드는 라우트도 화면도 **저장소에 0곳**이라 제출 수는 영원히 0 입니다. 분모가 0 이 아니니 신호가 제외되지 않고 **0.0 으로 신뢰도를 깎았습니다.**

```
다른 신호가 전부 완벽해도   0.9286   ← 1.0 이 아님
사유에 영구히              "동료평가 미제출자가 있습니다"
고친 뒤                    1.0000 · 사유 0건
```

시연 화면의 세 카드 전부에 그 문구가 붙어 있었습니다. 사람이 **할 수 없는 일**을 안 했다고 깎는 것이고, 이 저장소가 지키는 **측정 불가 ≠ 0점** 을 정면으로 어깁니다. 기여도는 성적에 쓰일 수 있는 값입니다.

고침은 한 줄입니다 — 제출된 것이 하나라도 있을 때만 기대치를 셉니다. **기능이 생기면 이 조건이 저절로 열립니다.**

```python
peer_expected = member_count * max(0, member_count - 1) if peer_submitted else 0
```

⚠️ **왜 안 잡혔나.** `conftest.py` 와 `test_scoring.py` 는 `CoverageStats` 를 **손으로 만들어** 넘깁니다(`peer_reviews_expected=4`, `peer_reviews_expected=0  # 미사용`). 그러니 `load_coverage` 가 실제로 무엇을 세는지는 아무도 안 쟀습니다 — **계산식에는 테스트가 있었고, 그 식에 무엇이 들어가는지는 없었습니다.** 이제 실제 프로젝트로 `load_coverage` 를 불러 확인합니다.

### ⭐ 진행률 화면이 파이프라인이 **말한 적 없는 단어**를 기다렸다 (결함 106)

로비의 진행률 문구는 `STAGE_TEXT` 표를 봅니다. 그 표에 `diarize`·`persist` 가 있었는데 **파이프라인은 그 단계를 보고한 적이 없습니다.** 반대로 파이프라인이 실제로 보내는 `align`·`validate` 는 표에 없었습니다.

```
파이프라인이 보내는 것   load · align · transcribe · analyze · validate · done
표가 아는 것            load · diarize · transcribe · analyze · persist · done
                              ↑ 없는 말        ↑ 없는 말
```

오류는 안 납니다. 모르는 단계가 오면 문구가 **비고**, 회의를 올린 사람은 진행이 멈춘 것과 구분하지 못합니다. 표를 파이프라인에 맞추고, `Stage` **전수**를 도는 가드를 넣었습니다 — 다음에 단계를 하나 더 만들면 표를 안 고친 채로는 통과하지 못합니다.

`failed` 는 일부러 뺐습니다. 실패는 진행률이 아니라 **다른 자리**에서 말해야 하고, `describe` 가 `meeting_status == "failed"` 를 **먼저** 봅니다.

같이 고친 것: 실패 진행률에 **예외 원문을 싣고 있었습니다.** `reporter.report(meeting_id, Stage.FAILED, 0, str(exc))` 가 남기는 값은 로비 화면으로 **그대로 나갑니다.** 한글 화면에 `KeyError: 'samples'` 가 뜨면 사람은 아무것도 못 얻고 — 스택이 없으니 — 우리도 못 얻습니다. 원문은 `logger.exception` 이 스택까지 남기게 두고 화면에서는 뺐습니다.

### ⭐ 마감 준수를 **UTC 달력**으로 판정하고 있었다 (결함 107)

이 저장소는 시각을 전부 UTC 로 저장합니다. 그건 옳습니다 — 순간을 저장할 때는 그래야 합니다. 틀린 것은 그 순간을 **&#34;며칠&#34; 로 읽을 때**입니다.

```python
met = completed_at.date() <= deadline.date()
```

`datetime.date()` 는 **UTC 달력일**입니다. 한국(UTC+9)에서 밤 9시 이후에 끝낸 업무는 UTC 로는 아직 어제입니다.

```
완료 2026-09-04T16:00Z = KST 09-05 01:00,  마감 09-04
UTC 로 보면   09-04 <= 09-04  →  제때   ← 틀림
팀 달력으로   09-05 >  09-04  →  늦음
```

**칸반 화면은 이미 로컬 달력으로 고쳐 놓고 그 이유를 주석에 길게 적어 뒀습니다. 서버만 안 고쳐져 있었습니다** — 같은 업무를 칸반은 &#34;지연&#34;, 기여도는 &#34;제때&#34; 라고 말했습니다. 사람은 어느 쪽을 믿을지 모릅니다.

⚠️ **오차가 한쪽으로만 기웁니다.** UTC 는 KST 보다 항상 뒤이므로 이 실수는 **늦은 사람을 봐주는 쪽으로만** 작동합니다. 무작위로 틀리는 것이 아니라 편향돼 있습니다.

`config.py` 에 `project_timezone`(기본 `Asia/Seoul`)을 두고 Celery 스케줄도 같은 값을 읽게 했습니다. 마감일(`deadline`)은 순간이 아니라 **달력 날짜**이고 이 저장소는 그것을 UTC 자정으로 저장하므로, 거기서 `.date()` 를 쓰는 것은 정확한 역변환이라 그대로 뒀습니다.

### ⭐ 같은 실수가 회의 기준일에 또 있었다 — &#34;다음 주 월요일&#34; 이 **회의 당일**이 됐다 (결함 108)

107 을 고치고 나서 같은 모양을 저장소 전체에서 찾아봤습니다. 하나 더 있었습니다.

```python
meeting_date = meeting.started_at.date()
```

이 값은 곧바로 `resolve_deadline` 의 기준일이 되어 &#34;내일&#34;·&#34;다음 주 월요일&#34; 같은 전사 표현을 실제 날짜로 바꿉니다. 새벽에 시작한 회의에서는 **요일까지** 어긋나고, &#34;다음 주&#34; 는 요일에서 주를 세므로 **주 단위로** 틀립니다.

```
회의 시작 2026-09-07 01:00 KST (월) = 09-06 16:00Z (일)

  "내일까지"         UTC기준 09-07   팀달력 09-08
  "3일 안에"         UTC기준 09-09   팀달력 09-10
  "다음 주 월요일"    UTC기준 09-07   팀달력 09-14
                            ↑ 회의가 열린 바로 그 날
```

승인 화면에 **이미 지난 마감**이 뜹니다. 밤샘 회의는 이 팀이 실제로 하는 일입니다.

각자 고치지 않고 `teamflow/clock.py` 로 모았습니다. 따로 고쳤으면 세 번째가 나왔을 때 또 따로 고쳤을 겁니다 — 이 저장소에서 가장 자주 나온 결함 부류가 **&#34;두 벌이 있으면 한쪽만 고쳐진다&#34;** 입니다.

가드는 **구문으로** 봅니다. 글자로 찾으면 이 결함을 설명하는 주석과 docstring 이 먼저 걸립니다 — `clock.py` 는 `completed_at.date()` 가 왜 틀렸는지 적으려고 그 모양을 그대로 쓰고 있습니다. `ast` 로 &#34;순간 이름 + `.date()` 호출&#34; 만 골라냅니다.

### ⭐ 그리고 화면은 **보는 사람의 달력**을 쓰고 있었다 (결함 109)

107 을 고치면서 서버는 `project_timezone` 이라는 하나의 달력을 정했습니다. **화면은 그 결정을 몰랐습니다.**

```ts
`${at.getFullYear()}-${pad(at.getMonth() + 1)}-${pad(at.getDate())}`
```

`Date#getFullYear()` 는 **브라우저가 있는 곳**의 달력입니다. 실제 브라우저 셋으로 확인했습니다 — 같은 업무, 같은 서버 응답입니다.

```
                       고치기 전        고친 뒤
Asia/Seoul             지연 1          지연 1
America/New_York       지연 0  ←       지연 1
Pacific/Kiritimati     지연 1          지연 1
서버(팀 달력)의 판정      늦음            늦음
```

뉴욕에서 열면 칸반이 **지연 0** 이라고 말하는데 기여도 이벤트는 `deadline_missed` 입니다. 시연을 어느 노트북에서 하느냐로 화면이 달라집니다.

같은 조각이 **세 벌** 있었습니다 — `board.ts` 의 `localDateOf`, `demo/kanban.ts` 와 `demo/review.ts` 의 `todayIso`. 셋 다 같은 실수를 따로 하고 있었습니다. `lib/time/calendar.ts` 한 곳만 달력을 알게 하고, 서버 `project_timezone` 과 값이 같은지 보는 가드와, 화면이 날짜를 손으로 짜 맞추지 않는지 보는 가드를 넣었습니다.

⚠️ **되돌림이 이 결함을 잡은 방식이 중요합니다.** 세 시간대에서 화면이 똑같이 나오는 것만으로는 아무것도 증명되지 않습니다 — 처음 잰 값은 셋 다 같았는데, 그건 제가 **지연 표시가 없는 자리**를 보고 있었기 때문입니다. `#counts` 와 경고 문구를 보도록 고치고 나서야 되돌림이 뉴욕에서 **지연 0** 을 냈습니다.

### ⭐ 회의록의 **절반이 DB 에만 남아** 있었다 (결함 110·111)

파이프라인은 회의에서 셋을 만듭니다.

```
요약         summary          →  저장됨 · 화면에 나옴
다음 안건     next_agenda      →  저장됨 · **읽는 곳 0곳**
미해결 사안   meeting_events   →  저장됨 · **읽는 곳 0곳**
```

뒤의 둘은 LLM 이 만들고 `validation` 이 **근거 발화까지 확인해** 통과시킨 산출물입니다. 그런데 API 응답에 없었고, 그래서 화면도 없었습니다. 오류는 안 납니다 — 회의에서 답이 안 난 것이 DB 에 쌓이고 사람은 영영 못 봅니다.

⚠️ **이 저장소는 같은 일을 이미 한 번 겪었습니다.** `models.py` 의 `next_agenda` 칸에는 그 기록이 주석으로 붙어 있습니다.

> 다음 회의에서 다룰 안건. LLM 이 만들고 검증까지 통과한 산출물인데 **`_serialize` 에 없어서** 파이프라인 밖으로 나온 적이 없었다.

그때 고친 것은 **파이프라인 → DB** 구간입니다. **DB → 화면** 구간은 그대로 남아 있었고, 아무도 그것을 세지 않았습니다. **사슬은 한 칸만 끊겨도 끊긴 것입니다.**

`meeting_events` 는 더 분명했습니다 — 저장소 전체에서 그 표를 **읽는 코드가 하나도 없었습니다.** 쓰는 곳 하나, 읽는 곳 0곳.

고침은 세 칸입니다. `MeetingDetail` 이 둘을 싣고, 승인 화면이 요약 아래에 그리고, 시드도 같은 모양으로 채웁니다 — **시드를 안 고치면 배선을 고쳐도 시연 화면은 그대로 비어 있습니다.**

근거는 지어내지 않습니다. 미해결 사안마다 **근거 발화 건수**를 같이 적습니다 — 근거 없이 &#34;이게 미해결입니다&#34; 라고만 하면 사람은 확인할 방법이 없고, 이 저장소는 후보 승인에서 이미 같은 규칙을 씁니다. 발화 시각도 근거가 있을 때만 적습니다. `_span` 이 0 을 돌려준 것을 `0:00` 으로 쓰면 **회의 맨 처음에 나온 얘기**로 읽힙니다.

⚠️ **화면의 &#34;근거 발화 없음&#34; 가지는 지금 운영에서 안 닿습니다.** `validation._check_evidence` 가 근거 없는 미해결 사안을 `NO_EVIDENCE` 로 **거부**하기 때문입니다. 지우지 않고 둔 이유는 그 문구가 없으면 근거가 빈 값이 들어왔을 때 화면이 **근거가 있는 것처럼** 보이기 때문입니다. 안 닿는다는 사실을 여기 적어 둡니다 — 나중에 이 가지를 &#34;쓰이고 있다&#34; 로 세면 안 됩니다.

가드는 **표마다 읽는 곳이 있는지**를 셉니다. ⚠️ 이때 `m.MeetingEvent(...)` 같은 **생성자 호출은 쓰기지 읽기가 아닙니다.** 그것까지 세면 쓰기만 있는 표가 &#34;쓰이고 있다&#34; 로 보입니다 — 결함 97 에서 겪은 함정과 같습니다(죽은 것이 죽은 것을 부르면 둘 다 살아 보인다). 그래서 생성자 위치를 먼저 모아 두고 **그 자리를 뺀 나머지**만 읽기로 셉니다.

⚠️ **가드가 제 코드도 잡았습니다.** 순수 함수를 만들면서 `hasMinutes` 를 썼는데 화면이 안 불렀고, 결함 75 의 &#34;화면이 안 부르는 export&#34; 가드가 **`lib/review/minutes.ts::hasMinutes — 테스트만 씀`** 을 그대로 찍었습니다. 실제로 그 함수는 모양이 틀렸습니다 — 요약까지 세고 있어서, 다음 안건도 미해결 사안도 없는 회의에서 **빈 상자 두 개가 열립니다.** 요약은 자기 자리가 따로 있습니다. `hasExtraMinutes` 로 고쳐 화면이 부르게 했습니다.

⚠️ **넓은 화면에서 근거 건수가 1000px 떨어져 있었습니다.** 내용 칸에 `flex: 1` 을 준 탓입니다 — 1440px 에서 내용은 `x=207`, 근거는 `x=1192` 였습니다. 무엇의 근거인지 안 보이고 표의 다른 열처럼 읽힙니다. 좌표로 재고서야 알았습니다. `flex: 0 1 auto` 로 붙여 두니 `x=392` 로 왔고, 360px 에서는 줄만 바뀝니다(넘침 0px).

### ⭐ &#34;GitHub 계정을 연결하세요&#34; 라고 하면서 **연결할 자리가 없었다** (결함 112)

`Member.github_login` 은 기여도의 GitHub 다리 전체가 서 있는 칸입니다.

```
웹훅 actor_login  ──(이 칸)──▶  user_id  ──▶  기여 이벤트
```

읽는 곳은 **넷**입니다 — 이벤트 배분(`member_logins`)·백필·업무↔PR 잇기·연결 진단. **쓰는 곳은 시드와 테스트뿐이었습니다.** 제품에는 이 칸에 값을 넣는 라우트도 화면도 없었습니다.

즉 실제로 배포하면 이 칸은 **영원히 NULL** 입니다. 그러면 `member_logins` 가 빈 표가 되고, **아무의 PR 도 주인을 못 찾습니다.** 기여도 화면은 그 사람을 &#34;활동 없음&#34; 으로 그립니다. 오류는 안 납니다.

⚠️ **더 나쁜 것은 화면이 이미 그 얘기를 하고 있었다는 것입니다.** 연결 진단은 이렇게 말합니다.

> GitHub 계정을 연결하지 않은 팀원이 있습니다: 김민수. 이 팀원들의 PR은 주인을 찾지 못해 기여도에 들어가지 않습니다.

맞는 말이고, **고칠 방법이 없었습니다.** 사람에게 할 일을 알려 주고 그 일을 할 자리를 안 주는 것은 결함 105 에서 고친 것(할 수 없는 일을 안 했다고 깎기)의 **거울**입니다.

고침은 `PATCH /api/projects/{id}/members/me/github` 하나와 설정 화면의 칸 하나입니다. 경로가 `/members/me/...` 인 것은 역할 저장과 같은 이유입니다 — **남의 id 를 넣을 자리 자체를 안 만듭니다.**

**남의 아이디는 못 씁니다.** 예의 문제가 아니라 점수 문제입니다 — 남의 로그인을 적으면 그 사람의 PR·리뷰가 통째로 내 기여가 됩니다. 그래서 한 프로젝트 안에서 같은 아이디를 둘이 쓸 수 없고, **대소문자를 무시하고** 비교합니다(`MinSu` 와 `minsu` 는 GitHub 에서 같은 사람입니다 — 이건 이미 `member_logins` 가 키를 소문자로 만드는 이유이기도 합니다).

⚠️ **이 검사는 소유 증명이 아닙니다.** 아무도 안 쓴 아이디라면 남의 것이라도 적을 수 있습니다. 진짜 증명은 GitHub OAuth 가 필요한데 이 환경에는 네트워크가 없습니다. 대신 **바꿀 때마다 감사 로그에 남깁니다** — 기여도 분쟁에서 필요한 것은 지금 값이 아니라 누가 언제 그렇게 적었는가입니다.

주소를 통째로 붙여 넣는 것(`https://github.com/minsu`·`@minsu`)은 받아서 정리합니다. 거절하면 &#34;형식이 틀렸습니다&#34; 만 보이고 무엇이 틀렸는지는 안 보입니다.

브라우저로 일곱 가지를 눌러 봤습니다.

```
① 열었을 때        minsu-dev · "지금 minsu-dev로 이어져 있습니다."
② 남의 아이디      거절 · **빨강**(rgb(163,32,32)) — 성공은 회색
③ 주소 붙여넣기    https://github.com/MinSu-New → MinSu-New
④ 새로고침         MinSu-New 그대로
⑤ 지운 뒤         "아직 연결하지 않았습니다 — 이 상태로는 내 PR이…"
⑥ 연결 진단        그 자리에서 "김민수" 를 이름으로 부르기 시작
⑦ 360px           넘침 0px
```

⑥ 이 이 결함의 요점입니다. **경고가 가리키는 것을 사람이 그 화면에서 고칠 수 있게 됐습니다.**

⚠️ **가드 둘이 제 코드를 잡았습니다.** 조사 가드(결함 88)가 `` `지금 ${value} 로` `` 를 찍었습니다 — GitHub 아이디는 영문·숫자로 끝나서 `로`/`으로` 가 갈립니다(`minsu-dev` 는 &#34;브이&#34;라 받침 없음, `hong7` 은 &#34;칠&#34;이라 받침 있음). `withJosa` 로 **계산**하게 고쳤습니다. 그리고 서버의 409 문구에 제가 **`은(는)`** 을 적어 놨고 그것도 잡혔습니다 — 결함 76 에서 화면에서 걷어낸 바로 그 표기입니다. 서버에 조사 계산기를 만들면 화면과 **두 벌**이 되므로, `josa.ts` 가 스스로 권하는 대로 **문장을 바꾸는 쪽**을 택했습니다.

### ⭐ 결함 111 을 고치자 **그 뒤에 숨어 있던 것**이 보였다 (결함 113)

`persist_results_task` 는 회의를 다시 처리할 때 앞판의 결과를 지우고 새로 씁니다. 그 정리 목록에 셋만 있었습니다.

```python
for model in (m.Utterance, m.MeetingTaskCandidate, m.Decision):
```

**미해결 사안이 들어가는 `MeetingEvent` 는 없었습니다.** 재처리할 때마다 같은 사안이 한 벌씩 더 쌓입니다. 두 번 돌려서 재현했습니다 — `재처리마다 쌓였습니다: 2건`.

재실행 경로는 실재합니다. `task_acks_late=True` + `reject_on_worker_lost` 라 **워커가 죽으면 같은 회의가 다시 돕니다.** 그 자리 바로 위 주석이 그렇게 적어 두고 있었습니다.

⚠️ **이 결함은 결함 111 전에는 아무도 못 봤습니다.** 그 표를 읽는 화면이 0곳이었기 때문입니다. 회의록을 화면에 올리자 중복이 그대로 보이게 됐습니다.

> **안 보이던 것이 안 틀렸던 것은 아닙니다.**

이건 이 PR 에서 처음 나온 모양입니다 — 결함을 고쳐서 **새 결함이 생긴 것이 아니라**, 고침이 이미 있던 결함을 **관측 가능하게** 만들었습니다. 배선을 잇는 일이 왜 값어치 있는지의 예이기도 합니다: 아무도 안 읽는 값은 틀려도 틀린 줄 모릅니다.

가드는 &#34;그 태스크가 **만드는** 표&#34; 와 &#34;**지우는** 표&#34; 를 맞춰 봅니다. `m.Xxx(...)` 로 만드는 것을 `ast` 로 모으고, `for model in (m.A, m.B, …)` 로 지우는 것을 모아 차집합을 봅니다. 회의마다 새로 만들지 않는 표 셋은 근거를 적어 면제했습니다 — `MeetingTrack`(녹음이 만든다) · `ContributionEventRow`(발화를 지우기 **전에** 따로 지운다) · `AuditLog`(무슨 일이 있었는가의 기록이라 지우면 안 된다).

### ⭐ 실패한 회의는 **막다른 길**이었다 (결함 114)

회의 상태를 쓰는 곳은 다섯입니다 — `queued`·`processing`·`failed`·`needs_review`·`confirmed`. **아무도 `pending` 으로 되돌리지 않습니다.** 그리고 `try_finalize_meeting` 은 이렇게 시작합니다.

```python
if meeting.status != "pending":
    return FinalizeResult(True, False, …, f"이미 처리 중입니다 ({meeting.status})")
```

즉 한 번 `failed` 가 되면 **그 회의는 영원히 그대로**입니다. `queued` 도 마찬가지입니다 — 브로커가 죽어 있어서 아무도 안 집어갔으면 영영 큐에 걸린 채입니다(`enqueue_meeting_processing` 은 브로커 장애 때 **조용히 `None` 을 돌려줍니다.** 요청을 실패시키지 않는 것이 그 함수의 규약입니다).

⚠️ **그런데 화면은 할 일이 있다고 말하고 있었습니다.**

```ts
case 'failed':
  return { label: '트랙 상태 보기',
           reason: '처리에 실패했습니다 — 트랙이 온전한지 확인하세요',
           actionable: true };
```

사람이 로비로 가서 확인하고, **트랙이 멀쩡해도 할 수 있는 일이 없었습니다.** 결함 112 와 같은 모양입니다 — 할 일을 알려 주고 그 일을 할 자리를 안 주는 것. 실패는 일시적인 이유로도 납니다(GPU 를 못 잡음 · 조각 하나가 깨짐 · 워커가 죽음). 그때마다 **그 회의의 기여가 전원에게 영영 빕니다.**

고침은 `POST /api/meetings/{id}/reprocess` 하나와 로비 버튼 하나입니다.

**다시 도는 것이 안전한 이유**는 이미 갖춰져 있었습니다 — `persist_results_task` 의 재처리 정리가 앞판의 발화·후보·결정·회의 이벤트를 지우고, 발화를 지우기 **전에** 그 발화에서 나온 기여 이벤트를 먼저 잊습니다(안 그러면 다시 돌 때마다 점수가 누적됩니다). 회의 이벤트가 그 목록에 들어간 것은 **바로 앞 결함 113** 입니다.

⚠️ **사람이 이미 판단한 회의는 큐에 넣기 전에 막습니다.** 태스크도 `already_reviewed` 로 거절하지만 그건 큐에 들어간 **뒤**라, 화면에는 &#34;다시 처리를 시작했습니다&#34; 로 보이고 아무 일도 안 일어납니다.

⚠️ **거절 문구에 `meeting.status` 를 넣지 않았습니다.** 그건 내부 enum 이고 그대로 띄우면 결함 78·86 이 반복됩니다. 한국어 어휘표는 화면이 들고 있으므로 서버는 **조건**만 말합니다 — &#34;처리에 실패했거나 큐에 걸린 회의만 다시 처리할 수 있습니다&#34;. 테스트가 그 문구에 내부 이름이 안 들어가는지 봅니다.

⚠️ **&#34;언제 다시 처리할 수 있는가&#34; 는 서버가 정합니다.** 진행률 응답에 `can_reprocess` 를 실어 화면은 그것만 봅니다. 화면이 상태를 보고 스스로 정하면 그 규칙이 두 곳에 생기고 한쪽만 고쳐집니다 — 진행률 **문구**를 서버가 만드는 것과 같은 이유이고, 그 이유는 `lobby.ts` 주석에 이미 적혀 있었습니다.

브라우저로 네 가지를 봤습니다.

```
① 홈                "처리 실패 — 트랙이 온전한지 확인하세요"
② 로비              "다시 처리하기" 44px 로 나타남
③ 검토된 후보가 있을 때  거절 · **빨강** · "이미 검토한 업무 후보가 1건 있습니다…"
④ 눌렀을 때(360px)   회색 안내 · 넘침 0px · 상태 queued · 감사 로그 1건
```

### 로그인 화면이 오프라인에서 **처리되지 않은 오류**를 흘렸다 (결함 115)

바꾼 화면 셋(승인·설정·로비)을 다시 찍어 **눈으로 보다가** 콘솔에 401 이 하나 있는 것을 봤습니다. 어디서 나오는지 재 보니 로그인 화면의 `GET /api/auth/me` 였고, 그건 **&#34;아직 로그인 안 함&#34; 이라는 맞는 답**이었습니다. 화면도 그 답을 제대로 씁니다 — `r.ok` 면 넘겨 주고, 아니면 폼을 그대로 둡니다.

그런데 그 김에 **오프라인**으로 열어 봤습니다.

```
오프라인 로그인 화면: 폼은 그대로 · 안내 없음      ← 여기까지는 맞다
pageerror: TypeError: Failed to fetch             ← 이건 아니다
```

`.catch` 가 없어서 거부가 **처리되지 않은 채** 남습니다. 사람에게 보이는 잘못은 없습니다 — 폼은 멀쩡하고, 아무 말도 안 하는 것이 맞습니다(가드의 면제 근거가 그렇게 적어 두었고 그 판단은 지금도 맞습니다). 그러나 **말을 안 하는 것과 오류를 흘리는 것은 다릅니다.** 로그인은 이 제품의 첫 화면이고, 시연에서 개발자 도구를 열면 그 빨간 줄이 첫 화면에 있습니다.

고침은 `.catch(() => undefined)` 한 줄입니다. 면제 근거도 &#34;말은 안 하되 거부는 삼킨다&#34; 로 채웠습니다 — 근거가 반쪽이면 다음 사람이 반쪽만 지킵니다.

⚠️ **가드를 처음 쓴 방식이 틀렸습니다** (측정 실수 스물세 번째). `void fetch(` 부터 **다음 세미콜론까지**를 문장으로 잘랐는데, 그 세미콜론이 `.then` **몸통 안**의 것이었습니다.

```ts
void fetch(…)
  .then((r) => {
    if (r.ok) location.href = next;   // ← 여기서 잘렸다
  })
  .catch(() => undefined);            // ← 그래서 이걸 못 봤다
```

**이미 고쳐 둔 코드를 위반으로 신고**했습니다. 괄호 깊이를 세어 문장 끝까지 가도록 고쳤습니다.

⚠️ 그리고 되돌림에서 한 번 더 걸릴 뻔했습니다. `.catch` 를 `.then` **앞**에 두는 모양(통과해야 맞습니다)으로 바꿔 봤더니 테스트가 하나 실패했는데, **무엇이 깨졌는지 보니 번들 신선도**였습니다 — 소스만 고치고 빌드를 안 한 탓입니다. 결함 70 에서 적어 둔 &#34;깨졌다는 사실 자체는 안심의 근거가 아니다&#34; 의 **뒤집힌 짝**입니다: **깨졌다고 해서 내 가드가 잡은 것도 아닙니다.**

### 눈으로 보다가 잡은 것 하나 더 — 이번엔 **제 흔적**이었습니다

같은 캡처에서 승인 화면이 &#34;전체 4 · 승인 0 · 거절 0 · **미결정 4**&#34; 라고 말하고 있었습니다. 시드는 &#34;승인 대기 **3건**&#34; 이라고 안내합니다. 수치 검사로는 안 보이는 어긋남입니다.

원인은 제품이 아니라 **저**였습니다. 결함 114 를 브라우저로 확인하면서 후보 넷을 전부 `pending` 으로 바꿔 놓고, 회의 상태와 감사 로그만 되돌리고 **후보는 안 되돌렸습니다.** 그 결과 시연 DB 가 시드 주석이 경고한 바로 그 상태가 됐습니다 — 이미 업무가 만들어진 후보(`created_task_id` 가 있는)가 &#34;아직 승인 안 됨&#34; 으로 보이는 상태입니다. 그대로 승인하면 **업무가 하나 더 생깁니다.**

`created_task_id` 가 있는 후보를 `approved` 로 되돌렸습니다. 기록으로 남기는 이유: **검증하느라 만진 것을 원래대로 못 돌리면, 다음 캡처가 그 상태를 제품의 모습으로 찍습니다.**

## 지우는 코드가 아무도 안 부르는데 &#34;부릅니다&#34; 라고 적혀 있었다 (결함 116)

프런트에는 **죽은 export 가드**가 있습니다(결함 75). 백엔드에는 같은 것이 없었습니다 — 이 저장소의 대표 실패 방식이 &#34;만들어 놓고 아무도 안 부름&#34; 인데, 그걸 세는 자리가 한쪽에만 있었던 것입니다. 그래서 한 번 세어 봤습니다: `teamflow` 안의 함수 **390개 중 74개**가 패키지 안에서 한 번도 안 불립니다.

74개 대부분은 정상입니다 — FastAPI 라우트(프레임워크가 부릅니다), Celery 태스크, 프로토콜 메서드, 실험용 API. **의미 있는 것은 넷이었고, 그중 하나가 결함이었습니다.**

### `auth_service.purge_expired` — 안 불려서 다행이었습니다

```python

    """만료된 세션 행 삭제. 유지보수 잡에서 부릅니다."""
```

독스트링이 **&#34;유지보수 잡에서 부릅니다&#34;** 라고 단언합니다. 그 잡은 없습니다. `tasks/maintenance.py` 에도 `beat_schedule` 에도 없고, 부르는 곳이 **0곳**입니다.

여기까지는 결함 63(마감일 조작 탐지가 통째로 죽어 있었다)과 같은 모양입니다. 다른 점은 **이쪽은 불렀다면 더 나빴다**는 것입니다. `UserSession` 모델이 바로 이렇게 적어 뒀습니다.

&gt; 로그아웃 시각. 행을 지우지 않는 이유는 감사 때문입니다 — &#34;누가 언제 로그인해 있었는가&#34; 는 기여도 분쟁에서 확인할 거리가 됩니다.

**모델은 남기겠다고 하고, 서비스는 지우는 함수를 들고 있고, 테스트는 그 삭제를 고정하고 있었습니다.** 셋 중 둘이 한편이고 문서화된 결정은 혼자였습니다. 다음 사람이 독스트링을 믿고 배선하면 — 그게 정확히 독스트링이 시키는 일입니다 — 학기 말 분쟁에서 확인할 기록이 매일 조금씩 사라집니다. 조용히, 되돌릴 수 없게.

지울 이유도 없었습니다. 만료 판정은 `resolve_session` 이 `expires_at` 으로 그 자리에서 합니다 — 행이 남아 있어도 그 토큰으로는 아무것도 못 합니다. `token_hash` 는 무작위 32바이트의 sha256 이라 되돌릴 수도 없습니다. **지워서 얻는 것은 없고 잃는 것은 감사 기록입니다.**

그래서 함수와 그 테스트를 지우고, 그 자리에 **왜 세션 정리 잡이 없는지**를 적었습니다. 테스트는 반대 사실을 고정하는 것으로 바꿨습니다 — 만료된 토큰은 그 자리에서 거절되고, **두 행 다 남아 있습니다.**

## ⭐ 결측색이 **글자로는 안 읽혔다** — 주장하지 않은 바탕은 아무도 안 잰다 (결함 117)

이 결함의 알맹이는 색이 아니라 **검사의 구조**입니다.

`test_design_tokens.py` 는 좋은 규칙 위에 서 있습니다 — *"파일이 주석으로 주장한 대비를 매번 다시 잰다."* 주석과 색이 갈라지는 것을 막으려고 만들었고, 실제로 여러 번 잡았습니다.

그런데 그 규칙에는 구멍이 하나 있습니다.

> **주장하지 않은 바탕은 영원히 안 재집니다.**

`--gap` 은 `/* gap-tint 3.04:1 ✅ */` 하나만 주장했습니다. `--ok`·`--warn`·`--bad` 는 셋 다 `surface` 위 주장을 갖고 있는데 `--gap` 만 없었습니다. 그래서 **의미색 중 이것만** 본문 면 위에서 한 번도 안 재졌습니다.

그 사이 화면 여덟이 이 색으로 **문장을 찍고 있었습니다.** 렌더해서 잰 값입니다:

```
kanban        "0"(흐름 지표)              3.46:1
kanban        "기여도에 반영 안 됨"        3.80:1
review        "34%"(확신도 배지)          3.25:1   ← 자기 14% 띠 위라 제일 나쁨
review        "담당자 · 마감일을 …" ×2     3.80:1
contributions "측정하지 못했습니다"        3.46:1
lobby         "커버리지 42% — …"          3.80:1
call          "마이크가 켜지지 않았습니다"  3.80:1
```

이 저장소가 스스로 정한 글자 하한은 **4.5:1** 입니다(`test_design_tokens.py` — *"11px 굵은 글자라 큰 글자 예외(3:1)를 못 씁니다"*). 전부 그 아래입니다.

**하필 결측을 설명하는 문장들입니다.** "측정 불가 ≠ 0점" 은 이 제품의 불변식 셋째인데, 그 불변식을 화면에서 말하는 문장이 안 읽히면 불변식이 화면에서 사라집니다.

### 왜 이 색만 그랬나

`docs/16` Stage A 표가 답을 적어 두고 있었습니다:

```
| `--gap` / `--gap-tint` | `#ae7747` / `#f0e4d8` | 3.04:1 | 3.0 ✅ 그래픽 |
```

**그래픽 기준(3:1)으로 고른 색**입니다. 트랙의 빗금·점·배너 막대에 쓸 생각이었고 거기서는 맞습니다. 그런데 나중에 화면들이 같은 색으로 글자를 찍기 시작했고, 그때 아무도 기준을 다시 보지 않았습니다.

### 고친 것

`--clay-600` 은 그대로 두고 **Layer 2 에서 파생**시켰습니다.

```css
--gap: color-mix(in srgb, var(--clay-600) 65%, var(--ink-900));
```

- **원시값을 안 건드린 이유**: `test_a_gap_is_still_clay_not_red_even_on_the_chrome` 이 `--clay-600` 을 껍데기 위에서 3:1 로 잽니다. 짙게 하면 그쪽이 깨집니다. 껍데기는 안 뒤집히므로 방향이 반대입니다.
- **`--ink-900` 쪽으로 민 이유**: 그것도 Layer 1 이라 모드마다 뒤집힙니다. 그래서 밝은 모드에서는 어두워지고 어두운 모드에서는 밝아집니다 — **두 모드 다 바탕에서 멀어집니다.** 한 줄이 두 모드를 같이 고칩니다.
- **65% 를 고른 이유**: 실제로 쓰이는 바탕 셋(`--bg`·`--surface`·자기 14% 띠) 전부에서 여유를 두고 넘습니다. 그리고 `surface` 위 6.42:1 은 `--ok`(6.44)와 같은 자리라, 의미색 가족 안에서 튀지 않습니다.

```
        전        후
--bg    3.46  →  5.85
surface 3.80  →  6.42
14% 띠  3.25  →  5.26
```

화면 파일은 **한 줄도 안 고쳤습니다.** 열넷이 한 번에 나았습니다.

⚠️ **`--raised` 와 `gap-tint 위 배지` 는 안 고쳤습니다** — 그런 자리가 **저장소에 없기 때문**입니다. 조사 중에 그 둘을 "빡빡한 바탕" 으로 세는 계산이 나왔는데, `grep` 해 보니 `--raised` 는 Tailwind 별칭 말고 쓰는 곳이 0곳이고 `--gap-tint` 배경은 빗금 하나뿐(글자 없음)이었습니다. **있지도 않은 바탕에 맞춰 색을 고르면 진짜 바탕에서 과하게 어두워집니다.**

### 그래서 붙인 가드 둘

구멍이 "주석에만 의존한 것" 이었으므로, 새 가드는 **주석을 안 봅니다.**

1. `test_every_body_ink_reads_on_every_body_bed` — 문장을 이고 다니는 색 일곱(`--text` 셋 + `--ok`·`--warn`·`--bad`·`--gap`)을 본문 면 둘(`--bg`·`--surface`) 위에서 두 모드 다 잽니다. 목록을 들고 직접 잽니다.
2. `test_text_on_a_tinted_band_still_reads` — 배지처럼 **자기 색 띠 위에 자기 색 글자**를 얹는 짝을 **화면 CSS 에서 읽어** 잽니다.

⚠️ **두 번째 가드를 처음엔 틀리게 만들었습니다.** "본문 색 전부에 대해 자기 14% 띠" 를 재게 했더니 `--text-subtle` 이 4.24:1 로 걸렸는데, **그런 띠는 저장소에 없습니다.** 방금 조사에서 지적한 그 실수를 가드 안에서 그대로 반복한 것입니다. 지금은 화면 CSS 를 읽어 실제로 쓰인 짝만 잽니다(찾은 것: `--primary` 셋 · `--gap` 둘).

### 심어서 확인한 것

- `--gap` 을 옛 원시값으로 되돌림 → 세 검사가 `3.46 / 3.80 / 3.25` 로 터짐 (브라우저 실측과 같은 숫자)
- 주장 숫자를 `bg 9.99:1` 로 틀리게 적음 → `주석은 9.99:1 인데 실제는 5.85:1`
- 없는 토큰을 섞음 → `값을 못 풀었습니다`
- 띠 가드의 정규식을 깨뜨림 → `한 짝도 못 찾았습니다` (0건 안전망)
- `color-mix` 를 **선형 보간**으로 바꿈 → `#8f633d 로 풀었는데 브라우저는 #775939`

마지막 것이 특히 중요합니다. `in srgb` 는 **감마 인코딩된 값끼리** 섞는데, 선형으로 섞어도 대비 주장은 얼추 맞아서 **다른 검사로는 안 걸립니다.** 그래서 Chromium 이 실제로 칠한 픽셀을 캔버스로 읽어 못 박아 뒀습니다.

⚠️ 그 픽셀을 읽을 때도 한 번 틀렸습니다. `getComputedStyle` 로 `color-mix` 를 읽으면 `color(srgb 0.46 0.35 0.22)` 라는 **0~1 실수**가 나오는데, 그걸 0~255 로 읽어 "14% 띠 2.75:1" 이라는 틀린 값을 냈습니다. 캔버스 픽셀로 다시 재니 3.25:1 이었습니다.

### 덤 — 이 조사가 드러낸 **거짓 주석 셋**

색과 무관하게, 옮긴 뒤 따라오지 않은 주석들입니다. 테스트가 안 터지므로 **사람만 속습니다.**

- `app.css` `.ctx-dot` — "껍데기 위 4.54:1" 이라고 적혀 있는데 `.ctx` 는 `background: var(--bg)` 입니다. 맥락 패널이 `docs/19 §18` 에서 본문으로 옮겨졌는데 색 주석만 안 따라왔습니다
- `tokens.css` — 같은 주장
- `docs/19` — 같은 주장. 게다가 그 4.54:1 은 `--gap` 이 아니라 **`--clay-600`** 의 값이었습니다

## B. 새로 만든 것

### 운행도표 — 구멍이 **언제** 생겼는지 (`d9b1819`)

이제 로비가 &#34;42% 가 비었다&#34; 가 아니라 **&#34;10~20분과 25~30분이 비었다&#34;** 를 말합니다. 회의 중이면 지금 폰을 보면 되고, 끝난 뒤면 어느 결정이 그 구간에 있었는지 되짚을 수 있습니다.

```
비율 막대   박지원 42%              → 확인해야 할 것: 그 사람
운행도표    12분~19분이 비었다      → 확인해야 할 것: 그 시각
```

근거는 Marey 의 1885년 열차 운행도표입니다 — 시간축 위의 평행선, 그리고 **빈 곳이 정보**라는 발상(`docs/16`).

⚠️ **축이 이 모듈의 전부입니다.** 서버는 구멍을 **트랙 자기 시작 기준** 밀리초로 줍니다. 오프셋을 안 맞추면 5분 늦게 들어온 사람의 &#34;내 기준 0~5분&#34; 구멍이 **회의 맨 앞**에 찍힙니다. 축이 틀리면 &#34;그 결정이 나올 때 이 사람이 끊겨 있었다&#34; 가 통째로 거짓이 됩니다. **축을 못 정하면 빈 도표를 돌려줍니다** — 거짓 위치는 안 그리는 것보다 나쁩니다.

### 모르는 것을 아는 척하지 않는 막대 (`f71007f`) — 그리고 그중 하나를 지운 것 (`eb36c2c`)

두 종류를 나눴습니다. 섞으면 거짓말이 됩니다.

| | 뜻 |
|---|---|
| **위치**가 뜻을 가지는 막대 | 구간(19%~29%) · 운행도표(12분~19분) |
| **양**만 뜻을 가지는 막대 | 커버리지 42% — **언제** 끊겼는지는 모른다 |

양만 아는 값을 시간축처럼 그리면 사람은 &#34;12분쯤에 끊겼구나&#34; 로 읽는데 **우리는 그걸 모릅니다.** 그래서 양만 아는 막대에는 눈금을 안 그리기로 했습니다.

⚠️ **그런데 양만 아는 막대(`.cov`)는 결국 지웠습니다** (결함 75). 이 PR 안에서 전제가 뒤집혔기 때문입니다 — **운행도표**가 들어오면서 `track_health()` 가 구멍의 **위치**까지 주게 됐고(`d9b1819`), 총량만 아는 자리가 사라졌습니다. 그러고도 코드·CSS·테스트 13개가 남아 있었고 **그리는 화면은 0곳**이었습니다.

**살아남은 규칙은 그대로입니다.** `coverage` 가 null 이면 **&#34;아직 모릅니다&#34;** 로 씁니다 — 0 으로 그리면 그 사람이 아무것도 안 한 것이 됩니다(**측정 불가 ≠ 0점**, `docs/05` §5). 그 판단은 지금 `lobby/room.ts` 가 하고, **화면에 실제로 나옵니다.** 지운 쪽이 아니라 이쪽이 살아 있던 구현이었습니다.

### 상태 화면 — 없는 것을 빈 것으로 답하지 않는다 (`0df2211`)

로딩 스켈레톤이 **0개**였습니다. 대신 정적 문구 다섯 개가 HTML 에 박혀 있었고, 화면을 열 때마다 한 번씩 깜빡였습니다.

**안 뜨는 것이 기본값입니다** — 200ms 안에 끝나면 로딩 표시를 아예 안 만듭니다(지시서 §4.7). 브라우저로 확인했습니다: 화면 넷을 20ms 간격으로 들여다봤을 때 스켈레톤 목격 **0회**, 1.2초 지연을 걸면 정상적으로 뜹니다.

⚠️ **최소 노출 시간은 안 뒀습니다.** 205ms 에 끝나면 5ms 만 보이니 여전히 깜빡임이지만, **지시서에 그 숫자가 없습니다.** (지금은 지운) `track/bar.ts` 에서 근거 없는 상수를 만들 뻔한 뒤로, 관찰되기 전에는 안 만듭니다.

빈 상태는 셋을 **반드시** 말합니다 — `what`(원래 무엇이 오는가) · `why`(**지금 왜 비었는가**) · `how`(채우려면). `why` 를 선택 항목으로 두지 않아 타입이 강제합니다. 승인 화면의 후보 0건은 **네 가지 뜻**이 있어(처리 중 / 뽑을 게 없었음 / 다 검토함 / 실패) 회의 상태에 따라 다른 말을 합니다 — 하나로 덮으면 사람은 영원히 새로고침합니다.

오류는 이제 **목록 자리에** 뜹니다. 예전에는 여섯 화면이 전부 오류를 화면 맨 아래나 위쪽 경고 줄에 한 줄만 남기고 목록 자리는 텅 빈 채로 뒀습니다 — **실패와 0건이 같은 모양**이었습니다. `describeHttpStatus` 는 **모르는 코드에 null 을 돌려줍니다**; 없는 고객센터도 안 지어냅니다.

### 디자인 토큰 3계층 (`569d9e0`)

**색을 눈으로 고르지 않습니다 — 계산합니다.** 실제로 손으로 고른 스파이크 팔레트가 제가 감사에서 지적한 바로 그 대비 결함(1.46:1)을 다시 냈습니다. 그 뒤로는 전부 대비비를 재서 정했습니다.

```
Layer 1  원색 계단 (ink/teal/clay/green/amber/red)   ← 다크는 여기만 바뀐다
Layer 2  역할 (--text / --line-strong / --primary)
Layer 3  치수 (4px 격자 --sp-*, --r-*, --fs-*, --dur-*)
```

`--line`(장식, 1.27:1)과 `--line-strong`(컨트롤, **3.07:1** ✅)을 나눈 것이 핵심입니다 — 한 값으로 쓰면 컨트롤 경계가 WCAG 3:1 을 못 넘거나 장식선이 너무 진해집니다.

한국어 조판도 같이 넣었습니다 — `word-break: keep-all`(어절 단위 줄바꿈), `text-wrap: balance/pretty`.

### Stage H — **그 토큰을 실제로 쓰게 만들었습니다** (`272d219`)

Stage D 에서 3계층을 세워 놓고 §11-A 를 항목마다 실측해 보니, **`var(--fs-*)` 를 쓰는 곳이 0곳**이었습니다. `font-size` 76곳이 전부 리터럴이고 그중 30곳은 **토큰과 똑같은 값을 손으로** 적은 것이었습니다. 간격도 15종 48곳이 4px 격자 밖(`.15rem` `.35rem` `.85rem` 같은 값)이었습니다 — 어느 한 곳도 눈에 안 띄는데 전체가 어수선해지는 종류입니다.

격자로 옮기고(43곳) 격자 위에 있던 리터럴도 이름으로 바꿨습니다(82곳 — **값은 그대로**). 화면당 글꼴 종류 **7종 → 4~6종**.

⚠️ **입력창만 16px 을 지킵니다.** iOS Safari 는 16px 미만 입력 칸에 포커스가 가면 확대하고 **확대된 채로 돌아오지 않습니다.** `--fs-body`(15)가 딱 그 함정이라 `--fs-input` 이라는 **이름을 따로** 줬습니다 — 이름이 없으면 다음 사람이 &#34;본문이랑 같게&#34; 하며 15로 내립니다.

**주 버튼이 화면당 셋이었습니다**(홈 3·로비 2). 원인은 둘 다 같습니다 — **상태에 따라 주 동작이 옮겨 가는데 버튼은 고정**. `classList.toggle('primary', 조건)` 두 줄로 고쳤습니다. 동의한 뒤에도 동의 버튼이 청록으로 남아 있으면 또 눌러야 하나 싶게 만듭니다. 실측: 보이는 주 버튼 전 화면 **1개**.

**이모지 넷(`🏠📋📊⚙️`)을 좌표로 그린 아이콘으로 바꿨습니다.** 이모지는 기기마다 그림이 다르고, 색이 박혀 어두운 모드를 안 따라오고, 베이스라인이 서체에 딸려 정렬이 틀어집니다.

⚠️ **lucide 가 아닙니다.** 규격(24×24 · stroke 2 · round)만 같습니다. 네트워크가 없어 실제 path 를 못 받았고, **받은 척하면 다음 사람이 그걸 믿고 원본과 대조하지 않습니다.**

⭐ 기여도 아이콘은 **시그니처가 아이콘이 된 것**입니다 — 평행 트랙 셋, **가운데 줄이 끊겨** 있습니다. 반복 모티프가 이걸로 세 곳이 됐습니다(트랙 막대 · 운행도표 · 탭 아이콘).

⚠️ **흑백 기호(`⚠ ✓ ⚑ → ①`)는 그대로 둡니다.** 본문 서체로 그려지고 `color` 를 따라가므로 위 세 문제가 없습니다. 가드는 **변이 선택자 U+FE0F** 를 잡습니다 — 그게 붙으면 흑백 기호가 색 이모지로 강제됩니다. 실제로 `⚠️ 화면이 가려짐` 이 그랬습니다.

### 처리가 어디까지 갔는지 — 진행률 (`8458614`, 감사 #8)

`pipeline/steps.py` 의 `RedisProgress` 는 처음부터 있었고 docstring 이 **&#34;API가 SSE로 프런트에 흘린다&#34;** 고 적어 두고 있었습니다. **그 API 가 없었습니다.** 1시간 회의는 처리에 10분이 걸릴 수 있는데, 그동안 화면이 할 수 있는 말은 &#34;처리 중입니다&#34; 뿐이었습니다 — 멈춘 건지 도는 건지도 몰랐습니다.

**SSE 로 안 만들었습니다.** SSE 는 이 저장소가 이미 거부한 방식입니다(`lobby.ts` 주석 — &#34;서버에 상태가 생기고, 그건 이 화면 하나 때문에 지불하기엔 비쌉니다&#34;). 로비는 이미 3초마다 폴링하므로 **읽기 엔드포인트 하나**면 새 연결도 새 상태도 필요 없습니다. 감사가 제안한 해법이 아니라 **감사가 지적한 문제**를 고쳤습니다.

⚠️ **모르는 것을 0% 로 답하지 않습니다.** 진행률이 없는 이유는 셋입니다 — 아직 시작 안 함 · 이미 끝남 · Redis 가 없음. 전부 &#34;0%&#34; 로 답하면 사람은 **멈춰 있다**고 읽습니다.

```
처리 중 + 진행률 없음  →  "처리 중입니다 — 진행 상황은 아직 알 수 없습니다"
처리 끝 + 진행률 없음  →  (아무 말도 안 함. 기다릴 필요가 없다)
```

Redis 는 **선택 부품**입니다. 없어도 회의는 열리고 녹음은 되고 기여도는 나옵니다. 그래서 클라이언트 생성도 조회도 예외를 안 던집니다 — 진행률 때문에 로비가 통째로 오류 화면이 되면 안 됩니다.

⭐ 키 `teamflow:meeting:{id}:progress` 가 **두 파일에 손으로** 적혀 있습니다. 한쪽만 바꾸면 읽는 쪽이 빈 값을 받고 화면은 영원히 &#34;알 수 없습니다&#34; 라고 말합니다. 그래서 테스트가 **실제로 쓰고 실제로 읽습니다** — `RedisProgress` 로 쓰고 `read_progress` 로 읽어 같은 값이 나오는지 봅니다.

⚠️ 그리고 **같은 결함을 한 층 위에서 반복하지 않게** 했습니다. 읽기 엔드포인트를 만들어 놓고 부르는 화면이 없으면 정확히 결함 47 입니다. 가드가 엔드포인트의 존재가 아니라 **호출**을 셉니다.

### 프런트에도 같은 그물을 쳤습니다 — 그리고 죽은 코드가 걸렸습니다 (`eb36c2c`, 결함 75)

**이 저장소의 대표 실패 방식**입니다 — 결함 47(`renderNav`) · 감사 #8(진행률) · #12(`extract_task_refs`) · #13(확정 테이블) · 결함 63(`DEADLINE_CHANGED`) 이 전부 같은 모양이었습니다. 백엔드에는 `EventType` 생산자 가드를 달았는데 **프런트에는 없었습니다.**

달고 나서 훑으니 여덟이 걸렸고, 그중 하나가 진짜였습니다 — `lib/track/bar.ts` 의 커버리지 비율 막대.

```
판단 코드   109줄
테스트      13개  ✅ 전부 통과
CSS         .cov 규칙 다섯 벌
그리는 화면  0곳
```

⭐ **같은 판단을 두 벌 가지고 있었습니다.** "커버리지가 null 이면 0% 가 아니라 '아직 모릅니다'" 라는 이 프로젝트의 핵심 규칙을 `lobby/room.ts` 가 따로 구현해 **화면에 그리고 있었습니다.** 살아 있는 쪽은 그쪽이고, 테스트가 붙은 쪽은 죽은 쪽이었습니다.

**전제가 사라져서 죽었습니다.** `.cov` 는 "서버가 총량만 준다" 를 전제로 만든 것인데, 그 뒤 **운행도표**가 들어오면서 `track_health()` 가 구멍의 **위치**까지 주게 됐습니다(`d9b1819`). 양만 아는 자리 자체가 없어진 것입니다.

지웠습니다 — 안 쓰는 그림을 남겨 두면 다음 사람이 **위치가 있는 자리에 그것을 씁니다.** ⭐ **지웠는데 번들이 한 바이트도 안 바뀌었습니다**(아무도 안 불렀다는 가장 짧은 증거).

⚠️ **면제에는 근거를 적게 했습니다.** "테스트가 쓰니까 됐다" 는 근거가 아닙니다. 실제로 `labelOf` 는 **지웠다가 되살렸습니다** — 지우고 나서야 그것을 쓰는 테스트가 "`navLinks` 와 `tabsFor` 의 라벨이 같은 표에서 나온다" 를 확인하고 있다는 걸 봤습니다. **죽은 것처럼 보여도 가드를 지탱하는 경우가 있습니다.**

### 이벤트 종류마다 만드는 곳이 있는가 (`c4c10d7`)

### 브라우저 통화 (`docs/15` §4.6·§4.7)

목소리는 서버를 지나가지 않습니다. SDP·ICE 만 오가고 그 다음부터 사람들끼리 직접 연결합니다. 시그널링은 **막는 규칙이 본체**입니다 — 중계 자체는 몇 줄입니다.

| 막는 것 | 왜 |
|---|---|
| 인증·구성원 확인을 `accept()` **앞에서** | 받아 놓고 끊으면 그 사이에 명단이 샌다 |
| `from` 을 본문에서 안 읽음 | 남의 이름으로 연결을 가로챈다 |
| 종류 **허용 목록** (`offer`/`answer`/`ice`) | 거부 목록은 새 종류마다 뚫린다 |
| 본문 16,000자 상한 | 없으면 이 통로로 파일을 보낸다 |
| 방 밖 대상은 조용히 거절 | &#34;있다/없다&#34; 를 달리 답하면 명단을 캐낸다 |
| 나갈 때 **연결 id 로** 뺌 | user_id 로 빼면 새로고침한 자기 자신을 쫓아낸다 |
| 한 사람당 연결 하나 | 탭 둘이면 같은 목소리가 두 트랙에 → 발언량 두 배 |

**캡처 설정이 같은 방 녹음과 반대입니다.** 같은 방에서는 옆 사람 목소리가 내 마이크에 들어오는 것이 정렬의 단서였는데, 원격은 그 누출이 없는 대신 **내 스피커 소리가 내 마이크로 되돌아옵니다.** `echoCancellation`·`noiseSuppression` 은 원격에서만 켜고, `autoGainControl` 은 **양쪽 다 끕니다** — 조용한 사람의 트랙이 증폭되면 발언량이 부풀려집니다.

⚠️ **방은 프로세스 메모리에 있습니다.** 워커를 늘리면 같은 회의의 두 사람이 서로를 못 보고 **오류도 안 납니다.** `test_packaging.py::test_the_api_runs_as_a_single_worker` 로 그물을 쳤습니다.

### 가드가 **너무 좁았습니다** — 기여도 payload 를 아예 안 보고 있었다

&#34;서버가 보내는데 아무 화면도 안 읽는 칸&#34; 가드(결함 93·95·96)의 표에는 셋만 있었습니다 — `TrackHealth`·`RosterEntry`·`FinalRow`. **이 제품에서 가장 큰 payload 인 기여도 점수(`MemberScore`·`Category`)는 표에 없었습니다.**

넣고 돌리니 둘이 걸렸습니다.

```
raw            정규화 전 원점수
evidence_ids   근거가 된 기여 이벤트 번호들
```

둘 다 **안 읽고 있습니다.** 다만 둘 다 결함이 아니라고 판단했고, 이유를 면제 목록에 적었습니다.

* `raw` — 화면은 `team_share`(팀 안에서의 비율)를 보여줍니다. 같은 것을 뜻하는 숫자를 둘 띄우면 사람이 어느 쪽을 믿을지 모릅니다. `capture_confidence` 를 뺀 것과 **같은 이유**입니다
* `evidence_ids` — 근거 **건수**는 `event_count` 로 이미 보여줍니다. 번호 자체는 사람에게 안 읽힙니다(&#34;이벤트 12, 45&#34;). 근거를 펼쳐 보는 화면이 생길 때 읽습니다. **그 화면은 아직 없고, 없는 것을 있는 척 그리지 않습니다**

⚠️ **대신 진짜 위험을 따로 막았습니다.** `event_count` 와 `evidence_ids` 는 `CategoryScore` 가 **각각 따로 받는 두 벌**입니다.

```python
evidence_ids=evidences[uid][category],
event_count=counts[uid][category],
```

갈라지면 화면은 &#34;근거 3건&#34; 이라고 말하고 실제 근거는 2건이 됩니다 — 기여도에서 그건 **&#34;숨겼다&#34;** 로 읽힙니다. 시연 자료로 재 보니 지금은 여덟 칸 전부 일치합니다. 앞으로도 그런지는 `test_scoring.py` 가 봅니다. 검사는 둘입니다 — **개수가 같은가**, 그리고 **그 이벤트의 번호가 맞는가**. 뒤엣것이 없으면 근거를 통째로 엉뚱한 목록으로 바꿔도 통과합니다(되돌림으로 확인했습니다).

### 전수로 훑었고 **없었습니다** — 사람이 적어 넣는 칸이 화면으로 돌아오는가

결함 94(저장된 거부가 동의로 되돌아옴)와 97(남의 조정이 말없이 지워짐)이 같은 부류였습니다. 그래서 **사람이 적어 넣는 칸을 전부** 훑기로 했는데, 그동안 화면 하나씩만 봤지 전수로는 안 봤습니다. 이번에 끝냈습니다.

물은 것은 둘입니다 — **다시 열면 그 값이 보이는가**, **다시 저장하면 남의 것을 지우지 않는가.**

| 어디 | 무엇 | 결과 |
|---|---|---|
| 설정 | 프로젝트 이름 · 저장소 · GitHub 아이디 · 역할 비중 **넷** | 이번에 브라우저로 확인 — **문제 없음** |
| 로비 | 동의 ②③ 체크박스 | 결함 94 에서 확인 |
| 기여도 | 조정 값 · 이유 | 결함 97 에서 확인 |
| 승인 | 후보 제목 · 담당자 · 마감일 · 거절 이유 | 제출 전 초안입니다. **폴링이 덮지 않는지**를 결함 94·97 작업에서 확인했습니다 |
| 녹음 | 화면 꺼짐 방지 | **저장 대상이 아닙니다** — 이 녹음에만 쓰는 선택이고, 시작할 때 읽습니다 |
| 홈·로그인 | 만들기 제목 · 참가 코드 · 이메일 · 비밀번호 | 한 번 쓰고 마는 입력입니다 |

설정 화면이 남아 있던 이유는 **칸이 넷이라 서로 지울 수 있기 때문**입니다. 넷을 하나씩 저장하고 매번 새로 열어 나머지 셋을 다시 읽었습니다.

