## 1. 결정: FastAPI 단일 백엔드

제안서 9장 안을 채택합니다. Spring Boot는 넣지 않습니다.

```
┌─────────────────────────────────────────────────────────────┐
│  Next.js (TypeScript)                                       │
│  대시보드 · 칸반 · 회의 타임라인 · 멀티트랙 녹음 클라이언트   │
└───────────────────────────┬─────────────────────────────────┘
                            │ REST + SSE(진행률)
┌───────────────────────────▼─────────────────────────────────┐
│  FastAPI + Pydantic                                         │
│  인증 · 프로젝트/업무 CRUD · GitHub App 웹훅 수신 · 잡 제출  │
└──────┬──────────────────────────────┬───────────────────────┘
       │                              │
┌──────▼──────────┐          ┌────────▼────────────────────┐
│ PostgreSQL      │          │ Redis (브로커 + GPU 락)      │
│ + pgvector      │          └────────┬────────────────────┘
└─────────────────┘                   │
┌─────────────────┐          ┌────────▼────────────────────┐
│ MinIO / S3      │◄─────────┤ Celery 워커                  │
│ (오디오 원본)    │          │  ├ CPU 워커 (다수)           │
│ ※ 분리 보관     │          │  └ GPU 워커 (동시성 1)       │
└─────────────────┘          └─────────────────────────────┘
```

**Spring Boot를 제외한 이유**: 16주에 소규모 팀입니다. 백엔드를 두 언어로 나누면
경계 API·직렬화·배포·디버깅이 전부 두 배가 됩니다. 이 프로젝트의 무게중심(STT, 화자, 임베딩,
LLM, 예측 모델)은 전부 Python입니다. Spring이 맡을 일은 CRUD뿐인데 FastAPI로 충분합니다.

> Spring 학습 자체가 목적이라면 판단이 달라집니다 → [`10-열린-질문.md`](10-열린-질문.md) Q1

## 2. 핵심 제약: GPU는 하나, 모델은 셋

[`02`](02-모델-선정과-VRAM-예산.md)에서 확인한 대로 **16GB에 ASR + 화자분리 + LLM을 동시에
올릴 수 없습니다.** 이건 아키텍처로 풀어야 합니다.

### 2.1 GPU 배타 락

```python
# Redis 기반 배타 락. GPU 잡은 동시에 1개만.
GPU_LOCK = "gpu:lease"

async def with_gpu(job_id: str, ttl=1800):
    ok = await redis.set(GPU_LOCK, job_id, nx=True, ex=ttl)
    if not ok:
        raise Retry(countdown=30)   # 큐에 되돌림
    try:
        yield
    finally:
        await redis.delete(GPU_LOCK)
```

- Celery **GPU 큐는 `--concurrency=1`** 로 띄웁니다. CPU 큐는 별도로 다수.
- 락에 **TTL 필수** — 워커가 죽으면 GPU가 영구 점유됩니다.
- 진행률은 Redis에 써서 SSE로 프런트에 흘립니다. (1시간 회의 처리에 10분 걸릴 수 있음)

### 2.2 단계별 서브프로세스

PyTorch에서 `del model` 만으로는 VRAM이 안 돌아옵니다.
`gc.collect()` + `torch.cuda.empty_cache()` 를 같이 불러도 단편화가 남습니다.

**가장 확실한 방법은 단계마다 프로세스를 갈아치우는 것입니다.**

```
GPU 잡 = [ 서브프로세스1: 화자분리 ] → [ 서브프로세스2: ASR ] → [ 서브프로세스3: LLM ]
         각각 종료 시 OS가 VRAM을 완전히 회수
```

중간 산출물은 파일/DB로 주고받습니다. 느려 보이지만 **배치 작업이라 상관없습니다.**
그리고 한 단계가 터져도 나머지가 살아 있어 **재시도 단위가 명확해집니다.**

### 2.3 CPU로 내릴 수 있는 것은 내리세요

| 단계 | 배치 | 비고 |
|---|---|---|
| 오디오 전처리 (FFmpeg, 정규화, VAD) | **CPU** | GPU 불필요 |
| 화자 분리 | GPU | |
| ASR | GPU | 가장 무거움 |
| 화자 임베딩 매칭 | CPU | ECAPA-TDNN은 작음 |
| 발언 유형 분류 (KLUE-RoBERTa) | CPU 가능 | 문장 단위, 짧음 |
| 문장 임베딩 (반복 논의 탐지) | CPU 가능 | |
| **LLM 회의록 생성** | **CPU 가능** | 1.2B급 Q4는 llama.cpp로 충분 |

**LLM을 CPU로 내리면 16GB 제약이 갑자기 여유로워집니다.** 배치 처리라 속도가 문제되지 않습니다.
이건 진지하게 검토할 가치가 있습니다.

## 3. 잡 파이프라인

```
[회의 업로드/종료]
   │
   ├─(CPU) 오디오 정규화 · 트랙 정렬 · VAD
   │
   ├─(GPU) 화자 분리                    ※ 멀티트랙이면 대폭 축소
   ├─(GPU) ASR + 타임스탬프
   ├─(CPU) 화자 임베딩 매칭 → 이름 후보
   │
   ├─(CPU) 발언 유형 분류
   ├─(CPU) 문장 임베딩 → 반복 논의 구간
   ├─(CPU) 규칙: 미응답 질문 · 불완전 업무 · 결정 번복 후보
   │
   ├─(GPU/CPU) LLM: 요약 · 결정 · 업무 후보  ← guided decoding
   │
   └─→ [사람 확인 화면] → 승인된 것만 칸반에 등록
```

⚠️ **마지막 화살표가 이 시스템의 안전장치입니다.** AI가 만든 업무는 **후보(candidate)**이고,
사람이 승인해야 실제 `tasks`가 됩니다. 제안서 5장의 워크플로와 동일합니다.
DB 테이블도 `meeting_task_candidates` / `tasks` 로 분리되어 있어야 합니다. (제안서 10장에 이미 있음 ✅)

## 4. GitHub 연동

### 4.1 GitHub **App** (OAuth App 아님)

| | GitHub App | OAuth App |
|---|---|---|
| 권한 | 필요한 것만 세밀하게 | 넓은 스코프 |
| 접근 범위 | 설치된 저장소만 | 사용자가 접근 가능한 **전부** |
| 토큰 | **1시간 TTL** 설치 토큰 | 장기 토큰 |
| 제거 | 즉시 소멸 | 고아 토큰 잔존 |

**남의 팀플 저장소에 접근하는 서비스**입니다. OAuth App이면 "이 서비스가 내 모든 레포를 본다"가
되어 아무도 안 씁니다. 이건 기능이 아니라 **신뢰 문제**입니다.

요청 권한: `Contents: Read`, `Pull requests: Read`, `Issues: Read`, `Metadata: Read`.
**쓰기 권한은 요청하지 마세요.**

### 4.2 웹훅 + 백필

- **웹훅**은 API rate limit을 소모하지 않습니다. 실시간 수집의 기본 경로.
- 다만 웹훅은 **설치 이후 이벤트만** 옵니다. 프로젝트 중간에 연결하면 과거가 비어 있습니다.
  → **최초 연결 시 REST API로 백필(backfill)** 하는 잡이 반드시 필요합니다. (제안서에 없음)
- 웹훅 유실 대비로 하루 1회 정합성 확인 잡을 두면 좋습니다.

### 4.3 이벤트 → 업무 연결

제안서 4.3의 "업무 번호 또는 브랜치명으로 자동 연결"을 3단 폴백으로:

1. 커밋 메시지/PR 본문의 `#123`, `TASK-123` 패턴 → 확정 연결
2. 브랜치명 `feat/123-login` → 확정 연결
3. 위가 없으면 **커밋 diff 임베딩 ↔ 업무 제목/설명 임베딩 코사인 유사도** → 후보 연결(사람 확인)

3번은 pgvector로 처리합니다. 제안서가 pgvector를 넣은 건 좋은 판단입니다.

## 5. 배포

제안서 9장의 `Docker Compose + Nginx` 유지. 다만 **GPU 워커는 별도 컨테이너**로 분리하세요.

```yaml
services:
  web:        # Next.js
  api:        # FastAPI
  worker-cpu: # Celery, concurrency=4
  worker-gpu: # Celery, concurrency=1, deploy.resources.reservations.devices: [gpu]
  postgres:   # + pgvector
  redis:
  minio:
  nginx:
```

⚠️ Blackwell(sm_120) 이미지 주의: **PyTorch 2.7.0+ 이면서 `-cuda12.8-` 태그**여야 합니다.
GPU 워커 컨테이너에는 `NVIDIA_VISIBLE_DEVICES`와 nvidia-container-toolkit 설정이 필요합니다.

**HuggingFace gated 모델**(pyannote community-1)은 토큰이 필요합니다.
`HF_TOKEN`을 시크릿으로 주입하는 경로를 배포 초기에 만들어 두세요. 나중에 하면 꼭 막힙니다.
