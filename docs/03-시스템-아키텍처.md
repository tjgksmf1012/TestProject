## 2. 핵심 제약: GPU는 하나, 모델은 셋

[`02`](02-모델-선정과-VRAM-예산.md)에서 확인한 대로 **10~16GB 어느 쪽이든 ASR + 화자분리 + LLM을
동시에 올릴 수 없습니다.** 이건 아키텍처로 풀어야 합니다.

### 2.1 GPU 배타 락

```python
# Redis 기반 배타 락. GPU 잡은 동시에 1개만.
GPU_LOCK = "gpu:lease"

async def with_gpu(job_id: str, ttl=1800):
    ok = await redis.set(GPU_LOCK, job_id, nx=True, ex=ttl)
    if not ok:
        raise Retry(countdown=30)   # 큐에 되돌림
    try:
        yield
    finally:
        await redis.delete(GPU_LOCK)
```

- Celery **GPU 큐는 `--concurrency=1`** 로 띄웁니다. CPU 큐는 별도로 다수.
- 락에 **TTL 필수** — 워커가 죽으면 GPU가 영구 점유됩니다.
- 진행률은 Redis에 써서 SSE로 프런트에 흘립니다. (1시간 회의 처리에 10분 걸릴 수 있음)

### 2.2 단계별 서브프로세스

PyTorch에서 `del model` 만으로는 VRAM이 안 돌아옵니다.
`gc.collect()` + `torch.cuda.empty_cache()` 를 같이 불러도 단편화가 남습니다.

**가장 확실한 방법은 단계마다 프로세스를 갈아치우는 것입니다.**

```
GPU 잡 = [ 서브프로세스1: 화자분리 ] → [ 서브프로세스2: ASR ] → [ 서브프로세스3: LLM ]
         각각 종료 시 OS가 VRAM을 완전히 회수
```

중간 산출물은 파일/DB로 주고받습니다. 느려 보이지만 **배치 작업이라 상관없습니다.**
그리고 한 단계가 터져도 나머지가 살아 있어 **재시도 단위가 명확해집니다.**

### 2.3 CPU로 내릴 수 있는 것은 내리세요

| 단계 | 배치 | 비고 |
|---|---|---|
| 오디오 전처리 (FFmpeg, 정규화, VAD) | **CPU** | GPU 불필요 |
| 화자 분리 | GPU | |
| ASR | GPU | 가장 무거움 |
| 화자 임베딩 매칭 | CPU | ECAPA-TDNN은 작음 |
| 발언 유형 분류 (KLUE-RoBERTa) | CPU 가능 | 문장 단위, 짧음 |
| 문장 임베딩 (반복 논의 탐지) | CPU 가능 | |
| **LLM 회의록 생성** | **CPU 가능** | 1.2B급 Q4는 llama.cpp로 충분 |

**LLM을 CPU로 내리면 VRAM 제약이 갑자기 여유로워집니다.** 배치 처리라 속도가 문제되지 않습니다.

> ⭐ **RAM 32GB가 확인되어 이게 1순위 전략이 되었습니다.**
> GPU는 ASR + 화자분리만 맡고(~8GB) LLM은 CPU에서 llama.cpp Q4로 돌립니다.
> GPU와 CPU가 **병렬로** 일할 수 있다는 부수 효과도 있습니다 —
> 다음 회의를 전사하면서 이전 회의를 요약합니다.
> → [`02-모델-선정과-VRAM-예산.md`](02-모델-선정과-VRAM-예산.md) §5 전략 C

## 3. 잡 파이프라인

```
[회의 업로드/종료]
   │
   ├─(CPU) 오디오 정규화 · 트랙 정렬 · VAD
   │
   ├─(GPU) 화자 분리                    ※ 멀티트랙이면 대폭 축소
   ├─(GPU) ASR + 타임스탬프
   ├─(CPU) 화자 임베딩 매칭 → 이름 후보
   │
   ├─(CPU) 발언 유형 분류
   ├─(CPU) 문장 임베딩 → 반복 논의 구간
   ├─(CPU) 규칙: 미응답 질문 · 불완전 업무 · 결정 번복 후보
   │
   ├─(GPU/CPU) LLM: 요약 · 결정 · 업무 후보  ← guided decoding
   │
   └─→ [사람 확인 화면] → 승인된 것만 칸반에 등록
```

⚠️ **마지막 화살표가 이 시스템의 안전장치입니다.** AI가 만든 업무는 **후보(candidate)**이고,
사람이 승인해야 실제 `tasks`가 됩니다. 제안서 5장의 워크플로와 동일합니다.
DB 테이블도 `meeting_task_candidates` / `tasks` 로 분리되어 있어야 합니다. (제안서 10장에 이미 있음 ✅)

### 3.x 녹음 수집 API

멀티트랙은 폰이 5초짜리 청크를 계속 올리는 구조입니다. 강의실 와이파이는
끊기고, LTE 로 넘어가고, 엘리베이터를 탑니다. **끊기는 게 예외가 아니라 정상**
이라는 전제로 설계했습니다.

| 엔드포인트 | 성질 |
|---|---|
| `GET /api/time` | 의존성 0. DB 도 안 탄다 — 그 지연이 왕복 추정에 노이즈로 낀다 |
| `POST /api/meetings/{id}/tracks` | **멱등.** 새로고침해도 같은 트랙 |
| `PUT …/tracks/{tid}/chunks/{seq}` | **멱등.** seq 가 주소라 재시도가 안전 |
| `GET …/tracks/{tid}/chunks` | 재개용. **파일시스템**을 본다 |
| `POST …/tracks/{tid}/complete` | 종료 요약. 보고된 커버리지를 실제 청크 수와 대조 |

세 가지가 설계의 핵심입니다.

**① 동의 검사를 서버에서 다시 한다.**
클라이언트 상태 머신이 이미 막지만, 요청은 curl 로도 보낼 수 있습니다.
제3자 녹음은 형사처벌 대상이라 (통신비밀보호법) 서버가 최종 방어선이어야 합니다.
**청크마다** 확인합니다 — 회의 도중에 철회할 수 있기 때문입니다.

**② 파일을 먼저 쓰고 DB 행을 넣는다.**
순서가 반대면, 파일 쓰기가 실패했을 때 서버가 "가지고 있다"고 답하고
클라이언트는 다시 올릴 기회를 잃습니다. 이 순서면 최악의 경우 고아 파일이
남을 뿐이고, 재개 조회가 파일시스템을 보므로 스스로 복구됩니다.

**③ 클라이언트가 보고한 커버리지를 그대로 믿지 않는다.**
클라이언트는 자기가 *만든* 청크 기준으로 계산합니다. 그중 일부는 업로드에
실패해 서버에 없을 수 있습니다. 서버가 받은 것과 대조해 **더 나쁜 쪽**을 씁니다.

## 4. GitHub 연동

### 4.1 GitHub **App** (OAuth App 아님)

| | GitHub App | OAuth App |
|---|---|---|
| 권한 | 필요한 것만 세밀하게 | 넓은 스코프 |
| 접근 범위 | 설치된 저장소만 | 사용자가 접근 가능한 **전부** |
| 토큰 | **1시간 TTL** 설치 토큰 | 장기 토큰 |
| 제거 | 즉시 소멸 | 고아 토큰 잔존 |

**남의 팀플 저장소에 접근하는 서비스**입니다. OAuth App이면 "이 서비스가 내 모든 레포를 본다"가
되어 아무도 안 씁니다. 이건 기능이 아니라 **신뢰 문제**입니다.

요청 권한: `Contents: Read`, `Pull requests: Read`, `Issues: Read`, `Metadata: Read`.
**쓰기 권한은 요청하지 마세요.**

### 4.2 웹훅 + 백필

- **웹훅**은 API rate limit을 소모하지 않습니다. 실시간 수집의 기본 경로.
- 다만 웹훅은 **설치 이후 이벤트만** 옵니다. 프로젝트 중간에 연결하면 과거가 비어 있습니다.
  → **최초 연결 시 REST API로 백필(backfill)** 하는 잡이 반드시 필요합니다. (제안서에 없음)
- 웹훅 유실 대비로 하루 1회 정합성 확인 잡을 두면 좋습니다.

### 4.3 이벤트 → 업무 연결

제안서 4.3의 "업무 번호 또는 브랜치명으로 자동 연결"을 **2단**으로 만들었습니다.
⚠️ 계획은 3단이었는데 **확정으로 치는 범위가 계획보다 좁습니다.**

1. `TASK-12` · `TF-12` → **확정**(`SOURCE_EXPLICIT`)
2. `#12`(이슈 참조) · 브랜치명의 숫자 → **후보**(`SOURCE_ISSUE_REF`·`SOURCE_BRANCH`)

⚠️ **2번을 확정으로 올리지 마십시오.** 이유가 `github/linking.py` 머리말에
있습니다 — `#12` 는 GitHub 이슈 번호이지 우리 업무 번호가 아니고, 브랜치의
숫자는 아무 뜻이나 될 수 있습니다. 틀린 확정은 **기여가 남에게 갑니다.**

임베딩 폴백(계획 3번)은 **만들지 않았습니다** — GPU 가 없고, 그 자리를
사람 확인으로 대신합니다. 코사인 유사도를 쓰는 곳은 `video/speaker.py` 의
성문 매칭 하나뿐입니다.

## 5. 배포

제안서 9장의 `Docker Compose + Nginx` 유지. 다만 **GPU 워커는 별도 컨테이너**로 분리하세요.

```yaml
services:            # 실제 docker-compose.yml — 일곱
  postgres:         # + pgvector
  redis:
  api:              # FastAPI (화면도 여기서 냅니다 — 별도 web 컨테이너 없음)
  worker-cpu:       # celery -Q cpu,gpu --concurrency=2
                    # ⚠️ -Q cpu 만 두면 회의가 'queued' 에서 영원히 멈춥니다
  beat:             # 보존기간 삭제 등 주기 잡
  worker-gpu:       # celery -Q gpu --concurrency=1
  llm:              # vLLM / llama.cpp
  # 오디오는 볼륨 마운트 (별도 볼륨 + 별도 권한)
  # ⚠️ nginx 는 없습니다 — 설정 파일 자체가 저장소에 없습니다
```

**외부 공개가 필요하면 Cloudflare Tunnel을 쓰세요 (무료).**
멀티트랙 녹음의 `getUserMedia()`는 **HTTPS(보안 컨텍스트)에서만 동작**하므로,
팀원 휴대폰이 `http://192.168.x.x`로 접속하면 마이크 권한 요청이 아예 뜨지 않습니다.
```bash
cloudflared tunnel --url http://localhost:3000   # → https://xxx.trycloudflare.com
```
→ [`11-비용-제로-구성.md`](11-비용-제로-구성.md) §3

GPU 워커 컨테이너에는 `NVIDIA_VISIBLE_DEVICES`와 nvidia-container-toolkit 설정이 필요합니다.
CUDA 12.x 계열 PyTorch 이미지면 동작합니다 (Ampere/Ada 세대 기준).
`python3 scripts/check_env.py` 로 실제 하드웨어를 먼저 확인하세요.

**HuggingFace gated 모델**(pyannote community-1)은 토큰이 필요합니다.
`HF_TOKEN`을 시크릿으로 주입하는 경로를 배포 초기에 만들어 두세요. 나중에 하면 꼭 막힙니다.
