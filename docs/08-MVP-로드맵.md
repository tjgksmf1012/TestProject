### 기여도 세 다리 — 전부 이어졌다 (2026-08-07)

기여도는 세 곳에서 이벤트를 받습니다.

| 다리 | 상태 |
|---|---|
| 칸반 업무 완료 → 기여 이벤트 | ✅ 이었음 (`task_service._record_completion`) |
| GitHub 활동 → 기여 이벤트 | ✅ 이었음 (`github_ingest_service`) |
| **회의 발화 → 기여 이벤트** | ✅ **이었음** (`meeting_contribution_service`, 2026-08-07) |

#### 마지막 다리가 왜 비어 있었나 (기록)

`scoring.py` 는 `UTT_DECISION`(5.0) · `UTT_COMMITMENT`(1.5/6.0) ·
`UTT_PROPOSAL`(2.0/5.0) 같은 가중치를 **정확히 알고 있었는데 그 이벤트를
만드는 코드가 없었습니다.** `Utterance.utterance_type` 컬럼도 저장 단계에서
한 번도 채워지지 않았습니다.

즉 **운영에서 회의 기여도는 언제나 0이었고**, 시연 화면의 숫자는
`seed_demo.py` 가 손으로 넣은 것이었습니다. 그래서 아무도 몰랐습니다 —
이 저장소에서 반복해서 나온 "만들어 놓고 아무도 부르지 않은 것" 의
세 번째 사례이고, 하필 **회의 분석 시스템에서 회의 쪽 다리**였습니다.

이건 두 부분이었습니다.

  · **분류기** — KLUE-RoBERTa 파인튜닝. GPU 가 필요해 이 환경에서 불가능
  · **배선** — 분류 결과를 기여 이벤트로 만드는 코드. **분류기와 무관하게**
    없었습니다. 분류기가 생겨도 이 배선이 없으면 여전히 0입니다

**배선을 먼저 했습니다.** 분류기는 규칙 기반 기준선으로 두되 — 그건
9주차 실험의 비교 기준선이기도 합니다 — **무엇이 매겼는지를 기록해
신뢰도에 반영**합니다. 규칙으로 매긴 회의는 학습 모델로 매긴 회의보다
신뢰도가 낮게 나옵니다. 자세한 것은 `docs/15` §4.5.

⚠️ 시연 데이터도 이제 **운영 코드와 같은 함수**를 부릅니다. 손으로
넣으면 시연과 운영이 갈라지고, 실제로 그게 이 결함을 가리고 있었습니다.

### 일정 대비

계획의 0~13주 항목 중 **모델 실행이 필요한 것(8·9·10주)을 뺀 나머지**는
코드와 테스트가 있습니다. 14주(평가 실행)와 15주(배포)는 하드웨어가 있어야
시작할 수 있습니다.

**남은 일의 성격이 두 번 바뀌었습니다.**

처음 계획은 "무엇을 만들 것인가" 였습니다. 그게 대체로 끝나자 남은 것이
**"만든 것을 실제 하드웨어에서 돌려 보는 것"** 이 됐습니다. 그리고
2026-08-07 에 방향이 바뀌면서(`docs/15`) 세 번째가 붙었습니다 —
**"각자 PC 에서 통화하며 회의한다" 를 만드는 것.**

세 갈래가 서로 막지 않습니다.

| 갈래 | 지금 할 수 있나 | 막는 것 |
|---|---|---|
| 이어 붙이기 (GitHub·업무·회의 발화 배선) | ✅ **지금 가능** | 없음 |
| 통화 (시그널링·WebRTC·통화 화면) | 🟡 만들 수는 있음 | **실제로 통화해 볼 수 없음** (네트워크 없음) |
| 모델 실행 (ASR·LLM·분류기) | ❌ | GPU |

그래서 **이어 붙이기가 먼저**입니다. 하드웨어 없이 끝까지 만들고 테스트할
수 있고, 이 프로젝트의 대표 주장(§5.1 의 필수 경로)이 바로 거기서 끊겨
있기 때문입니다.

> **`docs/09` 실험 5(폰이 회의 끝까지 녹음하는가)의 지위가 내려갔습니다.**
> "이 실험이 실패하면 모드 A 자체를 재검토해야 한다" 고 적혀 있었는데,
> PC 브라우저에서는 화면 보호기가 켜져도 탭이 죽지 않고 배터리 세이버가
> 마이크를 끄지 않습니다. **PC 우선이 기술적으로도 더 안전한 선택**이고,
> 실험 5 는 배치 1(같은 방, 폰)에만 적용되는 실험이 됐습니다.

## 1. 왜 조정이 필요한가

제안서 12장은 스스로 이렇게 규정했습니다:
> "졸업작품의 직접 연구 범위는 발언 유형 분류, 비효율 구간 탐지, 코드 활동 분류 중 **1~2개에 집중**한다."

**옳은 판단입니다. 그런데 나머지 장이 이걸 안 지킵니다.**

- 12장 실험 표: **5개**
- 13장 평가 대상: **8개**
- 14장 MVP "반드시 구현" AI 기능: **6개** (STT · 화자 · 발언유형 · 반복 · 미결정 · 업무추출)
- 15장 일정: 이 6개를 **7~10주, 4주 안에**

그리고 15장에 **환경 구축 기간이 0주**입니다.
torch·vLLM·pyannote·transformers 버전 충돌, 모델 다운로드 30~50GB, HF gated 토큰 발급,
그리고 폰 마이크 권한(HTTPS) 확인까지 하면 며칠이 사라집니다.
`python3 scripts/check_env.py` 로 진단부터 하세요.

## 2. 조정된 MVP 범위

### 반드시 구현 (이게 안 되면 프로젝트가 성립하지 않음)

| 영역 | 범위 | 제안서 대비 |

| 기여도 | 이벤트 로그 기반 항목별 지표 + 근거 링크 | + 재계산 구조 |

| 법적 | 3단계 동의 + 오디오 분리 보관 + 보존기간 | ⭐ 신규 |

### 일정이 남으면 (우선순위 순)

1. 반복 논의 구간 탐지 (문장 임베딩 + 클러스터링) — **차별점이라 여기가 1순위**
2. 미응답 질문 / 불완전 업무 탐지 (규칙 기반)
3. 이전 회의 결정 번복 탐지 (임베딩 대조)
4. 업무 편중·위험 경고 (규칙 기반)
5. 교수자 화면
6. 화자 자동 식별 (ECAPA-TDNN 임베딩 매칭)
7. 커밋 diff 작업 유형 딥러닝 분류
8. 프로젝트 지연 예측 모델

### 범위에서 제거

## 3. 왜 "반복 논의 탐지"가 1순위 확장인가

제안서의 기능 중 **가장 독창적**입니다. 검색으로 확인한 결과 일반 협업툴에도,
회의록 서비스에도 이 기능은 없습니다.

그리고 **구현 난이도 대비 효과가 큽니다.**
문장 임베딩 → pgvector 유사도 → 시간축에서 떨어진 유사 클러스터 탐지.
딥러닝 학습 없이 사전학습 임베딩 모델만으로 됩니다.

평가도 가능합니다 — 합성 회의에 반복 구간을 심어두고 IoU로 측정.
([`04-회의-처리-파이프라인.md`](04-회의-처리-파이프라인.md) §5.2)

방향이 바뀐 이유는 사용자의 한 문장입니다.

> "결국 PC 버전이 중요하다. 디스코드처럼 여럿이서 통화를 하는데 그 대화를
> 녹음하고 분석할 수 있고, **깃허브 연동이 가장 중요하다.**"

| 순 | 무엇 | 상태 | 하드웨어 필요? |
|---|---|---|---|
| 1 | GitHub 연결 상태를 보이게 + 소유권 검증 | ✅ **함** (`docs/15` §4.3, 결함 34~37) | 아니오 |
| 2 | **업무 ↔ PR 잇기** (`extract_task_refs` 배선) | ✅ **함** (`docs/15` §4.4, 결함 38·39) | 아니오 |
| 3 | 회의 발화 → 기여 이벤트 배선 | ✅ **함** (`docs/15` §4.5, 결함 40) | 배선 완료 / 분류기 상향은 GPU |
| 4 | 시그널링 WebSocket + 통화 로비 | ✅ **함** (`docs/15` §4.6) | 아니오 |
| 5 | WebRTC 메시 + 헤드폰 확인 | ✅ **함** (`docs/15` §4.7) | 같은 기기 통화는 됨 / **실제 네트워크는 실험 6** |
| 6 | 통화 모드용 캡처 설정 (AEC 켬, AGC 끔) | ✅ **함** (`docs/15` §4.7) | 아니오 |
| 7 | PC 화면 정리 (넓은 화면 활용) | ✅ **함** (`docs/15` §4.7, 결함 41~48) | 아니오 |
| — | PWA·안드로이드 셸 | **보류** (지운 게 아니라 뒤로) | |

> ⚠️ 5번의 "실측 불가" 를 정정합니다. 이전 판은 네트워크가 없어 WebRTC
> 를 확인할 수 없다고 적었는데 **틀렸습니다** — 같은 기기 안의 브라우저
> 컨텍스트끼리는 host 후보로 직접 붙고, 실제로 3인 통화를 띄워
> 확인했습니다. 남은 것은 서로 다른 NAT 뒤에서의 연결이고 그건 실험 6
> 입니다 (`docs/15` §4.7).

**1~3 이 §5.1 의 필수 경로를 끝까지 잇습니다.** 그게 이 프로젝트의 대표
주장이고, 지금 두 군데가 끊겨 있습니다.

```
회의 녹음 → 화자별 자막 → 업무 후보 → 승인 → 칸반
                                              ↓
                                     ✅ 이었음 (순서 2)
                                              ↓
                                     관련 PR 병합 → 업무 카드에 근거
                                              ↓
                                        기여도 화면
     ↑
   ✅ 이었음 (순서 3) — 발언 유형을 매겨 기여 이벤트로
```

**§5.1 의 필수 경로가 끝까지 이어졌습니다.** 남은 것은 모델 실행(GPU)과
통화(네트워크)이고, 둘 다 이 환경에서는 확인할 수 없는 것들입니다.

### 왜 통화(4~6)를 뒤로 미루는가

만들 수는 있지만 **이 환경에서 실제로 통화해 볼 수 없습니다** — 네트워크가
없습니다. 돌려 보지 못한 코드를 쌓아 두면 "테스트는 통과하는데 실제로는
동작하지 않는" 것이 늘어납니다. 이 저장소에서 37번 나온 부류입니다.

반면 1~3 은 **끝까지 만들고 테스트할 수 있습니다.** 확인할 수 있는 것을
먼저 합니다.

## 5. 완성 기준

제안서 14장의 문장을 그대로 유지합니다. 이보다 나은 정의가 없습니다.

> "가장 중요한 완성 기준은 **'회의에서 나온 업무가 실제 칸반과 GitHub 활동으로 이어지는 흐름'**이다."

이 한 흐름이 끝까지 동작하면, 나머지 기능이 절반만 되어도 프로젝트는 성공입니다.
반대로 개별 AI 기능이 다 좋아도 이 연결이 없으면 "회의록 만드는 툴"에 그칩니다.

### 5.1 데모 성공 조건 (18장 시연 시나리오 기준)

```
[필수 경로]
회의 녹음 → 화자별 자막 → "민수가 금요일까지 로그인 API 구현" 업무 후보 생성
        → 승인 → 칸반에 등록 → 관련 PR 병합 → 업무 카드에 수행 근거 표시
        → 기여도 화면에 근거와 함께 반영
```

이 경로가 **끊김 없이** 돌아가는지가 유일한 성공 기준입니다.
시연 전에 이 경로만 20번 반복 테스트하세요.
