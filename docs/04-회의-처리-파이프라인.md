# 04. 회의 처리 파이프라인

**이 문서의 핵심 주장: 멀티트랙 녹음을 1순위 경로로 채택하세요.**
프로젝트에서 가장 위험한 기술 요소(화자 분리 정확도)를 엔지니어링으로 우회할 수 있습니다.

---

## 1. 왜 화자 분리에 서비스를 걸면 안 되는가

pyannote `community-1`은 현존 최고 오픈소스 화자 분리 모델입니다. 그런데:

- AMI 회의 데이터 기준 DER이 개별 헤드셋 마이크 **17.0%**, 방 안의 단일 원거리 마이크 **19.9%**.
  데이터 환경에 따라 **8.9% ~ 46.8%** 까지 벌어집니다.
  (원본 ChatGPT 대화 인용 수치. [pyannote 벤치마크](https://www.pyannote.ai/benchmark)에서 재확인 필요)
- DER 20%가 의미하는 것: **발화 시간의 5분의 1이 잘못 귀속되거나 누락**됩니다.

여기까지는 원본 대화도 짚었습니다. **문제는 그 다음입니다.**

이 프로젝트에서 화자 라벨은 회의록 표시용이 아닙니다.
**기여도 지표의 입력값**입니다. (제안서 6.2: 팀원별 발언 시간·횟수·평균 길이)

> DER 20% → 회의 활동 기여도 지표에 20% 오차가 그대로 들어갑니다.
> 그 점수로 학생들이 다툽니다.

그리고 정확도가 가장 떨어지는 상황이 **하필 대학생 팀플 회의의 기본 조건**입니다:
여러 명 동시 발언 / "네", "맞아요" 같은 짧은 발언 / 노트북 마이크와 거리 / 카페 소음 /
비슷한 또래 목소리 / 빠른 끼어들기.

## 2. 멀티트랙 녹음

```
[단일 마이크 방식]
  노트북 1대 → 혼합 오디오 → 화자 분리 AI → SPEAKER_00/01/02 → 사람이 이름 매핑
  ├ 화자 라벨 정확도: DER 17~20%, 동시 발언에서 급락
  └ 동시 발언: 최대 난제

[멀티트랙 방식]  ← 권장
  팀원 각자 자기 폰으로 회의방 접속 → 각자 브라우저에서 자기 트랙 녹음
  ├ 화자 라벨 정확도: 100% (트랙 = 계정 = 사람)
  └ 동시 발언: 트랙이 분리돼 있으므로 자동 해결
```

### 2.1 오프라인 회의에서도 됩니다

"온라인 회의에서나 되는 거 아니냐"는 오해가 있는데, 아닙니다.
**같은 테이블에 둘러앉아서도 각자 폰을 앞에 놓고 브라우저로 참여하면 됩니다.**
`getUserMedia()` 로 각 기기에서 녹음 → 서버 업로드. 특별한 장비가 필요 없습니다.

### 2.2 화자 분리 AI는 여전히 필요합니다 (역할이 바뀔 뿐)

각 트랙에는 **본인 목소리 + 옆사람 목소리 누출(cross-talk)** 이 함께 담깁니다.
그래서 각 트랙에서 "이 사람이 실제로 말한 구간"만 남겨야 합니다.

**AI 없이 상당 부분 처리됩니다:**
- 같은 시각에 여러 트랙이 활성이면, **에너지가 가장 큰 트랙**이 실제 발화자.
- 트랙 간 상호상관(cross-correlation)으로 누출 여부 판정.
- 트랙별 VAD로 발화 구간 검출.

정밀도를 더 원하면 트랙별로 화자 분리 모델을 돌려 "주 화자 이외 구간"을 제거합니다.
**어느 쪽이든, "이 목소리가 누구인가"를 AI가 맞힐 필요가 없습니다.**

### 2.3 시간 동기화

각 기기의 녹음 시작 시각이 다릅니다. 정렬이 필요합니다.

1. **서버 타임스탬프 기반** — 각 클라이언트가 녹음 시작 시각을 서버 시각으로 보고. 오차 수백 ms.
2. **동기화 비프음** — 회의 시작 시 서버가 신호를 보내 각 기기가 짧은 톤을 재생.
   모든 트랙에서 그 톤을 찾아 정렬. 오차 수십 ms.
3. **상호상관 정렬** — 트랙 간 누출 신호로 오프셋 추정. 후처리로 미세 보정.

**채택: 1 + 3.** 2번(비프음)은 필요 없습니다 — 3번이 이미 신호에서 직접
오프셋을 구하기 때문입니다. 1번은 3번을 **탐색 범위 안으로 들여보내는** 역할입니다.

```
[클라이언트 시각 동기화]  ±수십 ms 로 좁힌다     ← frontend/…/clock.ts
            ↓
[GCC-PHAT]                샘플 단위로 확정        ← audio/multitrack.py
```

> ⚠️ **초안의 "수백 ms 오차는 큰 문제가 아니다"는 틀렸습니다.**
> GCC-PHAT 의 탐색창이 `MAX_PLAUSIBLE_TAU = 0.5초` 로 **유한**합니다.
> 그 밖으로 나가면 미세 보정이 아니라 정렬 실패입니다. 그래서 클라이언트가
> 오차 **상한**을 계산해서 250ms 를 넘으면 녹음을 시작하지 않습니다.

구현 세부 (`frontend/src/lib/recording/clock.ts`):

- NTP 방식으로 왕복을 여러 번 재고 **지연이 가장 짧은 표본**을 씁니다.
  평균을 내면 큐잉 지연이 낀 표본이 추정을 오염시킵니다.
- 오차 상한 = 왕복/2. 편도 지연이 완전히 비대칭이어도 이 값을 넘지 않습니다.
- `Date.now()` 가 아니라 `performance.now()` 로 잽니다. 벽시계는 회의 도중
  OS 의 NTP 보정으로 껑충 뜁니다.
- 기기 크리스털은 ±50ppm 정도 흐릅니다. **1시간이면 180ms** — 탐색창의
  3분의 1 이 넘습니다. 그래서 회의 중에도 5분마다 다시 재고 측정 사이를
  선형 보간합니다.

서버 쪽은 `GET /api/time` 하나입니다. 받은 시각(t1)과 보낸 시각(t2)을 **둘 다**
돌려줘야 클라이언트가 서버 처리 시간을 왕복에서 뺄 수 있습니다.

### 2.4 제안서 관점에서의 이득

| 제안서 항목 | 멀티트랙 도입 효과 |
|---|---|
| 17장 위험 "소음·동시 발언 → STT·화자 오류" | **대폭 완화** |
| 6.2 팀원별 발언 시간·횟수·평균 길이 | **정확한 수치가 됨** (지금은 DER 오차 포함) |
| 6.2 동시 발언·겹침 구간 | **오히려 더 정확해짐** |
| 6.3 질문 후 응답자·응답 시간 | 화자 확정이므로 신뢰 가능 |
| 18장 시연 | **실패 확률 급감** (시연은 실패하면 안 되는 자리) |
| 13장 평가 | 단일마이크 vs 멀티트랙 **DER 비교 실험이 하나 더 생김** |

### 2.5 폴백은 유지하세요

멀티트랙이 불가능한 상황이 있습니다 — 회의 중 일부만 앱을 켰거나, 이미 녹음된 파일을 올리거나.

```
모드 A (권장): 멀티트랙  → 트랙 = 화자, 화자분리는 누출 제거용
모드 B (폴백): 단일 파일 → pyannote community-1 → SPEAKER_XX → 사람이 이름 매핑
```

**두 모드를 다 지원하면 비교 실험이 생깁니다.** 발표에서 "우리는 두 방식을 정량 비교했고
멀티트랙이 DER을 X% 개선했다"고 말할 수 있습니다.

### 2.6 멀티트랙의 진짜 약점 — 폰이 녹음을 멈춘다

멀티트랙 설계에서 실제로 무너지는 지점은 정렬이 아니라 **트랙이 중간에 끊기는 것**입니다.

**iOS Safari 는 화면이 잠기거나 탭이 백그라운드로 가면 `getUserMedia` 오디오를
정지시킵니다.** WebKit 의 오래된 제약이고 2026년 8월 현재도 그대로입니다.
안드로이드 크롬도 배터리 세이버가 공격적이면 비슷한 일이 생깁니다.
회의 중에 카톡 한 번 확인하면 그 사람 트랙이 끊깁니다.

Screen Wake Lock API(Safari iOS 16.4+, 설치형 PWA 는 18.4+)로 화면 잠금은 막을 수
있지만 **홈 버튼을 누르면 그만입니다.** 막을 수 없으니 정확히 알아내는 쪽으로 설계했습니다.

위험한 건 30초를 잃는 게 아니라 **모르고 잃는 것**입니다.

```
[순진한 구현]  청크를 순서대로 이어붙인다
               → 중간 30초가 비면 그 뒤 전체가 30초 앞당겨진다
               → 트랙 정렬이 깨진다 (GCC-PHAT 탐색창의 60배)
               → 에너지 비교로 뽑는 주화자가 전부 틀린다
               → 엉뚱한 사람의 기여도가 된다        ← docs/05 §5
```

조용히 짧아진 트랙 하나가 회의 전체의 화자 판정을 망가뜨립니다. 그래서 청크마다
**동기화된 절대 시각**을 붙이고, 공백을 세 경로로 찾아 서버가 무음으로 메웁니다.

| 원인 | 어떻게 보이는가 | 어떻게 잡는가 |
|---|---|---|
| `recorder_stalled` | 청크가 아예 안 온다 | 청크 간격 vs timeslice |
| `track_muted` | 청크는 오는데 무음이다 | 트랙 `mute`/`unmute` 이벤트 |
| `chunk_lost` | 만들어졌는데 서버에 없다 | 업로드 큐가 포기한 seq |

**커버리지 80% 아래인 트랙은 버리고 사람에게 알립니다.** 폰이 잠긴 사람을
"말을 안 한 사람"으로 처리하면 그건 그냥 오답입니다. 조용히 낮은 점수를 주는 것보다
"이 트랙은 못 씁니다"라고 말하는 게 낫습니다.

> **화면이 가려졌다는 사실만으로 공백을 만들지는 않습니다.** 안드로이드는 화면이
> 꺼져도 계속 녹음되는 경우가 있습니다. 실제 공백은 청크 타이밍과 mute 이벤트로만
> 판정합니다. 추측으로 데이터를 지어내면 그게 또 다른 오답이 됩니다.

### 2.7 브라우저 오디오 가공을 전부 꺼야 합니다

`echoCancellation`, `noiseSuppression`, `autoGainControl` — 통화용 기본값이
여기서는 정확히 반대로 작용합니다.

- **잡음 억제** → 트랙 정렬은 *새어 들어온 옆사람 목소리*로 맞춥니다(§2.3).
  그걸 지우면 정렬할 근거 자체가 사라집니다.
- **자동 게인** → 조용한 트랙을 증폭합니다. 듣고만 있던 팀원이 말한 것으로
  잡히고 기여도가 부풀려집니다.

그런데 `getUserMedia` 의 맨값 제약은 **`ideal` 로 취급**됩니다 — `min`/`max`/`exact`
만 강제고 나머지는 요청일 뿐이라 브라우저가 조용히 무시할 수 있습니다.
그래서 요청한 뒤 `track.getSettings()` 로 실제 적용 여부를 확인하고, 안 꺼졌으면
그 사실을 트랙 메타데이터로 올려 **해당 트랙의 신뢰도를 낮춥니다.**

`exact: false` 로 강제하지 않는 이유는 못 끄는 기기에서 녹음이 아예 시작되지 않기
때문입니다. 아이폰 쓰는 팀원을 회의에서 빼는 것보다 낫습니다.

## 3. 전체 파이프라인

```
1. 회의 시작
   ├─ 참석자 확인 (녹음 동의 필수 → 07 문서)
   ├─ 프로젝트 용어 사전 로드 (팀원 이름, 기술 용어)
   └─ 각 기기 녹음 시작 (멀티트랙) 또는 단일 녹음

2. 전처리 (CPU)
   ├─ FFmpeg: 포맷 통일, 리샘플링 16kHz mono
   ├─ 음량 정규화
   ├─ 트랙 시간 정렬 (멀티트랙)
   └─ VAD: 발화 구간 검출

3. 화자 확정
   ├─ [모드 A] 트랙별 주화자 구간 추출 (에너지 + 상호상관)
   └─ [모드 B] pyannote community-1 → SPEAKER_XX
              → ECAPA-TDNN 임베딩 ↔ 등록 음성 코사인 유사도
              → 임계값 미달은 "알 수 없는 화자"로 남김 (억지 매핑 금지)

4. 음성 인식 (GPU)
   ├─ Qwen3-ASR-1.7B → 텍스트 + 타임스탬프
   ├─ (선택) Qwen3-ForcedAligner-0.6B → 단어 단위 정렬
   └─ 용어 사전 보정 (팀원 이름, 기술 용어)

5. 발화 단위 결합
   └─ 화자 구간 ∩ 단어 타임스탬프 → utterances 레코드

6. 텍스트 분석 (CPU)
   ├─ 발언 유형 분류 (KLUE-RoBERTa 파인튜닝) ← 직접 학습 대상
   ├─ 문장 임베딩 → pgvector → 반복 논의 구간 탐지
   └─ 규칙: 미응답 질문 / 담당자·마감일 없는 업무 / 이전 결정과 모순

7. LLM 구조화 (guided decoding)
   ├─ 입력: 화자별 전사 + 이전 회의 결정 + 현재 칸반 상태
   └─ 출력: 고정 JSON 스키마 (아래 §4)

8. 사람 확인
   └─ 승인된 것만 tasks / decisions 로 확정 등록
```

## 4. LLM 출력 스키마 — 프롬프트가 아니라 타입으로 강제

```python
from pydantic import BaseModel, Field
from typing import Literal

class TaskCandidate(BaseModel):
    title: str
    assignee_hint: str | None       # 전사에 등장한 이름 그대로. ID 매핑은 서버가 함
    deadline: str | None            # ISO 8601 또는 None
    confidence: float = Field(ge=0, le=1)
    evidence_utterance_ids: list[int]   # ← 근거 없는 항목 금지

class Decision(BaseModel):
    content: str
    supersedes: int | None          # 이전 결정 ID (번복 추적)
    evidence_utterance_ids: list[int]

class MeetingAnalysis(BaseModel):
    summary: str
    decisions: list[Decision]
    tasks: list[TaskCandidate]
    unresolved_issues: list[str]
    next_agenda: list[str]
```

**vLLM + xgrammar guided decoding**으로 이 스키마를 강제합니다.
JSON Schema에서 문법을 만들어 매 토큰마다 마스크를 씌우므로 **스키마 이탈이 원리적으로 불가능**합니다.
2026년 권장 백엔드가 xgrammar이고, **같은 스키마를 반복 사용할 때 캐싱 이득이 큽니다.**
이 프로젝트는 항상 같은 스키마를 씁니다.

> ✅ **구현 완료** — `backend/teamflow/meeting/schema.py`
> Pydantic 모델 + `json_schema()` 로 guided decoding 백엔드에 바로 넘길 수 있습니다.
> 담당자·마감일은 LLM이 **전사 표현 그대로** 넘기고(`assignee_hint`, `deadline_hint`),
> 실제 user_id·날짜 변환은 서버가 합니다 (`resolve.py`).
> LLM에게 날짜 계산을 시키면 회의일 기준을 자주 틀리고, 결정적이지도 않기 때문입니다.

### 4.1 `evidence_utterance_ids` 가 핵심입니다

제안서 6.6의 `"모든 리뷰에 시간 구간과 원문 발언을 근거로 연결"` 을 **스키마 수준에서 강제**하는 장치입니다.

- 이러면 환각이 UI까지 도달하지 못합니다. 제안서 17장 "LLM 환각" 대응이 실제로 작동합니다.

> ✅ **구현 완료** — `backend/teamflow/meeting/validation.py`

> `rejection_rate` 를 함께 노출하는데, **이 값이 높으면 모델·프롬프트에 문제가 있다는 신호**입니다.

>

> LLM 호출부만 페이크라 **GPU 없이도 전체 흐름이 검증됩니다.**

### 4.2 긴 회의 처리

1시간 회의 = 한국어 기준 대략 9,000~15,000 토큰. 프롬프트+출력까지 32K 컨텍스트가 필요하고,
KV 캐시만 수 GB를 먹습니다. ([`02`](02-모델-선정과-VRAM-예산.md) §2.1)

**계층적 처리로 컨텍스트 요구를 낮추세요:**
```
회의 → 10분 청크로 분할 → 청크별 부분 분석 → 부분 결과를 병합해 최종 요약
```
청크 경계에서 업무가 잘릴 수 있으니 **청크를 1~2분 겹치게** 자릅니다.

## 5. 평가

제안서 13장을 유지하되, 지표 우선순위를 명시합니다.

| 기능 | 지표 | 우선순위 메모 |
|---|---|---|
| 음성 인식 | **CER** (WER 아님) | 한국어는 교착어라 CER로 평가 |
| 화자 구분 | DER | 모드 A vs 모드 B 비교 |
| 발언 유형 | Macro F1 + Confusion Matrix | 유형 불균형 고려 |
| 반복·미결정 구간 | Precision/Recall/F1 + IoU | 정답 구간은 합성 회의로 확보 |
| 업무·결정 추출 | Entity F1 / Relation F1 | **recall 가중** — 아래 참조 |

### 5.1 업무 추출은 recall을 우선하세요

업무 하나를 놓치면 **그 담당자의 기여도가 통째로 누락**됩니다.
반대로 잘못 뽑힌 업무는 승인 화면에서 사람이 지우면 끝입니다.

> **과다 추출 후 사람이 지우는 게, 과소 추출 후 사람이 찾아 넣는 것보다 낫습니다.**

2026년 기준 회의록 평가에서도 "action item **completeness**가 결정적 차원"으로 보며,
'원본 전사의 모든 action item이 **담당자와 마감일과 함께** 요약에 등장하는가'를 루브릭으로 채점합니다.

### 5.2 정답 데이터 확보 — 합성 회의를 쓰세요

제안서 12장의 "합성 시나리오 회의"와 18장의 "의도적으로 포함할 장면"은 같은 아이디어입니다.
**이 둘을 연결하면 평가 데이터 문제가 풀립니다.**

```
시나리오 대본 작성 (결정 번복, 미응답 질문, 담당자 누락, 반복 논의를 의도적으로 배치)
  → 팀원들이 연기해서 녹음
  → 대본이 곧 정답 라벨 (구간 시각까지 포함)
  → IoU, Entity F1 계산 가능
```

실제 회의 녹음은 라벨링 비용이 크지만, **합성 회의는 정답을 먼저 만들고 녹음**하므로
라벨링 비용이 거의 0입니다. 10~15건이면 평가셋으로 충분합니다.
실제 회의 5~10건을 섞어 일반화 성능도 같이 봅니다.
