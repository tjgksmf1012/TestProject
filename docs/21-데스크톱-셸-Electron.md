# 21. 데스크톱 셸 (Electron) — 결정과 Phase 0~2

인계받은 「Electron 데스크톱 앱 개발 기술 자료집」(2026-08-11)을 이 저장소에
적용하면서 **자료집과 다르게 정한 것**과 **자료집이 사실과 다른 곳**을
적습니다. 자료집 자체를 여기 옮겨 적지는 않습니다 — 그건 두 벌이 됩니다.

---

## 1. 왜 Electron 인가 — 이유는 하나뿐입니다

화면을 예쁘게 하려는 것이 아닙니다. **브라우저가 못 고치는 결함 하나**
때문입니다.

    창을 내리거나 화면이 잠기면 녹음이 끊긴다.

`docs/17` 이 이 제품에서 제일 비싼 실패로 적어 둔 것입니다 — **녹음이 한 번
끊기면 그 구간은 영영 못 잽니다.** 그리고 그 구간이 없으면 그 사람의 회의
기여는 "측정 불가" 가 되고, 이 저장소는 측정 불가를 0점으로 만들지 않기로
정해 뒀으므로(`docs/05` §4.1.1) 결국 **팀 전체의 신뢰도가 내려갑니다.**

브라우저에서는 이걸 고칠 방법이 없습니다. 백그라운드 스로틀링을 정하는
것은 브라우저이지 우리가 아닙니다. Electron 에서는 `powerSaveBlocker` 와
`backgroundThrottling: false` 로 막을 수 있습니다.

⚠️ **그것 말고 다른 이유로 Electron 을 늘리지 마십시오.** 트레이·자동
실행·딥링크는 있으면 좋은 것이고, 그것만 보고 셸을 하나 더 두는 것은
`docs/15` 가 안드로이드 셸을 접었던 이유와 같은 실수입니다.

---

## 2. ⚠️ 자료집이 이 저장소에 대해 틀린 것

자료집은 좋은 문서인데, **이 저장소를 안 보고 쓴 부분**이 있습니다. 세어
보고 확인한 것만 적습니다.

| 자료집이 말한 것 | 실제 |
|---|---|
| "기존 **Vite+React** 코드는 renderer 로 그대로 재사용" | **Vite 를 안 씁니다.** esbuild + 손으로 쓴 `frontend/build.mts` 뿐입니다 |
| "권장: 이미 Vite+React 앱이 있으므로 **electron-vite**" | 그 권고의 전제가 없습니다. 아래 §3 참조 |
| `src/` 가 renderer (SPA 가정) | **SPA 가 아닙니다.** `public/*.html` **열여섯 장**짜리 MPA 이고, 화면마다 진입점이 따로 있습니다 |
| "최신 안정은 **Electron 42**" | npm 기준 **43.4.0** 입니다(메이저 39·40·41·42·43 이 있음). 한 메이저 낡았습니다 |

**교훈은 자료집을 탓하자는 것이 아닙니다.** 이 저장소의 규칙 그대로입니다 —
**문서에 적힌 것을 그대로 믿지 말고 세어 보십시오.** 저 넷 중 셋은
`frontend/package.json` 을 열어 보면 30초에 확인됩니다.

### 확인하지 못한 것은 확인 못 했다고 적습니다

자료집의 아래 값들은 **이 환경에서 검증할 수 없었습니다.** 그대로 옮겨
적으면 다음 사람이 검증된 사실로 읽습니다.

- 시스템 오디오 loopback 이 `Electron >= 31.0.1` 을 요구한다는 것 — 오디오
  장치가 없어 못 재 봤습니다
- Chromium 이 `autoGainControl: false` 를 무시하는 회귀(이슈 327472528)
- Azure Trusted Signing 월 $9.99 · Apple Developer 연 $99 — 가격·자격
  요건은 **가입 직전에 공식 문서에서 다시 보십시오.** 2025~2026 사이
  정책이 바뀌는 중이라고 자료집도 적어 두었습니다

## 3. 정한 것

### 3.1 electron-vite 를 **안 씁니다** — esbuild 그대로

자료집의 권장이지만 그 근거("이미 Vite 를 쓴다")가 이 저장소에 없습니다.
도입하면 **번들러가 두 벌**이 되고, 이 저장소가 반복해서 당한 실패 ②
그대로입니다.

`build.mts` 에 `buildDesktop()` 을 한 줄기 더했습니다 — main·preload 를
같은 esbuild 로 만듭니다. 새 도구 0개, 새 설정 파일 0개.

    npm run build   →  화면 15개 + 오프라인 목록 + 데스크톱 셸 2개

### 3.2 `frontend/electron/` 에 둡니다 (루트 `desktop/` 이 아니라)

루트에 두면 예전 `android/` 와 나란해 보기 좋았을 텐데, 그 셸은
Kotlin·Gradle 이라 **아무것도 공유할 수 없어서** 따로 있던 것입니다.
데스크톱 셸은 같은 esbuild·같은 tsconfig·같은 `npm test` 를 씁니다.
나란함은 겉모습이고 공유는 실질입니다.

⚠️ 그 안드로이드 셸은 **접고 지웠습니다**(2026-08-13). 이제 셸은
**PC 웹 + PC 앱** 둘입니다 — 아래 §6.

### 3.3 `file://` 이 아니라 **서버 주소**를 띄웁니다

화면이 `/api/...` 를 `credentials: 'same-origin'` 으로 부릅니다. `file://`
로 열면 **로그인부터 안 됩니다.**

그래서 이 창은 **원격 코드를 실행합니다.** 그 결과가 §3.4 입니다.

주소는 `TEAMFLOW_SERVER_URL` 로 받습니다. 코드에 박으면 다른 팀은 앱을
다시 빌드해야 합니다.

⚠️ **평문 http 는 loopback 에서만.** 안드로이드 셸의
`network_security_config.xml` 과 같은 규칙입니다 — 회의 음성과 세션 쿠키가
평문으로 나가면 안 되고, 그건 셸이 무엇이든 같습니다.

### 3.4 보안 기본값은 **협상 대상이 아닙니다**

원격 코드를 돌리는 창이므로, 아래는 "권장" 이 아니라 **서버가 뚫렸을 때
사용자 기계를 지키는 유일한 벽**입니다.

    contextIsolation: true · nodeIntegration: false
    sandbox: true · webSecurity: true
    setWindowOpenHandler → deny · will-navigate → origin 밖이면 차단
    권한은 기본 거절, 마이크만 우리 origin 에서

`guards.test.ts` 의 `데스크톱 셸 (Electron)` 이 여섯 항목으로 지킵니다.
**넷을 심어 보고 전부 잡히는 것과 되돌림을 확인했습니다.**

### 3.5 판단은 `src/lib/desktop/` 에, main 은 부르기만

main 프로세스에는 자동 검사가 안 붙습니다. "어떤 주소가 허용인가",
"바깥 링크를 열어도 되는가" 를 거기 두면 **검증 밖으로 나갑니다.**
화면(`src/demo/**`)과 판단(`src/lib/**`)을 가른 것과 같은 이유입니다.

## 4. Phase 0 — 지금 되는 것

    npm --prefix frontend run build     # 화면 + 셸
    TEAMFLOW_SERVER_URL=http://127.0.0.1:8811/home.html \
      npm --prefix frontend run desktop

창이 뜨고 **서버의 화면 열여섯 장이 그대로 돕니다.** 로그인·칸반·기여도
전부 브라우저와 같습니다.

### 눈으로 보고 재서 확인한 것

Xvfb 로 실제 실행해 확인했습니다(`Playwright _electron`).

| 무엇 | 결과 |
|---|---|
| 창이 뜨고 화면이 그려지는가 | ✅ 로그인 → 칸반 카드 4장 |
| preload 다리가 실제로 도는가 | ✅ `{shell:1, platform:'linux', electron:'43.4.0'}` |
| **격리가 진짜 걸렸는가** | ✅ 창 안에서 `require`·`process`·`module` 전부 `undefined` |
| 바깥으로 못 나가는가 | ✅ `location='https://example.com'` 을 실행해도 주소 그대로 |
| 콘솔 오류 | 0건 |

⚠️ **설정 파일을 읽어서 "켜져 있다" 고 한 것이 아니라, 돌아가는 창 안에서
쟀습니다.** 설정은 켜 놓고 다른 이유로 안 걸리는 경우가 있습니다.

## 4.5 Phase 1 — 셋 중 둘은 **이미 돌고 있었습니다**

Phase 1 을 시작하면서 **먼저 세어 봤습니다.** 로드맵이 셋으로 적어 둔 것
중 둘은 브라우저 시절에 이미 만들어져 있었고, 데스크톱 앱은 같은 화면을
띄우므로 그대로 돕니다.

| Phase 1 항목 | 실제 |
|---|---|
| 무처리 제약 | ✅ 있었음 — `capture.MULTITRACK_AUDIO_CONSTRAINTS`, `browser-adapter` 가 적용 |
| `getSettings()` 검증 | ✅ 있었음 — `client.ts:200` 이 부르고 녹음 화면이 경고를 그림 |
| **청크 디스크 append** | ❌ 없었음 → **이번에 만들었습니다** |

⚠️ 문서가 "아직 안 한 것" 이라고 적어 뒀다고 그대로 믿고 다시 만들면
같은 판단이 두 벌이 됩니다(대표 실패 ②). **세어 보고 시작하십시오.**

### 무엇을 고쳤는가 — 포기한 청크가 **소리를 잃지 않게**

`UploadQueue` 는 여섯 번 시도하고 실패하면 그 seq 를 `lost` 로 적고,
`buildTimeline` 이 그 자리를 공백으로 그립니다. **그 소리는 영영
없습니다.** 브라우저에서는 그게 최선입니다 — 붙잡아 둘 곳이 없습니다.

데스크톱 앱에는 디스크가 있습니다. 서버가 3분 꺼져 있었다는 이유로 회의
한 구간을 잃는 것은 이 셸이 존재하는 이유와 정면으로 어긋납니다.

    renderer                          main
    ─────────────────────────────     ────────────────────────────
    UploadQueue.enqueue()
      └ store.put(seq, atMs, bytes) → chunk:put
                                        └ chunk-paths.sessionDirName()
                                        └ chunk-paths.chunkFileName()
                                        └ writeFile(userData/chunks/…)
    올라감 → store.drop(seq)        → chunk:drop
    포기함 → parked                    (파일은 그대로 남습니다)

- **`parked` 는 `lost` 에서 빠지지 않습니다.** 지금 이 순간 서버에 없다는
  사실은 똑같고, 타임라인은 서버가 가진 것을 그립니다. `parked` 는
  "되찾을 수 있다" 만 더합니다
- **보관소가 없으면(브라우저) 동작이 예전과 한 글자도 다르지 않습니다**
- **디스크에 못 적었으면 `parked` 라고 하지 않습니다** — "이 컴퓨터에
  남아 있습니다" 가 거짓이면 사람은 되찾으려다 못 찾습니다
- 녹음 화면에 **다시 올리기 버튼**을 같이 뒀습니다. 알려만 주고 할 자리를
  안 주면 대표 실패 ③ 입니다

### ⚠️ renderer 는 **경로를 못 줍니다**

이 창은 서버가 준 코드를 돌립니다. 경로를 받는 IPC 를 하나라도 열면 그게
곧 임의 파일 쓰기입니다. 그래서 회의 id 만 건너가고, 폴더와 파일 이름은
`src/lib/desktop/chunk-paths.ts` 가 정합니다.

- 회의 id 는 **허용 집합**(`[A-Za-z0-9_-]{1,64}`)으로만 통과시킵니다.
  `..` 를 걸러내는 식으로 짜면 `%2e%2e`·`....//` 로 계속 뚫립니다
- 통과 못 하면 **던집니다.** 슬러그로 고쳐 주면 서로 다른 두 회의가 같은
  폴더를 쓰게 됩니다
- 파일 이름이 `seq` 와 `atMs` 를 **둘 다** 들고 있습니다(`c7@1700….chunk`).
  목록 파일을 따로 두면 하필 **크래시 직후**에 둘이 갈라집니다
- 확장자는 `.webm` 이 아니라 `.chunk` — 청크 하나는 스트림 중간 조각이라
  재생되지 않습니다. `.webm` 이면 사람이 눌러 보고 "녹음이 깨졌다" 는
  틀린 결론을 냅니다
- 자리수를 채워 글자순으로 정렬하지 **않습니다.** `c999999` → `c1000000`
  에서 글자순과 숫자순이 갈라집니다

### 돌아가는 창에서 잰 것

    보관소     : put → list [{seq:7, atMs:1700000000123, byteLength:5}]
                 get → 1,2,3,4,5   drop → 남은 것 0
    경로 잠금  : ../../evil: 막힘 / a/b: 막힘 / ..: 막힘

⚠️ 정상 경로(`smoke`)가 **통과하는 것을 같이 확인**했습니다. 전부 던져서
막힌 것과 구별이 안 되면 그 측정은 아무 말도 못 합니다.

## 4.7 Phase 2 — 화면을 꺼도 녹음이 삽니다

이 셸이 존재하는 유일한 이유가 이번에 들어왔습니다.

| 무엇 | 어디 | 왜 이렇게 |
|---|---|---|
| `backgroundThrottling: false` | 창 설정 | 창을 내리면 Chromium 이 타이머를 조여, 업로드 큐·시각 재동기화가 굶습니다 |
| `powerSaveBlocker` | `main/awake.ts` | ⚠️ **`prevent-app-suspension`** — 화면은 자게 두고 앱만 살립니다. 화면을 켜 두는 것은 목적이 아니라 막으려던 낭비입니다 |
| 잡고 놓는 장부 | `src/lib/desktop/awake.ts` | 부르는 쪽이 원격 코드라 hold·release 횟수를 못 믿습니다 — 참조 계수 + 음수 방지 |
| 언제 잡는가 | `src/lib/platform/awake.ts` | `recording`·`interrupted`·`stopping` 에서만. **항상 켜면 배터리만 탑니다.** `interrupted` 에서도 잡습니다 — 놓으면 기계가 잠들어 되살아날 기회가 사라집니다 |
| 화면 배선 | `demo/main.ts` | 시작 버튼이 아니라 **`onStateChange` 국면**으로 — 백프레셔·동의 철회처럼 화면을 안 거치는 정지 경로에서도 놓이게 |

`keepsAwake` 는 이제 **참**이고, 녹음 화면이 "화면을 꺼도 녹음이
이어집니다" 라고 말합니다. ⛔ **blocker 배선을 지우면 이 값도 같은
커밋에서 거짓으로** — `guards.test.ts` 의 짝 가드가 셋(main 의 blocker ·
`backgroundThrottling` · 화면의 `shouldHoldAwake`)을 잽니다.

### 돌아가는 앱에서 잰 것

`hold()`/`release()` 가 돌려주는 값은 main 이
`powerSaveBlocker.isStarted()` 로 **OS 를 다시 물어** 준 것입니다.

    절전 방지 : hold→켜짐 · hold→그대로 · release→아직 켜짐 ·
                release→꺼짐 · release 남발→그대로 꺼짐   (장부 의미 그대로)
    안전 배너 : "화면을 꺼도 녹음이 이어집니다. 앱을 완전히 닫지만 마세요."

⚠️ 창 최소화·hide 는 이 환경에서 걸 수 있지만 **실제 절전·화면 잠금은
못 겁니다**(§5 표). 그건 실기기에서만 재집니다.

## 4.8 녹음 생존율 — 재자마자 결함이 나왔습니다 (결함 173)

자료집 §12 의 생존율 테스트를 smoke 에 붙였습니다 — 가짜 마이크
(`--use-fake-device-for-media-stream` + `--use-file-for-fake-audio-capture`,
WAV 는 smoke 가 직접 만듭니다)로 **실제 녹음**을 돌리고, 녹음 중에 창을
`hide()` 한 채 청크 수를 셉니다.

    생존율 : 보이는 채 6.5초 → 1개 · 숨긴 채 11초 → 3개 (국면: 녹음 중)
             coverage 100.0% · 공백 0.0초

숨겨도 청크가 늘고 국면이 「화면이 가려짐」 으로 안 빠지는 것 — 그것이
`backgroundThrottling: false` 가 참말이라는 증거입니다. 설정 파일을 읽는
것으로는 이것을 알 수 없습니다.

⚠️ **첫 측정은 coverage 85.9% 였습니다.** 창 숨김 때문이 아니라,
`MediaRecorder.stop()` 이 정지 **뒤에** 흘려보내는 마지막 조각을 세션과
큐가 둘 다 버리고 있었습니다 — 회의의 끝 5초가 매번 사라지는, 브라우저·
데스크톱 공통 결함(173). 고치고 다시 재서 100.0% 입니다. 전문은
`docs/17` 173.

⚠️ 번들을 다시 만들었으면 `rm -rf ~/.config/Electron` — 서비스 워커가
옛 번들을 물고 있어, 고친 코드가 아니라 **고치기 전 코드를 재게** 됩니다.
(두 번째로 당했습니다.)

### 5.1 Phase 4 — 재개는 **절반씩 이미 있었습니다** (2026-08-19)

⚠️ 위 표는 오래 "아직 안 한 것" 이라고 적어 두고 있었지만, 실제로는 서버
엔드포인트(`GET …/chunks`)도 클라이언트 큐(`UploadQueue.resumeWith`)도
테스트까지 갖춰져 있었습니다. **둘을 잇는 코드만 없었습니다** — 이
저장소의 대표 실패 ①이고, §4.5 가 경고한 것과 같은 모양입니다.

- `RecordingClient.resumeFrom()` 을 두고 녹음 화면의 `online` 에서 부릅니다.
- ⚠️ **새로고침 직후에 부르면 안 됩니다** — seq 가 0부터 다시 시작하므로
  서버가 가진 목록을 그대로 건너뛰면 **새 소리를 버립니다.** 국면 판단은
  `resumeFrom` 안에 있습니다 (결함 176).
- **tus 는 안 들였습니다.** 필요한 능력(어디까지 받았나 묻고 중복을
  건너뛰기)이 이미 있고, 프로토콜을 갈아 끼우는 것은 의존성만 늘립니다.

그리고 이걸 실제 브라우저로 돌려 보다가 **결함 175** 가 나왔습니다 —
청크가 **한 개도** 서버에 안 올라가고 있었습니다(소수 밀리초 → 422).
Phase 4 를 "이미 됐다" 로 넘겼다면 못 찾았을 것입니다.

### ⚠️ Phase 1 에서 제일 조심했던 것 (끝났습니다)

자료집이 제일 크게 경고하는 것이고, 이 제품의 **전제조건**입니다.

> `echoCancellation`·`noiseSuppression`·`autoGainControl` 을 `false` 로
> 걸어도 **Chromium 이 무시하는 경우가 있습니다.**

그래서 제약을 걸고 끝내면 안 되고, **매번 `track.getSettings()` 로 실제
적용값을 확인**하고 안 꺼졌으면 화면에 경고를 띄워야 합니다. GCC-PHAT 는
누출이 보존돼 있다는 전제 위에 서 있습니다 — 그 전제가 조용히 깨지면
정렬이 전부 헛것이 됩니다.

이건 "나중에 검증" 이 아니라 **기능으로 넣어야 하는 것**입니다.

### ⚠️ Phase 1 은 `index`·`call` 을 건드립니다

그 둘은 **일부러 React 로 안 옮긴 화면**입니다(`docs/19` §24.9) — 화면이
아니라 장치를 붙잡고 있는 것이라, 수명 관리를 옮겨 적으면 같은 판단이 두
벌이 됩니다. 데스크톱 녹음 경로를 더할 때도 같은 함정이 있습니다.
`lib/platform/` 로 **인터페이스를 하나 두고 구현을 갈라야** 하지, 화면을
복제하면 안 됩니다.

## 6. 웹·데스크톱 — 무엇이 남는가

| 셸 | 상태 | 왜 |
|---|---|---|
| 웹 (PWA) | ✅ 계속 | 설치 없이 열림. 시연의 기본 경로 |
| 데스크톱 (Electron) | 🟡 Phase 2 | **녹음이 안 끊기게** 하는 유일한 길 — 절전 방지까지 들어옴 |

⚠️ **안드로이드 셸은 지웠습니다**(2026-08-13, `docs/14`). 이 표에 한 줄로
남겨 두면 "멈춘 것" 과 "없는 것" 이 섞입니다 — 없는 것은 표에서 뺍니다.

데스크톱 셸이 생겼다고 웹을 접지 않습니다. 회의에 들어오는 사람이 전부
앱을 깔아야 한다면 그건 회의 도구로서 실패입니다 — **녹음하는 사람만**
데스크톱이 필요합니다.
