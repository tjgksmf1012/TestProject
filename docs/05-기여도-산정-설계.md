# 05. 기여도 산정 설계

기반: ChatGPT 대화의 가중치 표 + 제안서 7장 + CATME 선행연구

**설계 원칙 (제안서 8장에서 그대로 가져옴):**
> 계산은 근거 기반, LLM은 설명 담당. LLM이 기여도를 임의로 결정하지 않는다.

---

## 1. 가장 중요한 결정: 점수를 저장하지 말고 재계산하세요

제안서 10장의 `analytics(scope, metric, value, period)` 스키마는 **계산 결과만** 저장합니다.
이러면 나중에 "왜 이 점수인가"를 재현할 수 없고, 가중치를 바꾸면 과거와 현재가 뒤섞입니다.
제안서 7장의 `"항목별 가중치와 산출 근거 공개"` 약속을 지킬 수 없게 됩니다.

```
점수 = f(불변 이벤트 로그, 가중치 버전, 역할)
```

- **이벤트는 append-only.** 수정·삭제 없음. 모든 활동은 `contribution_events`에 한 줄로 남습니다.
- **점수는 순수 함수의 출력.** 언제든 다시 계산할 수 있습니다.
- **모든 점수에 근거 이벤트 ID가 붙습니다.** 화면에서 클릭하면 원본 커밋/발화/업무로 갑니다.
- 가중치를 바꾸면 **전 기간을 재계산**합니다. 과거 점수가 오염되지 않습니다.

스키마: [`06-데이터-모델.md`](06-데이터-모델.md)

## 2. 무엇을 세는가 — 조작 저항성 중심으로

ChatGPT 대화의 문제 제기가 정확합니다:
> A: 오타 수정 커밋 30개 / B: 로그인 기능 전체 구현 커밋 3개
> 커밋 수만 보면 A가 높지만 실제 기여도는 B가 크다.

제안서 17장도 "GitHub 활동의 양적 왜곡 — 커밋 수 조작 가능"을 위험으로 잡았습니다.
대응책을 구체화합니다.

### 2.1 코드 기여

| 세는 것 | 세지 않는 것 | 이유 |
|---|---|---|
| **병합된 PR 수** | 커밋 수 | 커밋은 쪼개기 쉽고 PR은 어렵습니다 |
| PR당 리뷰 승인 여부 | 셀프 머지 | 리뷰를 거친 코드에 가중 |
| **남에게 준** 리뷰 코멘트 수 | 받은 코멘트 수 | 리뷰는 명백한 기여 |
| 유의미한 diff 라인 | 전체 diff 라인 | 아래 필터 참조 |
| 테스트 코드 추가 | | 제안서 7장이 이미 언급 ✅ |
| 이슈 생성·해결 | | |

**diff 라인에서 반드시 제외할 것** (이걸 안 하면 지표가 무의미해집니다):
```
lock 파일        package-lock.json, poetry.lock, yarn.lock, *.lock
생성 코드        *.pb.go, *_generated.*, migrations/ (자동생성분)
vendored         node_modules/, vendor/, third_party/
바이너리·에셋    *.png, *.jpg, *.pdf, *.zip, 폰트
포맷팅만 변경     공백/개행만 바뀐 hunk
대량 이동        파일 이동/리네임 (내용 동일)
```
→ `.gitattributes` 의 `linguist-generated` 규칙을 참고하거나 직접 목록을 관리하세요.

**PR당 상한(cap)을 두세요.** `MAX_LINES_PER_PR = 400`.
초기 스캐폴딩 PR 하나가 전체를 삼키는 것을 막습니다.

> ⚠️ **구현하면서 발견한 함정 — 고정 기본점을 주지 마세요.**
>
> 초기 산식은 병합 PR마다 고정 8점을 줬습니다. 조작 저항성 테스트에서
> **오타 PR 30개(250점)가 실제 기능 구현 1개(44점)를 이겼습니다.**
> 커밋 단위 조작 문제를 PR 단위로 옮겨놨을 뿐이었습니다.
>
> **이벤트 개수에 비례하는 보상은 무엇이든 개수 늘리기로 뚫립니다.**
> 점수는 개수가 아니라 실질 분량만 따라가야 합니다.
>
> 억제 장치 3개를 함께 씁니다 (`backend/teamflow/contribution/`):
> 1. 고정 기본점 없음 — `30 · (1−e^(−lines/150))`
> 2. 사소 변경 감쇠 — 파일당 2줄 이하는 가중치 0.25배
> 3. 카테고리 천장 — `raw = S · (1−e^(−points/S))`
>
> 실측 결과와 한계: [`09-리스크와-검증-실험.md`](09-리스크와-검증-실험.md) 실험 4

**작업 유형 분류** (제안서 4.3): 기능 / 버그 수정 / 리팩터링 / 테스트 / 문서.
MVP는 **커밋 메시지 규칙(Conventional Commits) + diff 경로 휴리스틱**으로 시작하고,
여유가 있으면 임베딩 기반 분류로 올립니다. CodeBERT 파인튜닝은 우선순위가 낮습니다.

### 2.2 회의 활동

⚠️ **발언 시간·발언량을 그대로 점수화하지 마세요.** 원본 대화도 제안서 7장도 같은 경고를 합니다.
> "회의에서 말을 많이 한다고 기여한 것은 아님"
> "발언량만으로 기여도를 평가하지 않음"

대신 **발언 유형별**로 셉니다 (제안서 6.3의 분류 결과를 그대로 활용):

| 세는 것 | 가중 |
|---|---|
| 제안 → 실제 결정으로 이어진 발언 | 높음 |
| 질문에 대한 **응답** (특히 기술 질문) | 높음 |
| 결정 사항 정리·확인 | 높음 |
| 업무 약속 → **실제 완료로 이어진** 것 | 높음 |
| 정보 제공 | 중간 |
| 단순 동의·맞장구 | **0점** |
| 총 발언 시간 | **점수 아님** (참고 표시만) |

**참석 여부**는 별도 지표로 둡니다. 이건 조작이 어렵고 명확합니다.

### 2.3 문서·산출물

- 파일 수정 **횟수**가 아니라 **버전 간 실질 변경량**을 봅니다. (횟수는 조작 쉬움 — 원본 대화 지적)
- 발표자료, 기획서, 요구사항 명세, 테스트 기록 (제안서 7장 ✅)
- 외부 문서(Google Docs, Notion)는 API 연동 없이는 잡을 수 없습니다.
  → MVP는 **플랫폼 내 업로드/편집만** 집계하고, 한계를 UI에 명시하세요.

### 2.4 일정 준수

- 마감 전 완료 비율
- 평균 지연 일수
- ⚠️ **주의**: 마감일을 스스로 늦게 잡으면 준수율이 올라갑니다.
  → 마감일 **변경 이력**을 이벤트로 남기고, 변경 횟수를 함께 표시하세요.

### 2.5 동료평가 (선택)

제안서 7장에는 없습니다. 넣는다면 **CATME의 5개 카테고리 개념을 참조**하세요.
아무 근거 없이 자체 설계하면 심사에서 방어하기 어렵습니다.

**CATME** 5개 카테고리:
1. 팀 업무 기여 2. 팀원과의 상호작용 3. 팀 궤도 유지 4. 품질 기대 5. 관련 지식·기술·역량

> 💰 **CATME 서비스 자체는 고등교육 기관에 유료입니다** (전년도 고유 학생 수 기준 계층별 라이선스).
> 무료는 대학 이전 교육에만 해당합니다. **catme.org에 가입하지 마세요.**
> 위 5개 카테고리는 [PMC 리뷰](https://pmc.ncbi.nlm.nih.gov/articles/PMC10159466/)와
> [ASEE 논문](https://peer.asee.org/assessment-of-the-catme-peer-evaluation-tool-effectiveness.pdf)에
> 공개돼 있어 무료로 읽을 수 있습니다. **프레임워크만 참조하고 문항은 직접 설계**하세요.
> 87개 항목 루브릭 전문 복사는 비용 문제이자 지식재산 문제입니다.
> → [`11-비용-제로-구성.md`](11-비용-제로-구성.md) §1

- 익명, **중앙값** 사용 (평균은 극단값에 취약 — 원본 대화 지적 ✅)
- 자기 평가는 제외하거나 별도 표시
- **모든 팀원이 제출해야 공개** (일부만 제출 시 왜곡)
- 최소 인원(예: 3명) 미만이면 비활성화

## 3. 역할별 가중치

ChatGPT 대화의 아이디어입니다. 제안서에는 없으므로 **추가 채택**을 권합니다.

프로젝트 시작 시 팀원이 역할을 고르고, 역할별로 다른 산식을 씁니다.

| 항목 | 개발자 | 기획자 | 디자이너 |
|---|---|---|---|
| 업무 완료 | 30% | 30% | 30% |
| 코드 기여 | **35%** | — | — |
| 기획 문서 | — | **30%** | — |
| 디자인 산출물 | — | — | **35%** |
| 문서 활동 | 5% | (기획문서에 포함) | — |
| 회의 참여 | 10% | 15% | 10% |
| 일정 준수 | 10% | 10% | 10% |
| 동료 평가 | 10% | 15% | 15% |

⚠️ **이 숫자들은 근거가 없습니다.** ChatGPT가 제시한 예시값이고, 저도 검증할 방법이 없습니다.
그대로 쓰지 마세요. 대신:

- **가중치를 설정 가능하게** 만들고 기본값으로만 제공하세요.
- 팀장이 프로젝트 시작 시 조정하고, **조정 이력을 남깁니다.**
- 발표에서는 "가중치는 팀이 합의해서 정하는 값이며, 우리는 기본 프로파일을 제공한다"고 설명합니다.
  이게 "우리가 정한 가중치가 옳다"보다 훨씬 방어하기 쉽습니다.

**한 사람이 여러 역할을 겸하는 경우**(대학 팀플에서 흔함)는 역할별 비중을 배분하게 하세요.
예: 개발 70% + 기획 30%.

## 4. 출력 형식: 단일 점수 금지

ChatGPT 대화의 제안이 정확합니다. 그대로 채택합니다.

```
김민수

  예상 기여도    27%
  신뢰도         보통
  팀장 조정 범위  22% ~ 32%

  주요 근거
  ├ 담당 업무 8건 중 7건 완료           → [업무 목록 보기]
  ├ 병합된 PR 12건, 코드 리뷰 7건        → [PR 목록 보기]
  ├ 테스트 코드 14개 추가                → [커밋 보기]
  ├ 회의 9/10회 참석, 기술 질문 4건 응답  → [발화 재생]
  └ 일정 준수율 87% (지연 1회)           → [지연 업무 보기]

  ⚠ 이 수치는 활동 기록에 기반한 참고값입니다.
     최종 기여도는 팀이 합의하여 확정합니다.
```

### 4.1 신뢰도는 데이터 커버리지에서 나옵니다

"신뢰도 보통"은 느낌이 아니라 계산값이어야 합니다.

```
신뢰도 ↓ 낮아지는 조건
├ 회의 녹음이 적음 (전체 회의 대비 녹음률)
├ 화자 라벨 불확실 (모드 B에서 임계값 미달 발화 비율)
├ GitHub 연결이 늦게 됨 (백필 이전 기간이 큼)
├ 문서 활동이 플랫폼 외부에서 이뤄짐
└ 동료평가 미제출자 존재
```

이걸 화면에 그대로 노출하세요. **"왜 신뢰도가 낮은가"를 보여주면 사용자가 데이터를 채웁니다.**

### 4.2 조정 범위

점수의 불확실성 구간입니다. 신뢰도가 낮을수록 넓어집니다.
팀장은 이 범위 안에서 조정할 수 있고, **범위를 벗어나려면 사유를 적게** 합니다.

## 5. 절대 하지 말 것

ChatGPT 대화의 "AI에게 맡기면 안 되는 일" 목록을 **제품 제약으로 고정**합니다.

| 금지 | 이유 |
|---|---|
| AI가 무임승차자를 **판정**하는 기능 | 대학 팀플은 인간관계가 걸린 환경. 서비스가 사회적으로 살아남지 못함 |
| AI가 팀원 간 갈등의 **책임**을 가리는 기능 | 같음 |
| AI가 성격·성실성·태도를 **단정**하는 표현 | 제안서 7장이 이미 명시 ✅ |
| 최종 점수를 시스템이 **확정** | 사람(팀장/교수)이 확정. 시스템은 제안만 |
| 근거 없는 점수 표시 | 모든 점수에 이벤트 ID 연결 필수 |
| 팀원 간 점수를 **순위**로 표시 | 순위는 비교를 강제함. 개별 근거만 표시 |

마지막 항목은 제 추가 제안입니다. **리더보드를 만들지 마세요.**
같은 데이터라도 "1등 김민수, 2등 이하늘"로 보여주는 순간 서비스의 성격이 바뀝니다.

## 6. 검증 방법

기여도 산식이 "맞다"는 걸 어떻게 보일 것인가 — 졸업작품에서 반드시 나올 질문입니다.

정답 라벨이 없으므로(교수 점수는 팀당 1개뿐) **직접 검증은 불가능합니다.**
대신 세 가지로 우회합니다:

1. **조작 저항성 테스트** — ✅ **구현 완료**. `backend/tests/test_anti_gaming.py`, 24개 시나리오.
   커밋 쪼개기 / 오타 스팸 / lock 파일 / 전체 재포맷 / 맞장구 반복 / 독점 발언 /
   마감일 미루기 / 셀프 머지 / 웹훅 중복 / 빈 약속을 모두 검증합니다.
   정답 라벨 없이 검증 가능하고, 발표에서 가장 인상적인 부분입니다.
   **알려진 한계(오타 PR 500건 이상)까지 테스트로 명시**해 두었습니다.
2. **사용자 인식 조사** — 실제 팀에 결과를 보여주고 "이 결과가 실제 기여와 일치하는가"를 설문.
   제안서 13장의 "보고서 유용성 — 수정률, 작성 시간, 만족도"와 같은 방법론입니다.
3. **팀 내부 순위와의 상관** — 팀원들이 스스로 매긴 기여 순위와 시스템 점수의 순위상관(Spearman).
   절대값이 아니라 **순서가 맞는지**만 봅니다.

## 부록: Shapley value에 대해

협력 게임 이론에서 팀 총이득을 공정 분배하는 표준 방법입니다.
각 참여자가 가능한 모든 연합에서 갖는 **한계 기여**를 평균 냅니다.

**이 프로젝트에서 실제로 계산할 수는 없습니다.** "김민수가 없었다면 프로젝트가 어떻게 됐을까"라는
반사실 시나리오를 만들 수 없기 때문입니다.

다만 **"왜 이 배분이 공정한가"의 이론적 근거로 인용**하면 발표에서 강합니다.
"우리 산식은 Shapley value의 한계 기여 개념을 근사한 것"이라는 프레이밍은 정직하고 방어 가능합니다.

**반드시 읽어볼 선행연구**: *AI-Driven Contribution Evaluation and Conflict Resolution:
A Framework & Design for Group Workload Investigation* ([arXiv 2511.07667](https://arxiv.org/pdf/2511.07667))
— 이 프로젝트와 거의 동일한 문제를 다룹니다.
(이 세션에서는 arXiv 접근이 차단되어 내용을 확인하지 못했습니다. 직접 읽으세요.)
