# 12. CCTV(영상) 기반 화자 판정 — 모드 C

**결론부터: 법적으로 막히지 않고 기술도 성립합니다. 다만 대학생 팀플에서는
"회의 장소가 고정되어 있는가"가 실제 성패를 가릅니다.**

---

## 1. 무엇이 바뀌는가

CCTV는 마이크를 대체하지 않습니다. **화자 분리(diarization)를 대체합니다.**

```
[모드 B] 단일 마이크 → pyannote 화자 분리 → SPEAKER_00 → 사람이 이름 매핑
                       DER 17~20%

[모드 C] 단일 마이크 + 카메라 → 얼굴 검출·추적
                              → Active Speaker Detection (누가 입을 움직이는가)
                              → 얼굴 ↔ 팀원 매핑
                              → 화자 확정
```

즉 **오디오는 여전히 필요**하고, 영상은 "이 순간 말하는 사람이 누구인지"를
알려주는 보조 신호입니다.

---

## 2. 법적 검토 — 막히지 않습니다 (조건부)

### 2.1 처음에 걱정했던 것

**개인정보보호법 제25조 제5항**:
> 고정형영상정보처리기기운영자는 (…) **녹음기능은 사용할 수 없다.**
> ([법제처](https://law.go.kr/법령/개인정보보호법/제25조),
> [CaseNote](https://casenote.kr/법령/개인정보_보호법/제25조))

이게 그대로 적용되면 "CCTV로 회의 녹음"은 **원천 불가**입니다.

### 2.2 확인 결과 — 회의실에는 적용되지 않습니다

**제25조는 「공개된 장소」에 설치하는 고정형 영상정보처리기기를 규율합니다.**
사무실·회의실은 **비공개 장소**라 제25조 적용 대상이 아닙니다.

> "사무실에는 근로자의 동의 하에 CCTV를 설치할 수 있습니다. 사무실은
> 「개인정보 보호법」 제25조가 적용되지 않는 '비공개 장소'이지만
> CCTV를 통해 수집되는 영상이 개인정보에 해당되기 때문입니다."
> — [벤처스퀘어](https://www.venturesquare.net/927886),
> [한국경제](https://www.hankyung.com/article/202312118053i)

따라서 **녹음 금지 조항도 걸리지 않습니다.** 대신 일반 개인정보 규정이 적용됩니다.

### 2.3 대신 지켜야 하는 것

| # | 요구사항 | 근거 |
|---|---|---|
| V1 | **참석자 전원의 영상 촬영 동의** | 영상은 개인정보 |
| V2 | 목적 달성에 필요한 **최소 범위**만 촬영 | 개인정보보호위원회 판단 |
| V3 | 안내 (촬영 중임을 명확히) | |
| V4 | 영상 원본 **별도 보관 + 보존기간** | 음성과 동일 논리, 더 엄격 |
| V5 | **얼굴 임베딩은 생체인식정보** | 성문과 같은 취급 |
| V6 | 개인 삭제 요청 처리 | |

> ⚠️ 개인정보보호위원회는 "회사가 정당한 이익을 위해 사무실에 CCTV를 설치했더라도
> 근로자 동의 없이 책상과 컴퓨터 화면까지 24시간 촬영·저장하는 것은
> **합리적 범위를 초과**한다"고 판단했습니다. **상시 촬영은 안 됩니다.**
> 회의 중에만, 회의 참석자만 찍어야 합니다.

### 2.4 이동형(웹캠·폰 거치)이면 제25조의2

고정 CCTV가 아니라 **노트북 웹캠이나 거치한 폰**을 쓰면
**제25조의2(이동형 영상정보처리기기)** 가 적용됩니다.
업무 목적 촬영은 원칙적으로 금지지만 **정보주체 동의가 있으면 허용**됩니다.

대학생 팀플에는 이쪽이 현실적입니다 (§4 참조).

## 3. 기술 검토 — 성립합니다

### 3.1 Active Speaker Detection 현황

| 모델 | AVA-ActiveSpeaker mAP | 비고 | 출처 |
|---|---|---|---|
| **D²Stream** | **95.6%** | 2026 SOTA | [arXiv 2512.19130](https://arxiv.org/pdf/2512.19130) |
| TalkNCE | 95.5% | ICASSP 2024 | [arXiv 2309.12306](https://arxiv.org/pdf/2309.12306) |
| **Light-ASD** | **94.06%** | CVPR 2023, **경량·오픈소스** ⭐ | [GitHub](https://github.com/Junhua-Liao/Light-ASD) |
| TalkNet | 90.8% | ACM MM 2021, 오픈소스 | [GitHub](https://github.com/TaoRuijie/TalkNet-ASD) |

**Light-ASD가 이 프로젝트의 1순위입니다.** 경량이라 VRAM 압박이 덜하고,
오픈소스이며, 94%면 충분합니다.

### 3.2 ⚠️ 하지만 94%를 그대로 믿으면 안 됩니다

**AVA-ActiveSpeaker는 영화 데이터입니다.**

> "AVA-ActiveSpeaker가 발전을 이끌었지만, **영화 데이터에 의존하기 때문에
> 실제 시나리오를 대표하는 데 한계**가 있다. ASD 모델은 저빈도 언어,
> 시끄러운 배경, 붐비는 장면 같은 문제를 다뤄야 한다."
> — [UniTalk, Interspeech 2026](https://arxiv.org/html/2505.21954v2)

영화는 조명이 좋고, 얼굴이 크게 잡히고, 정면을 보고, 편집이 되어 있습니다.
**회의실 구석에 놓인 카메라는 정반대 조건**입니다.

→ [`09-리스크와-검증-실험.md`](09-리스크와-검증-실험.md)에 실험을 추가하세요.
자체 회의 영상으로 실측하기 전까지 94%를 인용하면 안 됩니다.

### 3.3 파이프라인

```
카메라 영상 + 마이크 오디오
  ├─ 얼굴 검출 (프레임마다)
  ├─ 얼굴 추적 (트랙 유지 — 같은 사람인지)
  ├─ Active Speaker Detection (Light-ASD)
  │    입력: 얼굴 크롭 시퀀스 + 오디오
  │    출력: 프레임별 발화 점수
  ├─ 얼굴 ↔ 팀원 매핑 (사전 등록된 얼굴 임베딩과 비교)
  └─ 오디오 VAD와 융합 → 발화 구간 + 화자
```

## 4. ⚠️ 대학생 팀플에서 진짜 문제 — 장소가 고정되지 않습니다

이게 CCTV 모드의 **최대 약점**이고, 기술이나 법률보다 중요합니다.

```
회사 회의실   → 고정. CCTV 설치 가능. ✅
대학생 팀플   → 카페, 스터디룸, 도서관, 강의실, 누구 집, 학과 라운지…
                매번 다름. 고정 CCTV 불가. ❌
```

**카페에서 만나면 CCTV가 없습니다.** 그리고 카페는 공개된 장소라
직접 설치할 수도 없습니다.

### 현실적인 형태

"CCTV"를 **고정 설치 카메라**가 아니라 **그 자리에서 세우는 카메라**로 해석하세요.

| 형태 | 현실성 | 비용 | 법 적용 |
|---|---|---|---|
| 고정 CCTV (회의실 상시) | 낮음 (장소 고정 필요) | 카메라값 | 제25조 (비공개 장소면 미적용) |
| **노트북 웹캠** | **높음** — 어차피 노트북은 가져옴 | **0원** | 제25조의2 (동의 시 허용) |
| **폰 거치 (한 대를 카메라로)** | 높음 | 0원 | 제25조의2 |
| 삼각대 + 웹캠 | 중간 | 2~3만원 | 제25조의2 |

**권고: 노트북 웹캠 또는 폰 한 대를 카메라로 쓰는 형태로 설계하세요.**
"CCTV"라는 이름은 유지하되 구현은 이동형입니다. 비용 0원이고,
[`11-비용-제로-구성.md`](11-비용-제로-구성.md)의 원칙도 지켜집니다.

## 5. 모드 비교 — 무엇을 얻고 무엇을 잃는가

| | **모드 A 멀티트랙** | **모드 C CCTV** | 모드 B 단일 마이크 |
|---|---|---|---|
| 화자 정확도 | **100%** (트랙=사람) | ~90% 추정 (실환경) | DER 17~20% |
| **UX 마찰** | **높음** — 매번 전원이 앱 실행 | **없음** ⭐ | 없음 |
| 하드웨어 | 0원 (각자 폰) | 0원 (노트북 웹캠) | 0원 |
| GPU 부하 | **없음** (신호처리) | **큼** (프레임마다 검출+ASD) | 중간 |
| 법적 부담 | 음성 | **영상 — 훨씬 무거움** | 음성 |
| 사전 등록 | 불필요 | **얼굴 등록 필요** (생체정보) | 불필요 |
| 실패 조건 | 앱 미실행 | 화면 밖·가림·뒤돌아봄·역광 | 동시발언·소음 |
| 동시 발언 | **자동 해결** | 판정 가능 (누가 입을 움직이나) | 최대 난제 |

### 5.1 CCTV가 이기는 지점 — UX 마찰

[`10-열린-질문.md`](10-열린-질문.md) Q3에서 멀티트랙의 **진짜 리스크**로 이걸 꼽았습니다:

> "사용자가 '회의 때마다 다 같이 앱을 켜야' 함 — UX 마찰.
> 팀원 5명이 매 회의마다 앱을 켜줄까요?"

**CCTV는 이 문제를 없앱니다.** 그냥 앉으면 됩니다.
서비스가 실제로 쓰이느냐는 여기서 갈릴 수 있습니다.

### 5.2 CCTV가 지는 지점 — GPU와 법적 부담

- **GPU**: 이미 [`02`](02-모델-선정과-VRAM-예산.md)에서 ASR+화자분리+LLM을 동시에 못 올린다고
  결론냈습니다. 여기에 얼굴 검출 + ASD가 프레임마다 추가됩니다.
  30분 회의 = 30fps × 1800초 = **54,000 프레임**. 순차 적재 전략이 더 중요해집니다.
- **법적**: 영상은 음성보다 훨씬 민감합니다. 얼굴 임베딩은 성문과 같은 생체인식정보입니다.
  멀티트랙은 성문 등록이 **불필요**해서 이 부담을 아예 없앴는데, CCTV는 되돌립니다.

## 6. 권고 — 셋 다 두되 A+C 조합을 노리세요

**모드를 하나 고르는 문제가 아닙니다.**

```
모드 A (멀티트랙)  : 화자 정확도 100%, UX 마찰 높음
모드 C (CCTV)      : UX 마찰 0, 정확도 ~90%
모드 A+C (융합)    : ⭐ 둘 다 있으면 교차 검증 가능
모드 B (단일 마이크): 최후 폴백
```

### 6.1 A+C 융합이 강한 이유

1. **정확도**: 오디오 에너지(A)와 영상 ASD(C)가 독립적인 신호입니다.
   둘이 일치하면 확신도 높음, 불일치하면 사람 검토 대상으로 표시.
2. **강건성**: 앱을 안 켠 사람은 영상으로, 화면 밖으로 나간 사람은 오디오로 잡습니다.
3. **졸업작품 관점**: **"두 모달리티를 융합해 화자 판정 정확도를 높였다"**는
   그 자체로 연구 주제가 됩니다. 그리고 A vs C vs A+C 를 정량 비교하면
   [`09`](09-리스크와-검증-실험.md) 실험이 하나 더 나옵니다.

### 6.2 다만 범위를 조심하세요

[`08-MVP-로드맵.md`](08-MVP-로드맵.md)에서 **범위 과다가 이 프로젝트의 최대 위험**이라고
결론냈습니다. CCTV를 추가하면:

- 얼굴 검출 + 추적 + ASD + 얼굴 등록·매핑 = **모듈 4개 추가**
- 영상 저장·보존·삭제 = 법적 요구사항 추가
- GPU 예산 재검토

**MVP에 넣지 마세요.** 모드 A를 먼저 완성하고, 동작하면 C를 붙이세요.
11주차 통합 흐름(회의→업무→칸반)이 먼저입니다.

## 7. 설계 반영 사항

### 7.1 데이터 모델 추가

```sql
-- meetings.capture_mode 에 'cctv' 추가
--   multitrack | single | cctv | multitrack_cctv

CREATE TABLE meeting_video_assets (   -- audio_assets 와 같은 취급
    id, meeting_id, storage_key, encryption_key_id,
    retention_until, deleted_at
);

CREATE TABLE faceprints (             -- voiceprints 와 같은 취급
    id, user_id, project_id,          -- 프로젝트 범위 한정
    embedding vector(512),            -- ArcFace 등
    revoked_at
);

-- utterances.speaker_source 에 값 추가
--   track | voiceprint | manual | diarization | video_asd | fused
```

⚠️ `faceprints` 는 **생체인식정보**입니다. `voiceprints` 와 동일하게
프로젝트 종료 시 폐기하고, 별도 동의를 받으세요
([`07-법적-윤리-요구사항.md`](07-법적-윤리-요구사항.md) P3).

### 7.2 동의 유형 추가

```
① recording              "이 회의를 녹음합니다"
② raw_audio_retention    "원본 음성을 N일 보관합니다"
③ voiceprint_storage     "목소리 특징을 저장합니다"
④ video_recording        "이 회의를 촬영합니다"          ← 신규
⑤ raw_video_retention    "원본 영상을 N일 보관합니다"     ← 신규
⑥ faceprint_storage      "얼굴 특징을 저장합니다"         ← 신규
```

④⑤⑥을 거부해도 모드 A로 서비스가 동작해야 합니다.
**필요 최소 수집 원칙**을 지키는 설계입니다.

### 7.3 영상 보존 정책 (음성보다 짧게)

| 데이터 | 보존기간 | 근거 |
|---|---|---|
| 원본 영상 | **7일** | 음성(30일)보다 짧게. 훨씬 민감함 |
| 얼굴 크롭 | 저장 안 함 | ASD 처리 후 즉시 폐기 |
| 얼굴 임베딩 | 프로젝트 종료 시 폐기 | 생체인식정보 |
| ASD 판정 결과 | 전사와 동일 | 텍스트만 남음 |

**핵심: 영상은 처리 후 버리고 판정 결과만 남기세요.** 그러면 노출 면적이 급감합니다.
