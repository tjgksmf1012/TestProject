# 24. 베타 체험 QA — 배포된 것을 처음 받은 사람처럼

`docs/23` 의 페르소나 QA 는 **여섯 사람의 과업**을 끝까지 따라갔습니다.
이번은 다릅니다 — **베타 참가자**를 흉내 냅니다. 목표를 정해 두고 가는
것이 아니라, 받아 든 프로그램의 **버튼을 하나하나 눌러 보고 기능을 하나씩
써 봅니다.** 그리고 무엇이 남는지 봅니다 — 화면에, 그리고 **로그에.**

⚠️ 결함 번호는 `docs/17` 과 같은 번호입니다.

---

## 왜 또 다른 것이 나왔나

과업을 따라가면 **그 과업에 필요한 화면만** 지납니다. 베타 참가자는 그렇게
안 씁니다 — 눌러 보고, 만들어 보고, 둘째 것을 만들어 보고, 새로고침하고,
잘못된 것을 넣어 봅니다. 그 결과 이번에 나온 것은 전부 **"처음 한 번은
되는데 두 번째부터 안 되는 것"** 이었습니다.

| | 처음 한 번 | 두 번째부터 |
|---|---|---|
| 프로젝트 | 만들면 홈이 그것을 보여 줍니다 ✅ | **만든 것으로 갈 길이 없습니다** (197) |
| 팀 참가 | — | **내가 만든 프로젝트가 사라집니다** (197) |
| 회의 목록 | 다섯 개면 요청 7건 | 서른 개면 **33건** (200) |

그리고 **터졌을 때**가 통째로 비어 있었습니다 (199).

### 격리부터 — 앞사람이 바꾼 세계를 다음 사람이 재지 않게

`docs/23` 에서 "페르소나가 데이터를 바꿔 다음 페르소나가 없는 결함을
크게 적었다" 를 겪었습니다. 그래서 이번에는 체험하는 사람마다 **자기 포트 ·
자기 DB · 자기 로그**를 줬습니다 (`scratchpad/qa2/env.sh`).

## ⛔ 197. 프로젝트가 둘이 되는 순간 **하나가 사라집니다**

### 재현

1. 새로 가입한다.
2. `+ 새 프로젝트` 로 `내가 만든 프로젝트` 를 만든다 → 홈 제목이 그 이름. 정상.
3. 팀에게 받은 초대 코드로 `참가` 한다.

**기대** 두 프로젝트 사이를 오갈 수 있다.
**실제** 홈 제목이 팀 프로젝트로 바뀌고 **내가 만든 것은 화면에서
사라집니다.** 서버는 둘 다 알고 있습니다 (`#1`, `#6`). 그런데 홈의 링크가
전부 `/project/1/…` 이고 **`#6` 으로 가는 링크가 하나도 없습니다.**

```
서버가 아는 내 프로젝트: #1 TeamFlow 시연 프로젝트 · #6 내가 만든 프로젝트
화면의 링크: /app/project/1/kanban /app/project/1/contributions
             /app/project/1/settings/role …
#6 으로 가는 길: ❌ 없음
```

같은 뿌리의 다른 얼굴: **새 프로젝트를 만들면 그 프로젝트는 언제나 목록
끝**이라(`orderProjects` 는 검토거리 있는 것을 앞으로, 그다음 id 순)
**만들자마자 못 들어갑니다.** `+ 새 프로젝트` 는 모든 화면 상단에 늘
떠 있습니다. 이 저장소가 기록한 실패 ③ **"할 일을 알려 주고 그 일을 할
자리를 안 줌"** 그대로입니다.

프로젝트가 하나뿐일 때는 멀쩡합니다(가입 → 빈 홈 안내 → 만들기 → 레일이
그 프로젝트로 붙음). **그래서 여태 안 보였습니다.**

### ⚠️ 판단은 처음부터 있었습니다 — 부르는 곳만 없었습니다

`frontend/src/lib/nav/rail.ts` 는 이 문제를 위해 쓰인 파일입니다. 하나면
안 그린다(`railIsWorthIt`) · 자리는 id 로 고정한다 · 할 일은 자리가 아니라
점으로 말한다 · 이모지 이름의 머리글자를 안 깨뜨린다(`railInitial`) —
검사까지 붙어 있습니다.

**리디자인 SPA 가 그걸 안 부릅니다.** 옛 화면(`demo/nav.ts`)이 부르고
있어서 "아무도 안 쓰는 export" 가드도 조용히 통과했습니다. 렌더해서 옛
화면과 새 화면을 나란히 재 보고서야 나왔습니다:

```
[옛 화면 /home.html] #2·#3 으로 가는 길: 6개
[새 화면 /app/    ] #2·#3 으로 가는 길: ❌ 없음
```

AGENTS.md 가 적어 둔 그대로입니다 — **화면을 옮기면 가드가 눈을 감습니다.**

### 고친 것

- 셸 왼쪽 레일 위에 **프로젝트 네모**를 세웠습니다. 판단은 `rail.ts` 한 벌을
  그대로 쓰고, 주소 형식만 `appRailHref` 로 갈아 끼웁니다 — 옛 셸은
  `/kanban.html?project=7`, SPA 는 `/project/7/kanban`.
- 홈이 **주소가 가리키는** 프로젝트를 그립니다 (`?project=`).
  `homeProject(projects, requestedId)` 가 정하고, 내 목록에 없는 id 는
  **조용히 첫 번째로** 돌아갑니다(남의 프로젝트 이름을 넘겨다볼 수 없어야
  하고, 오타 하나에 "없습니다" 를 띄우면 사람은 자기가 망가뜨린 줄 압니다).
- 만들거나 참가하면 **그 프로젝트로 데려갑니다.**

⚠️ 고쳐 놓고 렌더해 보니 **「지금 보는 프로젝트」 표시가 거짓말**을 하고
있었습니다 — 홈 주소에는 `:projectId` 가 없어 셸이 목록 첫 번째로
떨어졌습니다. 코드만 봤을 때는 안 보였습니다.

## ⛔ 199. 화면이 터지면 **영문 스택**이 뜨고 **아무 데도 안 남았습니다**

서버가 계약과 다른 모양을 주는 상황을 만들어 봤습니다(베타에서 흔합니다).
사람이 본 것:

```
Unexpected Application Error!
e.filter is not a function
TypeError: e.filter is not a function
  at ls (http://…/app/assets/index-DskNXvnA.js:12:42055)
  at …
```

넷이 한꺼번에 잘못돼 있었습니다.

1. **영문**입니다.
2. **압축된 스택**입니다 — 사람이 할 수 있는 것이 없습니다.
3. **나가는 문이 없습니다** — 홈으로도, 다시 시도도.
4. **서버 로그에 한 줄도 안 남습니다.** 요청은 200 이었으니까요.

4번이 가장 나쁩니다. 베타 참가자가 "그냥 안 되던데요" 라고 말하면 그걸로
끝입니다. `uvicorn.access` 는 **브라우저 안에서 난 일을 볼 수 없습니다.**

### 고친 것

- 라우터 바깥 한 겹에 우리 오류 화면(`Crashed.tsx`)을 답니다. 한국어로,
  **지금 할 수 있는 것**을 말하고, 나가는 문을 둘 줍니다. 원래 오류 문구는
  **작게 아래에** 남깁니다 — 참가자가 그 한 줄을 옮겨 적어 주면 고치는
  시간이 크게 줍니다.
- `POST /api/client-errors` 로 **서버 로그에 한 줄** 남깁니다 (WARNING).
- ErrorBoundary 는 렌더 중에 던진 것만 잡습니다. `setTimeout` 안, 거절된
  `await` 은 `window.onerror`·`unhandledrejection` 으로 줍습니다.

### ⚠️ 무엇을 보내지 **않는가**

이 제품은 회의 내용을 다룹니다 (docs/07 P4).

- **주소는 `pathname` 만** — `?…`·`#…` 는 뗍니다. 지금은 `?project=3`
  뿐이지만, 나중에 누가 검색어를 주소에 실으면 그날부터 샙니다.
- **사람이 친 글자는 안 보냅니다.** 오류 메시지와 스택뿐입니다.
- 길이 상한(500·4000·200)과 **분당 60줄** 상한이 있습니다. 넘치면 조용히
  204 입니다 — 429 를 주면 화면의 오류 보고가 **또 오류**를 만듭니다.
- 인증은 **일부러 안 겁니다.** 로그인 화면에서 터진 것이 가장 알고 싶은
  것인데, 인증을 걸면 그건 영영 안 들어옵니다. `test_auth.py` 의 `PUBLIC`
  목록에 이유와 함께 적었습니다.

⚠️ 상한이 **두 벌**입니다(TypeScript · Pydantic). 갈라지면 화면은 보냈다고
믿는데 서버가 422 로 버리고, **오류 보고가 사라지는 것은 아무도 못
알아챕니다.** 그래서 숫자를 맞대 보는 검사를 붙였습니다.

## 200. 홈이 **회의 수만큼** 요청을 쏘고 있었습니다 (N+1)

로그를 읽다 나왔습니다. 홈 한 번에:

```
GET /api/auth/me
GET /api/projects
GET /api/projects/1/meetings
GET /api/meetings/1/tracks      ← 줄마다 하나씩
GET /api/meetings/3/tracks
GET /api/meetings/4/tracks
GET /api/meetings/5/tracks
```

회의 다섯이면 7건, **회의 서른인 팀이면 33건**입니다. 브라우저는 호스트당
여섯 개씩만 동시에 여니 나머지는 줄을 섭니다 — 목록이 길수록 홈이 느려지는
구조였습니다.

### 고친 것

목록 응답이 `coverage` 를 함께 싣습니다. 재서 확인: **7건 → 3건.**

⚠️ **못 잰 것은 `None` 입니다. 0.0 이 아닙니다.** 이 제품의 불변식
셋째(`docs/05`)이고, 0.0 으로 채우면 화면은 "녹음이 하나도 안 됐다" 를
그리는데 실제로는 **아직 회의가 안 끝나서 잰 적이 없는** 것입니다.
평균을 낼 때도 `coverage IS NULL` 인 트랙은 빼고 셉니다 — 넣으면 아직 안
끝낸 사람 하나가 회의 전체의 커버리지를 끌어내립니다. 검사 둘이 지킵니다.

## 로그에 대해 — 이번에 실제로 남겨 본 것

`logging_config.py` 는 제대로 돕니다. 확인한 것:

- 틀린 비밀번호(401)·없는 회의(404)·없는 프로젝트(404)가 전부
  `uvicorn.access` 한 줄로 남습니다.
- 데모 DB 가 낡아 로그인이 500 이 났을 때, **트레이스백이 통째로**
  남아 있었습니다 (`no such column: users.bio`) — 원인을 로그만 보고
  찾았습니다. 이 저장소의 로그 설정이 하려던 일 그 자체입니다.
- `sqlalchemy.engine` 이 WARNING 으로 눌려 있어 쿼리 파라미터(회의 내용·
  사람 이름)가 안 새어 나갑니다.

**비어 있던 절반이 브라우저 쪽**이었고, 그것이 199 입니다.

## 201·202. 열리기까지 — 사람이 흰 화면을 보는 시간

베타 참가자는 링크를 받아 **처음** 엽니다. 그 첫 몇 초를 아무도 안 재고
있었습니다. 400kbps(느린 3G 정도)로 스로틀을 걸고 캐시를 비워 재 봤습니다.

### 201. 서버가 번들을 압축 없이 보내고 있었습니다

    GET /app/assets/index-*.js  →  526,215 바이트 (content-encoding 없음)
    gzip 하면                        161KB          (3.2배)

**흰 화면 12.5초 → 4.8초.** 같은 계측기, 같은 조건에서 압축만 껐다 켜서
잰 값입니다(추정이 아닙니다).

⚠️ **소리는 제외**합니다 — webm 은 이미 압축돼 있어 줄어드는 양이 0에
가까운데, 회의 한 시간짜리 트랙을 매 재생마다 다시 압축하면 재생이
끊깁니다.

### 202. 그 4.8초가 **아무것도 없는 백지**였습니다

사람은 5초짜리 흰 화면을 "고장" 으로 읽고 새로고침을 누릅니다. 그러면
처음부터 다시입니다.

그리고 번들이 다 와도 끝이 아니었습니다 — `RequireAuth` 가 로그인 판별
중에 `null` 을 그리므로, 서버가 느리면 **레일도 appbar 도 없이** 계속
백지였습니다. `/api/auth/me` 를 3초 지연시켜 재 보니 7.4초.

`index.html` 안에 HTML 만으로 그려지는 껍데기를 뒀습니다.

| | 완전한 흰 화면 |
|---|---|
| 껍데기 없음 | 4,446ms |
| 껍데기 있음 | **523ms** |
| 서버 느릴 때 · 껍데기 없음 | 7,322ms |
| 서버 느릴 때 · 껍데기 있음 | **525ms** |

## 203. 둘이 같이 쓸 때 — 여태 전부 **혼자** 써 봤습니다

체험도, 페르소나 QA 도, 도는 검사도 전부 한 사람이었습니다. 베타는 늘
여럿이 같이 씁니다. 브라우저 둘(김민수 · 이하늘)로 같은 프로젝트를 열어
봤습니다.

| 해 본 것 | 결과 |
|---|---|
| 같은 후보를 둘이 승인 | ✅ 서버가 멱등 — 업무 하나만 생깁니다 (4개 → 5개, 겹치는 제목 없음) |
| 같은 카드를 둘이 다른 칸으로 | 마지막 쓰기가 이깁니다 (칸반에서 흔한 선택) |
| **A 가 바꾼 것을 B 가 보는가** | ❌ **20초가 지나도 그대로.** 새로고침하거나 다른 화면 갔다 와야 |
| 뒤에 승인한 사람이 듣는 말 | ⚠️ "칸반에 등록된 업무는 없습니다" — **거절했을 때와 같은 문장** |

세 번째가 문제입니다. B 는 옛 화면을 보고 A 의 결정을 조용히 덮을 수
있고, 이 제품에서 업무 완료는 **기여도로 들어갑니다.**

`refetchOnWindowFocus: true` 로 고쳤습니다 — 설명을 더하는 것보다 그
상황이 **안 생기게** 하는 쪽입니다.

⚠️ 승인의 멱등성은 `apply_approval` 에 이유까지 적힌 **의도된 결정**이라
손대지 않았습니다.

## 결함 197 이 알려 준 것 — 같은 모양을 다 훑었습니다 (204~209)

197(프로젝트 레일)은 하나짜리 실수가 아니라 **부류**였습니다. 그래서
저장소 전체를 같은 눈으로 훑었습니다: *판단은 `lib/` 에 있는데 SPA 만
안 부르는 곳.* 여섯 개가 더 나왔습니다.

| | 무엇 | 사람이 못 하던 것 |
|---|---|---|
| ⛔ 204 | **로그아웃이 `/app` 에 없음** | 한 번 들어오면 못 나가고 계정도 못 바꿈 |
| ⛔ 205 | 프로젝트 없는 사람의 레일 셋이 `/` 를 가리킴 | 눌러도 아무 일이 없음 |
| ⛔ 206 | 권한 3단계 UI 없음 + **시드에 소유자 0명** | 등급 변경·내보내기·설정 저장이 전부 막힘 |
| 207 | 지울 것이 없어도 "지웠습니다" | 지워진 줄 앎 (개인정보보호법 §36 결과 보고) |
| 208 | 칸반 PR 이 개수만 | 어느 PR 인지, 확정인지 추정인지 못 봄 |
| 209 | 관찰의 사유·근거 안 그림 | 지적을 확인하거나 반박할 수 없음 |

206 의 시드 쪽이 특히 나쁩니다 — **제품이 만들 수 없는 상태를 시드가
만들고**, 그 상태로 지금까지 화면을 재고 캡처해 왔습니다. 초대 코드
때(결함 71) 겪은 것과 같은 종류입니다.

## ⚠️ 베타 체험 워크플로는 **검증 단계가 잘렸습니다**

열두 영역을 각자 자기 서버에서 끝까지 눌러 보는 워크플로를 돌렸는데,
**체험 10영역은 끝났지만 검증 에이전트 117개가 전부 한도에 걸려**
죽었습니다. 그래서 그 워크플로의 "진짜로 판정된 결함" 목록은 **비어
있고, 그것은 「없다」 가 아니라 「못 쟀다」 입니다.**

체험 단계가 올린 **미검증 후보가 115건** 남아 있습니다(로그인 12 · 홈 10 ·
칸반 11 · 검토 13 · 기여도 11 · 설정 13+10 · 로비 9 · 녹음 15 · 통화 11).
그중 제가 직접 확인해 고친 것이 이번 204~206 이고, 나머지는 **아직 사실
여부를 모릅니다** — 특히 아래는 사실이면 무거운 것들이라 다음에 먼저
확인할 것으로 적어 둡니다.

- 녹음: "서버에 트랙이 없는데 「끊김 없이 완료 · 커버리지 100%」" ·
  "서버는 「쓸 수 없음」인데 화면은 「사용 가능」"
- 칸반: "목록을 못 받으면 「회의에서 0 · PR 연결 0 · 지연 0」 이라고 단언"
  (사실이면 **측정 불가 ≠ 0점** 위반)
- 통화: "마이크를 꺼도 「마이크가 켜졌습니다」" · "타일의 「이 기기에서
  녹음됩니다」가 조건 없이 뜸"
- 설정: "구성원이 아닌 프로젝트가 「팀원 0명」이라고 단언"
- 기여도: "음수 -5% · 999% 가 아무 경고 없이 확정됨"

### 그중 둘을 직접 확인했습니다 — 하나는 진짜, 하나는 재현 안 됨

- ✅ **칸반이 못 받은 값을 0 으로 단언** — 진짜였습니다. 서버를 500 으로
  막고 열어 보니 `회의에서 0 · PR 연결 0 · 지연 0`. 고쳤습니다(결함 210).
- ✅ **구성원이 아닌(없는) 프로젝트가 「팀원 0명」이라고 단언** — 진짜였고,
  기여도 쪽의 "무슨 일이든 네트워크 탓" 도 같이 나왔습니다. 둘을 한
  벌(`describeLoadFailure`)로 고쳤습니다(결함 211).
- ✅ **지운 업무를 옮기면 서버가 500** — 진짜였습니다. 같은 상황에서 담당자
  API 는 404 였고요. 둘 다 404 로 맞췄습니다(결함 212).
- ❌ **"「동의합니다」 를 두 번 누르면 500(UNIQUE 위반)"** — 재현되지
  않았습니다 (1차 200 · 2차 200, 로그 조용함).
- ❔ **"서버에 트랙이 없는데 「끊김 없이 완료 · 커버리지 100% · 사용
  가능」"** — **제가 도달한 경로에서는 재현되지 않았습니다.** 가짜 마이크를
  켜고 트랙 만들기(`POST …/tracks`)를 503 으로 막은 뒤 녹음 화면을 열었더니
  화면은 **「트랙에 참가하지 못했습니다: 막음」** 이라고 정직하게 말했고,
  판정·커버리지·사용 가능 칸은 전부 비어(`-`) 있었습니다.

  ⚠️ 이것이 "그 보고가 틀렸다" 는 뜻은 아닙니다 — 보고자가 지난 경로(동의와
  마이크가 모두 통과한 뒤 업로드만 실패하는 상태)에 저는 못 닿았습니다.
  **모르는 것은 모른다고 적습니다.**

### 그다음 셋 — 둘은 진짜, 하나는 **재는 방법이 틀렸습니다**

- ✅ **좁은 폭에서 회의 제목이 사라진다** — 진짜였고, 재 보니 **더
  나빴습니다.** 800px 에서 제목 8px, 640px 아래로는 0px 이고, 400px 에서는
  **액션 버튼이 화면 밖(오른쪽 끝 776px)** 이라 누를 방법이 없었습니다.
  고쳤습니다(결함 213).
- ✅ **「트랙 상태 보기」가 트랙 상태를 안 보여 준다** — 도착지는 맞는데
  **왜 왔는지가 없었습니다.** 다섯 상태에서 로비 화면이 글자까지 같았고,
  실패한 회의에 「실패」라는 낱말이 0회, 검토까지 끝난 회의에서
  「녹음 화면으로」가 안 막혔습니다. 고쳤습니다(결함 214).
- ❌ **"긴 제목 카드의 「⋯」 메뉴가 카드 밖으로 나간다"** — **재현되지
  않았고, 제 재는 방법이 틀렸습니다.** 긴 제목을 심으려던 요청이 405 였고
  (없는 주소를 찍었습니다) 그 카드가 아예 안 만들어졌습니다. 있는 카드에서는
  메뉴 상자(333~352)가 카드(96~365) 안에 있었습니다.

  ⚠️ 405 를 안 읽었으면 "심었는데 안 잡혔다 → 결함 없음" 이라고 적을
  뻔했습니다. **심은 것이 실제로 심겼는지**를 먼저 봐야 합니다.

### 그다음 — 기여도 확정에 **범위 검사가 아예 없었습니다**

- ✅ **"음수 -5% · 999% 가 아무 경고 없이 확정"** — 진짜였습니다. `-5 ·
  -894 · 999` 를 넣었더니 서버가 **201**, 화면은 경고 0줄, 「이 값으로
  확정」이 인디고 그대로였습니다. 셋의 합이 정확히 100 이라 합계 경고까지
  조용했습니다. 화면과 서버 **둘 다** 에 `0 ≤ 값 ≤ 100` 을 넣었습니다
  (결함 215).

  ⚠️ 고치다 하나 더 나왔습니다 — 사유 문구의 꼬리(「— 사유 없는 조정은 …」)를
  화면이 **목록 전체 뒤에** 붙이고 있어서, 범위 문제 뒤에도 상관없는 말이
  따라붙었습니다. 문제가 한 종류뿐인 동안은 안 보이던 것입니다.

### 통화 — 둘 다 진짜였습니다

- ✅ **"마이크를 꺼도 「마이크가 켜졌습니다」"** — 진짜였습니다. 가짜
  마이크로 재니 끈 뒤에도 상태줄이 그대로였습니다. 상태줄은 마이크를 열
  때 **한 번만** 쓰이고 토글은 버튼 글자만 바꿨습니다.
- ✅ **"타일의 「이 기기에서 녹음됩니다」가 조건 없이 뜸"** — 진짜였습니다.
  마크업에 **조건이 하나도 없었습니다.** 통화에 있는 것과 녹음이 도는
  것은 다른 일이고, 실제로 그 회의는 동의가 안 끝나 트랙 만들기가
  403 이었습니다 — 아무것도 안 남는데 남는다고 말하고 있었습니다.

둘 다 `@lib/call/mesh.ts` 로 판단을 올려 고쳤습니다(결함 216). 타일은
이제 `GET …/tracks` 를 5초마다 물어 **아는 것만** 말합니다.

⚠️ 검증 중에 트랙 만들기가 403 이었는데 그걸 안 읽고 "트랙 생긴 뒤" 를
쟀습니다 — **아무것도 안 심긴 상태를 재고 있었습니다.** 이번 회차만
두 번째입니다(405 · 403). 세 사람 동의를 먼저 받고 다시 재서 「녹음
중입니다」 를 확인했습니다.

### 검토 — 정하던 것이 새로고침에 날아가는 것도 진짜였습니다

- ✅ **"검토하던 것이 새로고침 한 번에 날아감"** — 진짜였습니다. 담당자를
  고르면 나간 요청이 0건이고(그건 맞습니다 — 검토는 한 번에 확정하는
  절차입니다), 새로고침하면 「미지정」으로 돌아가며 경고도 없었습니다.
  `sessionStorage` 에 회의마다 남기게 했습니다(결함 217).

  ⚠️ 확정 흐름을 검증할 때 「거절」 버튼을 DOM 순서로 찾아 여덟 번 눌렀는데
  **같은 후보를 여덟 번** 누른 것이었습니다. "눌렀다" 는 "다른 것을
  눌렀다" 가 아닙니다.

### 하나를 찾고 **같은 모양을 훑었더니 셋**이었습니다

- ✅ **"「검토 끝내기」 실패해도 화면 무반응"** — 진짜였습니다. 500 을
  받아도 화면 글자가 **한 글자도** 안 바뀌었습니다. 훑어 보니 로비의
  「회의 강제 종료」와 설정의 「지난 활동 가져오기」도 같았습니다. 셋 다
  브라우저로 확인하고 고쳤습니다(결함 218). 칸반은 멀쩡했습니다.

  ⚠️ 뒤의 둘은 **조건이 서야 뜨는 버튼**이라, 처음에는 조건이 안 선
  화면에서 누르고 "아무 일도 안 일어남" 이라고 적을 뻔했습니다. 버튼이
  있었는지를 먼저 찍게 고쳤습니다 — 이번 회차에 **세 번째**입니다
  (405 · 403 · 없는 버튼).

### 로비 — 키보드로 못 닿는 것도 진짜였습니다

- ✅ **"조건 미충족 「녹음 화면으로」 키보드로 못 닿음"** — 진짜였습니다.
  탭 60번을 눌러도 안 닿았습니다. `href` 없는 `<a>` 는 탭 순서에 아예
  없습니다. 훑어 보니 레일의 막힌 항목 셋도 같았고(40번), 그쪽은 사유가
  `title` 에만 있었습니다. 둘 다 고쳤습니다(결함 219).

  ⚠️ 고친 뒤 재는 스크립트가 **"아직 못 닿는다" 고 찍었습니다.** 클래스를
  `split(' ')[0]` 로 잘라 `rail__item--blocked` 를 못 본 것이었고, 훑은
  목록에 그 요소가 버젓이 있는 것을 눈으로 보고 알았습니다. **찍은 값을
  읽으십시오** — 이번 회차에 네 번째입니다.

### 녹음 — 「서버는 쓸 수 없음인데 화면은 사용 가능」 도 진짜였습니다

- ✅ 가짜 마이크로 7초 녹음하고 **아무것도 가로채지 않은 채** 쟀더니,
  서버는 `usable=false · coverage=0.515` 라고 답했는데 결과 칸은
  「커버리지 100.0% · 판정 사용 가능」 을 **초록으로** 띄웠습니다. 바로
  위 문장만 "서버 기준 45.0%" 였고요 — 한 화면에 두 숫자가 여덟 줄
  사이로 있었습니다. 고쳤습니다(결함 220).

  ⚠️ 앞서 「재현 안 됨」 으로 적은 "트랙이 없는데 100%" 와 **뿌리가
  같습니다.** 그때 기록은 지금도 맞습니다(그 경로에서는 정직했습니다) —
  못 재현한 것이 "없다" 가 아니라 "그 길로는 못 갔다" 였습니다.

  ⚠️ 재는 방법이 또 두 번 틀렸습니다: 동의·권한을 안 누르고 「녹음
  시작」만 눌러 결과 칸이 전부 `-` 였고, 고친 뒤 같은 DB 로 다시 재다
  이미 트랙이 있어(`uq_track_user`) **서버에 알리는 코드가 통째로 안
  돌았습니다.** 둘 다 찍힌 값이 이상한 것을 보고 알았습니다.

### 통화 — 「마이크 없는 사람이 먼저 거는 쪽이면 영영 안 붙음」 도 진짜였습니다

- ✅ 트랙 없이 만든 offer 는 **m= 줄 0개 · ICE 후보 0개**입니다(대조군:
  트랙 있으면 1개·2개). 거는 쪽은 `me < other` 로 정하므로, 마이크 없는
  사람의 번호가 작으면 그 짝이 죽습니다 — **번호로 운이 갈립니다.**
  받는 자리(`recvonly`)를 열게 고쳤습니다(결함 221).

  ⚠️ 화면은 이미 "이 상태로는 **내 발언이** 하나도 기록되지 않습니다"
  라고 경고하고 있었습니다. 남의 목소리는 들린다는 뜻인데, 절반의 경우
  아무 소리도 못 들었습니다 — **경고가 사실보다 부드러웠습니다.**

  ⚠️ 두 사람이 실제로 붙어 소리가 오가는 것은 여기서 못 잽니다
  (`docs/09` 실험 6). 잰 것은 SDP 와 후보 수집까지입니다.

  ⚠️ 「마이크 없는 상태」 를 만들려다 또 틀렸습니다 — 가짜 마이크 깃발이
  **브라우저 전체**에 걸려 새 컨텍스트도 마이크를 받았습니다. 깃발을 안
  켠 별도 브라우저로 다시 쟀습니다. 이번 회차에 일곱 번째입니다.

### 열 화면을 훑다가 — **서버 로그가 잡은 것**

화면을 하나하나 눌러 보는 훑기를 열 화면에 돌리고 **서버 로그를 같이
읽었습니다.** 트레이스백이 다섯 번 찍혔고, 따라가니 하나였습니다:

- ✅ **팀원을 한 번 내보내면 기여도가 영영 500** — `GET …/contributions`
  도 `POST …/final` 도 죽었습니다. 이 제품의 한가운데가 버튼 하나로
  멈춥니다. 고쳤습니다(결함 222).

  ⚠️ 화면만 봤으면 **못 찾았습니다.** 내보내기를 누른 사람은 204 를 받고
  성공했다고 생각하고, 기여도가 죽은 것은 나중에 다른 사람이 발견합니다.
  「로그도 남겨 보고」 가 그래서 필요했습니다.

  ⚠️ 처음 쓴 고침은 **정반대**였습니다("계산에서 뺀다"). `remove_member`
  주석이 "빼면 남은 팀의 비율이 조용히 부푼다" 고 적어 둔 것을 읽고
  돌렸습니다 — 크래시를 고치면서 조용한 왜곡을 심을 뻔했습니다.

⚠️ 훑기의 `skip` 목록에 「내보내기」 를 넣었는데도 눌렸습니다 — **버튼
글자가 달랐습니다.** 되돌릴 수 없는 것을 정말 안 눌렀는지는 글자가
아니라 **나간 요청**으로 확인해야 합니다.

### 진짜 처음 오는 사람으로 걸어 봤습니다

가입하고, 로그인하고, 남이 보내 준 주소를 눌러 보는 것 — 베타에서 제일
흔한 첫 몇 분입니다. 서버는 전부 403 인데 화면 셋이 **빈 사실을
단언**했습니다(결함 224):

- 칸반: 권한 이야기 없이 텅 빈 판
- 로비: 「아직 아무도 참가하지 않았습니다 · 0명」
- 검토: 「업무 후보 0건」 에 더해 **틀린 이유까지** — "녹음이 아직
  처리되지 않았거나, 녹음 없이 열린 회의입니다"

기여도·설정은 맞게 말했습니다. 결함 211 에서 그 둘만 고쳤고 나머지 셋이
남아 있었습니다.

⚠️ 처음에는 **판만 가렸습니다.** 머리줄의 「업무 후보 0건」 과 「아직
아무도 참가하지 않았습니다」 가 그대로 남아 있었고, 다시 재서 알았습니다.

⚠️ **기존 시연 계정으로는 영영 못 찾습니다** — 모든 프로젝트의 구성원이라
403 을 한 번도 안 만납니다. 새로 가입해서 **다른 사람이 되어** 봐야
했습니다.

### 권한이 다른 사람으로도 걸어 봤습니다

소유자가 아니라 평범한 구성원으로 들어가니 설정 화면의 셋이 **멀쩡히
눌리는 상태**였습니다 — 「프로젝트 이름 저장」·「코드 새로 만들기」·
「저장소 연결」. 전부 403 이고, 눌러도 **화면이 아무 말도 안 했습니다**
(결함 225). `canManage` 는 처음부터 `@lib` 에 있었고 SPA 만 안 불렀습니다.

⛔ **이걸 놓친 것은 제 가드가 거짓으로 통과했기 때문입니다.** 결함 218 의
훑기가 「호출 뒤 600자 안에 `onError` 가 있는가」 로 재고 있었고, 그 600자
안에 **다음 호출의 `onError`** 가 들어 있었습니다. 괄호를 세서 그 호출의
인자 안만 보게 고쳤습니다 — 가드가 낱말을 안 세도 **범위가 넓으면 같은
병**입니다.

### 확인해 보니 **정해 둔 것**이었던 것

끝난 회의에 동의를 내면 서버가 200 을 줍니다(회의 4·5 둘 다). 결함으로

막힌다." **정해진 것을 결함이라고 적을 뻔했습니다.**

⚠️ **검증 안 된 후보를 결함으로 세지 않았습니다.** `docs/17` 의 집계에도

## 회의를 진짜로 열고 걸어 본 사람 — 결함 229

시드 데이터 말고 **직접** 회의를 열었습니다. 홈의 「회의 열기」 → 로비 →

**잘 되고 있던 것**

- 동의가 쌓이는 것이 글자로 보입니다 — 「3명이 아직」 → 「2명이 아직」 →

  전원 동의만 되면 넘어갑니다 — 데스크톱 앱이 없다고 막히지 않습니다.

**안 되고 있던 것** — 녹음 화면이 동의를 스스로 선언. `docs/17` 229.

### 방법으로 남길 것 — **줄 하나를 당겨 보기**

첫 증상은 사소했습니다: "로비에서 동의했는데 녹음 화면이 또 물어보네."
그냥 넘길 수 있는 어긋남이었습니다. 그 줄을 당겼더니 화면이 동의 자체를
**지어내고** 있었고, 아무도 동의 안 한 회의에서 마이크가 돌았습니다.

### ⚠️ 도구가 또 틀렸습니다

`controls()` 가 `a[href]` 만 셌습니다. 이 저장소의 「아직 안 됨」 링크는
**href 를 떼고** `aria-disabled` 를 답니다 — 그래서 「녹음 화면으로」가
목록에 아예 없었고, 하마터면 "그런 버튼이 없다" 고 적을 뻔했습니다.

**안 되고 있던 것** — 커버리지 창이 페이지를 연 시각부터. `docs/17` 230.

### 방법으로 남길 것 — **두 숫자를 같은 줄에서 읽기**

공백이 0인데 커버리지가 72%일 수는 없다 — 그 모순을 보려면 **한 화면의

업로드 실패를 여전히 잡는지 보려고 청크 하나를 막았는데 커버리지가

| 철회가 이미 받은 오디오를 지우는가 | **안 지웁니다 — 그리고 그것이 설계입니다.** 엔드포인트가 「철회는 소급하지 않는다」고 적어 뒀고, 거부한 사람의 원본은 **전사 직후**에 지웁니다(`purge_unconsented_audio`, `docs/07` §2.3) |
| 그러면 나중에 지울 길을 알려 주는가 | 알려 줍니다 — 「설정의 "내 녹음 지우기" 로 언제든 지울 수 있습니다」 |
| **그 자리가 정말 있는가** | **있습니다** — 설정 → 「내 녹음 지우기」(`/settings/danger`) |
| 되돌릴 수 없는 일인데 묻는가 | 묻습니다 — 「되돌릴 수 없습니다. 계속할까요?」 · **거절하면 요청이 안 나갑니다** |
| 확인하면 정말 도는가 | `200 POST /api/projects/1/me/data` |
| 지울 것이 없을 때 「지웠습니다」라고 하는가 | **안 합니다** — 「지울 녹음이 없습니다. 이 프로젝트에 남아 있던 내 음성 자료가 없습니다.」 (결함 197 에서 고친 것이 살아 있음을 확인) |

**결함 없음.** 화면·서버·문서가 서로 맞고, 지워지는 것과 남는 것을 나눠
적고, 0건을 성공으로 답하지 않습니다.

### ⚠️ 하마터면 없는 결함을 만들 뻔했습니다

「내 녹음과 성문 지우기」를 눌렀는데 **요청도 대화상자도 글자 변화도
없었습니다.** 버튼은 실재하고(`btn btn--danger` · 132×32) 클릭도
들어갔는데 요소 수가 82 → 82 그대로였습니다.

원인은 그 버튼이 `window.confirm` 을 쓰고, **Playwright 가 네이티브
대화상자를 기본으로 거절**하기 때문입니다. `confirm()` 이 거짓을 주니
`mutate()` 가 아예 안 돕니다. 도구 사정인데, 모르고 적었으면 **이 제품에서
법적으로 제일 민감한 단추가 죽었다**고 보고할 뻔했습니다.
`page.on('dialog', …)` 를 걸고 다시 누르니 정상이었습니다.


## **시계를 옮겨 놓고 보기** — 결함 286

새 관점: 브라우저 시간대를 넷으로 바꿔 가며 같은 회의를 봤습니다.
AGENTS.md 가 「씨앗 회의는 전부 `10:00Z` 라 어느 시간대에서도 날짜가 안
넘어간다」고 적어 뒀으니, **자정을 넘는 회의를 심어서** 쟀습니다
(`2026-08-25T16:30Z` = 서울 8/26 01:30 · LA 8/25 09:30).

| 시간대 | 달력이 앉힌 날 |
|---|---|
| Asia/Seoul · UTC · America/Los_Angeles · Pacific/Kiritimati | **넷 다 26일** |

**화면은 맞습니다.** 팀 달력을 브라우저 달력으로 바꿔 심으니 UTC·LA 가
25일로 갈라졌으니 자도 제대로 듭니다.

**틀린 것은 가드였습니다.** 이걸 막는 가드(결함 246)가 `webapp/src` 만
걷고 있어서, 자동 테스트가 하나도 없는 레거시 화면 열셋이 감시 밖이었고
— 방금 잰 그 달력이 바로 레거시 화면입니다. 활동 화면에 브라우저 달력을
심고 번들까지 다시 만들었더니 **1708개가 전부 통과**했습니다.
`docs/17` 286.

**이 관점은 「고친 것을 지키는 자가 아직 그 자리를 보는가」입니다** —
결함을 찾는 게 아니라 **자를 재는 것**이고, 화면이 옮겨 다닌 저장소에서는
자가 화면보다 먼저 낡습니다.


## **만들어 둔 기능을 한 번 써 보고 나머지 화면을 열어 보기** — 결함 287

달력의 「회의 일정 잡기」로 회의를 **하나** 잡고, 그 뒤에 다른 화면들을
열었습니다. 레거시 기여도 화면의 콘솔에 500 이 둘 찍혀 있었고, 따라가니
회의 목록 엔드포인트가 통째로 죽어 있었습니다.

| 화면 | 머리말 | 목록 |
|---|---|---|
| 레거시 홈 | 회의 **6개** | 「회의를 열면 여기에 나옵니다」 |
| SPA 홈 | 회의 **6** | (줄 0개) |

회의 다섯이 멀쩡히 있는 팀에서 다섯이 전부 사라졌고, 화면은 자기 머리말과
반대되는 말을 했습니다. `docs/17` 287.

**이 관점은 「기능을 한 번 쓰고 *다른* 화면을 보기」입니다** — 기능 자체는
201 을 주고 달력에도 잘 그려집니다. 깨진 것은 **그 기능이 만든 데이터를
처음 보는 다른 화면**이었고, 씨앗 데이터에 그런 데이터가 하나도 없어서
여태 한 번도 안 나왔습니다.

### 검사가 흔들리지 않으려다 아무것도 안 재게 된 것

같이 드러난 둘째 병(레거시가 브라우저 달력을 씀)의 검사는 이랬습니다.

    // CI 시간대에 흔들리면 안 된다
    strictEqual(shown.includes('T'), false);
    strictEqual(shown.includes('Z'), false);

**브라우저 달력이든 팀 달력이든 똑같이 통과합니다.** `16:30Z`(서울 다음
날 01:30)로 바꾸니 기계의 시간대와 무관하게 답이 하나가 됐습니다 —
흔들림을 없애는 방법은 **재는 것을 줄이는 게 아니라 갈라지는 데이터를
고르는 것**입니다.


## **만든 문서를 실제로 읽어 보기** — 결함 288

결함 287 과 같은 관점의 다음 걸음입니다. 보고서 화면의 「최종 보고서
만들기」를 누르고, **만들어진 문서를 글자로 읽었습니다.**

    회의            6건
    처리된 회의       0건
      └ 6건은 아직 처리 전이라 그 회의의 발언은 기여도에 안 들어갔습니다

같은 제품의 기여도 화면은 그 사람의 회의 근거를 11건이라고 세고 있습니다.
**팀이 제출하는 문서가 제품 자신의 데이터와 정반대로** 말했습니다.
원인은 `x.status == "done"` — `"done"` 은 업무 상태라 어느 회의도 해당하지
않고, 이 값은 언제나 0 이었습니다. `docs/17` 288.

**이 관점은 「버튼을 누르고 나온 것을 읽기」입니다** — 만들기는 201 을
주고 화면에도 잘 그려집니다. 틀린 것은 **그 안의 숫자**였고, 숫자는
눌러서는 안 보이고 **읽어야** 보입니다.

### 검사 데이터가 결함과 같은 모양이었습니다

보고서 API 검사의 씨앗이 `m.Meeting(..., status="done")` 이었습니다 —
실기가 절대 만들지 않는 값입니다. 그래서 서비스가 `"done"` 을 세는 것이
검사 안에서만 맞아떨어졌습니다. **통과는 넣은 값에 대해서만 참입니다.**
새 검사는 `teamflow/` 뿐 아니라 **`tests/` 도** 걷습니다.


## **문서를 다섯 상태로 만들어 읽기** — 결함 289 · 나머지는 재현 안 됨

결함 288 의 관점(만든 문서를 **읽기**)을 회의록에 댔습니다. 씨앗 회의
다섯으로 회의록을 하나씩 만들고 「처리」 줄을 읽었습니다.

`pending`(발화 0 · 오디오 없음) 회의의 회의록이 「**처리를 마쳤습니다**」
라고 했습니다. 그 아래 요약·안건·사안은 전부 빈칸입니다 — 읽는 사람은
「처리는 됐는데 나온 게 없구나」로 읽습니다. `docs/17` 289.

검사는 있었는데 「**어디에도 안 떨어지는가**」만 보고 「맞는 칸인가」는
안 봤습니다. 게다가 분류표에 회의 상태가 아닌 값이 넷 섞여 있어 세 집합이
**꽉 찬 것처럼** 보였습니다.

### 같은 회차에 잰 것 — **재현 안 됨 (깨끗)**

| 무엇을 | 결과 |
|---|---|

Enter 는 줄바꿈이고 **「보내기」 버튼**이 따로 있습니다. 둘 다 화면의

## **화면이 한 약속을 따라가기** — 결함 293

설정 화면이 「바꾼 사실은 **기록에 남습니다**」라고 적어 뒀길래 따라갔습니다.
역할 비중을 바꾸고 · 업무를 완료로 옮기고 · 실패한 회의를 다시 처리한 뒤
활동 기록을 열었습니다.

    회의 재처리 요청  김민수  meetings/5
    역할 비중 변경    김민수  members/1
    업무 완료        김민수  task:4

그 화면은 스스로 「누가 언제 **무엇을** 바꿨는지」라고 말합니다. 「누가」와
「언제」는 맞고 **「무엇」만 식별자**였습니다. `docs/17` 293.

### 같이 잰 것 — 재현 안 됨 (깨끗)

| 무엇을 | 결과 |
|---|---|

| 홈 첫 줄이 나머지와 다른 모양인 것 | **일부러 그런 것**입니다 — 「머리말은 여기 한 번뿐」이라고 적혀 있고, 그룹 머리말 다섯이 목록 절반을 먹던 것을 걷어낸 자리입니다. **안 건드렸습니다** |
| SPA 화면들의 400 | `describeActionFailure` 로 가는 400 을 화면에서 일으킬 길을 못 찾았습니다 — 결함으로 안 셌습니다 |

### 그리고 하나 나왔습니다

채팅에서 **이미 있는 이름으로 채널을 만들면** 서버는 「`일반` 채널이 이미
있습니다」라고 하는데 화면은 「채널을 못 만들었습니다」만 띄웠습니다.
`docs/17` 301.

⚠️ **새 가드가 여섯을 잡았는데 셋이 거짓 양성이었습니다** — 예외 이름
(`setFeedFailure`)을 빠뜨렸고, 창(200자)이 좁아 **결함 298 에서 제가 고친
코드**를 잡았습니다. 자를 고치고 하나씩 확인했더니 남은 하나는 진짜였고,
그것도 **298 에서 무르기만 고치고 만들기는 그대로 뒀던 자리**였습니다.


## **채팅을 처음으로 끝까지 써 보기** — 결함 302

씨앗에 채널이 0개라 여태 한 번도 안 써 본 화면입니다. 채널을 만들고,
열 마디를 보내고, 멘션하고, 반응·고치기·지우기·찾기를 다 눌렀습니다.

「고치기」를 누르면 글이 **아래 작성칸으로 옮겨 가는데 초점은 누른 단추에
남습니다.** 키보드로는 **Tab 을 31번**(답글은 32번) 눌러야 그 칸에
닿습니다 — 남은 메시지마다 반응·답글·고치기·지우기 넷을 지나가기
때문입니다. `docs/17` 302.

### 같이 잰 것 — 재현 안 됨 (깨끗)

| 무엇을 | 결과 |
|---|---|
| **「채팅은 기여도로 세지 않습니다」** | 열 마디를 도배해도 기여 구간 `31~54%` 그대로 |

⚠️ 고친 뒤 **키보드와 마우스 둘 다** 눌러 봤습니다 (결함 280 의 교훈) —

## **한 결함을 성질로 바꿔 제품 전체를 쓸기** — 결함 303

결함 302(채팅)는 하나의 일이 아니라 **성질**이었습니다: 「어떤 칸을
채우는 컨트롤을 누르면 초점이 그 칸으로 가는가」. 네 자리를 키보드로
눌러 쟀습니다.

| 어디 | 그 칸 | 초점 | 판정 |
|---|---|---|---|
| 검토 근거칩 | 안 바뀜 | 칩에 그대로 | 판단 보류 (그 칸이 안 채워짐) |

| 일정 날짜 칸 | 90→100자 | 날짜 단추 | 맞습니다 (격자는 그대로 있어야 화살표로 넘깁니다) |
| 채팅 채널 고르기 | — | — | 선택자를 못 맞춤 |

로비는 **여닫이 셋이 다** 초점을 잃었습니다(열기·저장·취소).
`docs/17` 303.

⚠️ **제 가드가 낱말만 세고 있었습니다** — `void focusTitleBox;` 로 심어도

⚠️ 고친 뒤 **키보드와 마우스 둘 다** 눌렀습니다 — 키보드는 Enter 뒤 바로

## **빈 상자가 자기가 안 본 것을 단언한다** — 결함 304

결함 294(일정 화면)를 고칠 때 **그 화면만** 고쳤습니다. 이번에는 같은
성질을 제품 전체로 쓸었습니다 — 「빈 상자의 **왜**가 화면이 확인한 것만
말하는가」. 씨앗을 새로 심고 빈 상자가 나오는 자리를 전부 열었습니다.

**어떻게 쟀나** — `emptyHtml({...})` 를 부르는 자리를 두 프런트에서 **전부
뽑아** `why` 를 한 줄씩 읽고(아홉 자리), 그중 판정이 갈리는 둘은 **띄워서
눌러 봤습니다.**

| 어디 | 빈 상자의 「왜」 | 판정 |
|---|---|---|
| **활동 기록 (팀 활동)** | 「아직 **아무도 안 바꿨습니다**」 | **결함 304** — 같은 순간 회의 5·업무 4·기여도 근거 있음 (렌더해서 확인) |
| **채팅 (빈 채널)** | 「`#공지` 채널이 **방금 만들어졌습니다**」 | **같은 성질** — 화면은 만든 시각을 받지 않습니다 (아래) |
| 활동 기록 (GitHub) | `describeEmptyFeed` — 연결 상태를 실제로 봄 | 맞습니다 |
| 칸반 | 「아직 등록된 업무가 하나도 없습니다 — 고장이 아닙니다」 | 맞습니다 — **자기 목록**에 대한 말입니다 |
| 기여도 | 「아직 이을 활동이 하나도 없습니다 — **아무도 안 했다는 뜻이 아닙니다**」 | 맞습니다 (결함 191 이 못 박은 것) |
| 보고서 | 「보고서는 자동으로 생기지 않습니다 — 팀이 필요할 때 만듭니다」 | 맞습니다 — 제품의 성질이라 언제나 참 |
| 찾기 | 「이 프로젝트 안에서만 찾습니다」 | 맞습니다 — 범위에 대한 말 |
| 채팅 (채널 없음) | 「채널은 자동으로 생기지 않습니다」 | 맞습니다 |
| 채팅 (검색) | 「지운 메시지는 검색에 안 나옵니다」 | 맞습니다 — 검색의 성질 |

활동 화면이 적은 「아무도 안 바꿨습니다」는 **거짓**입니다. 이 감사 기록에
남는 것은 **열넷뿐**이고 회의를 열거나 녹음하거나 이야기 나눈 것은 애초에
여기 안 쌓입니다. 화면은 자기 목록 하나가 빈 것으로 **팀 전체**를
말했습니다. `docs/17` 304.

### 같은 성질의 **두 번째 자리** — 채팅의 빈 채널

빈 채널이 「`#공지` 채널이 **방금 만들어졌습니다**」라고 적고 있었습니다.
그런데 채널 목록이 돌려주는 것은 이것뿐입니다 —

    GET /api/projects/1/channels
    [{"id":1,"kind":"text","name":"공지","position":1}]

**만든 시각이 없습니다.** 표에는 `created_at` 이 있는데 화면까지 오지
않으므로 화면은 「방금」인지 **알 수가 없습니다.** 지난달에 만들어 두고
아무도 안 쓴 채널도 똑같이 그렇게 말합니다.

⚠️ **지워서 재현하려던 것은 실패했습니다** — 메시지를 지우면 「지워진
메시지입니다」가 자리에 남아 목록이 안 빕니다(의도된 것입니다). 그래서
「지난달 채널」을 만들어 보이는 대신, **화면이 그 값을 받지 않는다는 것**을
API 응답과 모델로 보였습니다. 없는 결함을 만들지 않으려고 근거를 바꾼
것입니다.

고친 뒤 (`describeEmptyChannel`, `@lib/chat/view.ts`):

    아직 아무 말도 없습니다
    이야기는 채널마다 따로 쌓입니다 — 다른 채널에서 오간 말은 여기 안 보입니다.
    아래에 첫 마디를 적어 보세요.

「왜 비었나」가 화면이 **아는 것**으로 바뀌었고, 바쁜 팀의 빈 채널에도
참입니다 — 사람들은 다른 채널에 있습니다.

⚠️ **고치면서 반대 방향으로 같은 실수를 했습니다** — 「사람의 **숫자**를
건드린 일만 쌓입니다」라고 썼는데 열넷 중 숫자는 둘뿐이었습니다. 업무를
완료로 옮긴 사람에게는 그것도 거짓말입니다. **범위를 말할 때는 세어 보고
쓰십시오.**

⚠️ **제 가드가 「부정」을 위반으로 잡았습니다** — 기여도 화면의
「아무도 안 했다는 뜻이 **아닙니다**」(결함 191 이 못 박은 옳은 문장)가
걸렸습니다. 「잡혔다」는 「맞다」가 아닙니다.

### 같은 회차에 **재현 안 됨 (깨끗)**

| 무엇 | 결과 |
|---|---|
| 로그인 직후 `GET /api/auth/me` 가 401 | **정상** — 로그인 **화면**의 「이미 들어와 있나」 확인입니다. 로그인 뒤 요청은 전부 200 |

## **로그인해서 갈 수 있는 곳을 전부 걸어 보기** — 결함 305

새 관점입니다. 화면 하나하나를 눌러 보는 대신 **홈에서 시작해 링크를 따라
갈 수 있는 곳을 너비 우선으로** 걸었습니다. 「만들어 놓고 아무도 안 부름」
(실패 ①)을 화면 **낱개**가 아니라 **제품 전체**에서 재는 자입니다.

    닿은 곳 : home · kanban · contributions · project · lobby · review   (여섯)
    있는 것 : 열다섯
    안 닿는 곳: chat · calendar · notifications · activity · search · reports (여섯)

**여섯 화면이 제품 어디에서도 안 닿았습니다.** 채팅·일정·알림·활동
기록·찾기·보고서 — 정의서 §6·§7·§16·§19 가 요구한 것들입니다. `docs/17` 305.

⚠️ **제 자부터 의심했습니다.** 처음 크롤러는 `<a href>` 만 따라갔으므로
「단추로 넘어가는 화면」을 놓칠 수 있었습니다. 그래서 소스에서 각 화면을
가리키는 곳을 세어 봤고, 여섯 다 **`@lib/nav/links.ts` 한 곳**에서만
참조되고 있었습니다 — 그리고 그 링크를 그리는 `#nav` 이 열두 화면 어디에도
없었습니다. 런타임에서도 여섯 화면 전부 `#nav=no · 여섯화면링크=0개`.

⚠️ **저장소의 가드가 제 CSS 를 잡았습니다** — 결함 55·56 의 「공용 CSS 가
id 에 레이아웃을 걸지 않는다」. `#nav` 을 예외에 넣기 전에 **다른 뜻으로
쓰는 화면이 있는지 세어 봤습니다**(0곳). 「잡혔다」는 「틀렸다」가 아니고,
예외로 넘기는 것도 근거가 있어야 합니다.

## **서버 갈래마다 부르는 곳이 있는가** — 결함 306

결함 305 는 「만든 **화면**에 들어갈 문이 있는가」였습니다. 같은 성질을 한
층 아래에서 쟀습니다. AGENTS.md 가 결함 298 을 적으면서 「서버의 갈래마다
부르는 곳이 있는지 세는 가드가 낱말을 세는 것보다 낫습니다」라고 써 뒀는데
여태 안 하고 있었습니다.

    라우트 81개 → 화면에서 부르는 곳이 0곳인 것 7개

⚠️ **그중 셋은 제 자가 틀린 것이었습니다.** 녹음 클라이언트는 주소를
`${trackUrl}/chunks/${seq}` 처럼 조각으로 만들어서, 전체 경로를 글자로
찾는 자가 못 봅니다. 그대로 적었으면 **없는 결함 셋**을 만들 뻔했습니다.
`POST /api/github/webhook` 은 GitHub 이 부르는 갈래라 맞습니다.

| 남은 셋 | 판정 |
|---|---|
| **`POST /api/meetings/{id}/minutes`** | **결함 306** — 보고서 화면이 「회의 로비에서 회의록을 만드세요」라고 하는데 로비에 그 단추가 없었습니다 |
| `PUT /api/projects/{id}/channels/order` | 서버만 있고 화면에 아직 안 이었습니다 (CHANNEL-005) — 예외 표에 사유와 함께 적어 뒀습니다 |
| `GET /api/projects/{id}/mentions` | 멘션 자동완성. 멘션 **자체**는 서버가 본문에서 찾아 내므로 동작합니다 |

로비의 단추를 전부 덤프해서 확인했습니다 — 동의합니다 · 거부 · 녹음
화면으로 · 통화로 회의하기 · 업무 후보 검토 · 칸반 보기 · 기여도 보기.
**「회의록 만들기」가 없습니다.** `docs/17` 306.

### 눌러 보고 **읽었습니다**

    201 POST /api/meetings/1/minutes → /reports.html 도착 → 목록에 나옴

여기서 멈추지 않고 문서를 열었습니다 (결함 288). 녹음 전 회의의 회의록이
「처리: 아직 처리하지 않았습니다」·「요약: 아직 회의를 처리하지 않아 요약이
없습니다」라고 정확히 적습니다 — 지어낸 사실 0건. 「일시 2026-09-08
**19:00**」이 홈과 같아 결함 290 도 그대로 고쳐져 있습니다.

**여러 번 눌러 봤습니다** (결함 296): 같은 회의 두 번 + 다른 회의 한 번 →
서버가 아는 보고서 **2개**. 안 쌓입니다.
