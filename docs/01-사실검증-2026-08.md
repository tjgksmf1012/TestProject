## A. 전략·방향에 대한 주장

### A-1. "LLM을 처음부터 직접 학습시키는 방향은 비추천" — ✅ 유효

전적으로 동의합니다. 그리고 원본 대화가 덧붙인 구분이 정확합니다:

> "API를 사용하지 않는 것과 생성형 AI를 사용하지 않는 것은 다르다."

이게 이 프로젝트의 포지셔닝을 결정하는 문장입니다. 심사자/교수에게도 이 한 문장으로
설명하면 됩니다. "외부 생성형 AI API 의존 없이, 오픈 웨이트 모델을 자체 인프라에서 서빙한다."

### A-2. 제안된 4단계 순서 — ✅ 유효, 단 3·4단계는 사실상 도달 불가

원본 순서:
1. 오픈소스 AI 모델을 내 서버에서 실행
2. 규칙 기반 기여도 계산 시스템 구축
3. 실제 팀플 데이터 모은 뒤 소형 모델/LoRA 파인튜닝
4. 데이터 쌓이면 기여도 예측 모델 학습

1·2단계는 정확합니다. **3·4단계는 데이터 확보 난이도를 과소평가**하고 있습니다.

- 3단계(LoRA)는 원본이 "수백~수천 건"이라고 했는데, 회의 녹취 + 정답 라벨(요약/결정사항/담당자/
  업무/마감일)을 **수백 건** 만들려면 회의 수백 회분의 라벨링 작업이 필요합니다.
  졸업작품 기간(보통 1~2학기) 내에 개인이 모을 수 있는 규모가 아닙니다.
- 4단계(기여도 예측 회귀)는 더 어렵습니다. 정답 라벨이 "교수 평가 점수 / 팀장 확정 기여도"인데,
  이건 **팀당 1행**밖에 안 나옵니다. 팀 100개를 모아야 100행입니다. LightGBM 학습에는 턱없이 부족합니다.

**대안 (이 연구의 제안)**: 3·4단계를 "학습"이 아니라 **"평가 데이터셋 구축"**으로 재정의하세요.
- 회의 20~30건에 정답 라벨을 붙여 **테스트셋**으로 씁니다. 학습이 아니라 **프롬프트/모델 비교 측정용**입니다.
- 이것만으로도 졸업작품에서 "우리는 정량 평가를 했다"고 말할 수 있고, 이게 훨씬 방어 가능한 주장입니다.
- LoRA는 "데이터가 모이면 이렇게 확장 가능하다"는 **설계 확장점**으로 문서에만 남기고,
  실제 학습은 여유가 생겼을 때 소형 모델(1.2B급)에 한 번 시도하는 정도로 잡으세요.

자세한 내용: [`09-리스크와-검증-실험.md`](09-리스크와-검증-실험.md)

## B. 음성 인식 (ASR)

### B-1. "Whisper를 서버에서 직접 실행할 수 있다" — ✅ 유효, 그러나 더 이상 1순위 아님

Whisper는 여전히 잘 돌아갑니다. 문제는 **한국어 성능**입니다.

- Whisper는 약 68만 시간으로 학습됐는데 비영어가 17%이고, 그 17%를 98개 언어가 나눠 씁니다.
  → 한국어 비중은 극히 작습니다. ([Edge AI and Vision Alliance](https://www.edge-ai-vision.com/2025/11/small-models-big-heat-conquering-korean-asr-with-low-bit-whisper/))
- `whisper-large-v3` 한국어 실측: **KsponSpeech Eval-Other 기준 CER 11.13%**
  ([Edge AI and Vision Alliance](https://www.edge-ai-vision.com/2025/11/small-models-big-heat-conquering-korean-asr-with-low-bit-whisper/))
- 참고로 한국어는 교착어라 **WER이 아니라 CER로 평가**해야 합니다. 원본 대화에는 이 언급이 없었습니다.

### B-2. "Qwen3-ASR 0.6B / 1.7B이 공개돼 있다" — ✅ 유효, 그리고 ⚠️ **1순위로 승격 권장**

원본 대화는 이걸 "후보"로만 언급했습니다. 검증 결과 **기본값이 되어야 합니다.**

| 항목 | 내용 | 출처 |
|---|---|---|
| 모델 | `Qwen3-ASR-0.6B`, `Qwen3-ASR-1.7B` | [QwenLM/Qwen3-ASR](https://github.com/QwenLM/Qwen3-ASR) |
| 라이선스 | **Apache 2.0** (상업 이용 가능) | [qwen-ai.com](https://qwen-ai.com/qwen-asr/) |
| 언어 | 52개 언어·방언, 언어 자동 식별 | [QwenLM/Qwen3-ASR](https://github.com/QwenLM/Qwen3-ASR) |
| 성능 | 1.7B가 오픈소스 SOTA, **Whisper-large-v3 상회**, 상용 API와 경쟁 가능 | [Qwen3-ASR Technical Report](https://arxiv.org/html/2601.21337v1) |
| 기능 | 타임스탬프 예측, 긴 오디오, **스트리밍 + 오프라인 통합** | [QwenLM/Qwen3-ASR](https://github.com/QwenLM/Qwen3-ASR) |
| 서빙 | 공식 툴킷이 **vLLM 배치 추론 / 비동기 서빙 / 스트리밍** 지원 | [QwenLM/Qwen3-ASR](https://github.com/QwenLM/Qwen3-ASR) |
| 통합 | 🤗 Transformers **v5.13.0+** 네이티브 지원 | [Qwen3-ASR-1.7B-hf](https://huggingface.co/Qwen/Qwen3-ASR-1.7B-hf) |
| 부가 | `Qwen3-ForcedAligner-0.6B` 별도 공개 (단어 단위 정렬) | [Qwen3-ForcedAligner-0.6B](https://huggingface.co/Qwen/Qwen3-ForcedAligner-0.6B) |

**이게 왜 중요한가**: 원본 대화의 추천 파이프라인은 WhisperX였습니다.
WhisperX = faster-whisper(전사) + wav2vec2(강제 정렬) + pyannote(화자분리) 3단 조합입니다.
Qwen3-ASR은 전사 + 타임스탬프를 **한 모델에서** 주고, 더 정밀한 정렬이 필요하면 ForcedAligner를
붙이면 됩니다. **의존성이 줄고, 한국어 성능은 올라가고, 라이선스는 Apache 2.0으로 깨끗해집니다.**

> `[원문 확인 필요]` Qwen3-ASR 기술보고서(arXiv 2601.21337)의 **한국어 개별 CER 수치**는
> 이 환경에서 PDF 접근이 막혀 확인하지 못했습니다. "Whisper-large-v3 상회"는 다수 출처가
> 일관되게 말하고 있으나, **한국어 단독 수치는 직접 벤치마크로 확인해야 합니다.**
> → [`09-리스크와-검증-실험.md`](09-리스크와-검증-실험.md) 실험 1

### B-4. 참고: 한국어 특화 경량 ASR — 🆕 원본에 없던 정보

## C. 화자 분리 (Speaker Diarization)

### C-1. "pyannote.audio를 쓸 수 있다" — ✅ 유효, 버전 정보 갱신 필요

2026년 기준 최신은 **pyannote.audio 4.0 + `speaker-diarization-community-1`** 입니다.
원본 대화가 인용한 "Community-1" 수치는 맞는 모델을 가리키고 있습니다.

| 항목 | 내용 | 출처 |
|---|---|---|
| 최신 OSS 파이프라인 | pyannote.audio 4.0 + community-1 | [pyannote.ai/blog/community-1](https://www.pyannote.ai/blog/community-1) |
| 3.1 대비 | 화자 수 추정·할당 모두 유의미 개선, 현존 최고 오픈소스 | [pyannote.ai/blog/community-1](https://www.pyannote.ai/blog/community-1) |
| **라이선스** | **CC-BY-4.0** (귀속 표시 조건, 상업 이용 가능) | [pyannote.ai/blog/community-1](https://www.pyannote.ai/blog/community-1) |
| 접근 | HuggingFace **gated** — 사용 동의 후 토큰 필요 | [HF 모델 카드](https://huggingface.co/pyannote/speaker-diarization-community-1) |

⚠️ **CC-BY-4.0이라는 점을 놓치지 마세요.** 상업 이용은 되지만 **귀속 표시(attribution) 의무**가
있습니다. 서비스 크레딧/라이선스 고지 페이지에 pyannote를 명시해야 합니다.
Apache 2.0인 Qwen3-ASR과 조건이 다릅니다.

### C-2. "AMI 기준 DER 17.0% / 19.9%, 범위 8.9~46.8%" — ⚠️ `[원문 확인 필요]`

원본 대화가 인용한 수치입니다. pyannote가 공개 벤치마크를 운영하는 것은 확인했으나
(https://www.pyannote.ai/benchmark), **표 자체는 403으로 열람하지 못했습니다.**

다만 **이 수치의 해석은 원본 대화가 정확합니다**:
> "17%가 곧 문장 17%의 이름이 틀렸다는 뜻은 아니다. 말소리 누락, 잘못 감지된 음성,
> 화자 혼동 시간이 모두 포함된다."

DER = (miss + false alarm + speaker confusion) / total speech duration 이므로 맞는 설명입니다.
발표 자료에 인용할 거면 **반드시 원본 벤치마크 페이지에서 재확인**하세요.

### C-3. 🆕 원본에 없던 중요 정보: pyannoteAI **Precision-2**

검색 중 발견한 사실인데, 이 프로젝트에 직접적인 영향이 있습니다.

- Precision-2는 community-1보다 **28% 더 정확**합니다.
- 그리고 **화자 식별(speaker identification), 성문(voiceprint), 배타적 분리 모드,
  신뢰도 점수(confidence score)를 지원하는 유일한 모델**입니다.
  ([pyannote.ai/blog/precision-2](https://www.pyannote.ai/blog/precision-2))

**여기가 함정입니다.** 원본 대화의 "방법 2: 팀원 목소리 사전 등록"과
"화자별 신뢰도 제공" 요구사항은 **Precision-2가 있어야 편하게 되는 기능**인데,
Precision-2는 **상용 API**입니다. 즉 "외부 API 안 쓴다"는 이 프로젝트의 핵심 포지셔닝과 충돌합니다.

**결론**: 오픈소스만으로 가려면 화자 식별은 **직접 구현**해야 합니다.
community-1으로 분리 → 별도 화자 임베딩 모델(ECAPA-TDNN 등)로 임베딩 추출 →
등록 음성과 코사인 유사도 비교. 이건 원본 대화가 설명한 방식과 같고, 구현 가능합니다.
다만 **"공짜로 얻어지는 기능이 아니라 직접 만들어야 하는 모듈"**이라는 점을 일정에 반영하세요.

### C-4. "NVIDIA NeMo도 화자 식별·임베딩을 제공한다" — ✅ 유효

- **Sortformer**: 화자를 도착 시간 순으로 정렬해 출력하는 트랜스포머 기반 diarizer.
- **Streaming Sortformer**: Arrival-Order Speaker Cache(AOSC)로 이전 화자 임베딩을 저장,
  저지연 실시간 다중화자 추적 지원. 모델 공개됨 (`nvidia/diar_streaming_sortformer_4spk-v2`).
  ([arXiv 2507.18446](https://arxiv.org/pdf/2507.18446),
  [NeMo 문서](https://docs.nvidia.com/nemo/speech/nightly/asr/speaker_diarization/intro.html))

⚠️ `4spk` — **4인 화자 모델**입니다. 원본 대화의 "팀원 2~5명" 목표와 미묘하게 어긋납니다.
5인 팀 회의에 쓰려면 확인이 필요합니다.

그리고 원본 대화의 결론에 동의합니다: **1차 버전은 스트리밍 말고 녹음 후 일괄 분석**이 맞습니다.

### C-5. 화자 임베딩 모델 후보 — 🆕 구체화

원본 대화는 "화자 임베딩"이라고만 했습니다. 실제 선택지:

| 모델 | 제공 | 비고 |
|---|---|---|
| **ECAPA-TDNN** | [SpeechBrain](https://huggingface.co/speechbrain/spkrec-ecapa-voxceleb), [WeSpeaker](https://huggingface.co/Wespeaker/wespeaker-ecapa-tdnn512-LM) | 사실상 표준. 화자 검증/분리 양쪽에서 검증됨 |
| **TitaNet** | NVIDIA NeMo | ContextNet 기반 |
| **3D-Speaker** | [modelscope/3D-Speaker](https://github.com/modelscope/3D-Speaker) | CN-Celeb 레시피 포함 → **아시아권 언어 화자 인식**에 상대적 강점 |

한국어 화자 데이터로 학습된 공개 모델은 찾지 못했습니다. VoxCeleb(영어 위주) 기반 모델을
쓰게 되는데, **화자 임베딩은 언어보다 음향 특성에 의존**하므로 한국어에서도 대체로 동작합니다.
다만 이것도 검증 대상입니다.

## E. 하드웨어 / 인프라

### E-1. "RTX 5080 16GB니까 2B급 또는 양자화된 7~8B급부터" — ✅ 방향 맞음, 근거 보강 필요

방향은 맞는데 원본 대화는 **동시 적재 문제를 언급하지 않았습니다.** 이게 더 큰 제약입니다.
자세한 예산표: [`02-모델-선정과-VRAM-예산.md`](02-모델-선정과-VRAM-예산.md)

### E-2. 🆕 원본에 없던 필수 정보: Blackwell(sm_120) 셋업

RTX 5080은 Blackwell, compute capability **sm_120**입니다. 2025년에는 이게 큰 고통이었습니다.
2026년 8월 현재 상황:

- **PyTorch 2.7.0이 sm_120 네이티브 지원을 추가한 최초의 stable 릴리스**입니다.
  cu128 사전빌드 휠 + 갱신된 cuDNN/NCCL/Triton 3.3(Blackwell + `torch.compile` 대응) 포함.
  ([PyTorch 2.7 블로그](https://pytorch.org/blog/pytorch-2-7/))
- 설치는 반드시 CUDA 12.8 인덱스를 명시:
  ```bash
  pip install torch --index-url https://download.pytorch.org/whl/cu128
  ```
  기본 인덱스로 설치하면 `sm_120 is not compatible with the current PyTorch installation`
  에러를 봅니다. 2025년 이슈 리포트가 검색에 잔뜩 남아 있는데 **대부분 이 원인**입니다.
- `-cuda12.8-` 태그가 붙은 PyTorch 2.7.0+ 이미지면 RTX 50 시리즈에서 동작합니다.
  ([SaladCloud](https://docs.salad.com/container-engine/tutorials/machine-learning/pytorch-rtx5090))

⚠️ 남아 있는 함정: CUDA 12.8/12.9 설치본에 `libnvptxcompiler.so`가 빠져 PTX JIT이 깨지는
사례가 보고돼 있습니다. vLLM/FlashAttention처럼 JIT 컴파일에 의존하는 도구에서 터질 수 있습니다.
([HF 포럼](https://discuss.huggingface.co/t/ptx-jit-broken-on-rtx-5080-blackwell-sm-120-missing-libnvptxcompiler-so-in-cuda-12-8-12-9/161827))
→ **환경 구축을 프로젝트 첫 주에 배치하세요.** 여기서 며칠 날리는 게 흔합니다.

### E-3. "llama.cpp로 로컬 추론" — ✅ 유효, 단 서빙에는 vLLM 권장

llama.cpp/GGUF는 실험·프로토타이핑에 좋습니다. 다만 이 프로젝트는 **JSON 스키마 강제**가
핵심 요구사항인데, 그 부분은 vLLM 쪽 생태계가 훨씬 낫습니다. (E-4 참조)

### E-4. 🆕 "JSON 형식으로 출력하도록 한다" → **프롬프트가 아니라 디코딩으로 강제하세요**

원본 대화 2단계:
> "모델에게 그냥 '요약해줘'라고 하면 결과가 매번 달라진다. 다음처럼 JSON 형식으로 출력하도록 한다."

방향은 맞지만 **방법이 약합니다.** 프롬프트로 부탁하는 건 확률적이고, 소형 모델일수록 깨집니다.
2026년의 정답은 **guided decoding (constrained decoding)** 입니다.

- vLLM은 `outlines`, `lm-format-enforcer`, **`xgrammar`** 를 guided decoding 백엔드로 지원합니다.
- JSON Schema에서 문법을 만들고 **매 토큰마다 마스크를 씌워** 스키마를 벗어나는 토큰 자체를
  생성 불가능하게 만듭니다. → **파싱 실패가 원리적으로 발생하지 않습니다.**
- **2026년 기준 xgrammar가 권장 기본값**입니다. JIT 컴파일 문법, 대부분의 스키마에서 최속,
  문법이 재사용될 때 캐싱 효과가 큽니다. (이 프로젝트는 **항상 같은 스키마**를 쓰므로 최적 조건)

출처: [Red Hat Developer](https://developers.redhat.com/articles/2025/06/03/structured-outputs-vllm-guiding-ai-responses),
[vLLM 문서](https://docs.vllm.ai/en/v0.8.2/features/structured_outputs.html),
[SqueezeBits 벤치마크](https://blog.squeezebits.com/guided-decoding-performance-vllm-sglang)

**설계 반영**: 원본 대화가 제시한 JSON 예시(`summary`, `decisions`, `tasks[]`,
`unresolved_issues`)를 **Pydantic 모델로 정의 → JSON Schema 추출 → vLLM guided decoding에 전달**.
이러면 "출력 형식 고정"이 프롬프트 엔지니어링이 아니라 **타입 시스템**이 됩니다.

### E-5. LoRA / PEFT — ✅ 유효, 16GB에서 충분히 가능

- LoRA는 전체 재학습 없이 일부 파라미터만 학습. HuggingFace **PEFT**가 지원. (원본 대화 정확)
- 2026년 실측: **QLoRA는 7B 모델에 최소 8GB, 16GB면 여유** 있음.
  Unsloth는 표준 QLoRA 대비 **2배 빠르고 VRAM 70% 절감**, Qwen3 30B-A3B QLoRA가 17.5GB에서 동작.
  ([Spheron](https://www.spheron.network/blog/gpu-vram-requirements-fine-tune-llm-2026/),
  [Unsloth 문서](https://unsloth.ai/docs/get-started/fine-tuning-for-beginners/unsloth-requirements))
- Unsloth dynamic 4-bit는 8-bit 대비 perplexity 차이 0.02 수준 — 사실상 무손실.

즉 **하드웨어는 병목이 아닙니다. 병목은 학습 데이터입니다.** (A-2 참조)

| 항목 | GitHub App | OAuth App |
|---|---|---|
| 권한 | 필요한 것만 세밀하게 요청 | 넓은 스코프, 과다 권한 |

출처: [Deviera](https://deviera.dev/blog/github-app-vs-oauth), [GitHub Docs](https://docs.github.com/en/apps/oauth-apps)

GitHub App이면 "이 저장소 하나에만, 읽기 권한만"이 가능합니다. **이건 기능이 아니라 신뢰 문제입니다.**

### G-4. 🆕 보강: 이미 확립된 선행 연구를 쓰세요

원본 대화는 동료평가를 "익명 평가의 중앙값 15%"로만 다뤘습니다. 바퀴를 다시 발명할 필요 없습니다.

**CATME (Comprehensive Assessment of Team Member Effectiveness)** — 공학교육 분야에서
가장 널리 쓰이는 팀 동료평가 도구. 29개 유형의 기여 행동에 대한 87개 항목 루브릭으로
**5개 카테고리** 점수를 산출합니다:

1. Contributing to the Team's Work (팀 업무 기여)
2. Interacting with Teammates (팀원과의 상호작용)
3. Keeping the Team on Track (팀 궤도 유지)
4. Expecting Quality (품질 기대)
5. Having Relevant Knowledge, Skills, and Abilities (관련 지식·기술·역량)

출처: [PMC 리뷰](https://pmc.ncbi.nlm.nih.gov/articles/PMC10159466/),
[ASEE](https://peer.asee.org/assessment-of-the-catme-peer-evaluation-tool-effectiveness.pdf)

**권고**: 동료평가 UI를 자체 설계하지 말고 **CATME 5개 카테고리 구조를 차용**하세요.
- 교수·심사자에게 "검증된 도구 기반"이라고 설명할 수 있습니다.
- 구조화된 심리측정 도구를 더하면 동료평가의 **공정성·정확도·평가자 간 신뢰도가 개선된다**는
  연구 결과가 있습니다. ([PMC](https://pmc.ncbi.nlm.nih.gov/articles/PMC10159466/))

**Shapley value** — 협력 게임 이론에서 팀 총이득을 공정 분배하는 방법. 각 참여자가 가능한 모든
연합에서 갖는 한계 기여를 평가합니다. ([Wikipedia](https://en.wikipedia.org/wiki/Shapley_value))
이 프로젝트에서 직접 계산하기는 어렵지만(반사실 시나리오를 만들 수 없음),
**"왜 이 배분이 공정한가"의 이론적 근거**로 인용하면 발표에서 강합니다.

**직접 관련 선행연구**: "AI-Driven Contribution Evaluation and Conflict Resolution:
A Framework & Design for Group Workload Investigation"
([arXiv 2511.07667](https://arxiv.org/pdf/2511.07667)) —
제목만으로도 이 프로젝트와 거의 동일한 문제를 다룹니다. **반드시 읽으세요.**
(이 환경에서 PDF 접근 실패. 직접 확인 필요.)

## H. 회의 요약 / 업무 추출

### H-1. "AI가 회의 요약·결정사항·업무·마감일 추출을 잘한다" — ✅ 유효

- 회의 요약 표준 코퍼스는 **AMI**와 **ICSI**. 둘 다 사람이 주석한 추출/생성 요약 포함.
  ([Meeting Summarization Survey](https://arxiv.org/pdf/2212.08206))
- Action item 중심 요약 연구 존재. AMI에서 BERTScore 64.98 달성(파인튜닝 BART SOTA 대비 +4.98%).
  ([arXiv 2312.17581](https://arxiv.org/abs/2312.17581))

### H-2. 🆕 평가 기준을 미리 정하세요

> "회의록에서는 **action item에 대한 completeness가 결정적 차원**이다. 커스텀 루브릭으로
> '원본 전사의 모든 action item이 담당자와 마감일과 함께 요약에 등장하는가'를 채점한다.
> 2026년 프로덕션급 요약 판정기는 관심 차원에서 0.6 이상을 찍어야 한다."
> — [Future AGI](https://futureagi.com/blog/evaluate-llm-summarization-step-by-step-2026/)

즉 **"요약이 잘 되었는가"가 아니라 "업무가 빠짐없이 뽑혔는가(recall)"** 로 평가해야 합니다.
이 프로젝트에서 업무 하나를 놓치면 그 사람 기여도가 통째로 누락되므로, **recall이 precision보다
훨씬 중요**합니다. 원본 대화의 "사람이 확인 후 확정" 설계와도 일치합니다 —
**과다 추출하고 사람이 지우게 하는 게, 과소 추출하고 사람이 찾아 넣게 하는 것보다 낫습니다.**

## I. 아키텍처

### I-1. "Spring Boot 메인 + Python FastAPI AI 서버 + React + PostgreSQL" — ✅ 유효, 좋은 선택

사용자가 Spring을 공부 중이라는 맥락에서 특히 합리적입니다.
FastAPI는 LLM 래퍼/추론 API에 적합합니다 — PyTorch/HuggingFace 생태계가 Python 네이티브이므로.
([Medium](https://medium.com/@reachyogeshchavan/fastapi-for-backend-apis-exploring-when-it-fits-and-when-it-doesnt-0ccd10f7682f))

### I-2. ⚠️ 보강: 업로드 라우트에서 직접 처리하면 안 됩니다

- 파일 업로드 라우트 안에서 처리하지 말고 **BackgroundTasks나 외부 잡 큐로 넘기세요.**
- 표준 구성: FastAPI(요청 수신·큐잉) + Redis(브로커) + Celery 워커(실제 AI 분석).
  ([Upsun](https://developer.upsun.com/posts/2025/building-async-processing-pipelines-with-fastapi-and-celery-on-upsun))
- ⚠️ **async만으로는 CPU/GPU 바운드 작업이 개선되지 않습니다.** 반드시 워커 프로세스 분리.
  ([Medium](https://medium.com/@reachyogeshchavan/fastapi-for-backend-apis-exploring-when-it-fits-and-when-it-doesnt-0ccd10f7682f))

이건 원본 대화가 "Background Job: Redis, Celery 또는 BullMQ"로 이미 맞게 짚었습니다.
다만 **GPU 배타 락**이 추가로 필요합니다 → [`03-시스템-아키텍처.md`](03-시스템-아키텍처.md)

## J. 법률

### J-1. 🆕 원본 대화가 "녹음에 개인정보 포함 가능"이라고만 언급한 부분 — 훨씬 구체적입니다

두 개의 다른 법을 동시에 봐야 합니다.

**통신비밀보호법 (녹음 행위 자체의 적법성)**
- **대화 당사자의 녹음은 합법.** 본인이 대화에 참여했다면 몰래 녹음해도 위법하지 않습니다.
- **제3자 녹음은 형사처벌 대상.** 대화자 중 1명의 동의를 얻었더라도 상대방 동의가 없으면
  위법한 감청입니다.
- 2022년 당사자 녹음도 금지하려는 개정안이 발의됐으나 **철회**되었습니다. 현행법은 여전히
  **"당사자 참여 여부"가 적법성 판단의 핵심**입니다.
  ([법무법인 법승](https://www.lawwin.co.kr/incheon/knowledgedetail?index=7039),
  [뉴로이어](https://www.newlawyer.co.kr/41/241))

→ **설계 반영**: 녹음 버튼은 **회의 참석자 본인만** 누를 수 있어야 합니다.
회의에 참석하지 않은 팀장이 원격으로 녹음을 시작하는 기능은 **만들면 안 됩니다.**

**개인정보보호법 (수집된 음성의 취급)**
- 개인정보보호위원회는 **회의 석상에서 녹음된 목소리도 개인정보**라고 판단했습니다.
  음성이 개인을 구별할 수 있는 고유 정보라는 이유입니다.
- 녹음된 음성은 **생체인식정보**로 간주될 수 있으며, **원본정보를 보관하는 경우 이용자 동의 또는
  법령 근거가 필요**하고, **다른 개인정보와 분리 보관**하도록 설계해야 합니다.
  ([보안뉴스](http://www.boannews.com/media/view.asp?idx=102064))
- 다만 전문가들 사이에 "식별정보 없는 단순 녹취록 목소리를 개인정보로 보는 건 과하다"는
  반론도 있습니다. ([공공투데이](https://www.publictoday.co.kr/news/articleView.html?idxno=65708))

→ **설계 반영**: 이건 "나중에 붙이는 기능"이 아니라 **데이터 모델 설계에 들어가야 합니다.**
원본 오디오는 별도 스토리지·별도 암호화 키·별도 보존기간·명시적 동의로 분리합니다.
자세한 내용: [`07-법적-윤리-요구사항.md`](07-법적-윤리-요구사항.md)

> ⚠️ 법률 자문이 아닙니다. 실제 서비스 출시 전에는 전문가 검토를 받으세요.
> 다만 졸업작품 발표에서 **"우리는 이 법적 요구사항을 설계에 반영했다"**고 말할 수 있으면
> 그 자체로 강력한 차별점입니다. 대부분의 학부 프로젝트는 이걸 안 합니다.
