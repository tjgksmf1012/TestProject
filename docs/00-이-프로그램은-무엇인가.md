# TeamFlow AI — 이 프로그램은 무엇인가

> 이 문서 하나만 읽어도 무엇을 만들었는지 알 수 있게 썼습니다.
> 화면 캡처는 `docs/images/tour/` 에 흐름 순서대로 있습니다.

---

## 1. 한 줄로

**팀 프로젝트에서 "누가 무엇을 했는지" 를 회의록·칸반·GitHub 기록으로
이어 붙여, 학기 말에 서로 얼굴 붉히지 않게 만드는 도구.**

---

## 2. 어떤 문제를 풀려고 하는가

대학 팀프로젝트에서 반복되는 장면이 있습니다.

- 회의에서 "그럼 로그인은 민수가 맡자" 라고 정했는데, **아무도 안 적습니다.**
  2주 뒤에 그런 얘기가 있었는지조차 흐려집니다.
- 학기 말 기여도 평가에서 **기억으로 싸웁니다.** "나는 발표 자료도 만들었다",
  "너는 커밋이 몇 개냐" — 근거가 서로 다릅니다.
- 조용히 일한 사람과 말만 많이 한 사람이 **똑같아 보입니다.**

문제의 뿌리는 하나입니다. **결정이 난 자리(회의)와 일이 도는 자리(칸반·
GitHub)와 평가하는 자리(기여도)가 서로 끊겨 있습니다.**

이 프로그램은 그 셋을 **하나의 사슬**로 잇습니다.

```
회의에서 한 말  →  업무 후보  →  사람이 승인  →  칸반 카드  →  PR/커밋  →  기여 기록
                       ↑                                            ↓
                   AI 가 뽑음                              근거를 거슬러 올라갈 수 있음
```

핵심은 **거슬러 올라갈 수 있다**는 것입니다. 기여도 화면의 숫자에서
출발해 "이 값은 어떤 업무에서 나왔나 → 그 업무는 어느 회의의 몇 번째
발언에서 나왔나" 까지 따라갈 수 있습니다. 근거 없는 숫자는 안 만듭니다.

## 3. 쓰는 순서 (화면 흐름)

캡처 파일 이름 앞의 번호가 이 순서입니다.

### `01-로그인`
팀 내부 자료(회의 녹음·기여도)라 로그인이 필요합니다.
비밀번호는 scrypt 해시로만 저장하고, 세션 토큰도 원문이 아니라 해시만 남깁니다.

### `02-홈`
내가 속한 프로젝트와 그 안의 회의들이 한 줄씩 보입니다.
회의 앞의 **점 하나가 상태**입니다 — 열림 / 처리 중 / 검토 필요 / 완료 / 실패.
각 줄 아래 문구가 **지금 어느 단계이고 다음에 뭘 해야 하는지**를 말합니다.

### `03-프로젝트-설정`
- **내 역할** (개발 / 기획 / 디자인, 겸직이면 나눠서). 이 값이 기여도
  **가중치**를 정합니다. 기획자는 코드 0% · 문서 30%, 개발자는 코드 35% · 문서 5%.
- **내 GitHub 계정**. 이걸 안 적으면 그 사람의 PR 이 주인을 못 찾습니다.
- **초대 코드**, **회의 열기**, **저장소 연결**과 그 **연결 진단**.

> ⚠️ 역할과 계정은 **본인만** 바꿀 수 있습니다. 남이 내 역할을 바꿀 수
> 있으면 그건 남의 점수를 바꾸는 일이기 때문입니다. 바꾼 사실은 기록에 남습니다.

### `04-회의-로비`
회의를 시작하기 전 대기실입니다.
- **동의**: 전원이 동의해야 녹음이 시작됩니다. 원본 음성 보관 · 목소리 특징
  저장은 **따로** 묻습니다 — 묶어 버리면 "녹음은 되지만 원본은 남기기 싫다" 를
  말할 방법이 없습니다.
- **참가자 상태**: 사람마다 한 줄짜리 **트랙 다이어그램**. 녹음이 끊긴 구간이
  빗금으로 남습니다. 이 그림이 이 제품의 시각적 시그니처입니다.

### `05-녹음`
각자 **자기 기기에서 자기 트랙**을 녹음합니다(멀티트랙). 한 대의 마이크로
회의실 전체를 담는 대신 사람마다 따로 담으면, 누가 말했는지를 추측하지 않아도
됩니다. 화면이 꺼지거나 다른 앱으로 넘어가도 녹음이 버티는지를 이 화면이 검증합니다.

### `06-통화`
각자 다른 곳에서 회의할 때 쓰는 브라우저 통화(WebRTC).
통화 중에도 녹음은 각자 기기에서 따로 돕니다.

> 캡처의 빨간 문구는 **버그가 아니라 정상 동작**입니다. 캡처를 뜬 서버에는
> 마이크가 없어서, 그 사실을 화면이 정직하게 말하고 있는 것입니다.

### `07-업무-후보-검토` ⭐ 이 제품의 안전장치
녹음이 처리되면 AI 가 회의에서 **업무 후보**를 뽑습니다. 여기서 사람이
승인해야만 칸반에 올라갑니다.

- 제목 옆 작은 알약이 **AI 확신도**입니다. 낮은 것부터 위에 옵니다.
- **근거 발화 번호**가 카드마다 붙습니다. 근거가 없는 후보는 **승인할 수
  없습니다** — 담당자·마감일을 채워도 마찬가지입니다. 회의에 없던 내용을
  사람이 "고쳐서" 통과시키는 경로를 만들면 안 되기 때문입니다.
- 결정한 뒤 **왜 그렇게 결정했는지** 메모를 남길 수 있습니다.

### `08-칸반`
승인된 업무가 여기로 옵니다. `할 일 → 진행 중 → 검토 중 → 완료`.
- 카드는 **전부 회의에서 나온 업무**입니다. 손으로 적어 넣는 길은 **일부러
  두지 않았습니다** — 무엇이 어디서 왔는지 못 따라가면 기여도가 근거를 잃기
  때문입니다. 카드를 열면 어느 회의의 몇 번째 발화에서 나왔는지가 나옵니다.
- 카드 아래 GitHub 줄이 **이 업무가 어느 PR 로 끝났는지**를 보여줍니다.
  PR 제목이나 본문에 `TASK-3` 을 적으면 자동으로 붙습니다.
- 맨 위 한 줄이 대표 주장을 요약합니다: `회의에서 나온 업무 N · PR로 이어진 업무 M · 지연 K`.

### `09-기여도`
지금까지 쌓인 것으로 계산한 **참고값**입니다. 이 화면이 이 프로젝트에서
가장 조심해서 만든 곳입니다 (아래 §4 참고).

## 4. 일부러 **안 한** 것들 — 이게 설계의 핵심입니다

기여도를 다루는 도구는 잘못 만들면 팀을 망가뜨립니다. 그래서 네 가지를
스스로 금지하고, **자동 테스트로 그 금지를 지키게** 했습니다.

### ① 순위·리더보드를 만들지 않는다
목록은 **이름 순**입니다. 점수 순으로 정렬하지 않습니다 — 리더보드를 안
그려도 목록이 점수 순이면 사람들은 1등과 꼴찌를 읽습니다.

막대그래프도 안 그립니다. 세 사람의 값을 같은 자 위에 세로로 세우는 순간
그건 순위표이기 때문입니다.

### ② 단일 점수를 주지 않는다
`32~52%` 처럼 **구간**으로 말합니다. 신뢰도가 낮을수록 구간이 넓어지고,
그 넓이가 곧 "이 값을 얼마나 믿을 수 있는가" 입니다.

화면의 흙빛 **점**은 값이 아니라 **"얼마나 모르는가"** 를 그립니다.
**점 하나가 4%p 의 "모름"** 이고, 점이 많은 사람은 기여가 큰 사람이 아니라
**우리가 가장 모르는 사람**이며, 그 자리가 다음에 더 재야 할 곳입니다.

길이가 아니라 **개수**인 이유가 있습니다. 사람은 길이를 눈대중하는 것보다
개수를 세는 쪽을 훨씬 잘하고, 무엇보다 길이는 옆 사람과 **나란히 놓이는
순간 순위표**가 됩니다. 점은 옆 사람이 몇 개든 상관없는 절대량입니다.

### ③ 측정 못 한 것을 0점으로 치지 않는다
녹음이 끊겨 발언량을 못 쟀다면 그건 **0이 아니라 모르는 것**입니다.
나머지 활동으로 추정하고, 추정했다는 사실을 그 줄에 적어 둡니다.

그래서 화면에서 **결측은 빨강이 아니라 흙빛**입니다. 빨강은 "네가 뭘
잘못했다" 로 읽히는데, 녹음이 끊긴 건 그 사람 잘못이 아닙니다.

### ④ 시스템이 최종 점수를 확정하지 않는다
계산값은 **참고값**입니다. 기여도 화면 맨 아래에서 **팀이 합의해 확정**하고,
시스템 값과 다르게 정했다면 **이유를 함께** 적습니다. 시스템 값은 지워지지
않고 나란히 남습니다.

> 화면 맨 위 경고도 지우지 않았습니다:
> *"팀 전원의 신뢰도가 낮습니다. 이 수치로 서로를 비교하지 마세요 —
> 연결되지 않은 데이터가 무엇인지 먼저 확인해야 합니다."*

## 5. 어떻게 만들었나 (기술 요약)

| | |
|---|---|
| 서버 | Python · FastAPI · SQLAlchemy · Alembic · Celery |
| 저장소 | PostgreSQL (시연·테스트는 SQLite) |
| 화면 | TypeScript + React (**화면 열셋**) · 나머지 셋(`index`·`call`·`offline`)은 손으로 쓴 것 |
| 음성 | 멀티트랙 녹음 → 시간 정렬(GCC-PHAT) → 누출 제거 → 주화자 판정 |
| 앱 | PC 웹(PWA) + **PC 앱(Electron)** 둘. 모바일은 범위 밖입니다(2026-08-13) |

**돈이 들지 않게** 만들었습니다. 외부 생성형 AI API 를 쓰지 않고, 중급
GPU(10~16GB) 한 대에서 도는 범위로 설계했습니다.

화면은 처음에 **라이브러리 없이** 손으로 썼습니다 — 졸업작품이 끝난 뒤에도
빌드 도구 버전이 깨져서 못 여는 일이 없게 하려고요. 그 뒤 팀에서 React 를
쓰기로 정해 옮겼고, **그 걱정은 다른 방법으로 지켰습니다**: 만들어진 화면
파일을 저장소에 함께 넣어 둡니다. 그래서 몇 년 뒤에도 **아무것도 설치하지
않고** 파일만 열면 화면이 뜹니다.

⚠️ 녹음과 통화 화면 둘은 **일부러 React 로 안 옮겼습니다.** 그 둘은 마이크와
통화 연결을 직접 붙잡고 있는데, 그런 것은 React 의 방식으로 다시 쓰면 같은
관리가 두 벌이 되기 쉽습니다. **녹음이 한 번 끊기면 그 구간은 영영 못 잽니다** —
얻는 것보다 잃을 수 있는 것이 큽니다.

## 6. 지금 어디까지 됐나

**된 것**
- 위 아홉 화면 전부 실제로 돕니다 (캡처는 실제 서버를 브라우저로 띄워 찍은 것)
- 회의 → 업무 후보 → 승인 → 칸반 → GitHub → 기여도 사슬이 끝까지 연결됨
- 자동 테스트가 백엔드·프런트 양쪽에서 전부 통과합니다 (개수는 `pytest`·`npm test` 가 직접 셉니다)

**아직인 것**
- 음성 인식(STT)과 요약은 **가짜 백엔드로 대체**해 두고 파이프라인만 검증했습니다.
  실제 모델을 붙이는 것은 GPU 가 있는 환경에서 할 일입니다.
- 로비의 "목소리 특징 저장" 동의는 **받고 있지만 실제로 쓰는 코드가 아직 없습니다.**
  (동의를 먼저 받아 둔 것이라 기능이 없는 상태)
- 로그인·통화 두 화면도 디자인 정리를 거쳤습니다(`docs/19` §26).

## 7. 피드백을 받고 싶은 부분

1. **`07-업무-후보-검토`** — 이 화면이 이 제품의 안전장치입니다.
   "AI 가 뽑고 사람이 승인한다" 가 화면만 보고도 전달되나요?
2. **`09-기여도`** — 순위처럼 읽히나요, 아니면 "아직 모르는 게 많다" 로
   읽히나요? 후자로 읽히는 게 목표입니다.
3. **`02-홈`** — 처음 들어온 사람이 "다음에 뭘 해야 하는지" 를 찾을 수 있나요?
4. 전체적으로 **어느 화면에서 가장 먼저 눈이 가는지**, 그게 그 화면에서
   제일 중요한 것이 맞는지.
