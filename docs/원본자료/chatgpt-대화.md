## 1. 최초 아이디어 (사용자)

대학생 팀 프로젝트 관리 서비스.
팀플에서 누가 얼마나 참여했는지를 자동으로 정리하는 시스템.

**주요 기능**
- 팀원별 할 일 배정
- GitHub 커밋 연동
- 회의록 작성
- 일정과 마감일 관리
- 팀원별 기여도 분석
- 지연 작업 자동 경고
- 최종 활동 보고서 생성

예를 들어 다음 데이터를 합쳐 기여도를 보여주는 것:
담당 업무 완료율 / GitHub 커밋 / 회의 참석 / 문서 수정 / 동료 평가

여기에 녹음을 넣어서 회의를 자동으로 요약하는 기능도.

**추가 질문**: 생성형 AI API 활용 말고 AI를 학습시키거나 LLM 같은 걸 사용해서
이런 프로그램을 만들어보는 건 어떤가?

## 2. ChatGPT 답변 (1차)

### 결론

졸업작품·공모전·실제 서비스 아이템으로 꽤 좋다. 특히 단순 팀플 일정 관리가 아니라,
**"팀 프로젝트 활동 증거를 자동 수집하고, AI가 회의록·업무 진행 상황·최종 활동 보고서를 만드는 서비스"**
로 잡으면 차별점이 생긴다.

다만 LLM을 처음부터 직접 학습시키는 방향은 비추천이다. 현실적인 순서:

1. 오픈소스 AI 모델을 내 서버에서 실행
2. 규칙 기반 기여도 계산 시스템 구축
3. 실제 팀플 데이터를 모은 뒤 소형 모델이나 LoRA 파인튜닝
4. 데이터가 충분히 쌓이면 기여도 예측 모델 학습

> **API를 사용하지 않는 것과 생성형 AI를 사용하지 않는 것은 다르다.**
> EXAONE·Qwen 같은 오픈 웨이트 생성형 모델을 직접 서버에 올리면
> 외부 생성형 AI API 없이도 구현할 수 있다.

### 서비스 핵심 흐름 — 회의 녹음

```
회의 녹음
→ 음성 구간 분리
→ 화자 구분
→ 음성을 텍스트로 변환
→ 발언자별 회의록 생성
→ 결정사항과 할 일 추출
→ 담당자에게 자동 배정
```

- 음성 인식: 서버에서 실행 가능한 Whisper. 2026년 기준으로는 Qwen3-ASR 같은 오픈 모델도 후보.
  공식 모델 카드상 0.6B와 1.7B 모델이 공개돼 있으며 한국어 포함 다국어 지원.
- 화자 구분: pyannote.audio. 사전 학습 모델을 추가 파인튜닝 가능.

예시:
```
[김민수 00:13] 로그인 기능은 이번 주 금요일까지 제가 구현하겠습니다.
[이하늘 00:25] 그러면 디자인 시안은 수요일까지 올릴게요.

AI 추출 결과
- 김민수: 로그인 기능 구현 / 마감 금요일
- 이하늘: 디자인 시안 작성 / 마감 수요일
- 결정사항: 로그인 방식은 JWT 사용
- 다음 회의: 다음 주 월요일 오후 7시
```

회의가 끝나면 자동으로 업무 카드를 만들되, **최종 등록 전에 사람이 확인**하도록 하는 방식이 좋다.
음성 인식 오류로 엉뚱한 사람에게 업무가 배정될 수 있기 때문이다.

### AI가 담당할 부분

**AI가 잘하는 일**: 회의 녹음 텍스트 변환 / 화자별 발언 정리 / 회의 요약 / 결정사항 추출 /
담당 업무와 마감일 추출 / 긴 활동 기록을 보고서로 변환 / 지연 가능성 탐지 / 팀원별 활동 설명 생성

**AI에게 전부 맡기면 안 되는 일**: 최종 기여도 점수 결정 / 무임승차 팀원 판정 /
팀원 간 갈등 책임 판단 / 커밋 코드의 실질적 가치 단독 평가 / 교수에게 제출할 공식 점수 확정

> 정량 데이터 계산: 일반 프로그램
> 데이터 의미 분석: AI
> 최종 결과 확정: 사용자 또는 팀장

### 기여도 계산 방식

단순히 커밋 수를 세면 안 된다.

> A: 오타 수정 커밋 30개
> B: 로그인 기능 전체 구현 커밋 3개
> 커밋 수만 보면 A가 더 높지만 실제 기여도는 B가 더 클 수 있다.

| 평가 항목 | 예시 비중 | 측정 방식 |
|---|---|---|
| 담당 업무 완료 | 30% | 완료된 작업의 난이도·중요도 |
| 코드 기여 | 20% | 병합된 PR, 리뷰, 테스트, 이슈 연결 |
| 문서 활동 | 15% | 보고서·PPT·기획서 수정 |
| 일정 준수 | 10% | 마감 전 완료 여부 |
| 회의 참여 | 10% | 참석과 유효 발언·결정 참여 |
| 동료 평가 | 15% | 익명 평가의 중앙값 |

**역할별 평가 기준** (모든 팀원에게 같은 비율을 적용하면 안 됨)

- 개발자: 코드 35% / 업무 완료 30% / 문서 5% / 회의 10% / 일정 10% / 동료평가 10%
- 기획자: 업무 완료 30% / 기획 문서 30% / 회의 15% / 일정 10% / 동료평가 15%
- 디자이너: 디자인 산출물 35% / 업무 완료 30% / 회의 10% / 일정 10% / 동료평가 15%

GitHub 데이터는 웹훅을 이용하면 커밋·푸시·PR 등의 이벤트가 발생할 때 서버가 자동으로 받을 수 있다.

### AI를 직접 학습시키는 방법

**1단계: 학습 없이 사전 학습 모델 사용**
- 음성 인식: Whisper 또는 Qwen3-ASR
- 화자 분리: pyannote.audio
- 회의 요약: 한국어 오픈 LLM (EXAONE 3.5 — 2.4B·7.8B·32B)
- 기여도 계산: 직접 만든 규칙

RTX 5080 16GB이므로 초기 실험은 2B급 또는 양자화된 7~8B급부터. 로컬 추론은 llama.cpp.

**2단계: 프롬프트와 출력 형식 고정**

```json
{
  "summary": "로그인 기능과 디자인 일정에 대해 논의함",
  "decisions": ["인증 방식은 JWT를 사용한다"],
  "tasks": [
    {
      "assignee": "김민수",
      "title": "로그인 기능 구현",
      "deadline": "2026-08-08",
      "confidence": 0.91
    }
  ],
  "unresolved_issues": ["배포 서버 미정"]
}
```

**3단계: LoRA 파인튜닝** — 수백~수천 건이 모이면 소형 모델에 적용. HuggingFace PEFT.

**4단계: 기여도 예측 모델 학습** — LLM보다 일반 머신러닝(LightGBM, XGBoost, Random Forest,
신경망 회귀)이 적합. 정답 데이터는 교수 평가 점수 / 팀장 확정 기여도 / 팀원 합의 기여도.
다만 초기에는 학습 데이터가 없으므로 규칙 기반으로 시작.

### 추천 기술 구조

```
Frontend    React 또는 Next.js — 녹음, 일정, 칸반 보드, 기여도 대시보드
Backend     Spring Boot 또는 FastAPI — 사용자·프로젝트·업무·회의 관리, GitHub 웹훅 수신
AI Server   Python FastAPI — Whisper/Qwen3-ASR, pyannote.audio, EXAONE, LoRA 학습
Database    PostgreSQL
Storage     녹음 파일, 회의록, 제출 문서
Background  Redis + Celery 또는 BullMQ
```

Spring을 공부하고 있으므로: 메인 서버 Spring Boot / AI 처리 서버 Python FastAPI /
화면 React / DB PostgreSQL 조합도 괜찮다.

### 가장 현실적인 MVP

**필수**: 회원가입·팀 생성 / 팀원 초대 / 할 일 배정과 마감일 / GitHub 저장소 연결 /
회의 녹음 업로드 / 자동 음성 변환 / 회의 요약·업무 추출 / 팀원별 활동 타임라인 /
규칙 기반 기여도 표시 / PDF 활동 보고서 생성

**나중에**: 실시간 회의 녹음 / 화자 음성 등록 / 동료 평가 / 지연 가능성 예측 /
AI 파인튜닝 / 교수용 관리 페이지 / 학교 LMS 연동 / 표절·대리 작업 탐지 / 팀 내 갈등 징후 탐지

### 차별점

일반적인 협업 도구는 업무를 관리하지만, 이 서비스는 **팀플 평가 자료를 자동으로 만들어 준다.**

```
프로젝트 기간: 2026.08.10~2026.11.20

김민수
- 담당 업무 8건 중 7건 완료
- GitHub PR 12건 / 코드 리뷰 7건
- 회의 참석 9/10회 / 일정 준수율 87%
- 주요 기여: 로그인, 회원가입, 인증 서버 구현

이하늘
- 담당 업무 10건 중 10건 완료
- 문서 수정 34회 / 회의 참석 10/10회 / 일정 준수율 100%
- 주요 기여: 서비스 기획, UI 설계, 발표자료 제작
```

### 반드시 해결해야 할 문제

가장 어려운 부분은 AI 기술보다 **공정성**이다.

- 커밋을 잘게 쪼개 점수를 올릴 수 있음
- 회의에서 말을 많이 한다고 기여한 것은 아님
- 문서 수정 횟수도 조작할 수 있음
- 코드 개발자와 발표 담당자의 활동 형태가 다름
- 동료 평가가 감정적으로 작성될 수 있음
- 녹음 내용에 개인정보가 포함될 수 있음

따라서 하나의 확정 점수보다 다음처럼 표시하는 게 낫다:

```
예상 기여도: 27%
신뢰도: 보통

주요 근거
- 핵심 업무 4건 완료
- 병합 PR 3건
- 회의 8회 참석
- 마감 지연 1회

팀장 조정 가능 범위: 22~32%
```

그리고 각 점수가 어떤 데이터로 계산됐는지 **모두 공개**해야 한다.

### 추천 방향

> 오픈소스 음성·언어 모델과 프로젝트 활동 데이터를 결합해, 대학생 팀 프로젝트의
> 진행 과정과 기여도를 자동 기록·분석하는 AI 협업 플랫폼

직접 학습시킬 부분은 거대한 LLM이 아니라 두 가지:
1. 회의 녹취에서 업무·담당자·마감일을 추출하는 소형 모델
2. 활동 데이터 기반 기여도 예측 머신러닝 모델

**딥러닝**: 음성 인식 / 화자 구분 / 발언 유형 분류 / 감정·억양 변화 분석 / 비효율적 회의 구간 탐지
**LLM**: 회의 내용 요약 / 결정 사항 추출 / 담당 업무와 마감일 추출 / 미해결 문제 정리 / 회의 개선 의견

## 4. ChatGPT 답변 (2차) — 화자 구분 현실성

현실적으로 가능하다. 다만 결과가 바로 `김민수: ...`로 나오는 게 아니라 두 단계를 거친다.

### 화자 구분(Diarization) ≠ 화자 식별(Identification)

**화자 구분·분리** — "누가 언제 말했는가"
```
[00:03~00:12] SPEAKER_00
[00:13~00:19] SPEAKER_01
[00:20~00:34] SPEAKER_00
```
pyannote.audio나 NVIDIA NeMo가 사전 학습 모델 제공.

**화자 식별** — SPEAKER_00이 실제로 김민수임을 알아내는 별도 과정.
음성을 고정 길이 벡터인 **화자 임베딩**으로 변환하고 미리 등록한 팀원 목소리와 비교.

### 구현 방법 3가지

**방법 1. AI가 구분하고 사용자가 이름을 한 번 지정** (가장 현실적인 MVP)
```
AI 분석: SPEAKER_00 / SPEAKER_01
사용자 확인: SPEAKER_00 = 김민수, SPEAKER_01 = 이하늘
```
별도 음성 등록 불필요, 잘못 구분된 부분도 바로 수정 가능.

**방법 2. 팀원 목소리 사전 등록**
```
회의 화자 A
→ 김민수 등록 음성과 유사도 0.87
→ 이하늘 등록 음성과 유사도 0.31
→ 김민수로 추정
```
유사도가 낮으면 억지로 이름을 붙이지 않고 **알 수 없는 화자**로 처리.

**방법 3. 각 팀원이 자기 기기로 참여** ⭐ (정확도·안정성 최고)
```
김민수 계정의 오디오 채널 → 김민수
이하늘 계정의 오디오 채널 → 이하늘
```
AI가 목소리만으로 이름을 맞힐 필요가 없다. Discord/Zoom 같은 온라인 회의에서 가장 안정적.
오프라인 회의라면 각자 스마트폰으로 접속하게 하거나, 단일 마이크 녹음에 화자 분리 모델 적용.

### 실제 정확도

pyannote Community-1 공개 모델, AMI 회의 데이터 기준:

| 녹음 환경 | DER |
|---|---|
| 개별 헤드셋 마이크 | 17.0% |
| 방 안의 단일 원거리 마이크 | 19.9% |

데이터 환경에 따라 약 **8.9% ~ 46.8%** 까지 크게 달라진다.
동시 발언을 제외하지 않는 엄격한 평가이므로, 17%가 곧 문장 17%의 이름이 틀렸다는 뜻은 아니다.
말소리 누락, 잘못 감지된 음성, 화자 혼동 시간이 모두 포함된다.

> 서비스 목표: **AI가 수정 가능한 화자별 회의록 초안을 만들고, 사용자가 몇 번의 클릭으로 바로잡는다.**
> 완전 자동으로 100% 정확하게 이름까지 판별한다는 목표는 현실적이지 않다.

### 정확도가 떨어지는 상황

여러 명 동시 발언 / "네", "맞아요"처럼 짧은 발언 / 마이크와 거리 / 주변 소음 /
비슷한 목소리 / 마이크 방향 변경 / 6명 이상 빠른 끼어들기 / 중간 합류

특히 **동시 발언**은 음성 하나에 두 사람 목소리가 섞이므로 가장 어렵다.

### 추천 처리 구조

```
1. 회의 음원 업로드
2. 잡음 제거 및 음량 정규화
3. 음성 구간 검출 VAD
4. 화자 구분
5. 음성 인식
6. 단어별 시간과 화자 구간 결합
7. 등록된 목소리와 비교해 이름 추정
8. 사용자가 화자 이름 확인
9. LLM이 화자별 회의 내용 분석
```

WhisperX는 음성 인식 결과에 단어 단위 타임스탬프를 붙이고, pyannote 화자 분리 결과와 결합해
다중 화자 회의록을 만드는 구조를 이미 지원한다.

### 1차 버전 권장 기준

팀원 2~5명 / 회의 종료 후 분석 / 예상 참석 인원 미리 입력 /
AI는 SPEAKER_00 형태로 우선 구분 / 사용자가 이름을 한 번 매칭 /
잘못 나뉜 발언은 클릭으로 수정 / 동시 발언은 별도 표시 / 화자별 신뢰도 제공 /
최종 회의록은 사용자 확인 후 확정

실시간으로도 구현할 수 있지만(NVIDIA NeMo가 스트리밍 화자 분리 모델 제공),
**졸업작품의 첫 버전은 녹음 후 일괄 분석**이 정확도와 개발 난이도 측면에서 훨씬 현실적이다.

> 결국 누가 말했는지 구분하는 기능은 충분히 구현 가능하지만,
> 완전 자동 판정이 아니라 **AI 분석과 간단한 사용자 보정을 결합**해야 실제로 쓸 만한 서비스가 된다.
