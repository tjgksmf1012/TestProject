# 텍스트 최소화 조사 — 시장 제품과 표준에서 배운 것

작성 2026-08-18. 대상은 `webapp/` SPA 아홉 화면 중 글자가 많던 다섯
(홈·칸반·기여도·검토·로비).

이 문서는 **왜 그렇게 고쳤는지**를 적습니다. 무엇을 고쳤는지는
`docs/22-리디자인-계측기.md` §텍스트 최소화 리모델링에 있습니다.

---

## 0. 왜 조사부터 했나

"글자를 줄여라" 는 지시는 혼자 두면 **말을 지우는 것**으로 끝납니다.
지우면 화면은 깨끗해지고 사용자는 모르게 됩니다. 그래서 먼저
"글자를 줄이면서 전달은 유지한 제품들이 무엇을 했는가" 를 봤습니다.

⚠️ **이 문서에 적힌 근거 중 하나는 조사 도중 뒤집혔습니다** (R4).
처음에 저는 "정성 표현과 그림을 겹치면 판단이 갈린다" 를 근거로 삼고
코드 주석에까지 적었는데, 다시 찾아보니 연구가 말하는 것은 그 반대에
가까웠습니다. 결론(수치를 앞세운다)은 같지만 **이유가 달랐고**, 틀린
이유를 적어 두면 다음 사람이 그 이유로 다른 결정을 합니다. 고쳤습니다.

---

## 1. 진단 — 무엇이 "지저분" 했나

고치기 전에 잰 값입니다 (1280×800, 라이트, 데모 데이터).

| 화면 | 화면에 찍힌 글자 수 | 설명 문장 수 |
|---|---:|---:|
| 홈 | 185 | 1 |
| 칸반 | 271 | 4 |
| 기여도 | 423 | 5 |
| 검토 (전체) | 878 | 22 |
| 검토 (발화 원문 제외) | 330 | 7 |
| 로비 | 257 | 10 |

원인은 셋이었습니다.

1. **같은 문장이 항목마다 반복** — 칸반 카드 넷에
   `연결된 PR이 없습니다 — PR 제목이나 본문에 TASK-n를 적으면 붙습니다`
   가 **네 번**(26자 × 4 = 106자). 검토 카드 셋에
   `담당자 · 마감일을 지정해야 등록할 수 있습니다` 가 두 번.
   로비는 방 상태를 한 화면에서 **네 번** 말했고 그중 둘은 글자까지
   같았습니다.
2. **값을 문장으로 씀** — `근거 1건`, `PR 1건` 대신 `연결된 PR이 …`.
3. **위계가 평평** — 12·13·14px 이 글자의 93%. 제일 큰 글자와 제일 작은
   글자의 비가 **1.45배**. 무엇이 주인공인지 화면이 말하지 않았습니다.

## 2. 본 것들

### R1 — Linear: 최소한의 껍데기, 제자리 수정

Linear 의 원칙은 "성능이 중요하고, 키보드로 다 되어야 하고, 인터페이스는
최소이되 강력해야 한다" 입니다. 실무에서 눈에 띈 것은 **필터를 걸면 필터
줄에 작은 표시가 하나 뜨고, 필요한 정보는 전부 그 자리에서 고칠 수 있다**
는 점입니다 — 별도 설명 문단이 없습니다.

→ 채택: 칸반 카드에서 안내 문장을 걷고, 규칙은 **열 머리말에서 한 번**만
말합니다. 카드에는 값(표식·근거 수·PR 수)만 둡니다.

### R2 — 대시보드 타이포그래피: 값은 크게, 라벨은 작게

여러 대시보드 지침이 같은 말을 합니다 — **데이터 값은 라벨보다 확실히
크고 무겁게, 대개 고정폭(monospace) 으로.** 라벨과 단위는 마이크로텍스트
자리에 둡니다. 인터페이스용 산세리프와 숫자용 고정폭을 짝지어 쓰면 라벨과
값이 시각적으로 갈립니다.

⚠️ **못 찾은 것**: "값:라벨 = N:1 이상" 이라는 **수치 하한을 못 박은
출처는 찾지 못했습니다.** 흔히 권장되는 대시보드 타입 스케일 비율은
1.309(반 황금비) 정도이고, 이건 한 단 차이입니다. 저희가 쓴
**28px / 11px = 2.55** 는 그 스케일로 서너 단 떨어진 값을, 4px 격자
위에서 고를 수 있는 것 중 고른 것입니다. **인용이 아니라 판단입니다.**

→ 채택: `Stat` 컴포넌트 (값 28px 고정폭 / 라벨 11px). 기여도에만 씁니다
(아래 §6 참고).

### R3 — WCAG 1.4.1: 색이나 모양만으로 말하지 않기

정보를 전할 때 색·모양·크기만 쓰면 안 됩니다. 글자가 함께 있어야 합니다.

→ 채택: 사슬의 빈 고리는 점선**이자** `—` 입니다. 조건 칩은 색이 아니라
채운 원 `●` / 빈 원 `○` 로 가릅니다 (흑백 인쇄·색각이상에서도 다름).

### R4 — 불확실성 표기: "낮음" 은 사람마다 다른 확률로 번역된다

⚠️ **여기가 처음에 틀렸던 곳입니다.**

- 제가 처음 적었던 것: "말과 그림을 같이 주면 판단이 갈린다 → 겹치지 마라"
- 실제로 찾은 것: 두 가지 불확실성 표현을 **겹쳐서 준 쪽이 각각 하나만
  준 쪽보다 나쁘지 않았습니다** — 중복이 해로울 것이라는 가설과 반대
  결과입니다. 그리고 확률 정보를 데이터와 **붙여 두면** 따로 두었을 때보다
  무시되거나 잘못 가중되는 일이 줄어듭니다.
- 진짜 근거: **`낮은 불확실성`·`거의 확실` 같은 말은 사람마다 매우 다른
  확률로 해석됩니다.** 시각적 부호화는 이 언어·수리력 장벽을 넘습니다.

→ 채택(이유를 고쳐서): 기여도 카드는 **잰 값**(`20%p 모름`)을 앞세우고,
`신뢰도 낮음` 이라는 **말**은 사유 팝오버로 내립니다. 겹쳐서가 아니라
말이 부정확해서입니다. 그리고 R4 의 "붙여 두라" 에 따라 `모름` 수치는
구간 막대 **바로 옆 칸**에 둡니다 — 별도 각주로 빼지 않습니다.

### R5 — NN/g 점진적 공개(progressive disclosure)

부차적 선택지를 아래 단계로 미루면 복잡도가 줄고 학습이 쉬워집니다.
다만 두 가지 단서가 붙습니다:

- **단계가 셋 이상이면 대개 쓸모가 떨어집니다** — 사용자가 길을 잃습니다.
- **자주 필요한 것은 전부 앞에 내놔야 합니다.** 아니면 복잡도를 줄인 게
  아니라 **옮긴 것**뿐입니다.

→ 채택: `Why` 팝오버는 **한 단계만**입니다. 그리고 앞에 남긴 것과 내린
것을 아래처럼 갈랐습니다.

| 앞에 남긴 것 | 내린 것 (`?` 한 번 눌러서) |
|---|---|
| 기여도 경고 배너 첫 줄 (`서로 비교하지 마세요`) | 나머지 경고 문장들 |
| 잰 값 (`20%p 모름`, `근거 2`, `PR 1`) | 그 값이 그렇게 나온 사유 |
| 조건 칩 (`● 근거 2 ○ 담당자`) | 조건의 전문 |
| 트랙 상태 한 낱말 (`끊김`) | 끊긴 구간의 원문 설명 |

### R6 — GOV.UK / Shopify Polaris: 비활성 버튼을 어떻게 다루나

- **GOV.UK**: 비활성 버튼은 **되도록 피하라.** 대비가 낮고 혼란스럽고,
  저시력 사용자에게 접근 가능하게 만들기 어렵고, **키보드로 포커스를 주기
  어렵습니다.** GOV.UK 는 버튼을 비활성화하지 않고, 문제가 있으면 **무엇을
  어떻게 고치는지 알려 주는 오류 메시지**를 냅니다. MOD.UK 도 같은 권고를
  따릅니다.
- **Shopify Polaris**: 비활성 버튼을 **툴팁으로 감쌌다가** VoiceOver 가
  엉뚱한 요소를 읽는 문제를 겪었습니다 — 툴팁이 첫 포커스 노드가 됩니다.
  또 비활성 버튼 위의 툴팁은 잘 사라지지도 않습니다. 정리된 방향은
  **`aria-disabled` + JS 로 기능만 막기** 입니다.

→ 채택: 등록 버튼(검토)·녹음 화면으로(로비) 는 HTML `disabled` 를 쓰지
않습니다. `aria-disabled` + `aria-describedby` 로 **버튼 옆 실제 DOM
노드**(조건 칩)를 가리키고, 눌리면 **첫 빈 칸으로 포커스를 옮깁니다.**
툴팁으로 감싸지 않습니다.

### R7 — WCAG 1.4.13: 올려서 뜨는 것의 세 조건

hover·focus 로 뜨는 내용은 **끌 수 있어야(dismissible)** 하고,
**그 위로 마우스를 옮겨도 안 사라져야(hoverable)** 하고,
**시간이 지나도 저절로 안 사라져야(persistent)** 합니다.

→ 채택: `Why` 는 툴팁이 아니라 **Radix Popover** 입니다 — 클릭으로 열고
ESC 로 닫히며, 내용 위로 마우스를 옮겨도, 몇 초가 지나도 떠 있습니다.
(실측은 `docs/22` 검증표.)

## 3. 그래서 만든 문법 — 네 원소

| 원소 | 무엇을 대신하나 | 파일 |
|---|---|---|
| **Stat** | "기여 구간은 32~52% 입니다" 같은 문장 | `webapp/src/components/Stat.tsx` |
| **Why** | 카드마다 반복되던 사유 문단 | `webapp/src/components/Why.tsx` |
| **Chain** | "연결된 PR이 없습니다 — …" 안내 | `webapp/src/components/Chain.tsx` |
| **Conditions** | "담당자·마감일을 지정해야 등록할 수 있습니다" | `webapp/src/components/Conditions.tsx` |

가장 큰 것은 **Chain** 입니다. 이 제품의 주장은 한 줄입니다 — *회의에서
한 말이 업무가 되고 코드가 된다.* 그 사슬을 **그려** 놓으면, 마지막 고리가
비어 있다는 사실 자체가 "아직 안 이어졌다" 를 말합니다. 문장이 필요 없어
집니다. 이건 새 발명이 아니라 이 저장소가 이미 하던 것(트랙 리본의 빗금
= 안 잰 구간)을 **관계**에 적용한 것입니다.

⚠️ **빈 고리를 `0` 으로 그리지 않습니다.** `0` 은 "재 봤더니 0건",
빈 고리는 "아직 안 이어짐" 입니다. 이 둘의 구분이 기여도 불변식 ③
(측정 불가 ≠ 0점) 그 자체입니다.

## 4. 채택하지 않은 것

시장 제품에 있지만 **이 제품에는 넣으면 안 되는 것**들입니다.

| 안 넣은 것 | 왜 |
|---|---|
| 기여도 정렬·필터 컨트롤 | 정렬 가능한 순간 리더보드가 됩니다 (불변식 ①) |
| 기여도 값을 세로 막대로 | 같은 축 위 세로 막대 = 순위표 (AGENTS.md 명시) |
| 단일 퍼센트 배지 (`87%`) | 단일 점수 금지 (불변식 ②) |
| 신뢰도 낮음을 빨강으로 | 빨강은 "네가 뭘 잘못했다" 로 읽힙니다 (불변식 ③) |
| 결측을 회색 0 으로 | 못 잰 것은 0이 아닙니다 — 흙빛 `--gap` 입니다 |
| 툴팁으로 감싼 비활성 버튼 | Polaris 가 겪은 VoiceOver 문제 (R6) |
| 새 hex 색 | `tokens.css` 는 전부 계산값. `color-mix()` 로 파생 |
| 두 단계 이상 접기 | NN/g 단서 — 셋 이상은 길을 잃습니다 (R5) |

## 5. 잰 결과

| 화면 | 글자 전→후 | 설명 문장 전→후 |
|---|---:|---:|
| 홈 | 185 → **164** | 1 → **0** |
| 칸반 | 271 → **169** | 4 → **0** |
| 기여도 | 423 → **260** | 5 → **2** |
| 검토 (발화 원문 제외) | 330 → **240** | 7 → **1** |
| 로비 | 257 → **205** | 10 → **5** |
| **합 (껍데기만)** | **1,466 → 1,038 (−29%)** | **27 → 8 (−70%)** |

검토 화면 전체 글자는 878 → 756 입니다. 줄어든 폭이 작아 보이는 이유는
**남은 것의 대부분이 회의 발화 원문**이기 때문입니다 — 그건 껍데기가
아니라 사용자가 읽으러 온 콘텐츠이고, 지우면 안 됩니다.

되풀이 문장(10자 이상이 한 화면에 두 번 이상)은 SPA 열두 화면에서
**0건**입니다. ⚠️ 이 "0건" 은 **되풀이를 하나 심어 검사가 잡는 것을 확인한
뒤에** 적은 숫자입니다 (심은 뒤 `3× 아직 아무도 참가하지 않았습니다` 로
잡혔고, 되돌린 뒤 다시 0건).

## 6. 정직하게 남기는 한계

- **위계 2.55배는 기여도 화면에만 해당합니다.** 나머지 네 화면은 여전히
  11~16px, 비 **1.45** 입니다. 그 화면들에는 "주인공 숫자" 가 없어서
  (칸반은 카드를 옮기는 곳, 검토는 고르는 곳) 크기 대신 **모양**(사슬 칸,
  조건 칩)이 위계를 나릅니다. 다섯 화면 전부가 2.55라고 적으면 거짓입니다.
- **`Why` 안의 문장은 요약하지 않고 원문 그대로 넣습니다.** 요약하면 판단이
  화면 코드로 새어 들어옵니다 (`src/lib` 밖 = 검증 밖).
- **`webapp/` 에는 텍스트 강제 가드가 없습니다.** 이번 정리는 자동 검사가
  지키지 않습니다. 다음에 화면을 늘릴 때 같은 문장이 다시 카드마다 붙는
  것을 막을 장치가 필요하면, `dupscan` 같은 검사를 가드로 승격하십시오.
