# 00 · 진단 — 지난 리디자인은 왜 실패했나

이 문서는 비난이 아니라 **재발 방지**를 위한 것입니다. 다음 에이전트가 같은 실패를
반복하지 않게 하려면, 무엇이 어떻게 실패했는지가 먼저 기록돼야 합니다.

---

## 1. 결론

**리디자인이 아니라 리스킨(reskin)이 일어났습니다.**

바뀐 것: 사이드바 → 상단 탭바, 색 변수 일부, 카드 테두리 두께.
안 바뀐 것: **정보 구조, 레이아웃, 스크롤 길이, 밀도, 타이포 위계, 화면의 목적.**

사용자가 "옛날이랑 달라진 게 하나도 없다"고 느낀 것은 착각이 아니라 정확한 관찰입니다.

---

## 2. 증거 — 스크롤 예산 측정

캡처 원본을 실측했습니다. 뷰포트를 1280×800으로 놓고 계산한 값입니다.

| 화면 | 캡처 높이 | 스크롤 | 판정 |
|---|---:|---:|---|
| 프로젝트 설정 | 3665px | **4.6 화면** | 심각 |
| 업무 후보 검토 | 2971px | **3.7 화면** | 심각 |
| 검토 (다크) | 1778px | 2.2 화면 | 나쁨 |
| 기여도 | 1718px | 2.1 화면 | 나쁨 |
| 홈 | 1657px | 2.1 화면 | 나쁨 |
| 회의 로비 | 1269px | 1.6 화면 | 주의 |
| 녹음 | 1221px | 1.5 화면 | 주의 |
| 달력 | 1201px | 1.5 화면 | 주의 |
| 칸반 | 1065px | 1.3 화면 | 주의 |
| 로그인 | 800px | 1.0 화면 | — (단, 아래 §4 참조) |

설정 화면 하나가 **4.6 화면 분량**입니다. 사용자가 자기 역할을 바꾸려면
페이지의 3분의 1 지점까지 스크롤해야 합니다. 이건 스타일 문제가 아니라
**정보 구조 문제**입니다. 색을 어떻게 칠해도 줄어들지 않습니다.

---

## 3. 근본 원인 — 아키텍처가 그대로다

갤러리 HTML의 경로가 이것을 그대로 드러냅니다.

```
/login.html
/home.html
/kanban.html?project=1
/contributions.html?project=1
/project.html?project=1
/review.html?meeting=…
```

**React로 이전되지 않았습니다.** 여전히 페이지마다 별도 `.html` 파일이고,
상태는 쿼리스트링으로 넘깁니다. 앞서 합의한 Vite + React + Tailwind + shadcn/ui
스택은 적용되지 않았습니다.

이게 왜 결정적이냐면 — **멀티페이지 구조에서는 "패널이 각자 스크롤되는 레이아웃"을
만들 수 없기 때문**입니다. 페이지 하나가 곧 문서 하나이므로, 콘텐츠가 늘면
문서가 길어지는 것 말고 다른 선택지가 없습니다. 그래서 모든 화면이 세로로
길어졌고, 세로로 길어진 걸 고치려면 색이 아니라 구조를 바꿔야 합니다.

갤러리 캡션에 에이전트가 직접 써 둔 문장도 같은 이야기를 합니다:

> "토큰의 원시값만 뒤집어 만든 다크입니다."

이게 정확히 안티패턴입니다. 다크모드는 값을 반전하는 게 아니라 **따로 설계하는
것**입니다(§07 참조).

---

## 4. 화면별로 구체적으로 무엇이 잘못됐나

### 로그인 — 1.0 화면이지만 사실상 빈 화면
- 카드 폭 383px가 1280px 캔버스 한가운데 떠 있고, 아래로 **약 270px가 죽은 공간**입니다.
- 수직 중앙 정렬도 아니고 상단 정렬도 아닌, 애매한 위치입니다.
- 설명 문단이 3줄로 어색하게 끊깁니다 (`기여 / 기록까지` 사이에서 줄바꿈).
- 이 제품이 뭘 하는 물건인지 보여줄 첫 화면인데, **아무것도 보여주지 않습니다.**

### 홈 — 예전 구조 그대로
- 프로젝트 카드 → 시작하기 카드 → 내 정보 카드가 세로로 쌓입니다.
- "내 정보"(프로필 사진·자기소개)가 새로 추가되면서 **더 길어졌습니다.**
  홈 화면에 프로필 편집기가 있을 이유가 없습니다. 설정으로 가야 합니다.
- 회의 상태를 여전히 **4px짜리 점 하나**로 표현합니다. 다섯 가지 상태를
  점 색깔만으로 구분하라는 건 색각 이상이 아니어도 어렵습니다.
- 각 회의 행이 2줄(제목 줄 + 설명 줄)을 쓰는데, 정작 **녹음이 얼마나 온전한지**는
  안 보입니다 — 이 제품에서 제일 중요한 정보인데도.

### 프로젝트 설정 — 최악 (4.6 화면)
카드 9개가 세로로 쌓여 있습니다:
`프로젝트 상태` → `팀원` → `내 역할` → `내 GitHub 계정` → `팀원 초대` →
`회의 열기` → `설정(이름·저장소·연결진단)` → `내 녹음 지우기` → 각주

- 성격이 완전히 다른 것들이 한 줄에 섞여 있습니다. **내 개인 설정**(역할, GitHub 계정),
  **프로젝트 관리**(이름, 저장소, 초대), **행동**(회의 열기), **위험한 작업**(녹음 삭제),
  **읽을거리**(프로젝트 상태 리포트)가 전부 동급으로 나열됩니다.
- "회의 열기"는 설정이 아니라 **행동**입니다. 설정 페이지 6번째 카드에 있으면
  아무도 못 찾습니다.
- 모든 카드가 흰 배경 + 1px 회색 테두리 + 같은 padding입니다. **위계가 0입니다.**
  눈이 어디로 먼저 가야 하는지 화면이 말해주지 않습니다.
- 카드마다 3~5줄짜리 설명 문단이 붙어 있습니다. 의도는 좋지만, 이게 전부
  본문 크기로 항상 펼쳐져 있어서 **화면의 절반이 설명문**입니다.

### 업무 후보 검토 — 두 번째로 나쁨 (3.7 화면), 그리고 목적이 뒤집힘
이 화면의 **단 하나의 목적은 "후보를 승인/거절하는 것"**입니다. 그런데 지금은:

```
발언 통계          ~150px
눈에 띈 것(반복 논의·주제 이탈)  ~250px
전체 타임라인 (전사 전문 20여 발언)  ~700px
─────────── 여기까지 스크롤해야 ───────────
필터 탭
후보 카드 1
후보 카드 2
후보 카드 3
제출 버튼          ← 2971px 지점
```

**주 작업에 도달하려면 1100px을 스크롤해야 합니다.** 회의 전문이 승인 작업 위에
통째로 쌓여 있습니다. 전사는 근거를 확인할 때 **참조하는 것**이지, 매번 처음부터
읽는 것이 아닙니다. 좌우 분할이었어야 할 것이 상하로 쌓였습니다.

### 칸반 — 이번 리디자인에서 **더 나빠진** 유일한 화면
- 카드마다 이동 버튼이 4~5개 붙었습니다: `진행 중으로` `검토 중으로` `완료로` `지우기`.
- 이 버튼들이 카드 폭에 맞춰 **불규칙하게 줄바꿈**돼서, 카드마다 버튼 배치가
  다 다릅니다. 정렬이 무너져 보이는 주된 원인입니다.
- 그 결과 카드 하나가 **330px**입니다. 칸반 카드는 원래 한눈에 여러 장을 훑는
  물건인데, 화면에 2.4장밖에 안 들어갑니다.
- 갤러리 캡션은 "끌어서도, 버튼으로도 옮깁니다(키보드·낭독기 경로 유지)"라고
  설명하는데, 접근성 의도는 옳지만 **해결책이 틀렸습니다.** 버튼 4개를 항상
  펼쳐두는 게 아니라, 카드 포커스 시 나타나는 메뉴 하나 또는 키보드 단축키로
  풀어야 합니다.

### 기여도 — 유일하게 실질적으로 개선된 화면
- 흙빛 막대가 **점 표시(dot plot)** 로 바뀌었습니다. 이건 연구 근거와 맞는
  올바른 변경입니다. "모르는 폭 20%p · 점 하나가 4%p"라는 설명도 정확합니다.
- 다만 여전히 2.1 화면이고, 상단 경고 박스 → 사람 3명 → 확정 폼이 세로로
  쌓여서 **세 사람을 동시에 볼 수 없습니다.**

### 회의 로비 — 제품의 시각적 시그니처가 사라짐
- 원래 있던 **참가자별 트랙 다이어그램**(0~40분 타임라인, 커버리지 빗금)이
  빈 상태에서 그냥 텍스트 목록으로 대체됐습니다:
  `김민수 — 아직 참가하지 않았습니다` × 3
- 문서에서 "이 그림이 이 제품의 시각적 시그니처"라고 직접 쓰신 요소입니다.
  빈 상태에서도 **축과 눈금은 그려져 있어야** 합니다. 그래야 "곧 여기에
  기록이 쌓인다"는 게 전달됩니다.

### 녹음 — 내부 문서가 사용자 화면에 노출됨
- 화면 제목이 **"녹음 생존율 테스트"**입니다. 사용자가 볼 이름이 아닙니다.
- 부제가 `docs/09 실험 5 — 폰이 회의 끝까지 녹음을 유지하는지 확인합니다.
  모드 A(멀티트랙)의 성립 여부가 여기서 결정됩니다.` — 내부 실험 문서 참조가
  그대로 나옵니다.
- 최하단에 `실험 조건: ① 화면 켜둠 ② 화면 잠금 ③ 다른 앱 전환 ④ 통화 수신.
  각각 10분씩 돌리세요.` — 개발자에게 하는 말이 사용자에게 표시되고 있습니다.

### 새로 추가된 화면들 — 내비게이션에서 도달 불가
`보고서` `채팅` `달력` `알림` `활동` `검색` 6개가 새로 생겼는데,
**상단 탭바에는 `홈 / 칸반 / 기여도 / 설정` 4개뿐**입니다.
나머지 6개 화면으로 가는 길이 화면에 없습니다.

또한 이 6개는 이 제품의 핵심 사슬(회의→후보→승인→칸반→PR→기여도)과
무관한 일반 협업툴 기능입니다. **채팅과 달력을 직접 만드는 건 졸업작품 범위에서
위험한 확장**입니다. 이미 있는 사슬도 STT가 가짜 백엔드인 상태인데,
채팅·달력·알림을 늘리면 어느 것도 완성도가 안 올라갑니다.

## 5. 왜 이런 일이 생기는가 (다음 에이전트가 알아야 할 것)

코딩 에이전트에게 "디자인을 예쁘게 바꿔줘"라고 하면 거의 항상 이 순서로 움직입니다:

1. 색 토큰을 바꾼다 ← **안전하고, diff가 작고, 티가 난다**
2. 폰트를 바꾼다
3. radius·shadow·border를 조정한다
4. 완료를 보고한다

레이아웃 재구성은 **컴포넌트를 쪼개고, 라우팅을 바꾸고, 상태를 끌어올리는**
작업이라 diff가 크고 회귀 위험이 있습니다. 명시적으로 요구하지 않으면
에이전트는 이걸 하지 않습니다. "예쁘게"는 스타일 요구로 해석되기 때문입니다.

**그래서 이 패키지의 `AGENTS.md`는 "예쁘게"라는 말을 쓰지 않습니다.**
대신 측정 가능한 제약으로 씁니다 — 화면별 최대 스크롤 예산, 금지된 패턴,
반드시 존재해야 하는 구조. 통과 여부를 눈이 아니라 자로 재게 만드는 것이
이번 지시서의 핵심입니다.

## 6. 그래도 잘한 것 (유지할 것)

리스킨이었다고 해서 전부 나쁜 건 아닙니다. 다음 판에서도 지켜야 할 것들:

- **기여도의 점 표시(dot plot)** — 연구 근거와 맞습니다. 유지하고 다듬으세요.
- **결측을 빨강이 아닌 흙빛으로** — 옳습니다. 새 토큰에서도 이 규칙을 유지합니다.
- **순위·리더보드 없음, 이름순 정렬** — 유지.
- **근거 없는 후보 승인 불가** — 유지. 이 제품의 존재 이유입니다.
- **"확신하지 못한 이유 N건" 접힘 UI** — 좋은 패턴입니다. 더 쓰세요.
- **UX 라이팅의 정직함** — "처리 중인 회의에는 버튼이 없습니다 — 눌러도 아직
  아무것도 없습니다" 같은 문장은 이 제품의 성격을 잘 드러냅니다. 톤은 유지하되,
  **분량을 줄이고 접어두세요**(§04 참조).
